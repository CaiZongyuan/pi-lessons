# 限制与非目标

---

> Pi Durable 保证的是单个进程和单份存储内部发生的事情；进程监管、身份、备份以及远端的恰好一次执行，都要由宿主来构建。
> 
> 

Pi Durable 能在进程崩溃后保留已提交的内部状态。外部副作用仍可能执行两次；这取决于工具的重放策略和远端系统的保障措施。它不会替你重启崩溃的进程，不会阻止两个进程打开同一个文件，也不知道你的用户是谁。本节划出这条边界。读完后，你就能列出生产部署必须在 Harness 周围补上的部分，并向 Pi 编码智能体用户解释，将会话迁移到 Pi Durable 后会有什么变化。

## 规范排除了什么



规范在结尾列出了系统“最初不具备”的十一项内容：这是范围上的决定，不是需要设法绕过的缺口。下表列出了全部项目。其中两项会影响日常代码：



不发布可见但未持久化的内容。UI 绝不会显示存储尚未持有的文本，因此流式显示的流畅度取决于进度提交，默认间隔为 100 ms（6\.2，原书第88页）。



不强制终止。忽略中止信号的工具无法在进程内部被停止；`close()` 会等待它。将调用的上下文传递给每一个 `await`。



<strong>在实践中意味着什么</strong>

|<strong>非目标</strong>|<strong>在实践中意味着什么</strong>|
|---|---|
|覆盖整个 Session 的 DOM|不存在一棵能观察一切的树；应观察对话视图、某个文档或任务图（8\.2，原书第129页）|
|发布可见但未持久化的内容|未提交进度没有快速通道；部分结果按提交节奏出现（6\.2，原书第88页）|
|Session 内核的语义事件日志|智能体事件由提交推导而来，并不存储（8\.3，原书第133页）|
|会话作用域的可回溯文档|`rewindable` 只适用于对话作用域（4\.1，原书第50页）|
|自动检查点启发式策略|只有 `checkpointWhen()` 指示时，文档才会存储基值（4\.3，原书第56页）|
|自动挂载第三方视图|视图只挂载内置文档；你自己的文档应通过 `snapshot()`、`documentState()` 或 `watchDoc()` 读取|
|CRDT／离线多写入者合并|每份存储只有一个写入者；不合并并发历史|
|将 Chord 操作转换为 SQL|SQLite 将操作存成记录，而不是 SQL 更新（9\.2，原书第144页）|
|JSONL 全局压缩或修复|`main.jsonl` 只会增长；数据损坏会使打开失败（9\.3，原书第148页）|
|与已移除的 Pico 原型兼容|没有从早期内部原型迁移的路径|
|强制终止扩展代码|忽略信号的处理器无法在进程内被杀死；关闭会等待它|

## 一份存储，一个所有者



一份存储同一时间只能由一个进程使用。“同一时间由一个进程拥有一份存储；没有跨进程锁”，见 README §Storage。没有任何机制会阻止第二个进程打开同一文件，而此时两个进程都会以为自己是唯一的写入者。SQLite 的 `busyTimeoutMs` 选项（默认 5,000 ms）只会让 SQLite 等待文件锁，见 `src/storage/sqlite/node.ts`；它不能让两个 Harness 安全地共用一个文件。



因此，崩溃恢复是进程监管器的职责。必须有某个组件发现进程已死、启动新进程，并重新打开存储。重新打开会处理余下的事情：原先处于 `running` 的任务变回 `pending`，下一次 `resume()`、提交请求或等待便会再次启动它们，参见“调度器”（原书第73页）。同样的重新打开过程也适用于计划内交接：一旦 `close()` 完成，“新的 Harness 就可以打开同一份 Storage”，见 spec §2\.2。



打开本身就是一次写入。即使之后没有恢复任何任务，`Harness.open()` 也会提交对运行中任务的重置，见 `research/capture/crash-reopen-tasks.txt`，因此仪表板绝不能“只是打开”另一进程所拥有的存储。对于 SQLite，可以通过独立的只读连接安全地读取正在使用的数据库；采集工具就是以这种方式读取运行中的行，见 `research/capture/sqlite-rows-midrun.txt`。



重新打开前，先安装所有扩展。缺少代码的任务不会失败；它会以阻塞状态等待，直到注册表能够运行它（5\.4，原书第73页）。

## 副作用归执行它们的系统负责



Harness 可以提交扣款意图，但无法让扣款恰好发生一次。工具调用先提交意图，再执行，再提交结果。如果进程在其间死亡，“副作用可能已经发生”，见 spec §5\.2，以及“副作用三明治”（原书第70页）。只有远端系统能解决这一点：通过它会遵守的幂等键，或者通过可供查询的句柄。没有设置 `replay: "safe"` 的工具根本不会重新运行；模型会收到一个表示调用中断的错误结果，参见“工具调用与重放”（原书第94页）。没有任何东西会自动回滚。撤销副作用的代码要由你来写，放在产生该副作用的任务的中止处理器中。

## 原版 Pi 会话与 Pi Durable



Pi Durable “并不取代 Pi 编码智能体。它是一个用于构建任何智能体应用的框架，编码智能体也包含在内”，见 `earendil.com/posts/pi-durable`。编码智能体继续使用自己的会话文件。下表面向熟悉前一种模型的读者，比较两种记录模型，参见“Pi Durable 用于什么”（原书第10页）。



|<strong>方面</strong>|<strong>Pi 编码智能体会话</strong>|<strong>Pi Durable</strong>|
|---|---|---|
|存储|`~/.pi/agent/sessions/` 下每个会话一个 JSONL 文件|内存、一个 SQLite 文件，或带附属文件的 JSONL 目录|
|历史形状|单个文件中的树；叶节点是当前位置<br>|多段对话；分叉是一段新对话，其父对话历史截止于 `parent.at`|
|分支|`/tree` 原地操作；`/fork`、`/clone` 写入新文件|在同一份存储中调用 `fork(entryId)`，并遵循文档分叉策略|
|写入单位|每个条目追加一行；有了用户或助手消息后，才首次写入文件|跨条目、任务、提交请求和文档的一次原子提交|
|系统提示词|系统消息修补提示词区段，以及 `toolsAdded`／`toolsRemoved`|遵循相同位置契约的 `pi.system` 条目|
|压缩|压缩条目：摘要、`firstKeptEntryId`、系统检查点|`head` 指向第一个保留条目的 `pi.compaction` 条目|
|上下文编辑|带 `targetId` 和替换内容的 `context_edit` 条目|条目上的 `edits`：省略或替换|
|模型与思考|`model_change`、`thinking_level_change` 条目|可回溯的 `pi.agent` 文档中的字段|
|扩展状态|带 `customType` 和 `data` 的自定义条目|带作用域、历史和分叉策略的类型化文档|
|排队消息|内存中的引导输入和后续输入；中止时将它们送回编辑器|`pi.inbox` 中的持久化提交请求，通过 `requestId` 去重|
|进行中的工作|没有任何条目类型记录正在生成的响应或工具调用|带检查点的 `pi.generation` 和 `pi.tool` 任务|

> 左侧：编码智能体文档和 `src/core/session-manager.ts`。右侧：`src/types.ts`、`src/entries.ts` 和 spec §2–§8。
> 
> 



两种设计共享对话记录的思路：仅追加条目、按位置生效的系统增量，以及保留原始条目的摘要。区别在于一次写入意味着什么。Pi 会话中的一行记录某件事发生了。Pi Durable 的一次提交记录允许被看见的状态，其中包括尚未完成的工作。

## 你需要自己构建什么



- 进程监管：在崩溃、部署和 OOM 后重启；确保每份存储只有一个进程，例如每个进程槽位或每个租户各用一份存储。

- 身份与权限：API 中没有用户、账户或凭据类型。守卫是带有 `beforeTool` 钩子的扩展，只有对话选择了它们，才会生效，参见“钩子”（原书第109页）。

- 备份：重新打开 JSONL 存储时，会丢弃末尾写到一半的行，但是“缺少必需的已确认数据属于损坏，打开会失败”，见 spec §11\.3。断电或宿主故障时，SQLite 可能丢失最新提交，见 README §Storage。没有任何机制会修复受损的存储。

- API 变动：该包处于实验阶段：“API 在不同版本之间可能变更，恕不另行通知”，见 README。1\.0\.3 版已经破坏了自定义 `FileSystem` 和 `Shell` 实现的兼容性，见 CHANGELOG 1\.0\.3。请锁定版本，并在升级后运行一致性测试套件（9\.4，原书第152页）。
