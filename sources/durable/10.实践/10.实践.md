# 10\.实践

# 构建编码智能体

---

> 编码智能体由一个注册表、一个设置对象和一个环境函数组成；用户为每段对话所做的选择，都以名称的形式保存在 `pi.agent` 中。
> 
> 

想象一个编码助手。用户将它切换到只读的计划模式，让它指向另一个文件夹，然后合上笔记本电脑。明天，它必须完全恢复到用户离开时的样子。只有把每项选择放在正确的位置，才能做到这一点。示例 26 至 31 展示了这些位置。读完本节，你就能把任何产品功能归到代码、策略或已存储的选择中，并说明一项变更何时生效。

> 代码和策略留在进程中；对话只存储自己的选择。Harness 每次需要它们时，都会将两者结合起来。本图根据示例 26–29 和 `src/harness/agent.ts` 整理。
>

## 三项宿主输入，一个已存储的文档



除了存储和模型，宿主程序还会向 `Harness.open()` 提供三样东西。它们都不会被存储，改变其中任何一个也都不会产生提交。提交是一次原子保存，其中的所有内容要么一起存入，要么完全不存：

- **注册表**：代码，也就是按名称安装的扩展。安装第二个同名扩展会替换第一个，参见“扩展与注册表”（原书第103页）。

- **设置**：所有对话共享的运行策略，例如重试和并行工具。Harness 每次需要时都会读取它们。

- **环境函数**：`env(target)` 构造某一段对话中的工具所能看到的文件系统和 shell。



用户为某段对话所做的选择，会存入该对话的 `pi.agent` 文档：模型、思考级别、扩展和工具名称、指令，以及工作目录（`cwd`）。它存储的是名称，绝不是代码，参见“每段对话的智能体”（原书第106页）。每一步开始前，Harness 都会在注册表中查找这些名称，取得真正的工具和提示词区段。

## 动态设置与会变化的文件夹



示例 26 是基础智能体。它安装了 `CodingTools`（`read`、`write`、`edit` 和 `bash` 工具），以及一个小型提示词扩展。不会有任何东西替你安装 `CodingTools`，见 `src/tools/index.ts`。设置通过 getter 读取用户会编辑的对象，环境则跟随对话的 `cwd`。



随文件变化的设置，以及跟随 `cwd` 的 `env`：`test/examples/26-coding-agent.ts`

```TypeScript
const userSettings = { parallelTools: true, maxRetries: 3 };
const settings: HarnessSettings = {
    get toolExecution() {
    return userSettings.parallelTools ? "parallel" : "sequential";
    },
    get retry() {
    return { maxRetries: userSettings.maxRetries };
    },
};
const env = ({ cwd = workspace }: { readonly cwd?: string }) =>
    new NodeExecutionEnv({ cwd });
...
await root.configure({ cwd: join(workspace, "app") }, context);
userSettings.parallelTools = false;
```

> 此处省略了 Harness 的 `open()` 调用和第一个轮次（…）。第一次 `pwd` 打印工作区路径，第二次打印 `workspace/app`（运行 26）。这两项变更都没有重启任何东西。
> 
> 



两项变更都从下一次使用起生效。每次决策都会重新读取设置；缺失字段使用默认值，见 `src/harness/agent.ts` 的 `resolveSettings`。`cwd` 的变更会提交到 `pi.agent`，下一次工具调用的 `env()` 就能看到它。由此带来一个后果：环境是按调用构造的，因此工具在崩溃后重新运行时，使用的是对话届时的目录，可能与首次尝试时使用的目录不同，见 `src/harness/tool.ts:253`。

## 计划模式是一项智能体变更



示例 27 不改动注册表，就能让一段对话变为只读。计划扩展带来了 `submit_plan` 工具和 `plan_mode` 提示词区段。它将计划保存在自己的文档 `app.plan` 中。这个文档是可回溯的，因此分叉会保留分叉点当时的计划，参见“定义文档”（原书第50页）。进入和退出计划模式，就是两次 `configure()` 调用。



进入和退出计划模式：`test/examples/27-plan-mode.ts`

```JavaScript
const read = createReadTool();
const enterPlanMode = { extensions: { add: [Plan] }, tools: [read, submitPlan] };
const leavePlanMode = { extensions: null, tools: null };

await root.configure(enterPlanMode, context);
const input = { type: "input", content: "Make the port configurable." } as const;
await (await root.submit(input, context)).wait(context);
await root.configure(leavePlanMode, context);
```

> 取自示例第 60–62 行和第 93–98 行；为适应页面宽度，提交请求被提取到 `input` 中。
> 
> 



```YAML
$ node --conditions=source --experimental-strip-types test/examples/27-plan-mode.ts
tools: [ 'read', 'write', 'edit', 'bash' ]
plan mode tools: [ 'read', 'submit_plan' ]
plan: [ 'Read PORT from the environment', 'Default to 3000' ]
tools again: [ 'read', 'write', 'edit', 'bash' ]
system: { sections: { plan_mode: '<plan_mode>\n...' },
    added: [ 'read', 'submit_plan' ], ... }
system: { sections: { plan_mode: null },
    added: [ 'write', 'edit', 'bash' ], removed: [ 'submit_plan' ] }
```

> 运行 27，第一行 `system` 已缩短。模型看到的每次切换都是一小段系统提示词变更，而不是一个全新的提示词，参见“系统提示词”（原书第115页）。
> 
> 



有三个细节让它得以运作。`{ add: [Plan] }` 在宿主默认扩展的基础上添加扩展，而 `tools` 数组则严格按给定顺序提供其中的工具。将两者都设为 `null` 会去掉覆盖设置，让对话重新跟随宿主默认值。此外，`submit_plan` 会交还控制权：`{ terminate: true }`。当一轮中的每个工具结果都提出这个要求时，运行便会结束，不再向模型发出请求，见 README §Tools。

## 审查者与沙箱：以对话为单位



示例 28 添加了一位审查者：它是第二段对话，拥有自己的智能体，使用更便宜的模型，只提供 `read` 工具，并以自己的检出目录作为 `cwd`。它的 `reviewer` 扩展带有 `onYield` 钩子。只要回答中还没有出现 “No further findings\.”，钩子就会返回 `{ continue: … }`，添加一条用户消息，让运行继续，参见“钩子”（原书第109页）。这些内容全部存储在 `pi.agent` 中，因此重启之后，审查者仍然是审查者。



示例 29 为每位用户的对话分配一个独立的沙箱文件夹。`app.sandbox` 文档保存路径，并在创建对话时写入。`env` 函数读取它，据此构造环境。该文档的分叉策略是 `initial`，因此分叉最初没有路径；此时 `env` 返回 `undefined`，内置工具会报错 “No execution environment is configured”，见 `src/tools/env.ts`。子智能体也不会继承这个文档：如果子对话需要共享沙箱，创建者就必须为它写入一个文档，见 spec §2\.2。

## 变更何时到达



每一种输入都有自己的生效时机。下表回答产品团队首先会问的问题：如果我现在改了它，谁会看到？

|**变更**|**何时读取**|**何时生效**|
|---|---|---|
|设置的 getter|每次使用时|下一次决策时；不写入任何内容|
|`configure()` 的模型、工具、提示词区段|每次模型请求前|下一次请求时；当前请求保留原有提示词|
|`configure({ cwd })`|每次使用时由 `env()` 读取|下一次工具调用时，即使该调用已经由模型发出|
|安装或替换扩展|每个阶段开始时，以及每次请求和调用时|下一阶段；正在执行的调用仍使用旧代码直到结束|
|进程重启|重新安装之后|已存储的名称绑定到新安装的代码|



依据 spec §2\.2、README §Per\-Conversation Agent 和 §Reload，以及运行 31：重新加载期间正在执行的调用打印 `v1`，下一个调用打印 `v2`；重启后的进程在安装扩展之前不会提供任何工具，参见“运行时重新加载”（原书第118页）。



**这对你意味着什么：**

- 把代码放进注册表，把共享策略放进设置，把每段对话的选择放进 `pi.agent`。

- 对话还有什么内容需要跨重启记住，就把它放进你自己的文档。

- 重新打开之前，先安装所有扩展；没有相应的代码，存储的名称毫无用处。

# 容易踩坑的契约

---

> Pi Durable 不会自行强制执行这些规则；违反规则时不会抛出异常，直到负载、并发或崩溃让故障显现。
> 
> 

假设某个扩展在提交内部等待网络调用。此时不会抛出异常。进程中的所有其他写入，包括 Harness 自己的写入，都会悄悄排在它后面等待。规范将 38 条这样的规则列为 “API footguns”（API 的易踩陷阱），并说：“这些是契约，并不是邀请你添加防御机制。”本节按照它们会在哪里造成问题来分组，列出症状和修正方法。你可以把它当成扩展和宿主代码的审查清单。



大多数规则源于两个事实。进程中的所有写入都经过同一个队列，即变更串行队列，一次只处理一个提交。而其他代码只能看到已提交的状态，参见“核心规则”（原书第16页）。代码如果过久占用队列、绕过 Harness 写入，或修改原本只应读取的值，就违反了其中之一。

## 事务与存储



把提交回调当作一次快速编辑。它可以是异步的，但内部每一个 `await` 都会让队列持续阻塞，让所有其他提交等待。

|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|保持提交简短（2\.2，原书第29页）|在回调内部等待模型、工具、进程、网络调用、人员或另一个提交，会让所有写入停滞或死锁|只使用提供给你的 `Tx`；在两次提交之间执行缓慢工作|
|回调结束后不得留下仍在运行的工作（2\.2，原书第29页）|一旦回调返回，它的草稿和 `Tx` 就会拒绝操作；在返回前，未被 `await` 的工作也不受支持|`await` 回调启动的全部工作|
|先读后写（2\.2，原书第29页）|第一次写表之后再读表，会抛出 `ReadAfterWrite`|先读取所有行；文档草稿仍然可以使用|
|显式创建文档（4\.2，原书第53页）|读取从未创建过的文档会返回 `undefined`|用 `tx.doc()` 创建它|
|文档族的种子只应用一次（4\.2，原书第53页）|为已有文档族成员传入的种子会被忽略|改用草稿修改该成员|
|存储故障是致命的（2\.3，原书第33页）|某次故障使写入是否落地变得不确定之后，后续每次提交都会抛出异常|不要捕获错误后继续；应重新打开|
|JSONL 需要 `fsync` 才能承受断电（9\.3，原书第148页）|机器宕机时，已经确认的提交仍可能丢失|在这点重要时，传入 `{ fsync: true }`|



致命情形值得单独说明。如果存储故障让写入是否落地变得未知，内存状态就可能与重新打开后读到的状态发生偏离。因此 Session 会停止：它拒绝后续每一次提交，必须重新打开；重新打开时，则读取存储实际持有的内容，参见“提交失败时”（原书第33页）。`StorageRejected` 错误属于无害情形：存储尚未触及任何内容就拒绝了写入，提交回滚，Session 继续运行。

## 运行、收件箱与进度



运行处于活动状态时，只有 Harness 可以向对话添加条目。下图解释了原因。每次模型请求之前，Harness 都会读取对话记录的末尾，判断模型需要哪些系统提示词变更，然后提交它们，见 `src/harness/generation.ts` 的 `prepare`。你在这期间添加的条目不在这项计划中，但这些变更却会落在它之后。`write` 提交请求可以避免这个问题：它会等待一个边界，也就是一轮工具调用结束后，或最终回答时的暂停点。



![image\.png](图片和附件/image.png)

> 原始条目可能在请求准备的读取和提交之间落地；`write` 提交请求则会等待边界。步骤 1–3 对应 `src/harness/generation.ts` 的 `prepare` 阶段；步骤 4–6 对应 spec §6。
> 
> 



同一条备注，分别以原始写入和提交请求写入：README §Busy Conversations

```JavaScript
// 运行可能处于活动状态时不安全：队列排到哪里，它就落在哪里。
await root.commit((tx) =>
    tx.appendEntry(root.id, { kind: "app.note", data: "user opened a file" }), context);
// 安全：空闲时立即添加，否则在下一个边界添加。
await root.submit(
    { type: "write", entry: { kind: "app.note", data: "user opened a file" } }, context);
```

> 第二种形式就是 README 自己使用的示例。`write` 提交请求绝不会启动模型轮次。
> 
> 



|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|不要向繁忙的对话写入（6\.1，原书第84页）|原始条目可能落在运行的系统提示词条目之间|使用 `write` 提交请求|
|不要手动把头指针移到过去（3\.4，原书第46页）|模型的上下文会改变，但已经打开的视图仍显示旧条目，直到重建为止|使用 `write` 提交请求；它会将这种操作作为过期请求拒绝|
|失败的运行会留下自己的队列（6\.1，原书第84页）|排队中的后续输入留在 `pi.inbox` 中，其 `wait()` 永远不会完成|重新提交，或者撤回它们|
|进度分步提交（6\.2，原书第88页）|崩溃会丢失上一次成功进度提交之后的流式文本；100 ms 是默认的最小间隔，不是最大丢失窗口|调整 `settings.progress`；绝不展示未提交文本|
|保持任务结果精简（5\.1，原书第63页）|已完成的任务记录会留在存储中，大结果也会一直留下|将数据存进条目或文档，返回它们的 ID|
|对话记录不等于模型上下文（3\.2，原书第40页）|原始条目不能体现编辑、仅供显示的条目和过滤效果|使用 `context()` 取得模型所见内容|

## 压缩



压缩用摘要替换旧轮次，参见“压缩”（原书第97页）。选定条目范围后，还要过一段时间才会写入摘要。在此期间，任何改变这个范围的操作都有风险。

|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|压缩会消耗一次模型调用|每次尝试都要为一次摘要请求付费，即使摘要到达时已经晚到无法使用|为此预留预算；它会计入 `pi.usage`|
|压缩期间的编辑|摘要写作期间放入的编辑，如果其目标被摘要覆盖，就会丢失；同时放入的头指针也会被截断操作撤销|在压缩之前完成此类写入|
|摘要时间戳|排队中的摘要携带的是压缩完成的时间，而不是放入的时间|与 Harness 一样，按条目顺序判断新旧|

## 所有权、钩子与关闭



具有所有者的工作形成一棵树。只要任务拥有的工作还在运行，该任务就不能结束；中止会在任何处理器运行之前先传递给子项，参见“所有权与结构化并发”（原书第76页）。



有一条所有权规则很容易违反，因为出错的提交看起来很合理：如果任务在结束自己的同一次提交中创建子任务，就会故障。在采集结果中，一个订单任务先扣款、打包，然后在结束时创建收据任务。



在结束提交中创建子任务：`research/capture/task-transitions.txt`，文本

```Plain Text
seq= 25 task 13 shop.pack owner=12 terminal outcome={"status":"completed",...}
seq= 26 task 12 shop.order owner=conv running checkpoint={"phase":"decide",...}
seq= 27 task 12 shop.order owner=conv terminal outcome={"status":"faulted", "error":{"message":"Task owner 12 is completing"}} effects in order: ["charged charge-d"]
```

> 场景 D，省略了时间戳和备忘值（…）。收据任务从未存储，扣款也从未退回，因为故障不会执行中止处理器。应在更早的一次提交中创建子任务；随后，正在结束的任务会以 `completing` 状态等待（spec §5\.5）。
> 
> 



|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|有所有者的工作会拖住其所有者（5\.5，原书第76页）|所有者保持 `completing`；子智能体的工作会拖住工具调用和运行|对于不得拖住任何其他工作的工作，以 `background` 创建|
|钩子启动的工作（7\.3，原书第109页）|它会拖住执行该钩子的任务；结果产生后才响应的代码，不能再延长该任务|在任务记录结果之前创建它|
|中止处理器不能创建子项（5\.6，原书第80页）|正在中止的任务不能创建自己拥有的子项|在副作用发生的地方撤销它，或者使用后台任务|
|钩子共享备忘名称（7\.3，原书第109页）|钩子和所属任务使用同一个备忘命名空间，因此名称会冲突|为备忘名称添加前缀|
|子智能体支出只计算一次（6\.6，原书第100页）|工具如果报告其子项的用量，总计中就会重复计算|让子项自己的 `pi.usage` 计数|
|遵守中止信号（2\.3，原书第33页）|忽略信号的代码会让 `close()` 持续等待，使存储保持打开|向每一个 `await` 传递 `context.abortSignal`|

## 文档与监听



文档种类和分叉策略属于存储格式：它们的寿命比定义它们的代码更长。读取到的值是共享的，不得修改；监听也只能缓冲有限数量的更新，参见“对话视图”（原书第129页）。



|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|不时存储完整副本（4\.3，原书第56页）|如果 `checkpointWhen()` 从不返回 `true`，存储就会无限增长|不时返回 `true`|
|有意识地选择分叉策略（4\.1，原书第50页）|`current`、`initial` 和 `asOf` 会改变分叉所见的内容|按产品语义选择|
|种类是永久的（4\.3，原书第56页）|迁移不能重命名种类；两个定义声明同一种类时，也不会被发现|若需重命名，复制到新种类，再退役旧种类|
|`pi.` 名称是保留的（3\.1，原书第37页）|没有机制强制执行这一点；重复使用会与 Harness 冲突|使用你自己的前缀，例如 `app.`|
|读取值不可变（8\.1，原书第125页）|修改快照或监听值会破坏共享状态|先复制，再修改|
|先读取，再启动监听（8\.2，原书第129页）|调用 `start()` 之前，`watch.value` 是取得监听对象时的值|先用它初始化，再启动|
|监听可能跳过更新（8\.2，原书第129页）|等待中的更新超过 100 条后，会由一个完整值替换；中间步骤会丢失|通过条目或日志统计事件|
|`stop()` 不会等待（8\.2，原书第129页）|它既不会中止，也不会等待正在执行的回调|自行与你的回调协调|
|先关闭客户端，再关闭 Harness（8\.1，原书第125页）|因关闭而结束的状态对象会永远保留最后一个值|先断开客户端和服务|



监听规则对远程客户端尤其重要。仅镜像最新值的客户端，在更新被合并时仍然正确，因为替换值包含完整的最新值。但统计状态转变的客户端，例如“每次工具启动时都发通知”，就不行：负载较高时，它会看到最终状态，却看不到中间步骤。凡是必须计数的内容，都应放在消费者会读取的条目或日志中。

## 扩展与智能体



一个扩展要么整体被选中，要么完全不被选中，因此守卫只会在该扩展被选中的地方运行。子对话只在创建时复制一次扩展选择，参见“每段对话的智能体”（原书第106页）。



|**规则**|**违反后的后果**|**应当怎样做**|
|---|---|---|
|每个列表都要包含守卫|显式扩展列表如果漏掉权限扩展，就会在没有该扩展的情况下运行|每个列表都要包含守卫|
|编辑会替换复制来的列表|对复制了列表的子对话应用 `{ add, remove }` 时，起点反而是宿主默认值|从解析后的智能体构造完整列表|
|复制只发生一次|后来对父对话的变更，永远不会传递给任务拥有的子对话|直接配置子对话|
|重新运行使用当前目录（9\.5，原书第155页）|崩溃后重新运行时，会根据当前 `cwd` 构造环境|不要假设它仍是第一次尝试的目录|
|默认值变更会付出缓存代价（7\.5，原书第115页）|更改设置或安装内容会添加 `pi.system` 条目，并导致提示词缓存未命中|预期每次变更会带来一次系统变更和一次缓存未命中|
|保持提示词文本稳定（7\.5，原书第115页）|内嵌时间的提示词区段每次请求都会变化，使缓存失效|只渲染真正的变更|
|延后释放资源（7\.6，原书第118页）|卸载时释放资源会破坏仍在执行的调用|等正在执行的调用结束后再释放|



各行转述 spec §12，并保留各组内部的原有顺序；规范有给出修正方法时，“应当怎样做”使用的就是规范自己的方法。



**没有安全网**



这里的规则几乎都不在运行时检查。注册表只检查提示词区段的键，以及工具名称在单个扩展内部是否唯一，见 `src/harness/registry.ts`。保留名称、种类冲突和不可变性，都要靠你的测试和审查保证。



**这对你意味着什么:**

- 代码审查时，三个问题就能发现其中大多数问题。任何一个回答为“是”都意味着存在缺陷，即使所有测试都通过，因为它只会在负载、并发或崩溃时显现。

- 提交回调内部的某个 `await` 是否会离开本进程？

- 是否有代码向一段对话写入，而它并不拥有该对话的运行？

- 是否有消费者修改自己读取到的值，或者依赖于看到每一次更新？

# 限制与非目标

---

> Pi Durable 保证的是单个进程和单份存储内部发生的事情；进程监管、身份、备份以及远端的恰好一次执行，都要由宿主来构建。
> 
> 

Pi Durable 能在进程崩溃后保留已提交的内部状态。外部副作用仍可能执行两次；这取决于工具的重放策略和远端系统的保障措施。它不会替你重启崩溃的进程，不会阻止两个进程打开同一个文件，也不知道你的用户是谁。本节划出这条边界。读完后，你就能列出生产部署必须在 Harness 周围补上的部分，并向 Pi 编码智能体用户解释，将会话迁移到 Pi Durable 后会有什么变化。

不发布可见但未持久化的内容。UI 绝不会显示存储尚未持有的文本，因此流式显示的流畅度取决于进度提交，默认间隔为 100 ms（6\.2，原书第88页）。

## 一份存储，一个所有者



一份存储同一时间只能由一个进程使用。“同一时间由一个进程拥有一份存储；没有跨进程锁”，见 README §Storage。没有任何机制会阻止第二个进程打开同一文件，而此时两个进程都会以为自己是唯一的写入者。SQLite 的 `busyTimeoutMs` 选项（默认 5,000 ms）只会让 SQLite 等待文件锁，见 `src/storage/sqlite/node.ts`；它不能让两个 Harness 安全地共用一个文件。



因此，崩溃恢复是进程监管器的职责。必须有某个组件发现进程已死、启动新进程，并重新打开存储。重新打开会处理余下的事情：原先处于 `running` 的任务变回 `pending`，下一次 `resume()`、提交请求或等待便会再次启动它们，参见“调度器”（原书第73页）。同样的重新打开过程也适用于计划内交接：一旦 `close()` 完成，“新的 Harness 就可以打开同一份 Storage”，见 spec §2\.2。



打开本身就是一次写入。即使之后没有恢复任何任务，`Harness.open()` 也会提交对运行中任务的重置，见 `research/capture/crash-reopen-tasks.txt`，因此仪表板绝不能“只是打开”另一进程所拥有的存储。对于 SQLite，可以通过独立的只读连接安全地读取正在使用的数据库；采集工具就是以这种方式读取运行中的行，见 `research/capture/sqlite-rows-midrun.txt`。



重新打开前，先安装所有扩展。缺少代码的任务不会失败；它会以阻塞状态等待，直到注册表能够运行它（5\.4，原书第73页）。

## 副作用归执行它们的系统负责



Harness 可以提交扣款意图，但无法让扣款恰好发生一次。工具调用先提交意图，再执行，再提交结果。如果进程在其间死亡，“副作用可能已经发生”，见 spec §5\.2，以及“副作用三明治”（原书第70页）。只有远端系统能解决这一点：通过它会遵守的幂等键，或者通过可供查询的句柄。没有设置 `replay: "safe"` 的工具根本不会重新运行；模型会收到一个表示调用中断的错误结果，参见“工具调用与重放”（原书第94页）。没有任何东西会自动回滚。撤销副作用的代码要由你来写，放在产生该副作用的任务的中止处理器中。

## 原版 Pi 会话与 Pi Durable



Pi Durable “并不取代 Pi 编码智能体。它是一个用于构建任何智能体应用的框架，编码智能体也包含在内”，见 `earendil.com/posts/pi-durable`。编码智能体继续使用自己的会话文件。下表面向熟悉前一种模型的读者，比较两种记录模型，参见“Pi Durable 用于什么”（原书第10页）。



|**方面**|**Pi 编码智能体会话**|**Pi Durable**|
|---|---|---|
|存储|`~/.pi/agent/sessions/` 下每个会话一个 JSONL 文件|内存、一个 SQLite 文件，或带附属文件的 JSONL 目录|
|历史形状|单个文件中的树；叶节点是当前位置<br>|多段对话；分叉是一段新对话，其父对话历史截止于 `parent.at`|
|分支|`/tree` 原地操作；`/fork`、`/clone` 写入新文件|在同一份存储中调用 `fork(entryId)`，并遵循文档分叉策略|
|写入单位|每个条目追加一行；有了用户或助手消息后，才首次写入文件|跨条目、任务、提交请求和文档的一次原子提交|
|系统提示词|系统消息修补提示词区段，以及 `toolsAdded`／`toolsRemoved`|遵循相同位置契约的 `pi.system` 条目|
|压缩|压缩条目：摘要、`firstKeptEntryId`、系统检查点|`head` 指向第一个保留条目的 `pi.compaction` 条目|
|上下文编辑|带 `targetId` 和替换内容的 `context_edit` 条目|条目上的 `edits`：省略或替换|
|模型与思考|`model_change`、`thinking_level_change` 条目|可回溯的 `pi.agent` 文档中的字段|
|扩展状态|带 `customType` 和 `data` 的自定义条目|带作用域、历史和分叉策略的类型化文档|
|排队消息|内存中的引导输入和后续输入；中止时将它们送回编辑器|`pi.inbox` 中的持久化提交请求，通过 `requestId` 去重|
|进行中的工作|没有任何条目类型记录正在生成的响应或工具调用|带检查点的 `pi.generation` 和 `pi.tool` 任务|

> 左侧：编码智能体文档和 `src/core/session-manager.ts`。右侧：`src/types.ts`、`src/entries.ts` 和 spec §2–§8。
> 
> 



两种设计共享对话记录的思路：仅追加条目、按位置生效的系统增量，以及保留原始条目的摘要。区别在于一次写入意味着什么。Pi 会话中的一行记录某件事发生了。Pi Durable 的一次提交记录允许被看见的状态，其中包括尚未完成的工作。

## 你需要自己构建什么



- 进程监管：在崩溃、部署和 OOM 后重启；确保每份存储只有一个进程，例如每个进程槽位或每个租户各用一份存储。

- 身份与权限：API 中没有用户、账户或凭据类型。守卫是带有 `beforeTool` 钩子的扩展，只有对话选择了它们，才会生效，参见“钩子”（原书第109页）。

- 备份：重新打开 JSONL 存储时，会丢弃末尾写到一半的行，但是“缺少必需的已确认数据属于损坏，打开会失败”，见 spec §11\.3。断电或宿主故障时，SQLite 可能丢失最新提交，见 README §Storage。没有任何机制会修复受损的存储。

- API 变动：该包处于实验阶段：“API 在不同版本之间可能变更，恕不另行通知”，见 README。1\.0\.3 版已经破坏了自定义 `FileSystem` 和 `Shell` 实现的兼容性，见 CHANGELOG 1\.0\.3。请锁定版本，并在升级后运行一致性测试套件（9\.4，原书第152页）。
