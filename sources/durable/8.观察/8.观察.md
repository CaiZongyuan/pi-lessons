# 8\.观察

# Chord 与文档状态

---

> 观察者看到的文档是一系列只读值，每个值都附带产生它的确切编辑操作；存储中没有的内容，观察者永远看不到。
> 
> 

**显示文档的面板必须与文档保持同步。工具更新任务列表时，面板应随之变化。崩溃后，它应准确显示已提交的内容。提交是一次原子保存：其中的全部内容一起存入，或者全部不存。Pi Durable 只向观察者提供已提交的变更：每次变更都包含一个新的只读值，以及产生它的一小组编辑操作。**读完本节，你就能把文档接到 UI 上，并说明在文档被退役、被迁移或进程终止时，UI 会显示什么。

## 观察者收到什么



文档构建在 Chord（@earendil\-works/chord）之上。**Chord 是一个用于复制 JSON 状态的小型库。**要观察文档，你需要理解其中两个概念（基值与增量，原书第56页）：

- **修订版（Revision）——一个不可变的 JSON 值。每次改变文档的提交都会产生一个新的修订版。**

- **操作（Operations）——从一个修订版到下一个修订版的确切编辑，以小型元组表示。其他位置的副本应用这些操作，就能保持同步。**

- 观察者只读。Pi Durable 是唯一的写入者，被观察的状态没有任何用于修改自身的方法，见 spec §9\.1。每个操作都是一个元组：先是单个字母的名称，再是由键和数组索引组成的路径，用来定位值中的位置。



|**元组**|**含义**|
|---|---|
|`["r", value]`|替换整个值|
|`["s", path, value]`|设置一个属性或数组元素|
|`["d", path]`|删除一个属性或数组元素|
|`["a", path, text]`|向字符串追加内容|
|`["t", path, count]`|从字符串开头移除 count 个 UTF\-16 码元|
|`["p", path, index, remove, items]`|对数组执行 splice 操作|
|`["m", path, permutation]`|对数组重新排序：`new[i] = old[permutation[i]]`|

> 来源：research/pi/packages/chord/src/delta/README\.md。同一个变更可以用不同的元组表示；较大的编辑可能以一个 s 或 r 操作到达。只有最终结果值受到保证。
> 
> 

## 观察同一文档的两种方式



- `DOCUMENTSTATE()` 你订阅的一个只读状态。它以当前值作为初始值，并在每次提交 \(commit\) 后调用你的监听器。使用它来驱动用户界面 \(UI\)。

- `WATCHDOC()` 由一系列数据帧 \(frames\) 组成的流，每次提交对应一帧：包含新值、其操作以及该次提交的 `Context`（上下文）。你的回调函数每次处理一帧。使用它来按顺序转发变更内容（参见 watch 契约 \(第 129 页\)）。



两者都接受与 snapshot\(\) 相同的参数，并遵守两条规则。观察不会创建文档：文档不存在时返回 undefined；只有 tx\.doc\(\) 会创建文档（访问与创建，原书第53页）。此外，观察者跟随的是一个具体的文档实例世代，即它附着的那份已存储副本。如果该文档被退役后再次创建，观察者不会转而跟随它。



![image\.png](图片和附件/image%202.png)

> 文档状态只有在存储持有提交之后才能看到它；你的监听器在 commit\(\) 完成前的一个微任务中运行。步骤1在 Session 的变更串行队列上运行，因此首次取值与附着之间不可能插入任何提交；随后 subscribe\(\) 立即以 hydrate 0 交付该值。Board 文档就是 research/capture/extra\-p8/doc\-observation\.txt 中捕获的文档（见下图）。来源：src/session/session\.ts、src/session/observation\.ts、chord/src/services/state\.ts。
> 
> 



这是从读取一侧看到的本书核心规则。在存储持有提交之前，观察者不会收到任何东西。提交在变更串行队列上的工作结束后、commit\(\) 完成之前，监听器会在一个微任务中运行。只有监听器的异步部分在队列之外运行：缓慢的同步监听器确实会拖延下一次提交，因此应把耗时工作交给 promise，见 spec §1。附着操作排在先前提交之后等待，所以首次取到的值已经包含所有这些提交。对于你尚未见过的修订版，你永远不会收到它的操作，见 spec §9\.1。

## documentState\(\) 的用法



示例4创建了一个文本为 "first" 的对话文档，附着一个状态，然后提交一次变更。

```JavaScript
const notesState = await session.documentState(Notes, chat.id, context);
const stopNotes = notesState.subscribe((value, _deliveryContext, delivery) => {
    console.log("Chord notes:", delivery.kind, delivery.sequence, value);
});
await session.commit(async(tx) => {
    (await tx.doc(Notes, chat.id)).text = "published through Chord";
}, context);
```



```Bash
$ node --conditions=source --experimental-strip-types test/examples/04-chord-state.ts
Chord notes: hydrate 0 { text: 'first' }
Chord notes: update 1 { text: 'published through Chord' }
```

> 这里省略了 Notes 定义、用于创建文档的提交、undefined 检查，以及末尾的 stopNotes\(\) 和 dispose\(\)。subscribe 立即以 hydrate 交付当前值，之后每次提交交付一次 update。输出来自运行04。
> 
> 



delivery\.sequence 从0开始计数，只统计这个状态自身的交付次数。它不是提交编号，也不会被存储，见 spec §9\.1。同一文档上的两个状态彼此独立。释放其中一个只会停止那个观察者，不会停止文档。

## 修订版不可变且共享结构



你收到的每个值都是一个 Session 永远不会再改变的修订版。提交未触及的部分与上一个修订版共享，而不会被复制。在下图所依据的捕获中，修改标题生成了一个新的根对象，但 V2\.cards 与 V1\.cards 是同一个数组对象。



![image\.png](图片和附件/image%206.png)

> 每次提交都会产生一个新的不可变修订版，以及产生它的确切操作。这里同时通过 documentState\(\) 和 watchDoc\(\) 观察一个会话作用域的 app\.board；退役之前又发生了101次提交。值、操作、序号和共享检查均来自 research/capture/extra\-p8/doc\-observation\.txt。
> 
> 



共享使发布的成本很低，但没有任何对象被冻结。如果你的代码修改了收到的值，就会悄无声息地破坏 Session 的副本以及其他所有观察者的副本。需要编辑时，先复制，见 spec §12。



要在另一个进程中维护副本，应从首次取得的值开始，使用 Chord 的 applyImmutable\(value, ops\) 按顺序应用每一批操作。测试套件会检查这样能否重建每一个交付值，见 test/session\-watches\.test\.ts。

## 退役、版本、关闭与崩溃



- 退役——最后一帧是 `[["r", null]]`。之后状态读出的就是 null，绝不会是过时数据。监听交付该帧后，以 retired 原因结束。若要看到重新创建的文档，需要重新附着。

- 新版本——当某次提交以不同的定义版本存储文档时，观察者收到的是以 `["r", value]` 表示的完整新值，而不是针对它并不拥有的数据结构的操作，见 src/session/session\.ts。

- Session 关闭——每个状态和监听都会结束。状态保留最后一个值，见 spec §2\.2。

- 崩溃——状态和监听都存在于内存中，随进程一起消失。重新打开后，再次附着；新状态从已提交的内容开始，见 spec §9\.1。



UI 不会因崩溃而丢失任何已经显示过的内容，因为它显示的始终只有已提交数据。自上次成功提交以来的进度可能消失。默认的100 ms最小间隔并不限定这种损失的上限（实时文档，原书第88页）。



> **这对你意味着什么：**
> 
> - 用 documentState\(\) 驱动 UI。它只显示已提交的数据，因此崩溃后无需额外处理就能保持正确。
> 
> - 绝不要修改收到的值。先复制它。
> 
> - 将 `["r", …]` 视为“替换所有内容”。文档退役、版本变化和缓冲区溢出时都会出现它。
> 
> - 文档退役或重新打开后，重新附着；观察者绝不会移到新的实例世代上。若要通过 Chord 服务为远程客户端提供数据，请遵循 docs/pico\-v5\-chord\-usage\.md。
> 
> 

# 对话视图与 watch\(\)

---

一个值同时包含对话的对话记录和当前正在运行的内容；它只在提交落定时变化，你可以把它作为状态读取，也可以把它作为帧流读取。



聊天 UI 需要两样东西：对话记录，以及当下正在发生的事情，例如模型正在流式输出文本，或工具正在打印输出。对话视图把这两者放进同一个只读值中，这个值只在提交落定时改变。读完本节，你就能渲染它、让远程副本保持同步，并预测缓慢客户端或晚加入的客户端会看到什么。

## 视图包含什么



视图只是一组存储数据：没有任何计算或过滤。下面是捕获中那段对话在运行开始前的视图。



附着时的 watch\.value，来源：research/capture/watch\-ops\.txt：

```JSON
{
    "conversation": { "id": 1 },
    "entries": [],
    "docs": {
        "pi.agent": { "model": { "provider": "faux", "modelId": "faux-1" } },
        "pi.live": {},
        "pi.inbox": { "items": [] },
        "pi.provider": { "sessionId": "01a10c8d-c25d-72c3-83b8-8dc6cf418d86" },
        "pi.usage": { "models": {}, "tools": {} }
    }
}
```

> 每个文档都折叠成了一行。pi\.live 为 \{\}，因为还没有任何工作在运行。
> 
> 



- `conversation`——对话记录；如果有父级和所有者，也会包含它们（记录与 ID，原书第25页）。

- `entries`——按存储形态呈现的活动对话记录：最新的头指针标记，随后是从该标记的头指针目标到当前尾部之间的非头指针条目。这些是记录，不是模型上下文（从对话记录到模型上下文，原书第40页）。

- `docs`——五个内置文档，以 kind 为键（内置文档，原书第60页）。文档不存在，对应的键也就不存在。



这些 kind 及其字段都是公开协议。你自定义的文档 kind 不包含在视图中；请用 documentState\(\) 观察它们，见 spec §9\.3。

## 视图如何变化



Harness 为每段对话保留一个共享视图。它在首次使用时从存储中构建，并在最后一个观察者离开时丢弃，见 src/harness/view\.ts。每次涉及该对话的提交都会产生一帧：一批把旧视图转变为新视图的操作。



![image\.png](图片和附件/image%205.png)

> 一个视图帧先包含提交的文档变更，再包含新条目，所有操作都改写成指向同一个值的路径。来源：src/harness/view\.ts 中的 advance\(\)。第一行来自 research/capture/watch\-ops\.txt 的第3帧；第1帧展示了操作顺序：先设置 pi\.live，再拼接插入条目7。
> 
> 



下面这一帧完成一个工具。五个操作一同落定：槽位的状态和条目、删除其进度的两个操作，以及拼接插入结果条目的操作。



第14帧：一次提交完成一个工具，来源：research/capture/watch\-ops\.txt：

```JSON
[
    ["s", ["docs", "pi.live", "tools", 0, "status"], "done"],
    ["s", ["docs", "pi.live", "tools", 0, "entry"], 13],
    ["d", ["docs", "pi.live", "tools", 0, "output"]],
    ["d", ["docs", "pi.live", "tools", 0, "details"]],
    ["p", ["entries"], 3, 0, [{ "kind": "pi.tool-result", "id": 13, ... }]]
]
```

> 条目内容已省略。槽位在插入条目13的同一帧中指向它，因此渲染器永远不会看到悬空引用。
> 
> 



按顺序应用一帧的操作；这些操作并不保证是最简集合。一帧没有触及的视图部分仍是同一批对象。只追加条目的帧会保留同一个 docs 对象，因此渲染器可以通过比较引用来跳过工作，见 test/harnessview\.test\.ts。

## 使用视图的两种方式



- **viewState\(\) **一个 Chord 状态，与 documentState\(\) 类似。如果在同一进程中只需要最新值，就使用它，例如每次更新时重新渲染的终端 UI。

- **watch\(\) **一个帧流。要跨进程边界维护副本，就使用它：先发送一次 watch\.value，再按顺序发送每一帧的操作。另一侧通过 applyImmutable\(\) 应用它们。



重新连接时，启动一个新的监听并再次发送其值。示例19加上 \-\-ops 会准确打印这个流：先是视图，随后每次提交输出一行操作。

## 监听契约



watch\(\)、watchDoc\(\) 和 watchTaskGraph\(\) 都返回 WatchHandle，并遵守相同的五条规则：

1. 先读取 watch\.value。它保存起始值。start\(\) 之前提交的帧会在缓冲区中等待。

2. 只调用一次 start\(listener\)。它绝不会同步调用监听器。第二次调用 start\(\)，或在监听结束后调用，都会抛出异常。

3. 每次只运行一个回调。每个回调都收到 \(value, ops, context\)。你的 promise 落定后，下一个回调才会开始。提交绝不会等待你。

4. context 来自该提交，但不带其 abort 信号。监听器启动的工作由你负责中止。

5. 可以安全地重复调用 stop\(\)。它会丢弃待处理的帧，并返回监听结束的方式。已经运行的回调不会被中止。

    

|**WatchEnd\.reason**|**原因**|
|---|---|
|stopped|调用了 stop\(\)|
|cancelled|附着时传入的 Context 被中止|
|session\_closed|Session 开始关闭|
|retired|已交付被退役文档的 null 帧|
|listener\_error|你的监听器抛出了异常；携带 error，且只有这个监听结束|

> 来源：src/types\.ts（WatchEnd）。先出现的原因生效。在任务或工具内部打开的监听也会在那次调用结束时停止（src/harness/scheduler\.ts）。
> 
> 

## 缓慢的使用方与晚加入的使用方



监听绝不会让提交等待。如果你的监听器落后超过100帧，等待中的帧就会被丢弃，并由一帧持有最新值的帧替换。



![image\.png](图片和附件/image%203.png)

> 一个监听会保留100个尚未交付的帧；下一次提交会用最新值替换它们全部。正在交付的帧绝不会被替换。规则来源：spec §9\.2 和 src/session/observation\.ts。一个测试在 start\(\) 之前提交了101个条目，最终收到一帧 `[["r", view]]`，其中包含所有101个条目。
> 
> 



替换帧是 `[["r", newest]]`，因此应用操作的代码不需要特殊处理。代价是某些中间状态永远不会被交付。监听显示的是最终到了哪里，而不是每一个步骤。如果你需要每次状态转换，就把每次转换记录为条目，或记录在文档中。要获取单个输入的结果，请使用 Submission\.wait\(\)（提交请求与收件箱，原书第84页）。



晚加入或重新连接的客户端从当前视图开始，不会重放任何内容。示例21在一个每100 ms打印一行的工具运行到一半时附着：

```Bash
$ node --conditions=source --experimental-strip-types test/examples/21-late-join.ts
view entries: [ 'pi.user', 'pi.system', 'pi.assistant' ]
view tool slot: running "1\n2\n3\n4\n5\n"
view output now: "1\n2\n3\n4\n5\n"
snapshot tools: [ 'count running' ]
view output now: "1\n2\n3\n4\n5\n6\n"
event output now: "1\n2\n3\n4\n5\n6\n"
```

> 这是 research/runs/21\-late\-join\.txt 的开头几行。视图已经包含已提交的输出；8\.3节（原书第133页）的事件流也从同一状态开始。
> 
> 



晚加入的客户端看到五行，是因为每一行都已提交。工具进度的默认最小提交间隔为100 ms（settings\.progress）。崩溃会丢失自上次成功提交以来的进度；实际间隔可能更长（运行控制与实时文档，原书第88页）。



> **这对你意味着什么：**
> 
> - 同一进程中，只需要最新值：viewState\(\)。远程副本：watch\(\) 配合 applyImmutable\(\)。
> 
> - 在流中的任何位置都要把 `["r", value]` 当作完整替换来处理。
> 
> - 不要把监听当成审计日志。请使用条目、文档或 Submission\.wait\(\)。
> 
> - 重新连接时，再次附着并重新发送 watch\.value。
> 
> 

# 智能体事件

---

> 一个实验性适配器把每次提交转换为一批编码智能体事件：快照是状态，每一批事件都是对该状态的一次变更。
> 
> 

你可能已经有读取编码智能体事件的代码，例如读取 message\_start 和 tool\_execution\_update 的 JSON 日志、CLI 或 UI。watchEvents\(\) 会从 Pi Durable 的提交中生成这些事件。读完本节，你就能使用这个事件流、从增量中重建流式文本，并了解它可能跳过哪些步骤。

## 附着



watchEvents\(harness, conversationId, context\) 从包的根入口导出，并被标为实验性：它的协议可能变化。它返回一个流，包含 snapshot（起始状态）、start\(listener\)、stop\(\) 和 closed。它遵守8\.2节（原书第129页）的监听规则：每次交付一批事件，提交绝不会等待，见 src/harness/events\.ts。



快照包含对话的条目、正在运行的工具、压缩、收件箱、智能体和用量。运行尚未结束时，还会包含 run 和 generation、正在流式输出的消息或重试等待，见 research/capture/agent\-events\.txt。



只有在使事件成立的那次提交完成之后，事件才会被发出，见 spec §9\.4。事件流只覆盖一段对话。子智能体的工作只会以父级工具调用的形式出现；若要查看内部情况，需要为子对话附着第二个事件流（子智能体，原书第121页）。

## 一次提交，一批事件



每次提交至多产生一批事件。下表展示了捕获中的一个轮次：模型思考，调用 count \{n: 3\}，然后回答。一次生成就是一次模型调用，以任务形式运行。

|**提交**|**发生了什么变化**|**事件批次**|
|---|---|---|
|1|用户消息已提交；运行开始|message\_start, message\_end, submission, run\_start, turn\_start|
|2|系统提示词条目|message\_start, message\_end|
|3|生成的第1次尝试开始|无|
|4|第一个流式部分内容|message\_start|
|5\-7|思考和文本流入|每次各有一个 message\_update|
|8|助手消息已提交；工具调用进入队列|message\_end, usage\_changed|
|9|工具开始运行|tool\_execution\_start|
|10\-13|工具输出和详情|每次各有一个 tool\_execution\_update|
|14|工具完成；其结果条目已提交|tool\_execution\_end, message\_start, message\_end|
|15|下一次生成替换第一次生成|turn\_end, turn\_start|
|16|第1次尝试开始|无|
|17\-19|回答流入|message\_start, message\_update ×2|
|20|回答已提交；运行结束|message\_end, turn\_end, run\_end, submission, usage\_changed|

> 来源：research/capture/watch\-ops\.txt（20帧）和 agent\-events\.txt（18批事件），它们来自 test/capture/view\-ops\.ts 的同一次运行。
> 
> 



提交3和16没有产生事件批次：开始一次尝试，并不会改变事件所描述的任何内容。工具开始事件要等到提交9，即调用实际运行时才出现。在提交15中，一次生成结束，下一次生成开始，因此轮次结束和轮次开始共处同一批次。



批次内部的顺序固定，并与编码智能体保持一致。先进度，再新条目，再结束，最后才是开始。因此，工具结束事件紧挨着其结果消息之前出现；一次已完成的运行会在下一次运行开始之前结束。

> 同一批次中，先进度，再条目，再结束，最后是开始。右侧：一次提交对某次运行给出回答，并把排队的后续输入作为下一次运行启动；图中是测试对此预期的事件批次（test/harness\-events\.test\.ts）。

## 每个事件的含义



|**事件**|**在提交执行以下操作时发出**|
|---|---|
|run\_start/run\_end|开始或结束一次运行。加入现有运行的引导输入并不是一次新的运行|
|turn\_start/turn\_end|把运行推进到一次新的生成／提交某次生成的结果|
|message\_start/message\_end|提交某次尝试的第一个流式部分内容，或提交一个此前没有流式部分内容的消息条目／追加一个包含模型消息的条目|
|message\_update|改变流式部分内容；携带 usage 和 changes|
|entry\_appended|追加一个不含模型消息的条目，例如普通的 pi\.reset|
|tool\_execution\_\*|启动一个工具调用／改变其 output、details 或 diagnostics／完成它，或随所属运行一起丢弃它|
|submission|写入属于这段对话的提交请求记录|
|inbox\_update, agent\_changed, usage\_changed|改变相应文档|
|auto\_retry\_start/\_end, deferred\_poll|开始或结束一次重试等待；安排或调整一次延迟轮询|
|task\_failed|将对话中的某个任务以 faulted 或 orphaned 状态完成|
|compaction\_start/\_end|开始或完成一次压缩|

> 来源：spec §9\.4；src/harness/events\.ts。
> 
> 



每个 message\_start 都会得到一个 message\_end，即使运行在流式输出途中被中止也是如此。只有已有内容时，部分内容才会被提交；每条清除它的内置路径也都会追加已结束的条目。崩溃前后同样如此：重新打开时，生成逻辑把残留的部分内容转成一个已中止的 pi\.assistant 条目（生成，原书第91页），事件流会据此结束消息，见 spec §9\.4；test/harness\-events\.test\.ts。

## 交付增量，而非完整值



message\_update 只携带流式消息中发生变化的内容。追加文本以 text\_delta 或 thinking\_delta 到达，追加的工具参数以 toolcall\_delta 到达，新内容块以 \*\_start 到达。其他任何变化都会重新发送整个内容块或整条消息。部分内容经历十次提交，产生的是十个小事件，而不是十份副本，见 spec §9\.4。



提交6的事件批次，来源：research/capture/agent\-events\.txt：

```JSON
{
    "type": "message_update",
    "usage": { "input": 56, "output": 19, ... },
    "changes": [
        { "type": "text_start", "contentIndex": 1, "block": { "type": "text", "text": "" } },
        { "type": "thinking_delta", "contentIndex": 0, "delta": "use the tool." }
    ]
}
```

> 两个视图操作按顺序变成两个 changes。usage 字段有所省略。
> 
> 



工具输出的处理方式相同。输出被替换时，tool\_execution\_update\.output 是 \{ set \}；从开头裁去旧文本并追加新文本时，它是 \{ trimStart?, append? \}。捕获中，第一行对应 `{"set":"1\n"}`，之后对应 `{"append":"2\n"}`。示例21这样重建输出：

stream.start(async (events) => {

# 任务图与 inspect\(\)

---

> 任务图展示每个存活任务的已提交状态；inspect\(\) 还会补充：在你当前的注册表下，调度器会如何处理每个任务。
> 
> 

当一次运行看起来卡住时，原因通常是某个任务正在等待对话记录中看不见的东西。两个只读工具可以展示这些任务。taskGraph\(\) 是用于任务面板的实时值。inspect\(\) 是一次性诊断，也会说明某个任务为何无法运行。读完本节，你就能从“什么都没发生”追踪到相应任务及其原因。

## 一个节点



整个任务图是一个值 \{ tasks \}，以任务 ID 为键。每个节点都是存储中的任务记录去掉载荷后的版本：没有 input、检查点 data、结果 data 或 memo。



图中一个正在等待的任务，来源：research/capture/extra\-p8/inspect\-vs\-graph\.txt：

```JSON
"8": {
    "id": 8,
    "kind": "app.join",
    "conversationId": 1,
    "background": false,
    "abortRequested": false,
    "state": { "status": "waiting", "phase": "done", "on": [7], "policy": "allSettled" },
    "conversations": []
}
```

> 没有 owner 键：这个任务由一段对话拥有。由另一个任务拥有的节点会携带 `"owner": <TaskId>`。abortRequested 在中止该任务的提交中变为 true。
> 
> 



|**state\.status**|**其他字段**|**含义**|
|---|---|---|
|pending|phase|已提交但尚未被调度器取走；也包括进程终止时正在运行、且尚未再次运行的所有任务|
|running|phase|已被当前进程中的调度器取走|
|waiting|phase, on, policy|已存储的等待，完全按提交时的状态呈现|
|completing|outcome|自身已完成，正在保留结果，直到它拥有的工作结束|

> 来源：src/harness/task\-graph\.ts；spec §9\.5。各状态的定义见“任务即状态机”（原书第63页）。
>

## 任务图如何变化



节点在创建其任务的提交中出现，在完成其任务的提交中消失。不改变任何节点的提交，例如 memo 写入，不会产生帧。任务图显示已提交的事实，因此阅读时要牢记三条规则；后面的图通过一个真实帧展示第一条规则。



on 是已存储的值——它列出该等待曾指明的每个任务，包括已经完成的任务。inspect\(\) 会告诉你哪些仍然存活。



running 指当前进程——重新打开 Harness 会把幸存的 running 任务改回 pending（调度器，原书第73页）。在它们再次被取走之前，显示的都是 pending。



只包含存活任务——后台子智能体的任务一旦完成，就不会再有节点列出它的对话。要在那段对话中放置后续任务，应使用该对话的 owner；对话视图也携带这个字段（子智能体，原书第121页）。

taskGraph\(\) 返回一个 Chord 状态；watchTaskGraph\(\) 返回一个遵守8\.2节（原书第129页）规则的监听。两者都不会启动调度，因此查看器可以附着到暂停中的 Harness，而不启动任何工作，见 spec §9\.5。

## inspect\(\)：调度器会做什么



harness\.inspect\(context\) 不写入任何内容，也不运行任何任务代码。它返回 scheduling（首次 resume\(\) 之前为 paused，之后可能是 running 或 closing）、每个存活任务的完整记录和派生状态，以及 queued 和 placed 状态的提交请求。



|**state\.kind**|**条件**|
|---|---|
|running|其代码正在当前进程中运行|
|completing|其结果被保留，直到它拥有的工作结束|
|waiting, on|它仍在等待的存活任务|
|blocked, reason|没有已安装的定义可以运行它：missing\_task、task\_too\_old 或 migration\_failed（带 error）|
|ready, migrates|下一轮调度会取走它；如果较新的定义会先迁移它，则带有 migrates|

> 来源：src/harness/scheduler\.ts。migration\_failed 只在调度器尝试过迁移之后出现；检查本身绝不会执行迁移。
> 
>

任务图无法显示“blocked”，因为没有任何地方存储这个状态。阻塞任务的记录是普通的 pending 或 waiting 记录，它永远不会自行完成。安装可以运行它的定义，或中止它：在捕获中，abortTask\(\) 让两个阻塞任务立即以 orphaned 完成，并把阻塞原因作为结果的 reason。

## 从“什么都没发生”找到原因



当一段对话一直忙碌，或 waitForTask\(\) 始终不完成时，调用 inspect\(\)，并按以下顺序检查:

1. scheduling 为 paused。没有任何东西调用过 resume\(\)，也没有调用会启动它的方法，例如 submit\(\) 或 waitForIdle\(\)。只读查看器绝不会启动它。

2. 某个任务为 blocked。注册表中缺少其 kind，或只有更旧的版本。修正安装，或中止任务，使其以 orphaned 完成（调度器，原书第73页）。

3. 某个任务为 waiting。沿着它的 on 找到存活任务，并重复检查。被中止的任务会先等待它拥有的工作（中止、故障与孤儿任务，原书第80页）。

4. 某个任务为 completing。它自身的工作已完成，但它拥有的工作尚未完成；在任务图中找出它拥有的节点（所有权与结构化并发，原书第76页）。

5. 某个任务为 running。其代码正在执行。对于生成和工具，对话视图中的 pi\.live 会显示尝试、重试等待或工具输出（实时文档，原书第88页）。

    

queued 状态的提交请求在等待排在它前面的运行；placed 状态的提交请求属于一个尚未回答的运行（6\.1节，原书第84页）。已完成的任务不在 inspect\(\) 中；请通过 getTask\(\) 读取它们。
