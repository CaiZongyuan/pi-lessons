# 5\.任务

# 作为状态机的任务

---

> 任务是被拆分成若干阶段的工作；崩溃之后，唯一能保留下来的任务信息就是它的存储记录。
> 
> 

假设你的智能体正在执行银行卡扣款，做到一半，笔记本上盖突然合上了。进程再次启动时，总得有某样东西说明上次做到了哪里。在 Pi Durable 中，这样东西就是任务。本节结束后，你就能编写任务，说出它的五种状态，并读懂存储中的任务记录。

## 任务是一系列阶段



**任务是 Harness 随执行推进而不断提交的工作单元。你将任务分为若干阶段，也就是 ****`prepare`****、****`charge`**** 这样的命名步骤。一个阶段完成自己那部分工作后，会提交一个检查点：一个小型 JSON 值，标明下一个阶段，并保存该阶段需要的全部内容。提交是原子保存：其中所有内容要么一并存储，要么全部不存储。如果进程死亡，下一个进程会读取最后一个检查点，再次运行相应阶段。除此之外，没有任何内容会延续下来。变量和闭包都已消失，只剩存储记录。**



Pi Durable 中的所有工作都这样运行，包括 Harness 自身的模型调用、工具调用和压缩。你用 `defineTask()` 编写任务，并将其注册到扩展的 `tasks` 列表中。Harness 每次启动任务时，都会根据任务名称找到对应代码（扩展与注册表，原书第103页）。



一个两阶段支付任务；来源：`test/examples/12-tasks.ts`

```TypeScript
type PaymentState = { phase: "prepare" } | { phase: "charge"; key: string };
const Payment = defineTask<{ amount: number }, PaymentState, { receipt: number }>({
    name: "example.payment",
    version: 1,
    initial: () => ({ phase: "prepare" }),
    phases: {
        prepare: async (task, runtime, taskContext) => {
            const checkpoint = { phase: "charge", key: `payment-${task.id}` } as const;
            await runtime.commit(() => ({ status: "running", checkpoint }), taskContext);
        },
        charge: async (task, runtime, taskContext) => {
            const key = task.state.checkpoint.key;
            if (!payments.has(key)) payments.set(key, task.input.amount * 100);
            const receipt = payments.get(key)!;
            const outcome = { status: "completed", result: { receipt } } as const;
            await runtime.commit(() => ({ status: "terminal", outcome }), taskContext);
        },
    },
    abort: async (_task, runtime, taskContext) => {
        const outcome = { status: "aborted" } as const;
        await runtime.commit(() => ({ status: "terminal", outcome }), taskContext);
    },
});
registry.install(defineExtension({ name: "payments", tasks: [Payment] }));
```

> 为适应页面宽度，两个内联状态字面量被提取为 `checkpoint` 和 `outcome` 常量。运行 12 打印 `{ status: 'completed', result: { receipt: 500 } }`。
> 
> 



从上到下阅读。`initial` 给出第一个检查点。`prepare` 选择一个幂等键，并将它提交到检查点 `{ phase: "charge", key }` 中。`charge` 从 `task.state.checkpoint` 读回该键，而不是从变量读取，因为重启后变量已经消失。随后，它提交最终结果。只有当某人中止任务时，`abort` 才会运行。



|**字段**|**含义**|
|---|---|
|`name`|任务的种类，存入每一条记录。重命名会让旧名称下已存储的任务失去对应代码|
|`version`|存入每一条记录。较新的定义必须迁移较旧的记录（调度器，原书第73页）|
|`initial(input)`|第一个检查点，在创建任务时提交|
|`phases`|每个阶段名称对应一个处理函数。每个处理函数看到的任务类型都已收窄到它自己的阶段|
|`abort`|中止后运行，必须提交最终结果（中止、故障与孤立，原书第80页）|
|`migrate?`|升级旧版本存储的输入和检查点|
|`hooks?`|其他扩展可以附加到此任务上的钩子（钩子，原书第109页）|

> 来源为 `src/types.ts` 中的 `TaskDefinition`。它的类型参数分别为输入 `I`、检查点 `S`、结果 `R` 和钩子 `H`。
> 
> 

## 五种状态



任务始终处于五种状态之一（`src/types.ts`）。其中三种是存活状态。**`pending`**** 表示它正在排队等待运行。****`running`**** 表示代码此刻正在执行它。****`waiting`**** 表示它暂停下来，等待其他任务结束。另外两种状态已经持有结果。****`completing`**** 表示结果已经确定，但任务启动的工作仍在运行。****`terminal`**** 表示它已经彻底完成，此时记录就成了一份回执。**



![image\.png](图片和附件/image%202.png)

> 故障或孤立结果在子工作仍存活时，也会暂存为 `completing`。
> 
> 



`abortRequested` 是存活记录上的标志，不是一种状态：下一次启动将运行中止处理函数。



任务有五种状态；你的代码提交检查点、等待和结果，其余事情由 Harness 处理。状态边来自 `src/harness/scheduler.ts`。带有中止标记的 `waiting` 任务也会提前离开等待状态，运行中止处理函数；带有中止标记的 `pending` 或 `waiting` 任务，如果没有代码能够接手，则以 `orphaned` 结束。



你的代码只能通过 `runtime.commit()` 推动任务。一个阶段可以提交新检查点并保持 `running`，开始等待，或以 `terminal` 结束。它绝不能设置 `pending`。只有 Harness 会在崩溃后重新打开，或将任务交给新加载的代码时设置该状态。Harness 还会写入故障、孤立结果和中止标记：“调度器负责启动reservation、协调、交接、故障与孤立处理；`abortTask()` 负责中止标记”（spec §5\.1）。如果一个阶段结束时，它启动的任务仍在运行，Harness 会改为将它存成 `completing`（所有权，原书第76页）。

## 记录



任务的完整状态位于一条 JSON 记录中，每次提交都会整体替换该记录。**下面是商店运行采集中的一个订单任务。它已完成银行卡扣款，启动了三个打包任务，目前正在等待它们。**



订单任务 7，正在等待（提交 seq 7）；来源：`research/capture/task-transitions.txt`

```JSON
{
    "id": 7,
    "kind": "shop.order",
    "abortRequested": false,
    "state": {
        "status": "waiting",
        "checkpoint": { "phase": "decide", "chargeId": "ch_a_1", "packs": [8, 9, 10], ... },
        "on": [8, 9, 10],
        "policy": "failFast"
    },
    "memos": { "chargeId": "ch_a_1" }
}
```

> 省略了 `conversationId`、`version`、`input`、`background` 和检查点的 `key`。任务 7 没有 `owner` 字段，因为它的所有者是所属对话。
> 
> 



- `state`：状态，以及任务存活时的检查点，或结果确定后的结果

- `on`、`policy`：它等待的任务，以及其中一个失败时会发生什么（所有权，原书第76页）

- `memos`：小型存储值，首次写入者胜出（阶段与进展，原书第67页）

- `abortRequested`：持久化的中止标志

- `owner`：仅在子任务上设置



`conversationId` 和 `owner` 永远不会改变。尝试将任务移到另一个对话的提交，会被拒绝并报错 `Task N cannot change conversations`（`src/session/transaction.ts`）。



订单完成后，其记录会缩减成一份回执。检查点和memos被丢弃，状态中只保留结果：`{"status": "terminal", "outcome": {"status": "completed", "result": {"chargeId": "ch_a_1", "boxes": [...]}}}`（`capture/task-transitions.txt`）。终态记录会永久保留，因此要让结果尽量小。将大块数据放到条目或文档里，只返回其 ID（spec §12）。

## 结果



|**状态**|**字段**|**写入方**|**含义**|
|---|---|---|---|
|`completed`|`result`|任务|成功；带类型的 `R`|
|`failed`|`error`、`result?`|任务|预期内的失败，例如银行卡被拒|
|`aborted`|`reason?`、`result?`|其中止处理函数|已中止，任务完成了清理|
|`orphaned`|`reason`|Harness|中止时没有代码能够接手|
|`faulted`|`error`|Harness|缺陷：抛出异常，或阶段没有取得进展|

> 来源为 `src/types.ts` 中的 `TaskOutcome<R>`。每个错误都是普通 JSON：`{ message, detail? }`，绝不是运行时 `Error`。
> 
> 

## 阶段可以调用什么



每个阶段处理函数接收 `(task, runtime, context)`。`task` 是存储记录。`runtime` 是本次任务运行的工具箱，运行结束后它就会失效（`src/types.ts`）。

|**用途**|**成员**|
|---|---|
|提交|`commit(change, context)`、`memo(name, candidate, context)`|
|读取已提交状态|`memo(name)`、`getTask`、`outcomes`、`entry`、`context`、`snapshot`、`snapshotAsOf`、`watchDoc`|
|等待|`waitForTask`、`sleep(until)`|
|环境|`agent()`、`hooks`、`registry`、`settings`、`models`、`env()`、`conversation()`|
|身份与时钟|`taskId`、`conversationId`、`signal`、`now()`、`report()`|

> 来源为 `src/types.ts` 中的 `TaskRuntime`。
> 
> 



`runtime.commit()` 是唯一的提交途径。回调接收一个事务和当前记录。它可以追加条目、写入文档、创建子任务，也可以返回任务的下一个状态。所有内容都在一次原子提交中落地，因此检查点绝不会与它描述的数据不一致。以这种方式提交的条目会将任务记为其作者（`byTaskId`）（spec §5\.1）。如果运行已经结束、Harness 正在关闭、任务不再处于 `running`，或任务带有中止标记，提交会被拒绝。



> **这对你意味着什么：**
> 
> - 将下一个阶段需要的所有内容放入检查点。变量无法跨重启保留
> 
> - 将 `name` 视为永久不变。检查点结构变化时，提高 `version` 并添加 `migrate`
> 
> - 在同一次 `runtime.commit()` 中提交检查点及其描述的数据
> 
> - 保持结果小巧；将大块数据存入文档或条目
> 
> 

# 阶段、步骤与进展

---

> 如果一个阶段没有提交任何新进展，它就会永远重复运行，因此 Harness 会改为以故障停止该任务。
> 
> 

**任务一个阶段接着一个阶段运行。在阶段之间，Harness 会快速检查：任务是否已经结束、被中止或正在关闭，以及上一个阶段是否提交了进展。**本节结束后，你就能预测这一检查对任意阶段会作出何种判断，设计始终能够取得进展的阶段，并安全地使用memos和休眠。

## 一次运行，多个阶段



Harness 启动任务时，会创建一次调用实例：任务在内存中的一次运行，拥有自己的中止信号。一个调用实例会连续执行各阶段，直到任务完成、开始等待或被停止。提交检查点不会结束调用实例。下一个阶段会立即在同一进程中开始。



每个阶段之前，Harness 都会执行一次步骤检查：读取已提交记录，并判断是否继续。这一步本身也是 Session 唯一写入队列上的一次提交（提交，原书第29页），因此它能看到阶段返回之前完成的每次提交。在这一步之后才进入队列的提交会被拒绝，错误为 `invocation has ended`（`test/harness-tasks.test.ts`）。



![image\.png](图片和附件/image%203.png)

> 每个阶段之前，步骤检查应用第一条匹配的规则；没有进展就属于故障。规则来自 spec §5\.1，由 `src/harness/scheduler.ts` 实现。
> 
> 

## 六条规则



第一个阶段之前只应用规则 1–3，因为还没有任何阶段返回。阶段返回后，以第一条匹配的规则为准：

1. **已结束、****`completing`**** 或 ****`waiting`****：停止。**该阶段已提交结果或等待状态，没有更多内容可运行

2. **Harness 正在关闭：停止。**检查点及任何中止标记保留给下一个进程。关闭绝不写入结果

3. **有中止标记：停止本次运行。**等任务自己的子工作完成后，再启动单独的中止运行（中止，原书第80页）

4. **阶段抛出异常：写入 ****`faulted`****，并附上错误消息。**与所有结果一样，只要任务的子工作仍然存活，它就暂存为 `completing`（所有权，原书第76页）

5. **检查点改变：继续下一个阶段，或将任务交给新加载的代码**（调度器，原书第73页）

6. **检查点未变：写入 ****`faulted`****，“因为没有取得持久化进展”；**同样，只要子工作仍然存活，就暂存为 `completing`



在两种情况下，顺序尤其重要。一个阶段先提交新检查点再抛出异常，仍会变成故障，因为规则 4 在规则 5 之前。一个阶段先提交最终结果再抛出异常，则会保留结果，因为规则 1 最先应用。此后它尝试的任何提交都会被拒绝，错误为 `Task N is terminal`（`test/harness-tasks.test.ts`）。

## 为什么没有进展就是故障



如果阶段结束时，检查点与开始时一样，它就会用同样的输入一遍遍运行，永无止境。因此，步骤检查会将两个检查点作为 JSON 比较，忽略键的顺序。如果二者相等，就将任务标为故障，错误为 `Task test.idle phase run returned without durable progress`（`test/harness-tasks.test.ts`）。三种模式会触发这条规则：

- 阶段没有提交任何内容就返回

- 阶段提交了条目或文档，但没有从 `runtime.commit()` 返回新状态。只有检查点才算进展

- 阶段提交了一个与旧检查点相等的副本



只要检查点发生改变，一个阶段可以再次运行自身。示例 13 的计数器只有一个阶段 `tick`，每次都提交 `{ phase: "tick", n: n + 1 }`。阶段名称没有变，但检查点变了，因此规则 5 允许继续。

## Memos：记住一个小决定



**Memos是存储在任务记录上的一个小型命名值。首次写入者胜出。**`runtime.memo(name, candidate)` 只在该名称尚无值时提交候选值，无论是否写入，都会返回已存储的胜出值。`runtime.memo(name)` 只读取（spec §5\.2）。同时写入 `"a"` 和 `"b"` 时，两次调用都会得到 `"a"`（`test/harness-tasks.test.ts`）。**Memos可以跨重启保留，并在任务结束时被丢弃。提交memos不算进展。**



**用memos避免一个阶段内的某个副作用重复执行。**示例 13 即便同一阶段运行两次，也只打印每个 tick 一次：



Memos保护同一阶段内的副作用；来源：`test/examples/13-recovery.ts`

```JavaScript
tick: async (task, runtime, taskContext) => {
    const n = task.state.checkpoint.n;
    if ((await runtime.memo(`printed-${n}`, taskContext)) === undefined) {
        await runtime.memo(`printed-${n}`, true, taskContext);
        console.log(`tick ${n}`);
    }
    // ...提交 { phase: "tick", n: n + 1 }，或在 n 达到 task.input.to 后提交 terminal
    await runtime.sleep(Date.now() + 50, taskContext);
},
```

> 省略了检查点提交和一个仅用于测试的钩子。
> 
> 



```Bash
$ node --conditions=source --experimental-strip-types test/examples/13-recovery.ts
tick 1
tick 2
closed; saved checkpoint: { status: 'pending', checkpoint: { phase: 'tick', n: 2 } }
memos: { 'printed-1': true, 'printed-2': true }
tick 3
tick 4
tick 5
after reopen: { status: 'completed', result: 'counted to 5' }
```

> 运行 13；`memos` 为了排版被换到了第二行。第一个进程打印 `tick 2` 后、提交 `n: 3` 前关闭。第二个进程重新运行 tick 2，找到memos `printed-2`，因此跳过打印。
> 
> 

## 休眠



`runtime.sleep(until)` 等待 Harness 时钟到达 `until`。休眠不是持久化的。关闭 Harness 会取消休眠，下一个进程会从检查点重新启动该阶段。如果截止时间必须跨重启保留，就将其放入检查点，正如示例 24 的支付任务使用 `at` 字段所做的那样。

### 细节



时钟由 Harness 的 `now` 选项提供，默认为 `Date.now`。较长的休眠会被拆分为每段最多 2,147,483,647 毫秒的定时器，每段结束后重新检查时钟。运行被停止或调用方的上下文被取消时，休眠会拒绝（`src/harness/scheduler.ts`）。



钩子与任务共享memos名称，因此要为自己的memos加上前缀。`toString` 这样的名称绝不会解析到继承属性（spec §5\.2；`test/harness-tasks.test.ts`）。



> **这对你意味着什么：**
> 
> - 每个阶段结束时，都要改变检查点、开始等待，或完成任务
> 
> - 条目和文档不算进展。请从 `runtime.commit()` 返回新状态
> 
> - 用memos记录小型决定，例如一个 ID 或选定的分支。大量进度信息应放入文档（spec §12）
> 
> - 将截止时间保存在检查点中，不要仅保存在休眠里
> 
> 



> 来源：spec §5\.1、§5\.2、§12；`src/harness/scheduler.ts`；`test/harness-tasks.test.ts`（任务阶段、任务运行时）；示例 13、运行 13；示例 24。
> 
> 

# 副作用三明治

---

> 先提交你准备做什么，执行它，再提交发生了什么；中途崩溃留下的是一个明确的问题，而不是无声的空白。
> 
> 

Harness 可以原子提交自己的记录，但无法让银行卡扣款、部署或电子邮件与这些记录一起原子完成。如果进程恰好在扣款后死亡，客户到底付过钱没有？本节结束后，你就能把任意外部动作拆分成若干阶段，让每个崩溃点都有明确定义且安全的恢复方式。

## 为什么副作用需要自己的阶段



副作用是任何改变存储之外世界的动作：一次支付、一次 API 调用、另一台机器上的一个文件。副作用不得在提交内部执行（spec §1，不变量 4）。一次提交会占用 Session 的写入队列，因此在其中等待网络会阻塞所有其他写入方（提交，原书第29页）。所以，副作用总是发生在两次提交之间，而进程也可能在两者之间死亡。规范给出的答案是一种固定结构：

```Plain Text
提交意图阶段
执行外部副作用
提交结果或下一阶段
```

> 对应 spec §5\.2 的原文。
> 
> 



![image\.png](图片和附件/image%204.png)

> 提交意图、执行副作用、提交结果；中途崩溃后，会重新运行副作用阶段。阶段来自 spec §5\.1 的支付示例。步骤 4 的条目和最终状态在同一次提交中落地。
> 
> 



规范自身的示例分为三部分。**`prepare`**** 创建一个幂等键，并将其作为下一个检查点提交。****`charge`**** 使用该键执行副作用，然后在同一次提交中追加回执条目并完成任务。中止处理函数撤销扣款，并提交 ****`aborted`****。**



意图、副作用、结果；来源：`docs/spec.md` §5\.1

```JavaScript
// 意图、副作用、结果。
prepare: async (task, runtime, context) => {
    await runtime.commit(() => ({ status: "running",
        checkpoint: { phase: "charge", key: newKey() } }), context);
},
charge: async (task, runtime, context) => {
    const receipt = await payments.charge(task.state.checkpoint.key); // 按键保证幂等
    await runtime.commit(async (tx, current) => {
        const entry = await tx.appendEntry(current.conversationId, receiptEntry(receipt));
        return { status: "terminal",
            outcome: { status: "completed", result: { entryId: entry.id } } };
    }, context);
},
// 中止处理函数决定结果；未提交结果就返回会使任务出现故障。
abort: async (task, runtime, context) => {
    await payments.cancel(task.state.checkpoint);
    await runtime.commit(() => ({ status: "terminal",
        outcome: { status: "aborted", reason: "user" } }), context);
},
```

> Two long lines are wrapped; nothing else is changed\.

## 每个崩溃点，以及重新打开后会发现什么



新进程打开存储时，之前处于 `running` 的每个任务都会带着检查点回到 `pending`（调度器，原书第73页）。说明任务做到哪里的，是检查点，而不是进程：

|**崩溃时机**|**重新打开后发现**|**会运行什么**|
|---|---|---|
|意图提交之前|检查点为 `prepare`|再次执行 `prepare`；尚未发出扣款|
|意图之后、扣款之前|检查点为 `charge`|首次执行扣款|
|扣款之后、结果之前|检查点为 `charge`|使用相同的键，再次执行扣款|
|结果提交之后|`terminal`|不执行任何内容|

> 对新进程来说，中间两行看起来完全相同。用规范的话说：“在意图阶段重新打开，意味着副作用可能已经发生。”
> 
> 



Harness 无法知道进程死亡之前，请求是否已经到达支付服务，因此无论是哪种情况，你的阶段都必须正确。规范指出了三种方式：“阶段处理函数安全地重试、轮询外部句柄，或记录中断”（spec §5\.2）:

- 安全重试：发送一个在意图阶段创建并存入检查点的幂等键。在恢复测试中，转账服务在关闭和重新打开前后被调用两次，但只执行一次转账，因为两次调用都携带 `transfer-N`（`test/harness-tasks-recovery.test.ts`）

- 轮询句柄：远程系统返回操作 ID 后，先提交该 ID，再等待，然后向远程系统查询结果。生成任务对延迟模型调用采用这种方式（生成，原书第91页）

- 记录中断：前两种方式都不可用时，提交一个结果，说明副作用可能已经发生，也可能尚未发生。未标记 `replay: "safe"` 的工具调用采用这种方式（工具调用与重放，原书第94页）

## 内置任务采用同样的结构



Harness 自身的任务也遵循副作用三明治结构，所以它们的恢复行为可以预测。`pi.tool` 任务在运行工具前一刻提交意图 `{ phase: "execute", arguments, replay }`。`replay` 来自工具，默认为 `"unsafe"`（`src/harness/tool.ts`）。在正常运行中，同一个阶段会继续执行工具并提交结果，因此 `execute` 阶段“只会在恢复时到达”。在该阶段，只有已存储策略和当前策略都声明安全时，它才会重新执行工具。否则，它会将调用提交为失败，错误为 `Tool NAME was interrupted and may have partially run`。



`pi.generation` 任务采用轮询。当提供商返回延迟句柄时，任务会提交一个 `poll` 检查点，包含该句柄和 `pollAt` 时间。循环中任何位置发生崩溃，重新打开时的检查点仍然指向该远程操作，中止处理函数也能用已存储的句柄取消它（`src/harness/generation.ts`）。



> **不回滚**
> 
> Pi Durable 绝不撤销外部副作用。提交失败只会回滚 Harness 自己的记录（提交失败时，原书第33页）。撤销扣款取决于远程系统：它的幂等键、取消端点和操作句柄（限制与非目标，原书第168页）。
> 
> 



> **这对你意味着什么：**
> 
> - 在意图阶段创建键。在副作用阶段内部创建的键会在每次重跑时改变，从而破坏去重。示例 12 从任务 ID 派生该键；商店采集记录在任何扣款发生之前，于 seq 4 提交 `"key": "charge-a"`
> 
> - 将结果与其后续变更一起提交。终态提交会原子地写入结果、追加结果条目、退役任务文档，并结算它所回答的提交请求（spec §5\.3）。分成两次提交会留下一个窗口：回执已经存在，但任务仍然存活
> 
> - 用memos保护同一阶段内的第二个副作用。商店订单的 `charge` 阶段只在memos `chargeId` 为空时调用服务（先 seq 5，再 seq 6）。调用与memos之间若发生崩溃，仍会重复调用，所以调用本身必须能够容忍重复
> 
> 

# 调度器

---

> Harness 中有一个部分决定接下来运行哪个任务；它绝不会仅仅因为缺少代码就结束任务。
> 
> 

**重启、升级和扩展缺失都会带来同一个问题：哪些任务现在可以运行，又该使用哪些代码？调度器负责回答。**本节结束后，你就能说明重启后的进程如何处理每个未完成任务，为什么任务可能永远停留在 `pending`，以及在任务运行期间重新加载扩展会发生什么。

## 启动任务



**调度器是 Harness 中负责启动任务的部分。每当发生变化，例如任务被提交、扩展被安装，或调用 ****`resume()`****，它都会寻找可以启动的任务。**当没有调用实例正在运行该任务、任务不处于 `completing`，并且没有等待某个存活任务时，它就可以启动。对于带中止标记的任务，“等待”指的是等待自己的子工作，因为清理从下往上进行（`src/harness/scheduler.ts`）。



**启动任务称为 reservation。在一次提交中，调度器按 ****`kind`**** 查找每个可启动任务的代码，将任务设为 ****`running`****，并创建其调用实例。等待中的任务直接进入 ****`running`****。**如果记录带有中止标记，调用实例会运行中止处理函数，而不是各个阶段（spec §5\.4）。



![image\.png](图片和附件/image.png)

> 调度器按 `kind` 查找任务代码；没有代码能够接手的任务保持 `pending`，只有中止会让它以 `orphaned` 结束。这是 spec §5\.4 中的表，由 `src/harness/scheduler.ts` 实现。迁移后的记录会与 `running` 状态一并提交。
> 
> 

## 被阻塞的任务



当没有已注册代码适合某个任务时，该任务就被阻塞。阻塞的任务并未失败。其记录保持不变，在空闲等待中仍计作未完成工作，调度器会在注册表每次变化时重新尝试。阻塞是“推导出的运行时状态，而不是持久化的任务状态”（spec §5\.4）。



|**原因**|**何时出现**|**如何解除阻塞**|
|---|---|---|
|`missing_task`|没有注册该名称的代码|注册相应代码|
|`task_too_old`|存储版本比代码版本新|注册该版本或更新版本的代码|
|`migration_failed`|代码较新，但缺少 `migrate`，或迁移抛出异常|注册不同的定义|

> 来源：spec §5\.4 和 `src/harness/scheduler.ts`。
> 
> 



恢复测试中，缺少定义的任务会一直保持 `pending`，直到 `addTask()` 注册定义，随后才完成（`test/harness-tasks-recovery.test.ts`）。使用 `harness.inspect()` 查找被阻塞的任务。它会为每个此类任务报告 `{ kind: "blocked", reason }`（任务图与 `inspect()`，原书第137页）。



迁移在任务被reservation时运行。一个回调 `migrate(input, checkpoint, fromVersion)` 负责升级所有旧版本记录。如果它抛出异常，错误会通过 `onReport` 报告一次；只有该 `kind` 注册了不同定义之后，调度器才会再次尝试。较新定义若没有 `migrate`，会以 `Task test.versioned version 2 has no migration from 1` 阻塞（`test/harness-tasks-recovery.test.ts`）。



“Harness 绝不会仅因注册表代码缺失或不兼容就将任务终结，无论是在打开时还是之后”（spec §5\.4）。只有中止会让被阻塞的任务以 `orphaned` 结束（中止、故障与孤立，原书第80页）。

## 崩溃之后：重新打开



在已有存储上打开 Harness 时，调度器会执行一次清理提交。所有遗留在 `running` 状态的任务，都会带着相同的检查点和memos回到 `pending`。此时还没有任何代码运行：打开过程“不会调度任何处理函数”（`src/harness/scheduler.ts`）。处理函数会在 `resume()` 之后启动，或在 `waitForTask()`、`submit()` 这类需要推进工作的调用之后启动（spec §2\.2）。打开过程还会安排第二次提交，应用崩溃留下的尚未处理完的中止标记和最终结果。



|**崩溃时状态**|**打开时写入什么**|**随后如何处理**|
|---|---|---|
|`pending`|无|在恢复后启动|
|`running`|`pending`；保留检查点、memos和标记|从检查点重新运行|
|`waiting`|无|`on` 中的任务结束后恢复|
|`completing`|无|下属工作结束后完成|
|`terminal`|无|永不再次运行|

> 来源：`src/harness/scheduler.ts` 和 spec §5\.1、§5\.5。
> 
> 



`SIGKILL` 之后以及打开之后的一个 `pi.tool` 任务；来源：`research/capture/crash-reopen-tasks.txt`

```JSON
// 被杀死进程留下的 SQLite 行
{ "id": 24, "kind": "pi.tool", "owner": 18, ...
    "state": { "status": "running",
        "checkpoint": { "phase": "execute", "arguments": { "target": "weekly" },
            "replay": "safe" } } }

// Harness.open() 之后、resume() 之前：只有状态发生了变化
    "state": { "status": "pending", "checkpoint": { ... unchanged ... } }

// 它的所有者，也就是生成任务 18，仍保持 "waiting"，且 "on": [24]
```

> 进程在工具执行中途被杀死。省略号（`…`）代表 `conversationId`、`version`、`input`、`background` 和 `abortRequested`，这些字段在打开时均不改变。
> 
> 

## 在任务运行期间重新加载代码



正在运行的调用实例会保留启动时使用的代码。在每个阶段边界，步骤检查会重新查看注册表。如果该 `kind` 现在注册了不同定义，并且新定义能够接手任务（相同版本，或带有 `migrate` 的更新版本），任务就会交接。步骤检查会将它设回 `pending`，保留检查点、memos和中止标记，下一次reservation便会使用新代码运行它（spec §5\.4）。交接测试记录了 `old:a start`、`old:a end`、`new:b start`，因此新旧代码绝不重叠执行（`test/harness-tasks-recovery.test.ts`）。如果新代码无法接手，旧代码会继续运行，并报告一次问题。“始终不结束的处理函数永远不会交接。”运行时重新加载（原书第118页）展示了这一机制的实际使用。

### 关闭



`close()` 会停止新工作，以 `closed` 错误拒绝尚未完成的 `waitForTask()` 和空闲等待，向每个调用实例发送信号，并等待它们返回。它不写入结果，也不设置标记，因此重新打开后所有工作都会恢复（spec §5\.1）。忽略信号的处理函数会让 `close()` 一直等待（spec §12）。

### 细节



调度器在内存中保留每条存活记录的副本，每次提交落地时都会更新。每轮检查都会在一次提交中reservation所有可启动任务。



如果存储拒绝reservation提交，内存中的reservation会被撤销，错误送往 `onReport`，下一轮再试。测试任务仍然恰好运行一次（`test/harness-tasks.test.ts`）。如果进程在该提交期间死亡，重新打开后的任务仍然是 `pending`，并且没有任何代码运行过（`test/harness-tasks-recovery.test.ts`）。



> **这对你意味着什么：**
> 
> - 崩溃之后，每个 `running` 任务都会从最后的检查点重启。编写每个阶段时，都要让它能够重复运行
> 
> - 永久停在 `pending` 的任务通常是被阻塞了。检查 `harness.inspect()`
> 
> - 检查点结构变化时，提高 `version`，并提供能接受所有旧版本的 `migrate`
> 
> - 让处理函数响应自己的 `signal`，使 `close()` 和交接能够快速完成
> 
> 

# 所有权与结构化并发

---

> 任务启动的工作归它所有：这些工作没有结束之前，任务就不能结束；中止任务也会中止这些工作。
> 
> 

一次结账会启动四笔银行卡支付。仍有支付在进行时，它不应该报告完成；如果客户取消，支付也应该被中止。所有权同时提供这两种保证。本节结束后，你就能创建子任务，用合适的策略等待它们，并预测任务何时会暂留在 `completing`。

## 一棵所有权树



**每个任务都有所有者，在创建时设置，此后永不改变。**通过 `tx.createTask(task, input, { ownership })` 的 `ownership` 传入它（spec §5\.5）：

- **`{ kind: "conversation" }`****：顶层任务，由所属对话拥有**

- **`{ kind: "task", taskId }`****：子任务，由另一个任务拥有，且始终位于该任务所在的对话中**



对话也可以有所有者。子智能体的对话由创建它的工具任务拥有（有所有者的对话，原书第43页）。任务和对话一起组成一棵树。分叉不参与这棵树。



![image\.png](图片和附件/image%205.png)

> 任务和对话组成一棵所有权树，后台任务会截断其下方的子树。图中并列展示了 README §Abort and Subagents 及示例 22 的前台子智能体，以及示例 23 的后台锚点。生成任务拥有自己的工具任务（README §Concepts）。
> 
> 



**创建子任务时，所有者必须仍然存活：不处于 ****`completing`****，不处于 ****`terminal`****，也没有中止标记。**检查使用的是提交结束后将留下的状态（`src/session/transaction.ts`）。因此，任务不能在使自己完成的同一次提交中创建子任务。商店采集记录的场景 D 正是这样尝试的。提交被拒绝，错误为 `Task owner 12 is completing`，阶段抛出异常，任务在 seq 27 发生故障。请在一次提交中创建子任务，再在之后的提交中完成自己。

## 前台与后台工作



任务拥有的工作，是树中它下方的所有内容：它的子任务、它所拥有对话中的任务，以及再往下的所有内容。规范将其称为普通的所属工作，遍历会在后台任务处停止。后台任务是以 `background: true` 创建、由对话拥有的任务。普通等待和中止会跳过它“以及它完整的所属子树”（spec §5\.4）。空闲等待采用相同规则：`Conversation.waitForIdle()` 会在该对话下方不再有存活的前台任务时返回。

## 等待任务



阶段通过返回 `{ status: "waiting", checkpoint, on, policy }` 来等待。此时任务没有调用实例。`on` 中的所有任务结束后，它从 `checkpoint` 恢复，并通过 `runtime.outcomes(ids)` 按顺序读取它们的结果。示例 24 的结账任务在同一次提交中创建四个支付任务并等待它们：



在一次提交中创建子任务并等待；来源：`test/examples/24-child-tasks.ts`

```TypeScript
pay: async (task, runtime, taskContext) => {
    await runtime.commit(async (tx) => {
        const payments: TaskId<PaymentResult>[] = [];
        for (const card of task.input.cards) {
            const ownership = { kind: "task", taskId: task.id } as const;
            payments.push(await tx.createTask(Payment, { card }, { ownership }));
        }
        return { status: "waiting", checkpoint: { phase: "decide", payments },
            on: payments, policy: "failFast" };
    }, taskContext);
},
```

> 为适应页面宽度，所有权字面量已被提取。`decide` 阶段读取 `runtime.outcomes(payments)`，只有每笔支付都 `completed` 时，才提交 `completed`。
> 
> 



提交等待时会检查 `on` 的规则，违反任意一条都会让任务出现故障（`src/harness/scheduler.ts`）：

- `on` 不能列出不存在的任务、任务自身，或其任意所有者，“因为它们不可能先于该任务结束”

- `failFast` 只能列出等待方拥有的任务。`allSettled` 可以列出任何任务，甚至已经结束的任务

- 空的 `on` 会在下一轮调度时恢复

- 中止处理函数完全不能进入等待状态

## `allSettled` 还是 `failFast`



策略决定某个任务失败时，其他任务会发生什么。使用 `allSettled` 时，什么也不会发生：无论结果如何，等待方都会在最后一个任务结束后恢复。使用 `failFast` 时，“`on` 中第一个暂存或以非 `completed` 结果结束的任务，会在调度器下一次协调提交中，为 `on` 中其他所有存活任务加上中止标记”（spec §5\.5）。等待方自身不会被中止。它会恢复，并决定自己的结果。



![image\.png](图片和附件/image%201.png)

> 一笔支付失败后，下次提交会中止其仍存活的兄弟任务；结账任务自身始终不会被标记为中止。这是示例 24 的第一个场景，逐提交记录在 `research/capture/extra-p5/checkout-transitions.txt` 中。每个条形代表一次提交后的状态，该状态持续到下一次提交改写它；终态记录永远不会重写（斜线填充）。`marked` 表示带有中止标记的 `running`。
> 
> 



从左向右阅读此图。在 seq 6，支付任务 9（`expired-2`）失败。在 seq 7，一次提交为支付任务 8、10、11 加上中止标记，其中止处理函数会退款。到 seq 10 时，三个任务都已 `aborted`。在 seq 11，结账任务从 `decide` 恢复，读到 `aborted`、`failed`、`aborted`、`aborted`，并在 seq 12 提交 `failed`。

## `completing`：所有者等待其工作



如果任务结束时，其拥有的工作仍在运行，它会被提交为 `{ status: "completing", outcome }`。结果已经固定，但任务尚未完成。一旦其下方不再有任何存活工作，调度器就会提交最终的 `terminal` 记录（spec §5\.5）。商店订单展示了完整过程：

|**SEQ**|**任务**|**状态**|**发生了什么**|
|---|---|---|---|
|13|7 order|running|检查点为 `finish`；在同一次提交中创建回执子任务 11|
|14|11 send\-receipt|running|已启动|
|15|7 order|completing|`finish` 提交 `completed`；子任务 11 仍存活|
|16|11 send\-receipt|terminal|`completed`，`"sent"`|
|17|7 order|terminal|调度器的最终提交；`waitForTask(7)` 完成|

> 场景 A，`research/capture/task-transitions.txt`。
> 
> 



暂存的结果遵循五条规则（spec §5\.5）：

1. 它是最终结果。阶段和中止处理函数都不会再运行，任务也绝不会重启或迁移

2. 中止一个 `completing` 任务，只会为它加上标记，从而中止下方工作。最终记录保留暂存结果

3. 非 `completed` 的暂存结果视为取消意图，因此先中止下方工作。这样的暂存失败，也会在自己的工作尚未全部结束时触发 `failFast`（`test/harness-structured.test.ts`）

4. 写入在暂存点处分开。结束提交中的条目和文档立即落地。终态、任务文档的退役，以及任务的等待方，都要等待最终提交

5. 等待方、空闲等待和 `inspect()` 都将 `completing` 任务视为仍然存活



> **容易出乎意料的暂留**
> 
> 扩展在子智能体对话中启动的前台工作，会让调用它的工具保持未完成，进而让整个运行保持未完成。在工具处于 `completing` 时继续向子智能体提问，会延长这一暂留。对于不应阻止所有者完成的工作，应将它创建为由对话拥有的后台工作（spec §12）。
> 
> 



> **这对你意味着什么：**
> 
> - 如果任务的结果依赖某项工作，就让该任务成为这项工作的所有者
> 
> - 对要求全部成功的子任务使用 `failFast`；希望拿到每个结果时使用 `allSettled`
> 
> - 在一次提交中创建子任务，再在后续提交中结束父任务
> 
> - 对不得阻止调用方完成的工作，使用由对话拥有的后台任务
>

# 中止、故障与孤立

---

> 中止是一个已提交的标记，会沿树向下传播；待下方所有工作都完成后，每个任务自己的处理函数再决定如何清理。
> 
> 

中止已经触及外部世界的工作，不只是让它停下来：已经扣款的银行卡需要退款。Pi Durable 让每个任务自己决定如何清理，并按安全顺序运行这些清理。本节结束后，你就能编写正确执行补偿的中止处理函数，读懂存储中的中止记录，并根据记录判断是否运行过任何清理。

## 中止如何工作



**使用 ****`harness.abortTask(id)`**** 中止任务。它不会当场停止任务，而是在记录上提交一个名为 ****`abortRequested`**** 的标志，称为中止标记。随后发生五个步骤**（spec §5\.4）：

1. 在任务上提交 `abortRequested`

2. 如果存在正在运行的调用实例，就向它发送信号，并等待它返回

3. 等待任务拥有的工作结束

4. 启动新的调用实例，运行中止处理函数

5. 中止处理函数提交最终结果



`abortTask()` 执行步骤 1 和 2，并返回 `"marked"`。对于已经结束的任务，它返回 `"terminal"`；对于未知 ID，则拒绝。它不会等待清理；请使用 `waitForTask()` 查看最终结果（spec §2\.2）。如果你取消自己的上下文，从而停止等待，标记已经提交，中止仍会继续（`test/harness-tasks.test.ts`）。



标记一经提交，正在运行的阶段就再也无法提交任何内容。所有 `runtime.commit()` 和memos写入都会以 `Task N has a durable abort mark` 拒绝，下一次步骤检查会结束本次运行（步骤规则 3，原书第67页）。中止处理函数稍后会在新调用实例中运行。它仍然能看到记录中的memos，并运行一次（`test/harness-tasks.test.ts`）。



中止处理函数必须决定结果，通常是 `aborted`。未提交结果就返回，会使任务以 `Abort handler of task N returned without a terminal outcome` 故障结束；抛出异常则会以异常消息故障结束。处理函数不能进入等待状态，也不能创建子任务，因为自己的任务已被标记（`src/harness/scheduler.ts`；spec §5\.5）。要执行补偿，可直接在处理函数内完成，或创建由对话拥有的后台任务，再用 `runtime.waitForTask()` 等待它们（spec §12）。

## 中止向下传播，清理向上执行



中止会传播给下方的工作。存活任务带有中止标记，或暂存一个非 `completed` 的 `completing` 结果时，都会向下传递。规范将这两种情况都称为取消意图，并说明它会“幂等地级联到所属的前台工作”（spec §5\.4）。调度器在另一次提交中写入子任务的标记，“并在打开时再次执行，因此即使中途崩溃，也不会丢失任何内容”。示例 24 中被中止的结账任务，通过八次提交执行完整协议，即 seq 17 到 24，如下图所示。



这一顺序有保证。只要所属工作仍存活，被标记任务的中止处理函数就不能启动，因此“中止处理函数看到的下方结果均为最终结果”。等待期间，`inspect()` 会将结账任务显示为 `{ kind: "waiting", on: [child] }`。三层测试中，每个处理函数都会记录：下一层已经是终态（`test/harness-structured.test.ts`）。



级联有以下限制（spec §5\.4）：

- 它会在本身没有取消意图的后台任务处停止

- 已完成的所有者绝不会继续传递中止。已完成子智能体的对话中新出现的工作，例如用户追加提问，“会正常运行”

- 等待方列在 `on` 中、但并不拥有的任务，既不会被标记，也不会被等待

    

级联触及的每个对话，都会按 `Conversation.abort()` 的方式处理：排队的输入变成未回答，原因为 `aborted`，排队的写入则保留（提交请求与收件箱，原书第84页）。被中止任务自己所在的对话会保留其队列。

## `orphaned`、`faulted`、`aborted`



|**结果**|**运行过哪些任务代码**|**它启动的副作用**|
|---|---|---|
|`aborted`|任务自己的中止处理函数|在处理函数能力范围内已完成补偿|
|`orphaned`|无：没有代码能够接手任务|“可能仍未清理”|
|`faulted`|抛出异常或未取得进展的阶段，或没有提交结果的中止处理函数|未知；未进行补偿|

> 来源：spec §5\.4。这里没有列出 `failed`，因为它与 `completed` 一样，是任务自己选择的结果。
> 
> 



- **`orphaned`****。被阻塞的任务无法运行中止处理函数，因为该代码缺失，或无法接手该任务。**因此，中止它会使其以 `orphaned` 结束，`reason` 为阻塞原因。恢复测试在 `resume()` 之前中止一个缺少定义的任务，读到 `{ status: "orphaned", reason: "missing_task" }`，此时任务的文档已经退役（`test/harness-tasks-recovery.test.ts`）。只有中止会让任务孤立。单纯缺少代码绝不会。

- **`faulted`****。故障来自任务缺陷、格式错误的提供商数据，或存储明确拒绝的提交（****`StorageRejected`****）。**不确定的存储失败则会停止 Session，不写入结果（提交失败时，原书第33页）。如果存储连故障结果本身也拒绝，任务会保持 `running`，并在下一次reservation时再次运行（`test/harness-tasks.test.ts`）。

## 中止期间的崩溃



唯一关键的是已经提交的中止标记，因此每个崩溃点都能据此恢复（`test/harness-tasks-recovery.test.ts`）：

|**崩溃时机**|**重新打开之后**|
|---|---|
|正在提交标记时|没有标记；恢复运行|
|标记之后、运行返回之前|带着标记进入 `pending`；只运行中止处理函数|
|中止处理函数运行期间|新的中止调用实例再次运行它|
|正在提交它的结果时|再次运行中止处理函数|
|最终结果之后|不运行任何内容；`abortTask()` 返回 `"terminal"`|

> 来源为任务崩溃恢复测试套件。中止处理函数可能运行不止一次，因此与任何副作用阶段一样，它必须可以安全重复（副作用三明治，原书第70页）。
> 
> 

## 细节：内置任务的清理



对于 Harness 自己写入的两种结果 `faulted` 和 `orphaned`，它会在使结果最终确定的提交中运行一个清理钩子（`src/harness/live.ts`；spec §5\.4）。只有三种任务使用它：

- `pi.generation`：如果它是当前运行的任务，已提交的部分响应会成为停止原因为 `aborted` 的 `pi.assistant` 条目；该运行的输入变为未回答，原因为 `faulted` 或阻塞原因；随后运行结束（运行控制，原书第88页）

- `pi.tool`：将工具调用标记为完成，但不写入结果条目。运行继续，构建模型上下文时再补上缺失结果（上下文，原书第40页）

- `pi.compaction`：清除压缩状态（压缩，原书第97页）



> **这对你意味着什么：**
> 
> - 编写可以安全运行两次的中止处理函数。崩溃可能让它们再次运行
> 
> - 始终从中止处理函数提交最终结果；没有结果就返回会让任务出现故障
> 
> - 直接执行补偿，或通过后台任务执行。中止处理函数不能创建子任务，也不能进入等待它们的状态
> 
> 

- 将 `orphaned` 和 `faulted` 视为“没有清理任何东西”。请自行核实外部世界的状态
