# 6\.运行

# 提交请求与收件箱

---

> 每条消息都会在发送的一刻提交；忙碌的对话会将其排队，而边界决定它何时进入对话记录。
> 
> 

用户在智能体仍在回答第一个问题时，又输入了第二条消息。它应该打断当前回答、等待，还是被拒绝？如果进程一秒钟后就崩溃了，这条消息会丢失吗？Pi Durable 用一条规则回答这些问题：**在对消息做任何其他处理之前，先提交它。提交是一次原子保存：其中的一切要么一起存储，要么完全不存储。**读完本节，你就能预测任意时刻发送的消息会发生什么，并选择忙碌的对话应该如何处理它。

## 两种提交请求



提交请求是你交给某个对话的内容的持久化记录，共有两种。input 是用户消息；它可能启动一次运行，也就是用于回答该消息的模型调用和工具调用。write 向对话记录添加一个条目，但不向模型提问，例如应用添加的一条备注。



`Conversation.submit()` 在一次提交中写入记录，并返回一个 `Submission` 句柄。这个句柄提供 `status()`、`wait()` 和 `abort()`。



`SubmissionDraft`，来源：`src/harness/types.ts`

```TypeScript
type SubmissionDraft = {requestId?: string} & (
    | { type: "input"; content: UserInput;
    whenBusy?: "steer" | "followUp" | "reject" }
    | { type: "write"; entry: EntryDraft }
);
```

> 此处为简化版本：源码将每个字段都标记为 `readonly`，还添加了 `never` 字段，确保两个分支彼此区分。
> 
> 

## 提交请求的去向



提交请求处于四种状态之一。等待时为 `queued`。input 的消息进入对话记录，并有运行正在回答它时，就变为 `placed`。当它有了对应条目，而且对于 input 来说还有了回答时，就变为 `done`。如果结束时仍没有回答，则为 `unanswered`，并由一个原因说明为什么。`wait()` 仅在 `done` 或 `unanswered` 时完成。



![image\.png](图片和附件/image%203.png)

> 提交请求处于排队、放入或最终结算状态；只有 input 才会处于 `placed` 状态。来源：`src/harness/submissions.ts`、`inbox.ts` 和 `live.ts`；原因取自规范 §6 和 §8\.3。玫红色箭头表示结束时没有回答。
> 
> 



它走哪条路径，取决于一个问题：对话忙碌吗？只要有一次运行正在进行，对话就是忙碌的（运行控制，原书第88页）。

|**提交时机**|**会发生什么**|
|---|---|
|空闲，且没有排队内容|input 被放入并启动一次运行；write 被追加并变为 `done`|
|忙碌，或已有其他条目排队|提交请求进入收件箱排队|
|忙碌，且指定 `whenBusy: "reject"`|不写入任何内容；`submit()` 抛出 `ConversationBusy`|
|`requestId` 已被使用|不写入任何内容；返回已有的提交请求|

> 来源：`src/harness/submissions.ts` 和规范 §6 的接纳规则表。唯一的例外是会撤销重置效果的 write；参见下文“细节”。
> 
> 



`requestId` 检查让重试变得安全。如果一次提交超时，或者进程重启，使用同一个 ID 再发送一次，就会得到同一个提交请求，而不是第二份副本。这个 ID 的作用域限于一个对话。

## 收件箱



排队的提交请求在 `pi.inbox` 中等待。这是一个小型内置文档，每个对话各有一个（内置文档，原书第60页）；分叉时会得到一个空收件箱。每个条目都有一个 mode，说明它可以在何时进入对话记录：

- `steer`：“当前工具调用一完成，就告诉智能体。”消息加入正在进行的运行

- `followUp`：“当前回答结束后再处理。”消息启动下一次运行。这是 `whenBusy` 的默认值

- `write`：排队的写入。它会在下一次机会进入对话记录，先于任何用户消息

## 边界：排队条目何时进入对话记录



边界是排队条目进入对话记录的那次提交。有两种边界。如果运行还要继续，一轮工具调用之后会执行 `postTools` 边界。运行成功结束时会执行 `final` 边界。

|**边界**|**WRITE**|**STEER**|**FOLLOW\-UP**|**它接收的用户消息**|
|---|---|---|---|---|
|`postTools`|全部|第一条|不接收|加入当前运行|
|`final`|全部|第一条|第一条|启动同一次新运行|

> 规范 §6；`src/harness/inbox.ts`。将 `steeringMode` 或 `followUpMode` 设为 `"all"`，便会接收该模式下的所有条目，而不仅是第一条（两者均默认为 `"one-at-a-time"`）。排队的重置会将 `postTools` 边界变为 `final` 边界（参见下文“细节”）。向仍有条目等待的空闲对话提交内容时，新提交会排在它们后面，并立即执行一次 `final` 边界（`src/harness/submissions.ts`）。
> 
> 



边界先放入 write，再放入用户消息；每类内部均按提交顺序处理。因此，在重置或压缩摘要之前排队的消息，会在它们之后进入对话记录，模型在新的上下文中读取它。



![image\.png](图片和附件/image%201.png)

> `postTools` 边界接收 write 和 steer；只有 `final` 边界接收 follow\-up。一个工具调用使第一次运行保持未完成状态，与此同时，后续消息、引导消息和一条备注进入队列；每条连线都将排队条目与它最终形成的条目连接起来。回答 21 与 `final` 边界在同一次提交中追加，并不是从收件箱取出的。ID、序列号和 `pi.live.run` 的值来自 `research/capture/inbox-steps.txt`。
> 
> 

## 撤回、失败与崩溃



`Submission.abort()` 会撤回仍在排队的提交请求。它以原因 `aborted` 结算为 `unanswered`，调用返回 `"aborted"`。一旦进入 `placed`，就来不及撤回了：调用返回 `"already_placed"`；如果已经结束，则返回 `"settled"`。`Conversation.abort()` 会撤回所有排队的 input，但保留排队的 write。



只有成功的运行才会执行 `final` 边界。失败或被中止的运行会将自己的 input 结算为 `unanswered`，并保持收件箱不变。



> **运行失败之后**
> 
> 排队的 follow\-up 会留在收件箱里，其 `wait()` 不会完成，直到另有内容被提交，或者你撤回它们。下一次提交会排在它们后面，因此较早的 follow\-up 先运行（`test/harness-inbox.test.ts`）。
> 
> 



崩溃不会改变这些规则：每条记录和每个收件箱条目都已提交。重新打开后，排队的 follow\-up 仍会在被打断的运行结束之后运行。丢失的只是内存中的等待者。使用 `harness.submission(id)` 获取一个新句柄，再等待它即可。

## 细节：移动头指针的写入



write 可以设置 head，从而移动模型上下文的起点（重置、交接与头指针，原书第46页）。如果 head 指向当前起点之前，就会重新引入被重置或摘要截去的历史。这种 write 已过时：无论它是在空闲时提交，还是到达了边界，都会以原因 `stale` 结算为 `unanswered`。重置（`head: "self"`）永远不会过时。如果 `postTools` 边界接收到重置，就会按 `final` 边界处理；当前运行的 input 以原因 `reset` 结算，因为它们在得到回答之前上下文就被截断了。压缩依赖的也是同一条规则（压缩，原书第97页）。



> **这对你意味着什么：**
> 
> - 凡是可能重试的提交，都传入 `requestId`
> 
> - 按消息选择 `whenBusy`：运行中希望智能体看到的纠正用 `steer`，下一个问题用 `followUp`，界面应该拒绝时用 `reject`
> 
> - 运行失败后，重新提交或撤回排队的 follow\-up；不要永远等下去
> 
> - 重启后，使用 `harness.submission(id)` 重新获取句柄
> 
> 

# 运行控制与实时文档

---

> 一个小文档就能表明对话是否忙碌，并展示正在形成的回答和工具输出；崩溃只会丢失上一次成功提交之后的进度。这段间隔可能超过配置的时间间隔。
> 
> 

**智能体工作时，有两个问题很重要：对话忙碌吗？屏幕此刻该展示什么，是写到一半的回答，还是工具不断滚动的输出？两个答案都在同一个文档 ****`pi.live`**** 中。和其他内容一样，它也会提交，因此，较晚连接的界面或重启后的进程看到的是同一幅状态图景。**读完本节，你就能读取 `pi.live`，判断对话是否忙碌、用户看到什么，以及崩溃会丢失什么。

## 结构



`pi.live` 是内置文档，每个对话各有一个。每个字段都是可选的；空闲对话的值为 `{}`。



`LiveState`，简化版本，来源：`src/harness/live.ts`

```TypeScript
type LiveState = {
    run?: { taskId: TaskId; inputs: SubmissionId[] }; // 忙碌时存在
    generation?: { // 正在进行的模型调用
        attempt: number;
        message?: AssistantMessage; // 目前为止的回答
        retry?: { at: number; error: string }; // 等待重试
        deferred?: { pollAt: number }; // 提供商稍后回答
    };
    tools?: ToolSlot[]; // 本轮工具调用
    compactions?: CompactionStatus[]; // 参见 6.5
};
```

> 存储的 message 是 `AssistantMessage` 的 JSON 形式。每个 `ToolSlot` 展示一次调用：它的 `callId`、name、值为 `pending`、`running` 或 `done` 的 status、目前为止的 output，以及完成后的结果 entry。
> 
> 

## 运行控制：忙碌标记



**run 就是锁。只要 run 存在，对话就忙碌；****`submit()`**** 不检查其他任何内容**（提交请求，原书第84页）。**inputs 列出本次运行将回答的提交请求。taskId 指定负责回答这些请求的 generation，也就是正在进行当前模型调用的任务**（生成，原书第91页）。



**一次运行是一串 generation，每个轮次一个。轮次之间会交接这把锁，绝不释放：旧 generation 在同一次提交中创建下一个 generation，并改写 taskId。此时进入的 steer 会追加到 inputs 中。运行结束时，一次提交会结算所有列出的 input，并删除 run、generation 和 tools。**



![image\.png](图片和附件/image.png)

> `pi.live` 在整个运行期间保存运行控制信息，而实时进度只在有工作执行时存在。示例包含一次输入、一次打印五行内容的 count 工具调用和一次回答；时间来自 `research/capture/extra-p6/live-run.txt`。（1）提交时设置 run；（2）模型请求工具，于是 generation 让位于 tools；（3）这一轮把 run 交给 generation 14；（4）回答完成后清除一切。
> 
> 

## 实时进度及其代价



generation 和 tools 的存在，是为了让界面展示正在形成的回答和工具输出。它们是普通的已提交状态，像其他文档一样发布（对话视图，原书第129页）。**每次更新都是一次提交，因此更新会受到节流限制。**`settings.progress` 有两个时间间隔，默认均为 100 ms：

- `partialIntervalMs`：流式回答多久提交一次。在采集记录中，第一个部分回答在请求开始后 103 ms 提交

- `outputIntervalMs`：工具输出多久提交一次。一段静默之后的第一行会立即提交；之后的写入至少间隔一个时间间隔，输出较大时还会更久



使用远程存储的宿主可以调大这两个间隔，让进度以更大的步幅显示。文档会保持小巧：只要没有工作正在执行，就会把它存储为完整快照，因此它的变更历史绝不会超过一次模型调用或一轮工具调用的范围（基值与增量，原书第56页）。

## 崩溃留下什么



崩溃会丢失尚未提交的回答文本或工具输出。自上一次成功提交以来的间隔可能超过配置的进度间隔。在崩溃采集记录中，进程在最后一次输出提交约 50 ms 后被终止，因此 deploy 槽位仍保存着它打印过的全部六行。



对话 1 在 `SIGKILL` 之后的 `pi.live`，来源：`research/capture/crash-reopen-tasks.txt`

```JSON
{
    "run": { "taskId": 15, "inputs": [14] },
    "tools": [
    {
    "callId": "deploy-1", "name": "deploy", "taskId": 22,
    "status": "running",
    "output": "deploy site: step 1/10 (pid 98319)\n ... step 6/10 (pid 98319)\n"
    }
    ]
}
```

> 输出的第 2–5 行已省略。对话仍然忙碌；在恢复流程确定发生了什么之前，没有任何内容回答 input 14。
> 
> 



恢复会将这些进度转化为对话记录，绝不会悄悄抹去它们。已经提交的部分回答会变为一个 aborted 助手条目，因此对话记录和界面保留了它已经开始说出的内容。之后的模型请求会排除这个被中止的回答。正在运行的工具，其已提交输出会成为 interrupted 结果的正文；如果进行安全重跑，则会先清除输出（工具调用与重放，原书第94页）。

## 细节：各字段何时设置和清除



|**字段**|**何时设置**|**何时清除**|
|---|---|---|
|`run`|运行开始|运行结束，无论经由哪条路径|
|`generation`|模型请求开始、等待重试或等待延迟回答|响应处理完毕，或运行结束|
|`tools`|模型请求工具|本轮结束，或运行结束|
|`compactions`|压缩开始|压缩结束|



规范 §8\.2；`src/harness/live.ts`、`generation.ts`、`tool.ts`、`compaction.ts`。如果调度器放弃某个运行任务（`faulted` 或 `orphaned`，参见中止、故障与孤儿任务，原书第80页），同一次提交会将其 input 结算为 `unanswered`，并清除相应字段。



> **这对你意味着什么：**
> 
> - 用 run 驱动忙碌指示，用 generation 和 tools 驱动流式视图
> 
> - 使用慢速或远程存储时，调大 `settings.progress` 的时间间隔
> 
> - 崩溃会丢失未提交的进度，而且没有固定的时间上界；已保存的运行则会保留下来
> 
> 

# 生成

---

> 每次模型调用都会在发送之前保存模型、选项和对话记录截止点。恢复时重建该上下文，并再次执行请求钩子。
> 
> 

调用模型是智能体中耗时、昂贵而且容易失败的一步。提供商可能返回 503，上下文可能过长，进程也可能在流式输出中途崩溃。Pi Durable 将每次模型调用作为一种名为 generation 的持久化任务运行。它会提交模型、选项和对话记录截止点。崩溃后，它根据这些记录重建请求，再次执行请求钩子。读完本节，你就能跟踪模型调用经历的各个阶段，读取其重试状态，并说明在每个阶段崩溃的代价。

## 一次生成，一个轮次



一次 generation 是一个 `pi.generation` 任务（阶段与步骤，原书第67页）。它执行一次模型调用，决定接下来做什么，并拥有本轮次的工具调用。一次运行是一串 generation，它们依次交接运行控制权（运行控制，原书第88页）。



![image\.png](图片和附件/image%204.png)

> 一次 generation 先准备，再调用模型，对响应分类，然后结束或循环。来源：`src/harness/generation.ts`。琥珀色方框是任务的阶段；request 和 poll 会调用提供商。白色方框表示任务如何结束。虚线方框表示任务正在等待它所拥有的压缩任务，之后以同一个 attempt 再次准备。工具轮次结束后，该任务完成，并由新的 generation 接管运行。图中未画出：可在任意阶段结束任务的中止，以及模型缺失的情形；后者会在 prepare、request 或 poll 中以 `no_model` 使任务失败。
> 
> 



|**阶段**|**做什么**|**检查点保存什么**|
|---|---|---|
|`prepare`|构建系统提示词与工具列表；检查压缩预算|尝试次数|
|`request`|调用模型并流式传输回答|模型、思考级别、流式选项和 cutoff|
|`retry`|等待退避时间结束|唤醒时间 `until`|
|`poll`|等待稍后回答的提供商|提供商的句柄和 `pollAt`|
|`tools`|等待本轮工具调用|助手条目和工具任务 ID|



对应 `src/harness/generation.ts` 中的 `GenerationCheckpoint` 联合类型。每个任务都从 `{ phase: "prepare", attempt: 1 }` 开始。

## 先准备，再发送



prepare 读取对话的智能体和设置（每个对话的智能体，原书第106页）。如果没有可用模型，运行以原因 `no_model` 失败。它渲染系统提示词（系统提示词，原书第115页），并检查是否需要先压缩上下文（压缩，原书第97页）。随后，一次提交将阶段转为 request，并固定模型、选项和对话记录截止点。cutoff 是请求中包含的最新对话记录条目。



恢复流程使用已保存的模型和选项，重建直到 cutoff 为止的已提交上下文。随后再次执行 `beforeRequest` 钩子：钩子对消息的替换不会被保存，重放时可能变化。智能体变更后的模型和选项会从下一次 prepare 开始生效，而每次重试都会经过 prepare。



request 构建消息，让 `beforeRequest` 钩子调整它们（钩子，原书第109页），然后流式接收响应。部分回答按照实时文档的节流规则提交（原书第88页）。每个请求都携带 sessionId：每个对话一个 ID，保存在内置的 `pi.provider` 文档中。提供商用它做提示词缓存。它会跨越重启、重试、重置和模型变更而保留；分叉则会获得一个新 ID。

## 响应决定什么



每个响应都会作为 `pi.assistant` 条目追加，并记录其费用（用量，原书第100页），失败响应也不例外。之后的请求会排除失败和中止的消息（从对话记录到上下文，原书第40页）。停止原因决定下一步。



|**模型返回什么**|**下一步**|
|---|---|
|工具调用（`toolUse`）|执行工具轮次（工具调用，原书第94页）|
|回答（`stop` 或 `length`）|回答 input；执行 final 边界|
|错误：上下文过长|压缩一次，然后再次 prepare|
|提供商可能恢复的错误|等待，然后重试|
|其他任何错误，或 `aborted`|input 以 `model_error` 结算为 `unanswered`；运行失败|
|`deferred`：“稍后再来”|在 `pollAfterMs` 之后轮询，默认为 5000 ms|

> `src/harness/generation.ts`。没有任何调用的 `toolUse` 响应视为回答。上下文过长的补救需要启用压缩，而且存在可截断的位置；缺少任一条件，或第二次溢出时，运行都会以 `model_error` 失败。
> 
> 



回答还可以继续延长。在结算 input 之前，`onYield` 钩子可以返回 `{ continue }`，附带更多用户内容。运行随后带着这条消息继续，input 保持未结算状态。只有同一个边界没有排队的用户消息或重置进入时，这才适用。

## 重试与延迟回答



重试策略是 `settings.retry`。默认在第一次尝试之后允许重试 3 次，从 2000 ms 开始，每次翻倍，上限为 60 000 ms。pi\-ai 决定哪些错误可重试。上下文过长从不按这种方式重试；只有压缩才能让它容得下。



一次 503、50 ms 的退避，然后得到回答，来源：`research/capture/extra-p6/retry.txt`

```Plain Text
seq 4 task 9 {"phase": "request", "attempt": 1, "cutoff": 7, ...}
seq 6 entry 10 pi.assistant, stopReason "error"
task 9 {"phase": "retry", "attempt": 1, "until": 1791211854633}
pi.live generation.retry = {"at": ..., "error": "503 service unavailable"}
seq 7 task 9 {"phase": "prepare", "attempt": 2}
seq 8 task 9 {"phase": "request", "attempt": 2, "cutoff": 10, ...}
seq 9 entry 11 pi.assistant; submission 8 done; task 9 completed
```

> 使用 `settings.retry.baseDelayMs = 50` 运行；部分提交已省略。第二次请求的 cutoff 包含错误条目，但构建上下文时会将其排除。
> 
> 



这两种等待都能跨重启保留。retry 会休眠到已提交的 until 时间，因此重新打开的进程只需完成剩余退避，而不必从头开始。poll 服务于稍后回答的提供商：它休眠到 pollAt，再次询问，并像处理流式结果一样处理返回结果。在 poll 期间中止，还会要求提供商取消该请求。

## 各阶段崩溃的代价



|**崩溃发生于**|**哪些工作会再次执行**|
|---|---|
|`prepare`|基于同一份对话记录重新准备|
|`request`，尚未流式接收任何内容|使用已保存的上下文、模型和选项；请求钩子再次执行|
|`request`，部分回答已提交|部分回答成为 aborted 条目；重建已保存的上下文，并再次执行请求钩子|
|`retry` 或 `poll`|剩余的等待|
|`tools`|本轮的收尾（工具轮次，原书第94页）|

> `test/harness-generation-recovery.test.ts` 和 `test/harness-tools-recovery.test.ts`。如果重启后固定的模型已经不存在，运行以 `no_model` 失败。
> 
> 



被打断的请求可能需要付费两次：提供商可能在崩溃之前已经完成工作，而重发又让它做了一遍。已提交的部分回答携带自己的 usage，因此账本会计入崩溃之前已流式传输的内容。



> **这对你意味着什么：**
> 
> - 重发保留已保存的模型和选项，但会再次执行请求钩子。如果需要完全相同的消息，应让钩子输出保持稳定
> 
> - 调整 `settings.retry`；`maxRetries` 统计的是第一次尝试之后的重试次数
> 
> - 为请求中途崩溃时偶尔出现的重复收费预留预算
> 
> 

# 工具调用与重放

---

> 每次工具调用都会先提交意图，再执行；崩溃后，只有声明可安全重复的工具才会再次运行，其余工具都会被报告为已中断。
> 
> 

智能体调用了 deploy 工具，进程却在中途被终止。重启时应该再部署一次吗？运行两次可能造成灾难；悄悄遗忘也同样糟糕。Pi Durable 从不猜测。它会提交“调用即将运行”这一事实；崩溃后，仅重新运行你声明可安全重复的工具。其他所有调用都会向模型报告为已中断。读完本节，你就能决定某个工具是否应该设置 `replay: "safe"`，并预测崩溃后模型会看到什么。

## 每次调用一个任务



模型发起的每次工具调用都会成为独立的 `pi.tool` 任务，由接收到该调用的 generation 拥有。这个任务有两个阶段。



`ToolTaskCheckpoint`，来源：`src/harness/tool.ts`

```TypeScript
type ToolTaskCheckpoint =
| { phase: "call" }
// 在 execute() 之前立即提交：最终参数和重放策略
| { phase: "execute"; arguments: JsonObject; replay: "safe" | "unsafe" };
```



一次调用经过以下步骤：

1. 按名称查找工具，并根据其 schema 检查参数

2. 运行 `beforeTool` 钩子；它们可能阻止调用，或更改参数（钩子，原书第109页）

3. 提交意图：阶段为 execute，附带最终参数和工具的重放策略；除非工具另有声明，否则为 `"unsafe"`

4. 运行 `execute()`，然后运行 `afterTool` 钩子

5. 提交结果：一个 `pi.tool-result` 条目，任务结束

    

这就是第 5 章的“副作用三明治”（原书第70页）：意图、副作用、结果。在第 3 步之前失败的调用绝不会触及外部世界，因此会立即得到一个错误结果。无论发生什么，运行都会带着一个结果条目继续：模型看到错误，并决定接下来做什么。

## 崩溃后的重放



重启后，如果发现工具任务处于 execute，它只知道一件事：副作用可能已经开始发生。规则很简单。只有存储的策略和工具当前的策略都为 safe，工具才会再次运行。否则，任务会用工具此前已经报告的输出构建一个 interrupted 错误结果并提交，不再运行工具。



采集记录在两个对话中运行两个慢工具，在两者都在打印内容时终止进程，然后在新进程中恢复。deploy 没有设置 replay，因此是不安全的；`fetch_report` 声明了 `replay: "safe"`。

## 选择策略



`replay: "safe"` 是一种承诺：执行两次该副作用不会造成危害，例如读取、幂等写入，或者带有远端认可的幂等键的写入（副作用三明治，原书第70页）。其他情况都应保持 unsafe，并诚实地告诉模型“可能已经部分执行”。三个细节让这条规则比表面上更严格：

- 两份策略都要满足：工具若改成 unsafe，就不会重跑；存储为 unsafe 的调用，即使工具后来改成 safe，也不会重跑

- 工具缺失：对话已无法使用的工具按 unsafe 处理

- 新的环境：重跑时会根据对话当前的工作目录重新构建环境，而目录可能已经改变（执行环境，原书第155页）

    

第 3 步之前崩溃的代价较小。任务仍处于 call，因此整个调用会从头运行一次，包括 `beforeTool`。

## 工具轮次



一个工具轮次就是一次模型响应中的所有调用。默认情况下它们并行运行；一个调用失败，绝不会取消其他调用。如果设置中的 toolExecution 为 `"sequential"`，或者任意被调用工具声明了 `executionMode: "sequential"`，本轮就会逐个执行调用。每个调用都结束后，generation 提交一次。工具结果可以影响这次提交（定义工具，原书第112页）：

- `terminate`：结束运行，不再调用模型，但前提是本轮每次调用都提出这一要求

- `handoff`：将上下文重置为交接文本，并结束运行（重置与交接，原书第46页）

- `addTools`：从下一轮次开始提供更多工具

    

否则，就会执行一次 postTools 边界，由新的 generation 接管运行。如果运行在本轮中途中止，尚未开始的调用会得到 aborted 结果。

## 细节：Harness 写入的错误结果



|**诊断代码**|**何时出现**|**任务的结束状态**|
|---|---|---|
|`tool_unavailable`|工具未提供给模型，或已不存在|`completed`|
|`invalid_arguments`|在 beforeTool 之前或之后，参数不符合 schema|`completed`|
|`blocked`|beforeTool 钩子阻止调用或抛出异常|`completed`|
|`tool_error`|execute\(\) 抛出异常，或无法构建其环境|`failed`|
|`interrupted`|调用中途崩溃，且没有安全策略|`failed`|
|`aborted`|调用被中止|`aborted`|

> `src/harness/tool.ts` 和 `generation.ts`。每个结果都带有 `isError: true`；最后三种会保留此前已经报告的输出。以 failed 或 aborted 结束的任务，也会中止该调用拥有的所有对话（所有权，原书第76页）。
> 
> 



> **这对你意味着什么：**
> 
> - 只有运行两次不会造成危害时，才将工具标记为 `replay: "safe"`
> 
> - 边执行边用 output 报告进度：调用被中断时，这就是模型看到的内容
> 
> - 如果 beforeTool 钩子在崩溃后必须作出相同决定，应把决定存入 memo（备忘，原书第67页）
> 
>

# 压缩

---

> 压缩用一段摘要替换模型所见内容中最旧的部分；不会删除任何内容，而截断位置推进得最远的摘要胜出。
> 
> 

长对话会超出模型的上下文窗口。压缩要求模型总结最旧的部分，然后用摘要代替这部分内容发送。完整历史仍保留在存储中；缩短的只是模型看到的内容。读完本节，你就能设置 token 预算，判断哪些压缩会让运行等待，并预测两个相互竞争的摘要哪一个会胜出。

## 压缩会写入什么



一次压缩是一个 `pi.compaction` 任务。它选择上下文的一段前缀，请模型对其总结，并添加一个摘要条目。条目的 head 指向第一个逐字保留的条目，因此模型的上下文现在从摘要开始，再从那里继续（头指针，原书第46页）。在这份采集记录中，三个问题回答完毕后执行了 `compact()`，而此时第四个回答正在写入。



摘要条目 25，来源：`research/capture/extra-p6/compaction.txt`

```JSON
{
    "kind": "pi.compaction", "id": 25, "head": 14,
    "model": [
    {
    "role": "user",
    "content": [
    { "type": "text", "text": "The conversation history before this point was compacted into the following summary:\n\n<summary>\n## Goal\nPlan a week in Lisbon.\n</summary>" }],
    ...
    }],
    "data": { "reason": "manual" },
    "byTaskId": 21
}
```

> 摘要文本在原书中折行为三行；timestamp 和 conversationId 已省略。对话当时忙碌，因此摘要以 write 提交请求 `compaction:22` 的形式在收件箱中等待，由正在运行的 generation，即任务 21，将它放入对话记录。
> 
> 

## 三种启动方式



|**由谁启动**|**reason**|**运行会等待吗**|**摘要如何进入对话记录**|
|---|---|---|---|
|你调用 `Conversation.compact()`|`manual`|否|作为 write 提交请求|
|generation，达到后台预算|`threshold`|否|作为 write 提交请求|
|generation，达到阻塞预算|`threshold`|是|直接追加|
|generation，上下文过长|`overflow`|是|直接追加|

> 规范 §8\.7；`src/harness/compaction.ts`。
> 
> 



最后一列是一条安全规则。运行中的 generation 不能在执行期间被改变其对话记录。阻塞压缩可以直接追加，因为等待它的正是它所属的 generation。其他摘要都像普通 write 一样提交，在下一个边界进入对话记录；如果对话空闲，则立即进入（提交请求，原书第84页）。非阻塞压缩绝不会让对话变为忙碌；执行期间，它显示在 `pi.live.compactions` 中。

## generation 何时压缩



在 prepare 中，generation 估算即将发送的请求大小，并与 `settings.compaction` 中的两个预算比较。



![image\.png](图片和附件/image%206.png)

> 两个预算决定 generation 何时压缩；`keepRecentTokens` 决定截断位置。数字来自示例 25，使用一个上下文窗口为 3000 token 的测试模型。默认值为 reserveTokens 16384、backgroundTokens 32768、keepRecentTokens 20000。下方一行是示意图：从后向前计数时落在工具结果中，所以截断点移到下一条消息，最终保留不到 400 token。
> 
> 



- 阻塞：超过 `contextWindow − reserveTokens` 时，generation 启动压缩并等待结束，然后再次 prepare；无论压缩结果如何，都会发送请求

- 后台：超过上述界线再减去 backgroundTokens 的阈值时，generation 在后台启动压缩，不等待就发送请求。`backgroundTokens: 0` 会关闭此行为

    

截断位置通过从最新条目向前计数来选择，直到保留 keepRecentTokens 为止。随后，它会落在下一条用户或助手消息上，绝不会落在工具结果上，因此保留的助手消息也会保留其工具结果。如果整个上下文小于 keepRecentTokens，就不做任何压缩。



过长的上下文有一次补救机会。如果提供商因请求过长而拒绝，generation 会压缩，并再次准备同一次 attempt。一个 generation 最多压缩一次，因此第二次溢出会以 `model_error` 使运行失败。运行记录 25 展示了这一点：它的最后一个轮次先因达到阻塞预算而压缩，然后遇到溢出并失败。

## 摘要相互竞争时



压缩之间从不协调；多个压缩可以同时执行。决定胜者的只有收件箱的过时头指针规则（原书第84页）。如果摘要的截断点比当前上下文起点更早，它会结算为 stale。如果截断点位于当前起点或其后，就会被放入，无论何时启动。



![image\.png](图片和附件/image%205.png)

> 压缩之间从不协调；截断点早于当前上下文起点的摘要会过时。这是规范 §6 的详细示例。阴影线标出各摘要替换的部分；虚线表示 A 进入对话记录后的上下文起点。

## 细节



- 摘要请求：没有工具，使用将工具结果截短到 2000 个字符的对话记录，以及你传给 `compact()` 的任何额外指令。只有正常停止且带有文本的结果才算摘要。可重试错误按 settings 中的 retry 策略重试。`beforeCompact` 钩子可以拒绝压缩，也可以提供自己的摘要（钩子，原书第109页）

- 中止：`Conversation.abort()`（Esc 键）会中止手动压缩。后台压缩会继续，除非传入 `{ background: true }` 或调用 `abortTask()`。阻塞压缩会随它所属的 generation 一起停止

- 压缩期间编辑：压缩执行期间放入的应用编辑或 head，可能在摘要进入对话记录时丢失或被撤销，见规范 §12



> **这对你意味着什么：**
> 
> - 默认值适用于大窗口。对于小窗口，应让 keepRecentTokens 远低于阻塞界线，否则还没压缩任何内容，上下文就可能溢出
> 
> - 随时都可以调用 `compact()`；它绝不会阻塞运行
> 
> - 应在压缩之前放入应用编辑，不要在压缩期间进行
> 
> - 每次摘要尝试都要付费，即使最终变为 stale 也不例外
> 
>

# 用量与费用

---

> 费用与产生它的响应在同一次提交中记录，因此账本与对话记录绝不会不一致。
> 
> 

这段对话到目前为止花了多少钱？`pi.usage` 会给出答案。账本与每次模型响应在同一次提交中更新，因此即使崩溃后，它也与对话记录完全吻合。读完本节，你就能读取账本，说明它统计了哪些尝试，并在不重复计费的情况下汇总多个对话的费用。

## 账本



`pi.usage` 是内置文档，每个对话一个，包含两个映射。models 以 `"provider/model"` 为键。tools 以工具名为键，用于那些自行支付模型调用费用的工具。每个值都是一条 pi\-ai 的 `Usage` 记录，与每条助手消息携带的结构相同。分叉从零开始计数。



一次工具调用和一次回答之后的 `pi.usage`，来源：`research/capture/extra-p6/live-run.txt`

```JSON
{
    "models": {
    "faux/faux-1": {
    "input": 74, "output": 15, "cacheRead": 54, "cacheWrite": 75, "totalTokens": 218,
    "cost": { "input": 0, "output": 0, "cacheRead": 0, "cacheWrite": 0, "total": 0 }
    }
    },
    "tools": {}
}
```



这是两次响应的总和：发起工具调用的响应（118 token）和最终回答。测试提供商报告的费用为零：

- token 计数：input、output、cacheRead、cacheWrite 和 totalTokens，始终存在

- 可选计数：提供商报告时，会有 cacheWrite1h（保留一小时的缓存写入）和 reasoning（用于思考的输出）

- cost：相同的分类，再加 total，由 pi\-ai 按模型定价

    

账本是持续累加的总和。每轮次费用仍保留在对话记录中：每个助手条目都携带自己的 usage。

## 哪些内容会计入



用量在追加响应的那次提交中记录，绝不延后。



|**费用来源**|**记入**|
|---|---|
|每次模型响应：回答、工具调用、失败尝试|`models`|
|崩溃或中止之前已提交的部分回答|`models`|
|每次摘要尝试，即使失败或最终过时|`models`|
|报告 usage 的工具结果|`tools[name]`|

> 规范 §8\.6；`src/harness/usage.ts`，由 `generation.ts`、`tool.ts` 和 `compaction.ts` 调用。
> 
> 



失败和中止的尝试也会计入，因为提供商已为它们收费。如果某次尝试在任何内容提交之前就被打断，它没有响应，因此不会计入任何费用；重发请求会在得到回答时计入。

## 跨对话汇总



每个对话只统计自己的费用。`harness.usage()` 将每个对话的账本累加成一个总额；这个总额不会存储在任何地方。对于其他汇总方式，例如一棵子智能体树，需要你自行遍历 `scanConversations()`，对账本求和。
