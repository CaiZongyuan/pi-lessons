# 7\.扩展与智能体

# 扩展与注册表

---

> 你的代码存在于进程内的注册表中；存储中只记录对话需要的扩展名称。
> 
> 

智能体需要工具、系统提示词和一些防护措施。你还希望不用停止智能体就能发布针对其中某项的修复，并在崩溃后重启而不丢失任何内容。**Pi Durable 通过将全部代码保留在内存中、只存储名称，同时做到这两点。**读完本节，你就能将代码打包为扩展，安装和替换它，并说明重启需要什么。

## 扩展包



扩展是一个有名称的代码包。它是普通对象，带有 name 和最多五个列表。`defineExtension()` 只为对象提供类型，不做任何检查，见 `src/harness/define.ts`。每个列表都通过字符串名称与系统的其余部分匹配，绝不依赖对象身份。



注册表是扩展与 Harness 对接的地方。`createRegistry()` 返回一个由你的应用拥有的对象。它已经包含三个内置任务定义：`pi.generation`、`pi.tool` 和 `pi.compaction`，这三者不能移除或替换。`Harness.open()` 会拒绝缺少它们的注册表，因此应始终从 `createRegistry()` 开始，见 `src/harness/registry.ts` 和 `src/harness/harness.ts`。



三个扩展，一个注册表，来源：README §Extensions · 规范 §7\.1

```JavaScript
import { createRegistry, defineExtension, hook, section, ToolTask }
    from "@earendil-works/pi-durable";
import { CodingTools } from "@earendil-works/pi-durable/tools";

const Coding = defineExtension({
    name: "coding",
    sections: [
    section("preamble", () => "You are a concise coding assistant.", { tag: false }),
    section("cwd", (input) => input.env?.cwd),
    ],
});

const Permissions = defineExtension({
    name: "permissions",
    hooks: [hook(ToolTask, {
    beforeTool: (call) => (isDangerous(call) ? { block: "Needs approval" } : undefined),
    })],
});

const registry = createRegistry();
registry.install(CodingTools); // "coding-tools"：read、write、edit、bash
registry.install(Coding);
registry.install(Permissions);
```



安装顺序很重要。默认情况下，每个对话都按安装顺序使用全部已安装扩展，因此 coding\-tools 的工具排在 coding 添加的任何内容之前。

|**字段**|**包含什么**|**按什么匹配**|**章节**|
|---|---|---|---|
|`tools`|模型可调用的工具|工具名|7\.4（原书第112页）|
|`sections`|系统提示词的组成区段|区段键|7\.5（原书第115页）|
|`hooks`|内置任务调用的处理函数|任务名|7\.3（原书第109页）|
|`wraps`|针对另一个扩展的工具或区段的装饰器|工具名或区段键|7\.2（原书第106页）|
|`tasks`|你自己的持久化任务定义|任务名|5\.4（原书第73页）|



`Extension` 接口，见 `src/harness/types.ts`。

## 名称在存储中，代码在内存中



注册表中的内容一律不会写入磁盘。用规范的话说，注册表“是进程本地的，生命周期可以长于 Harness，而且不会持久化”，见规范 §7\.1。对话在其 `pi.agent` 文档中，用一个名称列表记录它需要哪些扩展（每个对话的智能体，原书第106页）。每当 Harness 需要代码时，就到注册表中查找这些名称。



![image\.png](图片和附件/image%204.png)

> 代码位于进程注册表中；对话只存储名称。对话 1 没有存储选择配置，使用宿主默认值。对话 7 指定了三个扩展；skills 没有安装在这个进程中，因此被跳过，但存储的列表保持不变。前三个扩展来自上面的代码示例；reviewer 和 skills 扩展来自规范 §7\.1。
> 
> 



这种分离让重启的代价很低。在一轮已回答对话的数据库采集记录中，根对话的智能体仅存储为 `{"model": {"provider": "faux", "modelId": "faux-1"}}`，除此之外没有别的内容：没有工具代码，也没有提示词代码，见 `research/capture/sqlite-rows.txt`，文档 6。新进程安装自己的扩展，打开同一个存储，而每个已存储名称都会绑定到当前使用这个名称的代码。如果某个名称没有对应的已安装扩展，就跳过它，不算错误；“再次安装后，它会重新生效”，见规范 §2\.2。



任务定义也按同样方式工作。存储的任务以名称记录其 kind。如果没有任何已安装扩展定义这个名称，任务就会阻塞：它会等待，而不会失败。之后安装扩展就能解除阻塞（调度器，原书第73页）。不过，仍应在 `open()` 之前安装全部扩展，让恢复的工作立即继续。

## 安装、替换、卸载



注册表有两个操作。`install(extension)` 把新名称添加到末尾；如果已有同名扩展，则在原位置替换它。`uninstall(extension)` 移除当前占用该名称的扩展。每次变更立即生效，而且“扩展是重新加载的单位”，见规范 §7\.1。



![image\.png](图片和附件/image%206.png)

> 同名安装会原位替换；卸载后再安装，会将扩展移到末尾。操作与订阅者日志 `["a", "a,b", "a,b", "b", "b,a"]` 来自 `test/harness-registry.test.ts` 中的一个用例。最后一行是同一文件中的另一个用例：声明了两次 read 的扩展会被拒绝。卸载不存在的名称和被拒绝的安装都不会发布任何内容。
> 
> 



位置就是优先级。当两个扩展定义同名工具时，后面的扩展胜出；后面的钩子也会后执行（钩子，原书第109页）。由于替换会保留位置，重新加载扩展绝不会改变谁胜出。



如果一次安装会让注册表无效，它就会抛出异常，并且不改变任何内容。工具名和区段键在一个扩展内必须唯一；跨扩展重复使用工具名，则是一个扩展覆盖另一个扩展的方式。区段键使用小写（`^[a-z][a-z0-9 -]*$`），而且不能使用保留名称 instructions。任务名在整个注册表中必须唯一。已经运行的工作不会在执行途中看到注册表变化（运行期间重新加载，原书第118页）。



> **这对你意味着什么：**
> 
> - 在 `Harness.open()` 之前，按你想要的优先顺序安装所有扩展
> 
> - 不要重命名对话已经在使用的扩展、工具或任务：存储的名称将不再匹配
> 
> - 发布修复时，用相同名称安装新对象。install 和 uninstall 都不会调用清理代码，因此你需要自行释放共享资源，而且只能在旧调用结束之后释放，见规范 §12
> 
> 

# 每个对话的智能体

---

> 每个对话都把自己的选择存储为名称；Harness 每次需要它们时，再将这些名称转换为实际工具和提示词区段。
> 
> 

不同对话需要不同配置：主聊天得到全部工具，只读审查者得到两个工具，子智能体有自己的指令。对话的 agent 就是这套配置：模型、思考级别、扩展、工具、提示词区段、指令和工作目录。读完本节，你就能配置一个智能体，并准确预测模型会获得哪些工具。

## 存储的选择与解析后的智能体



智能体以两种形式存在。存储形式 `AgentState` 位于对话的 `pi.agent` 文档中，只保存名称。从未设置过的字段遵循宿主默认值。解析形式 `Agent` 则是 Harness 每次需要真实对象时，根据存储的名称、当前注册表和宿主设置构建的结果。存储的文档会随对话一起分叉和回退（内置文档，原书第60页）。



|**字段**|**存储形式**|**未设置时**|
|---|---|---|
|`model`|`{ provider, modelId }`|没有模型；请求以 `no_model` 失败|
|`thinkingLevel`|一个 pi\-ai 级别|`"off"`|
|`extensions`|名称列表，或 `{ add?, remove? }`|宿主默认值：全部已安装扩展|
|`tools`|名称列表，或 `{ remove }`|所选扩展的全部工具|
|`instructions`|字符串|无；设置后渲染为最后一个提示词区段|
|`cwd`|路径|无；传给宿主的环境工厂（9\.5，原书第155页）|

> `AgentState` 及其默认值，见 `src/harness/types.ts` 和 `src/harness/agent.ts` 中的 `resolveAgent()`。
> 
> 



`Conversation.configure(change, context)` 编辑存储的智能体。每个字段都遵循一条规则：“给定字段替换已存储值，null 清除它，undefined 不作更改”，见 `src/harness/agent.ts`。你可以传入扩展对象和工具对象；它们会以名称存储。独立函数 `configure(tx, id, change)` 在更大的提交中执行同样操作；提交是一次原子保存，其中的一切要么一起存储，要么完全不存储。示例 7 展示了每次调用会存储什么。



配置后再读回，来源：示例 07 · `research/runs/07-configuration.txt`

```TypeScript
// 默认工具：['read', 'write', 'grep']

await root.configure({
    model: { provider: "anthropic", modelId: "claude-sonnet-4-5" },
    thinkingLevel: "high",
    tools: [write, read], // 传入对象，存储名称
}, context);
// 存储结果：{ model: {...}, thinkingLevel: 'high', tools: ['write', 'read'] }

await root.configure({ extensions: { remove: [Search] }, tools: null }, context);
// 去掉 search 后：['read', 'write']

await root.configure({ extensions: [Files, Search] }, context);
registry.uninstall(Files); // files 卸载后：['grep']
registry.install(Files); // files 重新安装后：['read', 'write', 'grep']
```



由于字段会整体替换，`{ remove }` 列表不会累加。先移除 edit，再移除 bash，最终只会移除 bash：“edit 会再次提供给模型”，见规范 §2\.2。界面的开关必须读取当前列表，再写入新列表。配置不会向对话记录追加任何内容；下一个模型请求会采用这项更改。

## 从名称到工具



解析将存储的名称转换为请求使用的工具和区段。每次都执行相同的四步，不写入任何内容：

1. 选择扩展。若存储的是列表，就严格按列表顺序选择其中的名称。否则，从宿主默认值开始（按安装顺序排列的所有已安装扩展），再应用 add 和 remove。未安装的名称会被跳过

2. 按扩展顺序收集工具。后面出现的同名工具会原位替换前面的工具

3. 将包装器应用于当前占用目标名称的工具或区段

4. 过滤工具。若存储的是列表，就严格按列表顺序只保留这些名称；`{ remove }` 则删除指定名称。区段以同样的方式收集，instructions 放在最后



![image\.png](图片和附件/image%209.png)

> 解析先按扩展顺序收集工具，原位替换同名项，包装胜出的工具，最后过滤。扩展、描述和过滤器来自 `test/harness-registry.test.ts`。最后一行展示存储的过滤器从上一行保留了哪些内容。
> 
> 



两种失败会被刻意安静处理。若包装器抛出异常或重命名目标，本次解析就移除该工具，并向 `HarnessOptions.onReport` 报告；调用它时会得到 `tool_unavailable` 结果。如果包装器的目标没有被选中，它就什么也不做，因此没有 bash 时也可以安全使用计时包装器，见规范 §7\.1。

## 更改何时生效



Harness 在每次决策时重新解析智能体，而不是每次运行只解析一次：“每个读取方在每次决策时解析一次”，见规范 §7\.1。宿主设置也一样。`HarnessOptions.settings` 保存 Harness 级别的策略，包括默认选择、重试、压缩、工具执行模式和队列模式。它从不被复制或存储，因此一个带 getter 的 settings 对象“无需向 Session 写入，就能跟随用户偏好”，见规范 §2\.2。默认值参见“设置与默认值”（原书第180页）。



|**谁读取**|**读取什么**|**何时读取**|
|---|---|---|
|模型请求|模型、工具、提示词、流式选项|准备该请求时读取一次|
|工具调用|被调用工具的代码|调用开始时，以及恢复时再次读取|
|任意任务阶段|钩子|每个阶段一次，从该阶段的注册表快照读取|
|工具轮次|并行或顺序执行|每轮一次|
|输入边界|引导与后续消息的队列模式|每个边界|
|工具与提示词区段|当前 cwd 的环境|每次使用时|

> 精简自规范 §7\.1 的“谁解析什么，以及何时解析”。
> 
> 



因此，在一个轮次中途作出的更改，会在下一个模型请求中生效。模型已经发起的调用，会在实际执行时解析其工具。如果期间移除了该工具，调用会得到 `tool_unavailable`；如果修改了 cwd，调用会看到新目录，见 README §Per\-Conversation Agent。

## 创建时的副本



新对话一开始，要么拥有某个智能体的副本，要么什么都没有，见 `src/harness/agent.ts` 中的 `createAgent()`：

- 分叉：父对话在分叉点时的智能体（分叉，原书第43页）

- 任务拥有的对话：复制拥有它的任务所属对话的每个已存储字段，包括 instructions。之后拥有者的更改不会传递给它

- 无拥有者的对话：空对象 `{}`；每个字段都遵循宿主设置

    

随后，`root()`、`createConversation()` 和 `fork()` 的 agent 选项会在同一次提交中应用其更改。



> **复制的列表**
> 
> `{ add, remove }`“始终编辑宿主的默认选择”，绝不编辑复制的列表。某个子对话复制了列表 `["a", "b"]`，随后接收到 `{ remove: [b] }`，最终得到的是宿主默认值去掉 b，而不是 `["a"]`。要编辑复制的列表，应读取解析后智能体的 extensions，再写入新列表，见规范 §2\.2、§12。
> 
> 



> **这对你意味着什么：**
> 
> - 对话应遵循宿主设置时，就让字段保持未设置；只有需要不同配置时才设置
> 
> - 对话需要精确、稳定的工具集时，例如审查者，应使用存储的列表
> 
> - 配置更改会在下一个模型请求生效，不会在请求中途生效
> 
>

# 钩子

---

> 钩子是内置任务在提交某项决定之前，向你的扩展提出的问题；你的回答会影响最终写入的内容。
> 
> 

你常常希望不重写智能体就能引导它：阻止危险的 shell 命令，在发出请求之前裁减旧消息，或者在模型回答不够好时要求它继续。钩子就是为此而设。读完本节，你就能编写每一种钩子，预测多个扩展的回答如何组合，并让人工批准在崩溃前后保持稳定。

## 会询问谁



扩展通过 `hook(task, handlers)` 注册处理函数，例如 `hook(ToolTask, { beforeTool })`。任务对象提供类型检查；系统只保留它的名称，因此“钩子能够跨越其任务的重新加载而保留”，见规范 §7\.2。



任务只询问其所属对话选中的扩展中的钩子。这就是全部作用域规则：“要将钩子限制到部分对话，只在这些对话中选择它所属的扩展”，见 README §Hooks。没有全局钩子。反过来，这对安全性很重要：如果对话的扩展列表没有包含你的权限扩展，它就会在没有该防护的情况下运行，见规范 §12。

## 七种钩子



generation 任务询问四种钩子，tool 任务询问两种，compaction 任务询问一种。多个扩展回答时，每种钩子按自己的方式组合回答。



|**钩子**|**由谁询问**|**可以做什么**|**抛出异常时**|
|---|---|---|---|
|`beforeRequest`|generation|替换这一次请求的消息；每个处理函数接收上一个处理函数的结果|报告并忽略|
|`afterResponse`|generation|观察每次模型响应|报告并忽略|
|`onYield`|generation|对最终回答返回 `{ continue }`；第一个胜出|报告并忽略|
|`afterTools`|generation|观察一轮已完成的工具结果|报告并忽略|
|`beforeTool`|tool|改写参数，或阻止调用；第一个阻止决定胜出|阻止调用|
|`afterTool`|tool|逐个处理函数替换结果|报告并忽略|
|`beforeCompact`|compaction|拒绝压缩，或提供摘要；第一个决定胜出|报告并忽略|



`GenerationHooks`、`ToolHooks` 和 `CompactionHooks`，见 `src/harness/types.ts`；规范 §7\.2；`src/harness/tool.ts`。“报告”指传给 `HarnessOptions.onReport`。处理函数按扩展顺序运行。防护钩子抛出异常时会阻止调用，也就是在失败时保持关闭。

## 用 memo 让决定经得住崩溃



钩子可能运行两次：“如果在使用钩子结果的提交之前崩溃，可能会再次运行它们”，见规范 §7\.2。对于纯粹的检查，这无伤大雅，但人工批准不应该再次询问或发生改变。用 `api.memo(name, …)` 保存决定；它保留第一个写入的值：重跑时尝试记录 `"denied"`，仍会得到 `"approved"`，见 `test/harness-tools.test.ts`。钩子共享发问任务的 memo 名称空间，因此应给自己的名称加上前缀（阶段、步骤与进度，原书第67页）。要在界面中显示状态，就将它提交到文档中（对话视图，原书第129页）。

## 将状态保存在文档中



选择扩展，决定对话是否拥有某种行为。文档则保存这种行为的状态。规范 §7\.2 中的计划模式就是这一模式：扩展在所有地方都被选中，它的 beforeTool 读取当前对话自己的 plan\-mode 文档。



由扩展文档驱动的钩子，来源：规范 §7\.2

```TypeScript
const PlanModeDoc = defineDoc<{ enabled: boolean }>({
    kind: "app.plan-mode", version: 1, scope: "conversation",
    history: "latest", fork: "current", initial: () => ({ enabled: false }),
});

export const PlanMode = defineExtension({
    name: "plan-mode",
    hooks: [hook(ToolTask, {
    // 文档不存在，表示计划模式关闭。
    beforeTool: async (call, api, context) =>
    (await api.snapshot(PlanModeDoc, api.conversationId, context))?.enabled
    && writes(call)
    ? { block: "Plan mode: read-only" }
    : undefined,
    })],
});

// plan 切换这个对话的状态；不改变扩展选择。

await root.commit(async (tx) => {
    (await tx.doc(PlanModeDoc, root.id)).enabled = true;
}, context);
```

> 创建对话时，扩展没有初始化步骤，因此钩子会将缺失的文档视为“关闭”。示例 27 构建了另一种变体：通过改变选择配置来切换模式（构建编码智能体，原书第159页）。
>

> 细节：
> 
> - 参数检查两次：在 beforeTool 之前和之后，都根据工具的 schema 检查。改写后不符合 schema，会产生 `invalid_arguments`；阻止调用则产生 `blocked`
> 
> - 提交意图之后，不再重新执行 beforeTool：一旦调用意图已提交，恢复就会复用存储的参数（工具调用与重放，原书第94页）

> 
> - 把防护放在 beforeTool 中；抛出异常会阻止调用，这是安全的默认行为
> 
> - 在每个需要防护的对话中选择防护扩展，包括使用存储扩展列表的子智能体
> 
> - 将人工决定存入 memo，将模式状态存入文档

# 定义工具

---

工具由 schema、重放策略和 `execute()` 函数组成；Harness 将它报告的内容转化为恰好一个结果条目。



工具是模型作用于世界的方式：读取文件、执行命令、调用 API。困难在于执行中途崩溃。读完本节，你就能定义带类型的工具，将输出流式传给界面，选择重放策略，并读懂它留下的结果条目。

## 十一行定义一个工具



`defineTool()` 根据工具的 TypeBox 参数 schema 确定类型。Harness 在 `execute()` 运行之前，根据该 schema 检查模型参数，因此下面的 `args.n` 确实是一个数字。



count 工具，来源：README §Tools · `research/capture/scripts/one-turn.ts`

```TypeScript
import { Type } from "@earendil-works/pi-ai";

const count = defineTool({
    name: "count",
    description: "Count from 1 to n",
    parameters: Type.Object({ n: Type.Number() }),
    execute: async (args, api) => {
    for (let i = 1; i <= args.n; i++) api.output(`${i}\n`);
    return {};
    },
});

registry.install(defineExtension({ name: "count", tools: [count] }));
```

> `execute()` 没有返回 content，因此它用 `api.output()` 写出的文本会成为结果。
> 
> 



只有标准的 pi\-ai 工具字段（name、description、parameters）会发送给模型。你自己的字段，例如提示词区段，仍留在代码中（系统提示词，原书第115页）。四个可选字段设置策略：

|**字段**|**默认值**|**含义**|
|---|---|---|
|`replay`|`"unsafe"`|调用因崩溃而中断后，是否可以在重启时再次运行？|
|`executionMode`|`"parallel"`|`"sequential"` 让整轮调用逐个执行|
|`prepareArguments`|无|在检查之前修复参数，例如应该是数组的地方却收到 JSON 字符串|
|`outputLimits`|50 KiB、2,000 行、保留开头|限制为结果保留的输出|

> `ToolRegistration`，见 `src/harness/types.ts`；限制值来自 `src/truncate.ts`。执行模式的默认值来自 settings 的 toolExecution。
> 
> 

## 选择重放策略



每位工具作者都必须回答一个问题：如果进程在我的工具执行时崩溃，它可以再次运行吗？调用执行之前，工具任务将最终参数和策略写入磁盘。重启后，只有存储的策略和当前工具都声明 `"safe"`，才会重跑调用。否则，它会用已保存的输出写入一个 interrupted 错误结果。只有使用相同参数运行两次也无害时，才声明 safe。完整说明及实际崩溃采集记录，参见“工具调用与重放”（原书第94页）。

## 从结果到条目



返回结果的每个字段都是可选的：content、isError、details、diagnostics、usage 和 control。工具任务会补齐缺项，运行 afterTool 钩子，限制长文本（添加 truncated 警告），然后写入一个条目。存在诊断信息时，模型看到的文本末尾会附加一个 `<harness>` 块，每条诊断占一行；条目的 data 以列表保存这些诊断。



![image\.png](图片和附件/image.png)

> 工具结果条目准确保存模型看到的内容，并附上结构化诊断。这里是 `research/capture/sqlite-rows.txt` 中的条目 13，即 count 工具对 `count {"n": 3}` 的回答，键按采集记录中的顺序排列。
> 
> 



错误有两种，区别很重要。带有 `isError: true` 的结果是普通回答：任务会完成。`execute()` 抛出的异常也会转化为错误结果，代码为 `tool_error`，并保留部分输出，但它会让工具任务以 failed 结束，进而中止该调用启动的所有内容，见 `src/harness/tool.ts`。Harness 自行写入的错误携带说明原因的代码：`tool_unavailable`、`invalid_arguments`、`blocked`、`interrupted` 或 `aborted`。



两个结果字段会影响轮次。usage 记录工具自己的费用（用量与费用，原书第100页）。control 可以提供更多工具（addTools），在本轮每个结果都提出要求时结束运行（terminate），或者交接到全新的上下文（handoff，参见重置、交接与头指针，原书第46页）。

## execute\(\) 接收什么



`execute(args, api, context)` 接收一个专为本次调用创建的 api 对象。调用一旦结束，对这个对象的每项操作都会失败。你最常使用的部分有：

- `env`：对话当前 cwd 的文件和进程；如果宿主没有配置环境，则为 undefined（执行环境，原书第155页）

- `output(chunk)`：像 stdout 一样追加执行中的文本。如果结果没有 content，保留的文本就成为 content

- `details(value, context)`：向界面发布结构化进度；如果结果没有 details，最后一个值就成为结果的 details

- `diagnostic(d)`：附加给模型的说明，例如警告，与工具数据分开

- `commit`、`memo`、`createTask`：提交、备忘和子任务，与任何任务中一样

- `conversation(id)`：指向本次调用创建的对话的句柄（子智能体，原书第121页）

    

工具运行期间，output、details 和 diagnostics 会通过实时文档大约每 100 ms 传到界面。结果条目写入之前，模型看不到其中任何内容（运行控制与实时文档，原书第88页）。

## 内置工具与包装器



`@earendil-works/pi-durable/tools` 提供 read、write、edit 和 bash，将它们打包为 `CodingTools` 扩展（coding\-tools）。没有任何东西会自动帮你安装它们。它们只通过 `api.env` 工作，而且四个工具的重放策略都是 unsafe。bash 保留长输出的尾部，提供指向完整输出文件的路径，并在退出码非零或超时时失败，见 `src/tools/`。



要为部分对话改变工具，应覆盖或包装它，而不是复制。较后扩展中的同名工具会替换较早工具，而 `wrapTool(tool, wrapper)` 会装饰最终胜出的工具。包装器“从不捕获基础工具，因此重新加载基础工具仍会保留它的包装器”，见规范 §7\.3。示例 30 为一个对话提供会激活 virtualenv 的 bash，并对两个对话的每次 bash 调用计时，见运行记录 30。



> **这对你意味着什么：**
> 
> - 除非重跑无害，否则让 replay 保持 unsafe；先把任何随机值记录到 memo 中
> 
> - 对预期内的失败，返回 `isError: true`；只有在调用自身的工作应该被中止时才抛出异常
> 
> - 给模型的说明使用 `diagnostic()`，不要混入工具输出
> 
> 

# 系统提示词

---

> 提示词本身不会被单独存储；每个请求都从区段渲染它，只有发生变化的部分才会加入对话记录。
> 
> 

提供商会缓存提示词的开头，因此每个轮次都重写系统提示词会浪费金钱和时间。Pi Durable 用小型的命名区段构建提示词；某个区段变化时，只发送该区段。读完本节，你就能编写提示词区段，并维持对话提示词缓存的有效性。

## 区段



区段是系统提示词中有名称的一部分。`section(key, render)` 构建一个区段。render 返回字符串，或者返回 undefined 以省略该区段。默认情况下，文本用标签包裹，即 `<key>…</key>`；`{ tag: false }` 会原样发送文本。所选扩展的区段与智能体的 instructions 是提示词文本的唯一来源，见规范 §7\.4。



渲染函数接收解析后的 agent（包括本次请求提供的工具）、本次请求的 env（cwd 区段渲染 `input.env?.cwd`），以及用于读取已提交文档的 read。区段按扩展顺序排列，较后的同键区段会原位替换较早区段，随后应用 `wrapSection()` 装饰器，instructions 放在最后。示例 15 在两个对话上展示了全部这些行为。



![image\.png](图片和附件/image%202.png)

> 区段按扩展顺序渲染，包装器会应用，未选中的扩展被排除，instructions 最后出现。渲染值来自 `research/runs/15-system-prompt.txt`；各标签内的换行显示为空格。
>

区段抛出异常不会让请求失败。它会保留上一次显示的文本（如果有），并报告错误。区段不应关心自己在哪里运行：“没有任何区段检查自己是否运行在子智能体中。”对话提示词的差异只来自其选择配置、指令、环境和文档，见规范 §7\.4。

对话记录保存模型看到过的内容，因此提示词也保存在其中。每次请求之前，generation 任务会重放先前的系统条目，了解模型已经拥有哪些内容。它渲染现在需要的区段，如果发现差异，就追加一个只包含变更的 `pi.system` 条目。该条目保存 sections 补丁以及 toolsAdded 和 toolsRemoved（条目与内置类型，原书第37页）。

# 运行期间重新加载

---

> 以相同名称安装新版本，会立即为所有未来工作替换代码；已经运行的工作则继续使用启动时的代码直至完成。
> 
> 

你在智能体执行到一个轮次中途时修复了工具中的错误。你希望修复立即生效，又不想终止该轮次，也不想让一次工具调用一半用旧代码、一半用新代码。读完本节，你就能在正在运行的 Harness 中重新加载扩展，说明哪些工作看到旧代码、哪些看到新代码，并避免注册表无法发现的两类重新加载错误。

## 重新加载就是安装



没有 reload API。你只需以相同名称安装新的扩展对象。它会原位替换旧对象，而且“Harness 继续运行；无需关闭或重新打开”，见规范 §7\.5。由于位置保留，扩展的工具、钩子和区段都保留其优先级。示例 31 在某个工具调用运行期间重新加载该工具，然后重启进程。



调用中途重新加载，然后重启，来源：示例 31（节选）

```JavaScript
const submission = await root.submit({ type: "input", content: "Which version?" }, context);
await running;    // v1 的 execute() 已开始
registry.install(loadVersioned("v2"));    // 同一个名称 "versioned"
release();
await submission.wait(context);    // 重新加载期间正在执行的调用：v1
await (await root.submit({ type: "input", content: "And now?" }, context)).wait(context);
    // 下一次调用：v2
await harness.close(context);

registry = createRegistry();    // 第二个进程：尚未安装任何扩展
harness = await open(registry);
root = await harness.root(context);
// 重启后、安装前：[]
registry.install(loadVersioned("v3"));
// 安装后：['version']
```

> 注释对应 `research/runs/31-reload-and-restart.txt`。两个进程使用同一个 SQLite 文件；对话按名称选择了该扩展。
> 
> 



![image\.png](图片和附件/image%203.png)

> 运行中的工作保留它取得的代码；下一个请求或调用使用替换后的代码。示例 31 中，调用在 v1 下启动并返回 “v1”；下一个请求在 v2 下准备，其调用返回 “v2”。重启后，存储的选择配置不变，并绑定到 v3。虚线标记安装时刻。
> 
> 

## 谁看到哪份代码



由三条规则决定：

- 一个阶段保留自己的代码：每个任务阶段（两个检查点之间的一次处理函数执行）都基于开始时取得的注册表快照工作。它的钩子和智能体直到阶段结束都保持不变，见 `src/harness/scheduler.ts`

- 下一个阶段看到新代码：每个新阶段都取得新快照。一次运行的不同阶段可以使用不同版本：“没有任何要求规定，一次运行只能看到一种注册表状态”，见规范 §7\.1

- 工具调用在完成前固定代码：调用在同一个阶段内查找工具、运行钩子、执行并写入结果，“因此解析与结算之间没有任何分隔”，见 `src/harness/tool.ts`

    

测试明确验证了两方面。工具在调用中途被替换后，仍返回 “v1”。如果工具运行期间重新加载某个区段和 beforeRequest 钩子，第一次请求会显示 `mode: v1`，第二次会显示 `mode: v2`，见 `test/harness-tools.test.ts`。替换代码“绝不会向正在运行的工作发送信号或打断它”，见规范 §7\.5。

## 任务定义的交接



你自己的任务定义同样按名称重新加载。运行中的任务完成一个阶段时，如果其 kind 现在安装了不同的定义，而且新代码能够接手，任务就会交给新代码：新定义版本相同，或者版本更新且带有 migrate 函数。否则，旧代码继续运行该任务，并报告不匹配。版本与迁移参见“调度器”（原书第73页）。



安装也会解除阻塞。如果任务因为打开时缺少扩展，或者存储的版本过新而被阻塞，只要安装匹配的定义就会运行。`harness.inspect()` 显示哪些任务被阻塞（任务图与 inspect\(\)，原书第137页）。

## 重新加载不会触及什么



磁盘上没有任何内容改变。重新加载不提交任何内容，不发出事件，也不改写对话记录。使用该扩展的对话会在下一个请求中得到系统增量，但前提是渲染后的区段或工具声明发生了变化（系统提示词，原书第115页）。



重启相当于从空注册表开始重新加载。第二个进程打开文件后，根对话的智能体没有工具，直到重新安装扩展；之后，它就拥有新代码的 version 工具，见运行记录 31。该扩展的待处理任务在安装后恢复。旧 Harness 的 `close()` 完成之前，绝不要打开新的 Harness：两个实例不能同时拥有同一个 Session。



> **两个容易踩的坑**
> 
> 过早清理：替换扩展“只会阻止新的使用”。如果刚调用完 `install()` 就关闭数据库连接池或子进程，会破坏仍在旧对象上运行的调用。移动任务：将任务定义从一个扩展移到另一个扩展，“会在两次安装之间留下一个空档，在此期间，它的待处理任务会被阻塞”，见规范 §7\.5、§12。
> 
> 



> **这对你意味着什么：**
> 
> - 以相同名称安装即可重新加载；无需调用其他东西
> 
> - 任务存储的输入或检查点含义改变时，应提升任务版本
> 
> - 如果旧代码忽略取消且永不结束，`close()` 仍会等它。只有把扩展放在独立 worker 或进程中运行，才可以强行终止它们，见规范 §7\.5、§13
> 
> 

# 子智能体

---

> 子智能体是由创建它的工作所拥有的普通对话；所有权和请求 ID 让它可中止、能经受崩溃，无需专门的子智能体 API。
> 
> 

子智能体是第二个智能体，拥有自己的对话记录；你的智能体把工作交给它，例如“研究这个”或“审查那个 diff”。你用对话、所有权和一个工具来构建它。读完本节，你就能编写本包提供的两种模式，并预测中止、等待空闲和崩溃分别会对它们产生什么影响。

## 前台模式



**前台子智能体存在于一次工具调用内部。工具创建一个由自身工具任务拥有的子对话，将工作发给它，等待回答，再返回回答。每个持久化操作都设有标识键，因此崩溃后重跑时能够找到第一次尝试创建的内容。**



subagent 工具，来源：示例 22（节选）

```TypeScript
defineTool({
    name: "subagent", replay: "safe",
    parameters: Type.Object({ task: Type.String() }),
    execute: async (args, api, ctx) => {
    const child = await api.commit(async (tx) => {
    const found = await tx.scanConversations({ ownerTaskId: api.taskId }, 1);
    const existing = found.items[0];
    if (existing !== undefined) return existing.id;
    const created = await tx.createConversation({
    ownership: { kind: "task", taskId: api.taskId },
    });
    await configure(tx, created.id, { extensions: { remove: [Subagent] } });
    return created.id;
    }, ctx);
    await api.details({ conversationId: child }, ctx);
    const handle = (await api.conversation(child, ctx))!;
    const request = { type: "input", content: args.task,
    requestId: `subagent:${api.taskId}` } as const;
    const settled = await (await handle.submit(request, ctx)).wait(ctx);
    // ... 除非 settled 是已回答的 input，否则抛出异常（此处省略）
    const text = await answerText(api, settled.answer, ctx);
    return { content: [{ type: "text", text }] };
    },
})
```

每个部分都回答了一个与崩溃有关的问题：

- 先查找，再创建：子对话由工具的任务拥有，因此重跑时使用 `scanConversations({ ownerTaskId })` 找到它，而不会创建第二个

- 在一次提交中创建并配置：子对话一开始得到父对话智能体的副本（创建时的副本，原书第106页）；同一次提交会移除 subagent 扩展，因此子对话不能自行启动子智能体

- 从任务派生请求 ID：重跑时，用相同 ID 调用 `submit()` 会返回第一次提交请求，而不会把工作发送两次。绝不要使用提供商的调用 ID：它“在一个 Session 内并不唯一”，见规范 §7\.3

- details 让界面指向子对话：界面在工具执行更新事件中看到 `{ conversationId }`，并订阅子对话的事件（智能体事件，原书第133页）

## 所有权决定中止和空闲



拥有子对话，就意味着它是本次调用工作的一部分。“中止调用会中止子对话”，调用失败也一样；“只有子对话空闲后，父对话才算空闲”，见 README §Abort and Subagents。拥有仍在运行的工作的工具任务，会在这些工作结束之前保持未关闭状态（所有权与结构化并发，原书第76页；中止、故障与孤儿任务，原书第80页）。

## 后台模式



后台子智能体的生命周期超过父对话的各个轮次：用户之后仍可以给它发消息、停止它或列出它。示例 23 用一个 subagent 工具封装这些操作，提供 spawn、send、stop 和 status 动作。一次 spawn 在同一次提交中记录三件事。锚点任务 `app.subagent-anchor` 是父对话的后台任务；它立即完成，但子对话工作期间会保持未关闭状态。子对话由锚点拥有，不含 subagent 扩展，并有自己的指令。父对话的 `app.subagents` 文档将子智能体名称映射到子对话；父对话分叉时，该文档从空内容开始。



每条消息都经过一个后台 reporter 任务 `app.subagent-reporter`。它向子对话提交消息，等待结果，再将回答作为 follow\-up input 发给父对话。两次提交都使用从 reporter ID 派生的请求 ID，“因此子对话只收到一次消息，父对话也只收到一次回答”，见规范 §7\.3。运行记录 23 在子智能体工作期间关闭 Harness；重启后，父对话仍能收到 `reader: Moby Dick.`。



background 标记是一道墙。父对话的 Esc 和空闲等待止于锚点，因此不会影响子智能体。`abort(context, { background: true })` 仍可以越过这道墙。stop 动作直接中止子对话：当前回答结束，排队消息被丢弃，而子智能体仍可使用，和任何已完成的子智能体一样，见规范 §5\.4。



> **这对你意味着什么：**
> 
> - 为每个持久化操作设置标识键：按拥有者查找子对话，从任务 ID 派生请求 ID
> 
> - 一次回答中的工作用前台模式；用户之后还要继续与之交流的智能体用后台模式
> 
> - 绝不要把子对话的费用报告为工具 usage；那会重复计入（用量与费用，原书第100页）
