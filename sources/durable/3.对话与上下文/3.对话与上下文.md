# 3\.对话与上下文

# 条目与内置种类

---

> 条目是对话记录中不可变的一行，分别用不同字段保存模型读取的内容、代码读取的内容，以及模型上下文的起点。
> 
> 

**聊天记录是一系列已发生的事情：一个问题、一个回答、一个工具结果。Pi Durable 将每件事存为一个条目，此后绝不修改。**本节结束后，你就能读懂任何已存储的条目，判断是谁写入的，并添加自己的条目种类。

## 一条记录，三种读者



一个对话 conversation 对应一份对话记录  transcript，条目  entry 就是其中“一条不可变的对话记录”（spec §1）。系统的三个不同部分都会读取条目，但各自读取不同字段：

- 模型读取 `model`：该条目为下一次请求添加的消息

- 你的代码读取 `data`：模型永远看不到的 JSON

- 上下文构建逻辑读取 `head` 和 `edits`：模型上下文从哪里开始，以及隐藏或替换哪些早先条目。已存储的内容不会被重写



![image\.png](图片和附件/image.png)

> 条目将模型看到的内容、应用看到的内容和上下文的起点彼此分开。这是 `research/capture/context.txt` 中的条目 20，由一次手动压缩写入；摘要文本仅保留了前三个词。
> 
> 



**结构说明：**

1. `kind`：这里是内置种类；你自己的种类可以是任意字符串

2. `model`：该条目添加到上下文中的 `Message[]`；缺省时不添加消息

3. `data`：供应用使用的 JSON；永远不会发送给模型

4. `id` · `conversationId`：由 Session 在追加条目时分配

5. `head`：上下文先放本条目，再放 \#18 起的条目；条目 7–15 仍然保留在存储中

6. `byTaskId`：压缩任务 19；宿主写入的条目没有此字段



|**字段**|**保存的内容**|**设置方**|
|---|---|---|
|`id`|一个 `EntryId`，在整个 Session 内有序|Session|
|`conversationId`|所属对话|Session|
|`kind`|表明条目种类的字符串|写入方|
|`model?`|给模型的消息；仅用于显示或记账时缺省|写入方|
|`data?`|供视图、扩展和你的代码使用的 JSON|写入方|
|`head?`|从现在起模型上下文的第一个条目|写入方；`"self"` 表示本条目|
|`edits?`|仅在上下文中隐藏或替换早先条目|写入方|
|`byTaskId?`|在其提交中追加该条目的任务|Session|

> `EntryRecord` 的字段，改述自 `src/types.ts` 中的字段注释。
> 
> 



条目是在一次提交中写入的。提交是原子保存：其中所有内容要么一并存储，要么全部不存储。你绝不需要设置 `id`、`conversationId` 或 `byTaskId`。`tx.appendEntry()` 会填入这些字段，并将 `head: "self"` 转成新分配的 ID。因此，`byTaskId` 能可靠地记录条目由哪个任务写入。通过宿主的 `Conversation.commit()` 追加的条目没有这个字段。

## 内置种类



Harness 会写入六种条目。每一种都作为带类型的 `Entry` 令牌导出（`src/entries.ts`）。其中只有两种携带 `data`（spec §8\.1）。

|**种类**|**`model`**|**`data`**|**写入方**|
|---|---|---|---|
|`pi.user`|一条用户消息|—|提交请求|
|`pi.assistant`|一条助手消息，停止原因不限|—|生成任务|
|`pi.system`|一条表示变更的系统消息|—|生成任务，在发送请求之前|
|`pi.tool-result`|一条工具结果消息|`{ diagnostics }`|工具任务|
|`pi.reset`|无消息，或将交接文本作为用户消息|—|`reset()`、工具的交接|
|`pi.compaction`|将摘要作为用户消息|`{ reason }`|压缩任务|

> 来源：spec §8\.1 和 `src/entries.ts`。这些令牌分别为 `UserEntry`、`AssistantEntry`、`SystemEntry`、`ToolResultEntry`、`ResetEntry` 和 `CompactionEntry`。
> 
> 



`pi.assistant` 记录每一次响应，包括失败：“回答、带有错误文本和用量的失败尝试，以及转换后停止原因为 `aborted` 的部分响应”（spec §8\.1）。对话记录不会隐去任何内容，因此花掉的每个 token 都清晰可见。随后构建上下文时，会将失败的响应排除在后续请求之外（上下文推导，原书第40页）。

## 系统条目记录变更，而不是头部



`pi.system` 条目不保存完整提示词，而是在对话记录的某个位置保存提示词和工具列表的变更。下面是一次采集运行中的首个系统条目：



条目 10，对话中的第一个 `pi.system`；来源：`research/capture/sqlite-rows.txt`

```JSON
{
    "kind": "pi.system",
    "model": [
        {
            "role": "system",
            "content": "",
            "sections": { "preamble": "You are a terse assistant." },
            "toolsAdded": [ { "name": "count", "description": "Count from 1 to n, ..., ... } ],
            "timestamp": 1791211974788
        }
    ],
    "id": 10, "conversationId": 1, "byTaskId": 9m
}
```

> 已调整顺序并合并排版；工具的描述和参数模式经过截断。
> 
> 



每个命名区段都会被添加或替换，`null` 则用于移除区段。工具也以相同方式移除和添加。按顺序重放每个系统条目，就能得到当前的提示词和工具集（spec §2）。Harness 只会在提示词或工具实际变化时写入新的 `pi.system` 条目，因此一个稳定的对话只会有一个这样的条目。完整说明见系统提示词（原书第115页）。

## 自定义种类



任何非空字符串都是有效的 `kind`。`defineEntry()` 将它变成带类型的令牌；追加和读取时，令牌为 `data` 提供类型：



带类型的应用条目；来源：`src/entries.ts` · `src/types.ts`

```TypeScript
const NoteEntry = defineEntry<{ text: string }>("app.note");

// 没有 `model`，因此模型永远看不到它。
await root.commit(
    (tx) => tx.appendEntry(NoteEntry, root.id, { data: { text: "user pinned b.md" } }),
    context,
);

// 条目 `id` 不存在或种类不符时，返回 undefined。
const note = await harness.commit((tx) => tx.entry(NoteEntry, id), context);
```

> `app.note` 是本书使用的示例种类。令牌的 `is()` 类型守卫可根据种类收窄任意条目的类型。
> 
> 



按读者选择字段。模型必须看到的内容放入 `model`；只有代码需要的内容放入 `data`。只带 `edits` 的条目很常见：采集记录中的 `app.correction` 会在上下文中替换一个早先的回答，而不添加自己的消息（`research/capture/context.txt`，阶段 5）。



> **这对你意味着什么：**
> 
> - 将面向模型的文本放入 `model`，其余内容放入 `data`
> 
> - 永远不要修改条目；应追加一个带 `edits` 的新条目
> 
> - 调试时，通过 `byTaskId` 查看哪个任务写入了条目
> 
> - 运行处于活动状态时，要通过写入提交请求添加条目，不要直接追加（spec §12；提交请求，原书第84页）
> 
> 

# 从对话记录到模型上下文

---

> 对话记录记下所有发生过的事情；九条固定规则将其转换成提供商能够接受的请求，而不重写任何已存储的内容。
> 
> 

真实的对话记录往往很杂乱。一次响应被崩溃中断。一次工具调用始终没有结果。两个结果乱序到达，中间还夹着一条用户消息。如果原样发送，提供商会拒绝它。本节结束后，你就能逐条预测：在请求钩子修改内容之前，已提交的历史如何变成模型上下文。

## 同一份对话记录的两种读法



已存储的对话记录只会增长。上下文是模型看到的内容，每次都根据历史重新计算。`Conversation.context()` 会并列呈现这两种读法（`src/harness/types.ts`，`ContextView`）：

- `entries`：活动范围内的原始条目。UI 显示这些内容

- `messages`：根据已提交历史推导的消息，尚未经过准备更新和请求钩子的处理

- `head`：决定范围起点的条目（如果存在）

- `contributions`：工具结果重新排序之前，各条目贡献的内容。调试时很有用

## 九条规则



规范将推导过程定义为九条有序规则（spec §2\.1）。右列指向下面的完整示例。

|**\#**|**规则的直白说明**|**示例**|
|---|---|---|
|1|找到最新的带 `head` 的条目|\#20|
|2|上下文从该 `head` 指向的位置开始；若没有头指针，则从开头开始|\#10|
|3|读取从那里到末尾的每一个条目|\#10–\#20|
|4|应用编辑：对同一条目的最新编辑优先；`omit` 隐藏它，`replace` 替换它的消息|\#19 替换 \#11|
|5|将头指针标记条目放在最前面，其余条目按顺序排列|\#20 在最前面|
|6|所有系统消息都保留在原写入位置|保留 \#10|
|7|按工具调用顺序，将每次调用的结果移到发出该调用的助手消息之后，紧挨着它|\#16、\#14 紧随 \#13|
|8|为每个没有结果的调用添加错误结果；丢弃没有对应调用的结果|`call-c`|
|9|排除没有 `model` 的条目，以及以 `aborted`、`error` 或 `deferred` 停止的助手消息|\#12、\#18|

> 改述自 spec §2\.1。
> 
> 

## 完整示例



这份对话记录是逐条写入后，再用 `context()` 读回的。智能体收到修复两个文件的任务。一次响应被中止。两次读取乱序返回，中间夹着一条用户消息。第三次读取始终未完成。随后，应用添加了一条备注，修正了用户的措辞，并写入一条摘要，其 `head` 跳过了开头的交流。

- **范围（规则 1–3）**。最新的带 `head` 的条目是摘要 \#20，其 `head` 为 \#10。因此上下文覆盖 \#10 到 \#20。条目 \#8 和 \#9 仍被存储且仍可读取；只是不会发送出去。

- **编辑（规则 4）**。\#19 替换 \#11。消息 3 是修正后的文本 “Fix the typos in a\.md and b\.md”，而非原文。只有位于范围内的编辑才会生效。

- **顺序（规则 5 和 6）**。摘要 \#20 成为消息 1。系统条目 \#10 留在原位置，成为消息 2。

- **排除（规则 9）**。被中止的响应 \#12 和备注 \#18 不添加任何消息。只包含编辑的 \#19 也不添加消息。

- **工具结果（规则 7 和 8）**。\#13 先调用 `call-a`，再调用 `call-b`。对应结果 \#16 和 \#14 会提前，按调用顺序紧接在 \#13 之后，并位于用户消息 \#15 之前。最后一条助手消息 \#17 调用了 `call-c`，但没有收到回应，因此系统会为它合成一个结果：

```JSON
{
    "role": "toolResult",
    "toolCallId": "call-c",
    "toolName": "read",
    "content": [{ "type": "text",
        "text": "Tool result unavailable: history ends before this call completed." }],
    "isError": true,
    "details": { "reason": "missing_result" },
    "timestamp": 1791300010000
}
```

## 为什么需要这些规则



每条规则都处理持久化对话记录可能合法处于的一种状态：

- 崩溃与中止：被打断的响应会存为停止原因为 `aborted` 的 `pi.assistant` 条目（生成，原书第91页）。规则 9 会将未完成的文本及其中的工具调用排除在后续请求之外

- 被打断的工具：失败或被放弃的工具任务不会写入结果。规则 8 告诉模型，该调用没有完成（spec §5\.4）

- 并行工具与引导：结果按完成顺序落入存储，用户也可以在两次结果之间进行引导（提交请求与收件箱，原书第84页）。提供商要求结果紧接在调用之后；规则 7 恢复这一顺序

- 分叉：在调用与结果之间创建的分叉会继承调用，但不会继承结果。示例 09 在包含两次调用的助手消息处分叉；分叉的上下文以两条错误结果结尾（运行 09）



> **这对你意味着什么：**
> 
> - 要查看模型将收到什么，请调用 `context()` 并读取 `messages`。不要自行根据 `entries` 重建上下文
> 
> - 崩溃绝不会产生无效请求，因此你不需要编写对话记录清理代码
> 
> - 读取上下文绝不会写入内容。对同一份对话记录读取两次，会得到相同的消息
> 
> 



> 来源：spec §2\.1、§2\.2（`ContextView`）、§5\.4、§8\.1；`src/harness/context.ts`；`src/harness/types.ts`（`ContextView`）；示例 09；运行 09；`research/capture/extra-p23/context-derivation.txt`（脚本 `test/capture-p23-context.ts`）。
> 
> 

# 分叉与有所有者的对话

---

> 分叉在某个条目处分出一条对话支路，并共享此前的历史；有所有者的对话属于某个任务，因此中止该任务也会影响到它。
> 
> 

**用户希望回到早先的消息，尝试另一种做法，同时保留原有对话。智能体希望为子智能体开启旁支对话。这两种情况都会产生新对话。**本节结束后，你就能创建这两种对话，并预测它们能看到什么。

## 获得对话的四种方式



|**调用**|**得到的结果**|
|---|---|
|`harness.root(context, options)`|对话 1，首次调用时创建；后续调用不写入任何内容|
|`harness.createConversation(options, context)`|一个全新的空对话；必须指定所有权|
|`conversation.fork(at, options, context)`|一条共享截至条目 `at` 的历史的分支|
|`tx.createConversation()`、`tx.forkConversation()`|同样的操作，但位于任意提交内，例如工具的提交|

> 来源：spec §2\.2 和 `src/harness/harness.ts`。选项为 `ownership`、`agent` 和 `init`。
> 
> 



**创建过程只需一次提交。它会写入对话、五个内置文档（内置文档，原书第60页）、任何智能体设置，以及你的 ****`init(tx, id)`**** 写入的全部内容。**不会出现创建一半的状态（spec §2\.2）。



**创建对话和发送第一条消息是两个独立调用。**如果进程可能在两者之间崩溃，就在 `init` 中写入一个键，以便再次找到该对话，然后携带请求 ID 提交消息，避免重试时重复发送（spec §2\.2）。

## 分叉



分叉是一个新对话，从父对话的某个条目 E 开始。它的记录存有 `parent: { conversationId, at }`。没有任何内容被复制。分叉能看到自己的条目，然后看到父对话截至 E 的条目，再看到祖父对话截至其相应上限的条目，依此类推（spec §2\.1、§3\.7）。每个祖先对话的条目都按沿途最小的上限截断。



```Bash
$ node --conditions=source --experimental-strip-types test/capture-p23-context.ts
root 1: #9:"three" #8:"two" #7:"one"
fork 10: #16:"fork-only" #8:"two" #7:"one"
grand 17: #23:"grandchild-only" #7:"one"
fork2 24: #16:"fork-only" #8:"two" #7:"one"
grand.fork(#9) -> Entry 9 is not visible from conversation 17
```

> 来源：`research/capture/extra-p23/forks.txt`；条目按从新到旧排列。对话 17 看不到 \#9，因此不能在那里分叉。
> 
> 



头指针也会跨越分叉。压缩之后创建的分叉，其上下文会从父对话的摘要开始（`research/capture/context.txt`，阶段 6）。在工具调用与结果之间创建的分叉，其上下文会得到一条错误结果（上下文推导，原书第40页）。

> 分叉能看到自己的条目，以及每个祖先截至 `parent.at` 上限的条目。对话 32 没有父对话；它由位于对话 1 中的任务 31 拥有。对话、条目与可见范围来自 `research/capture/extra-p23/forks.txt`。

## 分叉继承什么



|**状态**|**分叉中的情况**|
|---|---|
|条目|共享截至 E 的条目，绝不复制|
|`fork: "asOf"` 的文档|父对话在 E 时的值的副本|
|`fork: "current"` 的文档|父对话当前值的副本|
|`fork: "initial"` 的文档|不继承；首次使用时全新创建|
|`pi.agent`|父对话在 E 时的智能体设置|
|`pi.provider`|一个新的提供商会话 ID，绝不使用父对话的 ID|
|实时状态、收件箱、用量|为空|
|任务和任务文档|绝不复制|
|Session 文档|共享，不复制|



来源：spec §2\.2、§3\.7。文档的分叉策略见定义文档（原书第50页）。



采集记录展示了 `asOf` 规则。写入 \#8 时，根对话的智能体指令为 `"v1: be brief"`，后来变成了 `"v2: be thorough"`。在 \#8 处创建的分叉从 v1 开始，并拥有自己的提供商会话 ID（`research/capture/extra-p23/forks.txt`）。

## 有所有者的对话



有所有者的对话属于某个任务。创建时使用 `{ kind: "task", taskId }` 所有权；记录随后保存 `owner: { conversationId, taskId }`。任务也可以在同一次提交中创建：



在一次提交中创建任务及其拥有的对话；来源：`test/capture-p23-context.ts`

```JavaScript
const owned = await harness.commit(async (tx) => {
    const taskId = await tx.createTask(Supervisor, null, {
        ownership: { kind: "conversation" }, conversationId: root.id, background: true,
    });
    const child = await tx.createConversation({ ownership: { kind: "task", taskId } });
    return { taskId, child };
}, context);
// child: {"id":32,"owner":{"conversationId":1,"taskId":31}}
```

> 注释是 `research/capture/extra-p23/forks.txt` 中采集到的输出。
> 
> 



所有权描述的是工作关系，而不是历史关系。有所有者的对话最初为空。它会一次性复制所有者所在对话的智能体设置；之后所有者对话中的变更不会传递过来（spec §2\.2）。所有权边会将两者关联起来，以支持中止和空闲等待。中止任务会触及该对话中的非后台工作，而等待任务空闲也会涵盖这些工作（所有权与结构化并发，原书第76页）。子智能体正是建立在这一机制之上的（子智能体，原书第121页）。



所有者必须仍处于存活状态。正在完成、已经完成或正在被中止的任务不能再获得新对话，即使是在同一次提交中也不行（spec §3\.3）。



> **这对你意味着什么：**
> 
> - 要“从这里重新尝试”，就使用分叉。原对话不受影响
> 
> - 对于任务停止时也应该停止的工作，例如子智能体，使用有所有者的对话
>

# 重置、交接与头指针

---

> 头指针将模型上下文的起点向前移动，而不删除任何内容；重置、交接和压缩都采用这一机制。
> 
> 

有时，模型应该忘掉一些内容。**上下文窗口已经用满，或用户希望在同一任务上重新开始。Pi Durable 绝不删除旧消息；它只是告诉模型从后面的位置开始读取。**本节结束后，你就能开启一个全新上下文，可以附带交接说明，也可以不带，并能预测模型下一步看到什么。

## 什么是头指针



**头指针是一个条目字段，含义是“模型上下文从这里开始”**（`src/types.ts`）。**带有该字段的条目称为头指针标记。只有最新的标记有效，上下文推导会把这个标记条目放到最前面**（规则 1、2 和 5，原书第40页）。**更早的条目仍留在存储中，只是不再发送**（spec §2\.1）。



头指针有两种指向方式：

- 向后指向保留的条目：压缩摘要的头指针指向它保留的第一个条目。上下文变成“摘要，然后是保留的尾部”（压缩，原书第97页）

- 指向自身：重置条目的头指针指向它自己。上下文变成重置条目本身，以及此后出现的所有内容

## `reset()` 与交接



`Conversation.reset(handoff, context)` 开启一个新上下文。它会提交一个 `head: "self"` 的 `pi.reset` 条目。如果传入交接文本，该条目会将其作为用户消息携带（spec §2\.2）：

- `reset(text)`：模型的上下文变成这一条消息。下图阶段 4 中的文本为：`"We were doing arithmetic for Ada. Continue from 5+5."`

- `reset(undefined)`：条目不含消息，因此下一次输入到来之前，上下文为空（`research/capture/extra-p23/heads.txt`）



重置与其他写入一样进入队列。如果对话空闲，它立即落入对话；如果运行处于活动状态，它会等待下一个边界，也就是模型步骤和工具步骤之间的安全点（提交请求与收件箱，原书第84页）。若在工具轮次期间落入对话，就会结束运行，并将该运行的输入报告为未回答，原因为 `reset`。若在回答之后落入，则不会改变已经给出的回答（spec §6）。`reset()` 在提交请求提交后即返回，而不是等到条目真正落入对话；请观察对话来确认。

工具也可以请求相同操作。如果其结果的 `control` 携带 `handoff: string`，那么工具轮次结束时，运行会以一个包含该文本的 `pi.reset` 条目结束，“与 `reset(handoff)` 写入的内容完全相同”（spec §7\.3）。如果多个工具都提出交接请求，则按调用顺序，以最后一个为准。

## 过时的头指针写入



头指针只能向前移动。若一次头指针写入指向当前起点之前，就会重新带回已被切掉的历史，因此系统会以过时为由拒绝它：提交请求以未回答状态结束，原因为 `stale`，并且不写入任何内容（spec §6）。重置的头指针指向自身，因此永远不会过时。



在 \#9 处重置后的两次头指针写入；来源：`research/capture/extra-p23/heads.txt`

```Bash
context entries: [#9 pi.reset, #11 pi.user]

write with head=#8 (before the start): status "unanswered", reason "stale"
write with head=#11 (inside the range): status "done", entry 13
context entries now: [#13 app.summary head=11, #11 pi.user]

stored entries (newest first), nothing deleted:
    [#15 pi.reset, #13 app.summary, #11 pi.user, #9 pi.reset, #8 pi.assistant, #7 pi.user]
```

> 同样的规则也用于裁决相互竞争的压缩：会将起点向后移动的摘要以 `stale` 结束（压缩，原书第97页）。
> 
> 

## 头指针绝不会做什么



- 删除内容：上面的每个条目仍被存储，`entries()` 仍会返回它们。你仍然可以在旧条目处分叉

- 更改提供商 ID：重置和压缩会保留对话的 `pi.provider` 会话 ID（spec §2\.2）

- 丢失系统提示词：头指针变动之后，下一次请求会写入一个全新的完整 `pi.system` 条目（系统提示词，原书第115页）



> **这对你意味着什么：**
> 
> - 使用 `reset(text)` 重新开始，同时告诉模型上次进行到了哪里
> 
> - 通过写入提交请求写入自定义头指针条目，而不是直接调用 `tx.appendEntry()`。只有提交请求路径会检查头指针是否过时，直接写入可能让已挂载的视图落后于当前状态（spec §12）
> 
> - 如果写入以 `stale` 结束，说明更新的头指针已经越过它的目标。请根据当前上下文重新计算
> 
>
