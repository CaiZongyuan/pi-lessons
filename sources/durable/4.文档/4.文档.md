# 4\.文档

# 定义文档

---

> 定义是一个带类型的 token，用于确定文档的种类、版本、所有者和分叉行为；存储记录会记住所有这些选择。
> 
> 

**智能体需要聊天之外的状态：待办清单、计划、用户设置。如果这些状态与对话记录分开存储，崩溃就可能让两者不同步。文档就是这样的状态，与条目在同一次提交中存储。提交是原子保存：其中所有内容要么一并存储，要么全部不存储。**本节结束后，你就能定义一个文档，并选择对话分叉时它如何变化。



**文档是一个随每次提交而变化的 JSON 对象。存储将每次变更保存为一小组编辑，或保存为整个值（基值与增量，原书第56页）。Harness 将自身状态放在五个内置文档中**（内置文档，原书第60页），**而你用同一个函数 ****`defineDoc()`**** 定义自己的文档。**



每个对话各自拥有的待办清单；来源：README §Your Own State

```TypeScript
const Todos = defineDoc<{ items: string[] }>({
    kind: "app.todos",
    version: 1,
    scope: "conversation",
    history: "latest", // 也可用 "rewindable"，通过 snapshotAsOf() 读取旧值
    fork: "initial", // 分叉的初始状态："initial"、"current" 或 "asOf"
    initial: () => ({ items: [] }),
});

await root.commit(async (tx) => {
    (await tx.doc(Todos, root.id)).items.push("write docs");
}, context);
```

> 省略了导入行。`"asOf"` 只允许与 `history: "rewindable"` 一起使用；编译器会强制检查。
> 
> 

## 定义就是 token



`defineDoc()` 返回一个 token：携带定义和值类型的普通对象。它只检查 `version` 是否为正整数（`src/documents.ts`）。没有任何注册过程。每次读写都传入token，例如 `tx.doc(Todos, root.id)`；token为这一次调用提供类型、初始值和迁移逻辑（spec §3\.3）。每个token只在一个模块中定义一次，其他地方统一导入。不支持对同一个 `kind` 使用两个不同定义，也没有机制检测这种情况（spec §12）。



|**字段**|**类型**|**决定什么**|
|---|---|---|
|`kind`|`string`|存储名称。它是公共协议的一部分，不能重命名|
|`version`|正整数|值结构的版本；每次变更都会存储它|
|`scope`|`"session"` · `"conversation"` · `"task"`|谁拥有它，以及它存活多久|
|`history`|`"latest"` · `"rewindable"`|仅用于对话文档。旧值是否仍可读取|
|`fork`|`"current"` · `"initial"` · `"asOf"`|仅用于对话文档。分叉副本从什么值开始|
|`initial()`|`() => T`|新文档的值；必须是 JSON 对象|
|`migrate?`|`(value, fromVersion) => T`|读取较旧的已存储值时将其升级（4\.3，原书第56页）|
|`checkpointWhen?`|`(value, ops, info) => boolean`|何时存储整个值，而不是存储编辑（4\.3，原书第56页）|

> 定义字段，来源：`src/types.ts`（`CommonDocDefinition`、`DocumentSemantics`）。
> 
> 

## 作用域、历史与分叉



**作用域决定所有者和生命周期。会话文档由所有对话共享，一直存活到你将其退役。对话文档属于一个对话。任务文档属于一个任务，并在任务结束时自动退役**（spec §3\.1）。**只有对话文档需要选择历史策略和分叉策略，由此形成七种合法组合。**

> 作用域确定所有者和生命周期；只有对话文档需要选择历史策略和分叉策略。来源为 `src/types.ts` 的联合类型 `DocumentSemantics`；分叉结果来自 spec §3\.7。右列列出采用相应组合的内置文档。
> 
> 



**`history: "latest"`**** 只保留当前值。****`"rewindable"`**** 保留每一次已存储的变更，因此 ****`snapshotAsOf(token, conversationId, entryId)`**** 可以返回写入任意条目时的值。代价是存储空间：旧变更永远不会删除**（4\.3，原书第56页）。



**`fork`**** 决定分叉对话的初始状态**（分叉，原书第43页）。**`"current"`**** 复制父对话现在的值。****`"asOf"`**** 复制分叉条目时的值，只有可回溯文档还保有该值。****`"initial"`**** 不复制任何内容；分叉第一次调用 ****`tx.doc()`**** 时会创建一个全新的文档。**在运行 02 中，父对话的备注文档内容是 `after goodbye`，而在更早条目处创建的分叉以 `after hello` 开始。

## 文档族



文档族是同一个所有者下多个文档共用的定义，通过字符串键彼此区分。可以把它理解为“每个文件一个审阅文档”。`defineDocFamily()` 接受同样的字段，另外加上 `family: true`，其初始化函数接收一个种子：



每个文件一个审阅文档；来源：`docs/pico-v5-chord-usage.md` §2

```JavaScript
const ReviewDoc = defineDocFamily<ReviewState, ReviewInput>({
    kind: "app.diff-review", version: 1, family: true, scope: "conversation",
    history: "latest", fork: "current",
    initial: seed => ({ path: seed.path, patch: seed.patch, comments: [] }),
});

await tx.doc(ReviewDoc, conversationId, review.key, review.seed);
```

> 键是地址的一部分，种子不是。种子只在首次创建成员时使用一次，之后便被忽略（spec §12）。采集记录中，针对键 `src/a.ts` 的第二次 `tx.doc()` 调用传入种子 `{"path":"IGNORED"}`，但该成员仍保持 `"path":"src/a.ts"`。要改变成员，就直接编辑它。
> 
> 

## 选择会被存储



**每个已存储的文档都会记录其 ****`kind`****、****`scope`****、****`history`**** 和 ****`fork`**** 策略，因此即使定义它的代码已经缺失，现有数据仍然有明确含义（spec §3\.2）**。每次访问都会将token与该记录核对。如果在代码中把 `fork` 从 `"initial"` 改成 `"current"`，现有文档不会改变，而是无法通过新token读取，并抛出 `Document 4 (app.todos) does not match the supplied definition semantics`（`src/documents.ts`）。



> **这对你意味着什么：**
> 
> - 对描述对话记录的状态，例如计划，使用 `rewindable` \+ `asOf`，这样从旧条目分叉时就能看到对应的计划。示例 27 的 `app.plan` 和内置 `pi.agent` 都采用这种组合
> 
> - 对属于用户的状态，例如草稿，使用 `current`，使分叉取得其当前状态（`docs/pico-v5-chord-usage.md` §2）
> 
> - 对属于单一分支的状态，例如沙箱或花费，使用 `initial`。复制花费计数器会造成重复计算，因此“分叉从零开始”（spec §8\.6）
> 
> - 将 `kind`、`scope`、`history` 和 `fork` 视为永久不变的选择。只有值的结构可以通过 `version` 和 `migrate()` 演进
> 
> 

# 访问、创建与生命周期

---

> 只有 `tx.doc()` 会创建文档；所有读取操作对不存在的文档都返回 `undefined`，而作用域决定文档的生命何时结束。
> 
> 

**你永远不需要显式“创建”文档。一次提交首次请求它时，它就存在了。读取则不同：读取绝不创建任何东西。本节结束后，你就能创建、读取和退役文档，并说明各个文档何时存在。**

## `tx.doc()` 是获取或创建



在一次提交内，`tx.doc()` 返回一个草稿：只在本次提交内可编辑的文档视图。如果文档尚不存在，同一次调用会将它创建出来。参数取决于token的作用域：

|**作用域**|**单个文档**|**文档族成员**|
|---|---|---|
|`session`|`tx.doc(Doc)`|`tx.doc(Doc, key, seed)`|
|`conversation`|`tx.doc(Doc, conversationId)`|`tx.doc(Doc, conversationId, key, seed)`|
|`task`|`tx.doc(Doc, taskId)`|`tx.doc(Doc, taskId, key, seed)`|

> 来源为 `src/types.ts` 中 `Tx.doc` 的重载。读取操作接收同样的所有者和键，但不接收种子，另外还接收一个 `Context`。
> 
> 



![image\.png](图片和附件/image%201.png)

> 创建就是写入：对不存在文档的第一次 `tx.doc()` 调用会在该提交中存储它的完整值。来源：`src/session/transaction.ts`；ID 4、seq 2 及该值来自 `research/capture/extra-p4/documents.txt`。
> 
> 



图中跟踪了一次创建过程。Session 找不到当前文档（步骤 2–3），于是运行 `initial()`、向存储申请新 ID，然后把一个草稿交给你的代码（步骤 4–7）。在同一次提交中再次请求，会得到同一个草稿（spec §3\.3）。你的编辑进入草稿（步骤 8）。回调返回时，草稿被关闭，提交存储的是完整的最终值 `{"items": ["write docs"]}`，而不是最初的空值（步骤 9–10）。只有提交成功后，其他读取方才能看到它（提交，原书第29页）。



对不存在的文档调用 `tx.doc()` 就是一次写入，即便代码只读取草稿也一样。若只想查看而不创建，请使用 `snapshot()`。提交结束后仍被保留的草稿已经失效：向它赋值会“抛出异常：草稿已被撤销”（spec §3\.4）。

## 读取绝不创建



对于不存在的文档，“snapshot、state 和 watch 查询均返回 `undefined`”（spec §12）。将 `undefined` 视为默认值。在示例 11 中，待办清单不存在时，提示词区段不显示任何内容；工具首次写入时，才由 `tx.doc()` 创建清单（示例 11）。



|**方法**|**返回内容**|
|---|---|
|`snapshot()`|当前值|
|`snapshotAsOf()`|写入某个条目时的值；仅适用于可回溯文档|
|`documentState()`|只读的实时状态（8\.1，原书第125页）|
|`watchDoc()`|已提交变更的流（8\.2，原书第129页）|



以上为读取方法。Session、Harness、任务、工具和钩子都可以使用 `snapshot()` 和 `snapshotAsOf()`（`src/types.ts`、`src/harness/types.ts`）。



快照是共享的，而不是复制的，也没有被冻结。如果代码修改了它，后续读取方会看到该变更（spec §3\.4）。修改前先复制。

## 什么会结束文档的生命



文档从创建到退役的每一段生命称为一个实例世代，各有自己的 ID。将文档退役后重新创建，会获得新的 ID；ID 永远不会复用（spec §3\.2）。采集记录在提交 12 中将 `app.draft`（ID 5）退役，又在提交 13 中重新创建了它（ID 18）。观察者看到退役时，得到的值为 `null`。

# 基值、增量与迁移

---

> 存储用偶尔写入的基值，也就是完整值副本，加上其间的小幅编辑来保存文档；你的定义决定何时写入基值。
> 
> 

每次变更都保存整个文档会浪费空间。只保存编辑又会让读取越来越慢，因为每次读取都需要重放全部编辑。Pi Durable 大多数时候存储编辑，偶尔存储一份完整副本，称为基值。本节结束后，你就能读懂存储转储中的文档行，选择何时写入基值，并安全地改变文档结构。

## 两种记录



每一项已存储的变更都属于以下两种之一（`src/types.ts`，`DocumentContent`）：

- 基值：整个值。在创建文档、版本变更，或 `checkpointWhen()` 返回 `true` 时写入

- 增量：本次提交产生的编辑列表，形式为 Chord 操作。其他每次变更都写入增量。Chord 根据普通的草稿编辑生成这些操作；你不需要手工编写



没有改变任何内容的提交不会写入内容。两种记录都会记下写入时使用的定义版本。采集记录对两个文档执行了五次提交，两者都使用同一条规则：`info.deltasSinceBase >= 2`。`app.todos`（ID 4）是可回溯文档，`app.draft`（ID 5）则只保留最新值。



五次提交后的 `document_revisions`；来源：`research/capture/extra-p4/documents.txt`

![image\.png](图片和附件/image%203.png)



SQLite 行，每个已存储的变更占一行。`"p"` 表示数组拼接操作（路径、索引、删除数量、项目），`"s"` 表示设置一个值。



读取时，先找到最新基值，再按顺序应用此后的每个增量。ID 5 在 seq 5 之前没有记录，因为只保留最新值的文档一旦写入基值，存储就可以删除所有更早的记录。

## 检查点判定函数



每次普通变更都会调用一次 `checkpointWhen(value, ops, info)`。若返回 `true`，该变更就存为基值。`info.deltasSinceBase` 是从上一个基值起的增量数量，不包括本次变更；Session 会跟踪它，因此检查时不需要读取存储。采集记录中，规则依次看到 0、1、2，因此 seq 5 成为基值。如果判定函数抛出异常，整个提交都会失败。



两种写法都很实用。一种使用数量，例如 `info.deltasSinceBase >= 31`，为读取需要重放的增量数量设置上限。另一种检查状态，例如 `pi.live` 的做法：每当文档回到较小的静止值，就写入一个基值。这一选择只影响存储：无论选哪种方式，观察者和视图接收到的编辑都相同（8\.1，原书第125页）。



没有 `checkpointWhen` 时，文档只在创建时存储一个基值，此后永远存储增量。读取会越来越慢，存储“在文档存活期间可能无限增长”（spec §12）。存储绝不会自行生成基值（spec §3\.5）。

## 基值允许存储删除哪些内容



对于只保留最新值的文档、Session 文档或任务文档，基值会让所有更早的记录失去用途，三种存储后端都会删除它们。此类文档退役时，其全部记录也会删除。可回溯文档则保留所有记录，因为旧值必须仍可读取（spec §3\.5）。



这正是 `snapshotAsOf()` 能够工作的原因。在 `app.todos` 中，条目 6（写于 seq 3）时的值由基值 2 加增量 3 得到：`{"items":["write docs","fix build"]}`。对 `app.draft` 发起同样调用则失败，错误为 `Document 5 does not retain historical content`。

## 版本与迁移



要改变文档结构，请提高 `version` 并添加 `migrate()`。每条记录都存有其版本，每次读取都会将它与token的版本比较（spec §3\.6）：

|**存储的版本**|**发生什么**|
|---|---|
|与token版本相同|按存储原样使用该值|
|较旧，且token有 `migrate`|`migrate(value, storedVersion)` 返回当前结构|
|较旧，没有 `migrate`|抛出 `requires migration from version 1`|
|比token版本更新|抛出 `has newer version 2 than 1`|

> 来源：`src/documents.ts` 和 spec §3\.6。
> 
> 



采集记录将 `app.todos` 从字符串列表改成了对象列表：



版本 2 的token；来源：`test/capture-p4-documents.ts`

```TypeScript
const TodosNext = defineDoc<TodosV2>({
    kind: "app.todos", version: 2,
    scope: "conversation", history: "rewindable", fork: "asOf",
    initial: () => ({ items: [] }),
    migrate: (value, fromVersion) => {
        if (fromVersion != 1) throw new Error(`no migration from ${fromVersion}`);
        return { items: (value.items as string[]).map((text) => ({ text, done: false })) };
    },
});
```

> `kind`、`scope`、`history` 和 `fork` 均保持不变；改变的只有结构和版本。采集代码中的 `checkpointWhen` 行已省略。
> 
> 



迁移在使用文档时发生，绝不会批量执行。通过新token调用 `snapshot()`，会返回迁移后的值，但不写入任何内容。第一次通过新token写入时，会存储版本 2 的基值（seq 8）。此后，旧的版本 1 token会因 `has newer version 2 than 1` 而失败，因此代码一旦回滚到这次写入之前的版本，就无法再打开该文档。旧的版本 1 记录仍然保留，通过新token调用 `snapshotAsOf()` 时，会即时迁移这些记录。

每个副本都是全新且独立的文档，具有新的 ID 和一个基值（spec §3\.7）。复制由存储自行完成；远程后端会在服务端完成复制。副本保留已存储的版本，子对话在自己首次使用时再迁移。复制的是已提交值，因此有一条限制：执行分叉的提交不能同时修改父对话采用 `current` 策略的文档，否则会失败并报错 `Cannot fork conversation 2 while changing its current-policy documents`。请先提交父对话的变更（`src/session/transaction.ts`）。

>

> 
> - 通过新版本和 `migrate()` 改变文档结构。永远不要重命名它的 `kind`：新名称查不到旧文档，会在旧文档旁创建一个空文档。重命名需要显式复制并退役旧文档（spec §12）
> 
> - 只有需要旧值时才选择 `rewindable`。它永远不会释放空间
>

# 内置文档

---

> 五个对话文档保存 Harness 在提交之间需要的信息：智能体是什么、提供商识别到的是谁、什么正在运行、什么正在等待，以及花了多少。
> 
> 

Harness 与你一样，以文档存储自身状态。UI 读取这些文档来显示加载指示、队列或账单。本节结束后，你就能读懂任何对话视图的 `docs` 块，并说明各部分由什么写入。



这五个文档使用与你相同的 `defineDoc()` 定义，并导出各自token：`AgentDoc`、`ProviderDoc`、`LiveDoc`、`InboxDoc` 和 `UsageDoc`（`src/index.ts`）。五者都属于一个对话，随对话创建，并以 `docs[kind]` 的形式出现在其视图中（对话视图，原书第129页）。你自己的文档不会挂载到那里；请用 `watchDoc()` 观察它们。



|**种类**|**保存的内容**|**历史 · 分叉**|**何时写入基值**|**参见**|

## 创建时与分叉时



每个新对话都在创建提交中获得这五个文档。其中四个总是以相同方式开始。只有 `pi.agent` 取决于对话的创建方式（spec §2\.2；`src/harness/agent.ts`，`createAgent`）：

## 各个文档



- `pi.agent`：为此对话选定的内容：模型、思考级别、扩展、工具、指令和工作目录。它只存名称，从不存代码（`src/harness/types.ts`，`AgentState`）。`configure()` 会更改它，工具结果也可以添加或移除工具。名称如何变成运行中的智能体，见每个对话的智能体（原书第106页）。

- `pi.provider`：`{ sessionId }`，即提供商看到的 ID，用于保持提示词缓存亲和性。重置、压缩、模型变更和重新打开都会保留它（spec §2\.2）。在 1\.0\.2 之前存储的对话，会在首次请求时获得一个 ID（`src/harness/provider.ts`；`CHANGELOG.md`）。

- `pi.live`：运行控制与进度。对话忙碌时 `run` 恰好存在；`generation`、`tools` 和 `compactions` 展示正在进行的工作（`src/harness/live.ts`）。

- `pi.inbox`：`{ items }`，按顺序保存等待下一个边界的输入和写入（`src/harness/inbox.ts`）。

- `pi.usage`：本对话的花费，以 `provider/modelId` 和工具名称为键。失败和中止的尝试也计入其中（spec §8\.6）。`Harness.usage()` 汇总所有对话的用量。

- `pi.live` 展示了一条好的检查点规则如何控制存储规模。每当没有内容正在运行时，它都会写入基值，因此编辑最多只累积一个工具轮次：工具运行时的 `pi.live` 记录；
