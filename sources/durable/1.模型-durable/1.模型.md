# 1\.模型

# Pi Durable 的用途

---

智能体进程可能在执行任意一条指令时终止；Pi Durable 将每个可见步骤都变成已存储的commit，因此轮次中途的终止只是暂停，不会造成丢失。



你的智能体正执行到部署工具的一半，笔记本电脑的盖子合上了。进程恢复之后，哪些工作已经完成？Pi Durable 会记录中断之前已知的状态。工具的重放策略决定是再次执行，还是报告该工具可能已经部分执行。本节介绍没有它时会发生什么问题、它采取的三项措施，以及它刻意不做的事情。

## 问题：一个轮次有四种状态



智能体进程会因很普通的原因终止：部署替换进程、内核因内存不足而将其终止，或者笔记本电脑进入睡眠。轮次中途的终止会截断四种正在变化的状态：

- 对话记录，即到目前为止的消息

- 模型调用，即流式传输到一半的响应

- 工具调用，即执行到一半的副作用

- 应用状态，例如工具正在更新的待办事项列表



它们各自存放在不同地方。崩溃之后，它们会彼此不一致，而且没有任何记录说明各自进行到了哪一步。Earendil 的公告明确了目标：让智能体能够经受崩溃、重新部署和服务中断，并恢复被打断的工作，而不是从头开始。见 `earendil.com/posts/pi-durable`。

## 原版 Pi 保留了什么



Pi 编码智能体已经会持久化其会话。会话是 `~/.pi/agent/sessions/` 下的一个 JSONL 文件。每行是一个带有 `type` 的 JSON 对象；第一行是会话头，其余都是通过 `id` 和 `parentId` 组成树的条目。见 `coding-agent docs/session-format.md`。这棵树让 Pi 支持原地分支：`/tree` 可以移动到较早的条目，而不抹掉你离开的分支。见 `coding-agent docs/sessions.md`。



智能体循环生成一行，就追加一行。用户消息、包含工具调用的助手消息、工具结果，各自都是一条消息行。见 `session-format.md §Entry Types`。循环会在提供商完成流式传输后记录响应，然后执行每个工具调用并记录结果。见 `coding-agent docs/how-pi-works.md §Agent loop`。



**这种设计保留了对话，却没有保留轮次。如果进程在工具运行时终止，文件就会结束于发起该工具调用的助手消息。没有任何一行说明工具已经启动，或者打印了什么。流式传输到一半的响应不会写入文件，扩展仅保存在内存中的状态也会消失。下一个进程可以重新读回对话，但无法判断工具的副作用是否已经发生。**



![image\.png](图片和附件/image%202.png)

> 工具执行中途发生崩溃后，原版 Pi 留下的文件以调用结束；Pi Durable 重新打开的则是一个被中断的任务。虚线左侧是 SIGKILL 之前写入的内容，右侧是下一个进程发现的内容。Pi Durable 的行记录来自 `research/capture/crash-*.txt` 中崩溃运行的对话 1，其中 `deploy` 已打印出 10 行中的 6 行。原版 Pi 的一行遵循 `session-format.md`。
> 
> 

## Pi Durable 的答案



**Pi Durable 是一个 harness：一个已打开的存储**，加上在其上运行智能体的机制。它采取三项措施，每项都弥补了上面的一处缺口：

- **所有可见内容都经过commit**：“对话、模型轮次、工具调用以及你自己的状态，都会在显示任何内容之前commit到存储。”见 `README`。流式传输到一半的回答和工具运行中的输出也会commit；进度commit之间默认至少间隔 100 ms。崩溃会丢失自上次成功commit以来的进度；存储延迟和输出节奏可能使这个间隔更长。见 `README §Watching a Conversation`。

- **工作以带检查点的任务形式执行**：模型调用和工具调用分别作为任务运行；任务是一个持久化状态机，在每个步骤都commit检查点。工具任务会在 `execute()` 运行之前，commit其意图、最终参数和重放策略。见 `src/harness/tool.ts`。重新打开时，harness 准确知道哪些调用已经开始。

- **应用状态以文档形式包含在同一次commit中**：文档是与对话记录一起存储的带类型 JSON。它与条目在同一次原子commit中变化，因此待办事项列表永远不会超前于修改它的消息。见 `README §Your Own State`。



崩溃运行展示了实际结果。第二个进程重新打开 SQLite 文件。仅仅打开这一步，就让运行中的工具任务回到了 `pending`。调用 `resume()` 后，未声明可安全重跑的 `deploy` 工具得到一个 `pi.tool-result` 条目，其中保留了其六行已commit输出，并附有一个错误：

```JSON
{
  "role": "toolResult",
  "toolCallId": "deploy-1",
  "toolName": "deploy",
  "content": [
    {
      "type": "text",
      "text": "deploy site: step 1/10 (pid 98319)\n...step 6/10 (pid 98319)\n"
    },
    {
      "type": "text",
      "text": "<harness>\n[error] Tool deploy was interrupted and may have partially run\n</harness>"
    }
  ],
  "isError": true,
  "timestamp": 1791211977057
}
```

> 这是条目 25 的模型消息。第一个文本块在这里有所删节，原本包含被终止进程的全部六行输出。条目的 `data.diagnostics` 带有同一个错误，其 `code` 为 `"interrupted"`。
> 
> 



模型随后读取该结果并作答，输入最终结算为 `done`。在同一次崩溃中，声明了 `replay: "safe"` 的 `fetch_report` 工具直接在新进程中从第1步重新运行。见 `research/capture/crash-README.md`。下一个进程没有猜测，而是读取一个说明“该副作用可能已经发生”的检查点，再应用预先选择的策略。副作用三明治（原书第70页）及工具调用与重放（原书第94页）会详细拆解这一过程。

## 它不是什么



其范围是刻意收窄的。从一开始就需要了解三个限制：

- **每个存储只由一个进程使用**：“同一时间，一个存储由一个进程拥有；没有跨进程锁。”见 `README §Storage`。Harness 不是集群调度器。监督和重启进程是宿主的工作。

- **没有多写入者合并**：规范将“CRDT／离线多写入者合并”列为非目标之一。见 `spec §13`。多个客户端可以观察和引导同一个对话，但每次写入都经过同一个 Harness。

- **不会回滚外部世界**：commit的原子性只限于存储内部。外部副作用“不会在 Session 变更事务内部运行”。见 `spec §1`，不变量 4。当harness无法知道支付是否成功时，它会明确报告这种不确定性，交由幂等键或远端记录来确定答案。见限制与非目标（原书第168页）。



> **这对你意味着什么：**
> 
> - 重新打开同一个存储，并恢复未完成的工作。安全工具可以再次运行；不安全工具会报告一个被中断的结果
> 
> - 逐个工具决定重复运行是否安全。这一个选择，就决定了调用被截断后的处理方式
> 
> - 将应用状态放在文档中，而非内存中，这样它永远不会与对话记录不一致
> 
> - 每个存储保持只有一个进程，并让进程监督程序负责重启
> 
>

# 一页看懂架构

---

**Harness 以 Session 为内核，上层提供对话、commit请求和任务调度器，下层连接一个存储，其余一切都由宿主接入。**



可以把这个软件包看作一个**分层栈**。**你的程序请求 Harness 执行工作，Harness 将每个请求转化为commit，一个存储负责保存这些commit。**本节介绍每一层的名称、各自拥有的状态，以及哪些内容仅存在于内存中、会在进程重启时重新构建。

## 四个层次



软件包由**四层叠成**。你的进程，也就是宿主，位于顶层并调用 Harness。Harness 将这些调用转化为一个 Session 上的commit。Session 将每次commit写入一个存储。扩展、模型和执行环境等代码虽然由harness运行，却不归它所有；宿主会在打开 Harness 时将这些代码传入。



![image\.png](图片和附件/image%204.png)

> 宿主驱动 Harness，Harness 通过一个 Session commit，Session 写入一个存储。右栏是 `HarnessOptions`；Chord 是软件包依赖，不是选项。依据 `src/harness/harness.ts` 和 `src/session/session.ts` 绘制。
> 
> 



- **Storage**：**存储记录和文档、并以原子方式commit一批写入的后端。**软件包自带三种。见 `README §Storage`；第9部分介绍存储契约（原书第141页）。

- **Session**：内核。它“**拥有一条变更串行队列、对话、条目、任务、commit请求和文档”**。见 `spec §1`。变更串行队列一次执行一个commit。Session 还为每个已加载文档保留一个跟踪器，并向观察者发布每次commit。见 `src/session/session.ts`。你可以通过 `createSession()` 单独使用它；示例 00 至 05 就是这样做的。

- **Harness**：在 Session 内核上“扩展了对话句柄和注册表”。见 `src/harness/harness.ts`。它增加了你所调用的句柄、commit请求处理机制、任务调度器和视图。

## Harness 内部



四个组件承担 Harness 的工作，各自位于 `src/harness/` 下独立的文件中。

|**组件**|**文件**|**拥有的内容**|
|---|---|---|
|对话句柄|`harness.ts`|无：句柄只是一个 ID 加一组方法；“通过 ID 比较句柄”，见 `README §Concepts`|
|commit请求|`submissions.ts`、`inbox.ts`|输入与写入的接纳、每个对话的收件箱，以及 `wait()` 背后的等待者|
|任务调度器|`scheduler.ts`|每个活动任务的内存镜像；对任务进行预留、运行和中止|
|视图|`view.ts`、`task-graph.ts`、`events.ts`|`viewState()`、`watch()`、任务图和智能体事件|



harness通过三个内置任务回答输入。`pi.generation` 准备提示词并调用模型。`pi.tool` 执行一次工具调用。`pi.compaction` 总结较早的上下文。见 `spec §8`。它们“不是扩展，不能被移除或替换”。见 `src/harness/registry.ts`。因此，始终使用 `createRegistry()` 构建注册表；`Harness.open()` 会拒绝缺少它们的注册表。

## 宿主接入哪些内容



`Harness.open(storage, options, context)` 通过 `HarnessOptions` 接收其他所有内容。见 `spec §2.2`。

|**选项**|**含义**|**详见**|
|---|---|---|
|`models`|pi\-ai 的 `Models` 接口；生成过程调用 `models.streamSimple()`|生成（原书第91页）|
|`registry`|已安装的扩展：工具、提示词区段、钩子、包装器和任务|注册表（原书第103页）|
|`settings`|每次使用时读取、从不存储的运行策略|设置与默认值（原书第180页）|
|`env`|为每次工具调用和提示词渲染构建 `ExecutionEnv`|环境（原书第155页）|
|`conversationCreated`|在每次创建或分叉对话的commit中运行|访问与创建（原书第53页）|
|`now`、`onReport`|时钟，以及接收harness所报告的非致命错误的接口|—|



有两个依赖不属于选项：`@earendil-works/pi-ai` 提供消息类型和 faux 提供商，`@earendil-works/chord` 提供文档状态。见 `package.json`。每个异步调用都接收一个 Chord `Context`；取消它会取消等待，绝不会取消工作。见 `README §Quick Start`。

## 一次调用如何穿过各层



沿着 `root.submit(input, context)` 向下走过整个分层栈，就能看到各层如何分工：

1. Conversation 句柄把输入交给 Submissions 组件。见 `src/harness/submissions.ts`

2. Submissions 进行一次commit。它追加用户条目、记录commit请求、创建第一个生成任务，并在该对话的 `pi.live` 文档中将其标记为忙碌

3. Session 把这次commit写入存储，之后才通知监听者。见 `src/session/session.ts`

4. 调度器是这些监听者之一。它看到新任务后，会领取任务以便运行。领取本身是另一次commit。见 `src/harness/scheduler.ts`

5. 任务在任何commit之外运行。它通过 `models` 调用模型，凡是想保留的结果，都会作为新的commit写回



没有哪一层会绕过另一层；调度器只从已发布的commit中获知新工作。一次输入得到回答的全过程（原书第19页）将用真实记录串起这条链路。

## 内存与存储



内存与存储的分工是理解整个软件包的关键。存储保存事实，内存保存一个始终可据此重建的工作集：

- **活动任务**：调度器“镜像每一条已commit的非终态任务记录”。见 `src/harness/scheduler.ts`。打开时，它加载所有这些任务，并在一次commit中，将已终止进程遗留的所有 `running` 任务改回 `pending`

- **已加载文档**：已读取文档的缓存。见 `src/session/session.ts`

- **等待者与观察订阅**：`wait()` 背后的 Promise，以及视图背后的订阅；下一个进程会重新创建它们



如果进程终止，上述列表中的任何内容都无关紧要：打开时会全部读回。“重新打开存储，即可从工作停止的地方继续。”见 `README`。

# 核心规则及其不变量

---

一句话定义了整个系统：将一切一起commit，绝不展示未commit的内容。八个不变量确保这句话成立。



**整个设计可以归结为一个理念：commit之前，什么都不算数。commit是一次原子保存：其中所有内容要么一起存储，要么全都不存储。如果屏幕上已经显示出来，崩溃就不能让它消失。**本节阐明这条规则，定义本书后续使用的术语，并解释使该规则成立的八项保证。

## 规则



规范在引入任何类型之前，就用两句话说明了完整设计：

> **核心规则**
> 
> **“Session 以原子方式commit不可变条目、完整任务记录，以及由 Chord 跟踪的文档。只有已commit的状态才是可观察的。”**
> 
> 



第一句说明commit包含什么：对话记录、任务记录和文档变更，作为一个整体写入。第二句说明其他内容都不可见。**屏幕、等待者、观察订阅以及调度器本身，读取的都是已commit状态，不存在旁路。**见规范前言。**可以把它理解为一扇门：每次变更都经过commit，每个观察者都位于门后。**



![image\.png](图片和附件/image%201.png)

> 每个可见变更都经过变更串行队列上的一次commit；副作用只有通过commit才能到达观察者。阶段名称遵循 `spec §4`：从回调到发布，全程持有该队列。
> 
> 

## 术语



规范在 §1 中一次性定义了所有名词。本书后续始终严格按以下含义使用它们。

|术语及定义|
|---|
|**Session（会话）**：拥有一条变更串行队列、对话、条目、任务、commit请求和文档|
|**Conversation（对话）**：一个对话记录作用域。它可以从另一个对话分叉|
|**Entry（条目）**：一条不可变的对话记录|
|**Task（任务）**：附属于一个对话的持久化状态机|
|**Document（文档）**：应用的 JSON 状态，与对话或任务一起保存|
|**Definition（定义）**：为文档命名，并设定其初始值和存储规则的 TypeScript 声明|
|**Source（源）**：已保存文档更新的只读流|
|**Turn（轮次）**：一次助手响应及其发起的工具调用|
|**Run（运行）**：从一个已接纳输入到最终答案之间的一系列轮次。运行处于活动状态时，对话为忙碌状态|

## 八个不变量



接着，`spec §1` 列出了八个“必需的不变量”。每个不变量都封堵了一种特定的故障。下表简要引用这些不变量，后面的段落解释各自带来的保障。

|**编号**|**不变量（SPEC §1）**|**缺少它会怎样**|
|---|---|---|
|1|一次commit在所有记录与文档写入之间具有原子性|工具调用已经存储，却没有相应任务|
|2|文档更新只在其存储commit成功后才会发布|屏幕显示出崩溃后会消失的状态|
|3|所有可见进度都是持久化的；不存在易失性发布路径|流式显示的文本，在重新打开后却从未存在|
|4|外部副作用不在变更事务内部运行|一个缓慢调用阻塞所有对话|
|5|条目和 ID 不可变，且绝不复用|引用指向错误的记录|
|6|回调结束时撤销草稿；值会被复制，且必须是严格 JSON|写入绕过commit|
|7|在操作结算与状态采纳期间始终持有队列；用户回调稍后在队列之外运行|在尚未采纳的状态之上构建下一次commit|
|8|不确定的存储失败会使已打开的 Session 发生致命故障|内存和磁盘悄然分歧|

### 1 · 记录与文档之间的原子性



一次commit对应一次 `Storage.commit(writes)` 调用，要么存储全部写入，要么一条也不存储。见 `src/session/session.ts`。在单轮捕获中，commit 6 写入包含工具调用的助手条目，将生成任务 9 移到 `waiting`，创建工具任务 12，并更新两个文档。如果拆成两次写入，两者之间的崩溃就会留下一个永远不会有任务去执行的工具调用。

### 2 和 3 · 存储之后才能发布



Session 只有在 `Storage.commit()` 返回且新修订已被采纳之后，才会发布commit。不变量 3 排除了另一条路径：没有commit，就没有任何显示内容的办法。因此，部分回答和工具输出也会commit，并由 `settings.progress` 进行节流。其中每次commit都是一次存储写入；这就是确保屏幕永远不会显示任何可能被崩溃夺走的内容所付出的代价。见 `src/harness/generation.ts`（`streamResponse`）。

### 4 · 副作用留在队列之外



“外部模型、进程、工具、网络和人工副作用都在其外部运行。”见 `spec §4`。一个 Harness 的所有对话共享一条变更串行队列，因此在commit内部等待模型调用，会阻塞其他所有commit，直到该调用返回。更糟的是，commit的内容会依赖一个无法撤销的副作用。工具任务展示了这一模式：commit意图，在队列之外运行 `execute()`，然后commit结果。见副作用三明治（原书第70页）。

### 5 · 条目不可变，ID 永不复用



所有记录类型共享同一个 ID 空间。在 SQLite 捕获中，对话 1、文档 2 到 6、条目 7、commit请求 8 和任务 9，都来自同一个计数器。见 `research/capture/sqlite-rows.txt`（`record_ids`）。记录通过 ID 互相指向：工具任务 12 的输入为 `{"assistant": 11, "callId": "call-1"}`，commit请求 8 的答案是条目 15。如果 ID 可以复用，或条目可以改写，这些指针的含义就会悄然改变。即便是一次故障commit已经领取的 ID，也仍然视为已使用。见 `research/capture/NOTES.md §6`。

### 6 · 草稿与其回调同时失效



在commit内部，`tx.doc()` 返回可变草稿。回调结束时，Session 会“同步准备或中止每个打开的变更”，随后撤销草稿。有一个测试在commit结束后仍保留草稿，并检查此时读取或写入它都会抛出异常。见 `test/session-documents.test.ts` 中的“revokes escaped drafts”测试。没有这项保障，一个游离引用就可能在任何commit之外修改文档，从而破坏规则。

### 7 · 队列覆盖存储与采纳阶段



队列会一直保持占用，直到存储操作结算且新修订被采纳。因此，下一次commit总是从上一次已存储的状态开始。commit观察者在队列上运行，但仅用于捕获不可变值。你的观察订阅回调和文档状态回调稍后才会在队列之外运行，因此缓慢的 UI 无法阻塞harness。见commit与变更串行队列（原书第29页）。

### 8 · 不确定的失败会使 Session 中毒



如果一次存储错误可能已经写入了一些内容，内存就无法知道磁盘究竟保存了什么。此时，Session 会拒绝之后的每次调用，并给出：“Session is poisoned by a failed commit after storage admission; reopen it”（Session 在存储接纳之后因commit失败而中毒；请重新打开它）。见 `src/session/session.ts`。只有 `StorageRejected` 保证完全没有写入，也只有它允许 Session 继续工作。准备阶段的失败，例如草稿含有非 JSON 值，发生在存储看到这批写入之前，因此会正常回滚。见commit失败时会怎样（原书第33页）。



> **这对你意味着什么：**
> 
> - 对任何设计都问一个问题：你展示或据以行动的状态，是否已经commit？如果没有，它就还不存在
> 
> - 将相关内容放在一次commit中修改，这样崩溃永远无法将它们拆开
> 
> - 绝不要在commit回调内部调用模型、工具或网络
> 
> - 如果存储失败且可能已经写入，请关闭并重新打开，不要重试
> 
> 

# 一次输入得到回答的全过程

---

> 一个问题、一次工具调用和一个答案，需要十七次commit；按顺序读完这些commit，也就读懂了整个harness。
> 
> 



用户提出“Count to 3\.”，模型调用 `count` 工具，然后给出回答。这一小段交互需要十七次commit。本节按顺序走过这些commit，让你能够阅读任何commit日志，说清楚每一行由谁写入、为什么写入，以及如果恰好在那一刻崩溃，会留下什么。

## 这次运行



README 的 Quick Start 是最小的宿主示例。它在存储之上打开一个 Harness，获取根对话，commit输入，然后等待答案：



**快速开始，节选** · `README.md §Quick Start`

```JavaScript
const harness = await Harness.open(
    new MemoryStorage(), { models, registry: createRegistry() }, context
);
const root = await harness.root(context, {
    agent: { model: { provider: "openai", modelId: "gpt-6-sol" } },
});

const submission = await root.submit(
    { type: "input", content: "What is the capital of France?" }, context);
const settled = await submission.wait(context);
// settled.answer 是作出回答的 pi.assistant 条目的 ID
await harness.close(context);
```

> 此处省略了导入、模型设置和读回答案的代码。输入变为 `done` 或 `unanswered` 时，`wait()` 即兑现。
> 
> 



捕获脚本在 SQLite 上执行相同步骤，因此每次commit都可以作为行记录读回。见 `research/capture/scripts/one-turn.ts`。faux 模型以 `{n: 3}` 调用 `count` 工具，然后回答“I counted 1, 2, 3\.”。工具通过 `api.output()` 打印三行，并返回 `{}`。一个 `subscribeCommits()` 监听者会记录每次commit。



下面两幅图展示这次运行。每个编号箭头都是一次commit，编号就是该commit在存储中的 `seq`。

### commit 1–2：先有对话，再有输入



**`root()`**** 在commit 1 中创建根对话。同一次commit还创建其五个内置文档，ID 为 2 到 6：****`pi.live`****、****`pi.inbox`****、****`pi.usage`****、****`pi.provider`**** 和 ****`pi.agent`****。**见 `src/harness/harness.ts`（`conversationCreated`）。智能体文档存储模型选择 `faux/faux-1`。打开 Harness 时也运行过一次commit，用于协调处理运行中的任务，但它没有任何写入。没有写入的commit会被丢弃，不占用序号。见 `src/session/session.ts`。



**`submit()`**** 是commit 2，也是让输入持久化的那次commit。对话当前空闲，所以接纳操作会在一次commit中做三件事。**见 `src/harness/submissions.ts`（`admitSubmission`）。**它追加一个 ****`pi.user`**** 条目 7，创建状态为 ****`placed`**** 且 ****`entry: 7`**** 的commit请求 8，并启动一次运行：创建生成任务 9，将 ****`pi.live.run`**** 设为 ****`{"taskId": 9, "inputs": [8]}`****。从此刻起，对话变为忙碌，因为“忙碌”的定义就是存在 ****`pi.live.run`****。**见运行控制（原书第88页）。**此次commit之后的崩溃，不会丢失用户输入的任何内容。以相同 ****`requestId`**** 重新commit，会返回commit请求 8，而不是创建新的commit请求。**

> commit 1–8 将输入从 `submit()` 推进到工具调用意图已持久化的状态。依据 `research/capture/sqlite-commits.txt`；文档操作来自 `research/capture/extra-p1/sqlite-commit-ops.txt`。

### commit 3–6：第一次生成



**commit 3 是调度器在工作。它将任务 9 从 ****`pending`**** 改写为 ****`running`****，以此预留任务，但不改变其检查点 ****`{phase: "prepare", attempt: 1}`****。**见调度器（原书第73页）。这次运行中的每个任务，都以这样的预留commit开始。



**`prepare`**** 阶段渲染系统提示词和工具列表，并将其作为 ****`pi.system`**** 条目 10 commit；其中包含 preamble 节和 ****`count`**** 工具。同一次commit，即commit 4，还将任务移到 ****`request`**** 阶段，并记录模型、思考级别和条目 10 这一截止点。****`request`**** 阶段首先commit ****`pi.live.generation = {attempt: 1}`****（commit 5），然后在队列之外调用 ****`models.streamSimple()`****。**faux 流在 100 ms 的节流窗口内就已结束，因此没有commit部分响应。较慢的流会在这里增加经过节流的部分响应commit。见生成（原书第91页）。



响应以 `toolUse` 为停止原因结束。commit 6 是本轮的转折点。它将响应写为 `pi.assistant` 条目 11，并将其用量计入 `pi.usage`。它创建归任务 9 所有的工具任务 12，在 `pi.live.tools` 中列出该调用，并将任务 9 改为等待 `[12]`，策略为 `allSettled`。见 `src/harness/generation.ts`（`startToolRound`）。如果在commit 6 之后崩溃，重新打开时调用已经记录，其任务为 `pending`，因此工具会运行。如果在此之前崩溃，重新打开时处于 `request` 阶段，模型调用会直接重新发起。

### commit 7–8：先有意图，再执行副作用



commit 7 预留任务 12。接着，它的 `call` 阶段从条目 11 读取调用，解析工具、验证参数，并运行所有 `beforeTool` 钩子。然后，在执行任何工具代码之前，它先commit意图，即commit 8：



**commit 8 之后的工具任务 12** · `research/capture/sqlite-rows-midrun.txt` · JSON（节选）

```JSON
{
  "id": 12,
  "kind": "pi.tool",
  ...
  "input": { "assistant": 11, "callId": "call-1" },
  "owner": 9,
  ...
  "state": {
    "status": "running",
    "checkpoint": {
      "phase": "execute",
      "arguments": { "n": 3 },
      "replay": "unsafe"
    }
  }
}
```

> 这是在 `execute()` 运行时，通过第二个连接读取的 tasks 行；省略了 `conversationId`、`version` 和两个布尔标志。`count` 没有声明 `replay`，因此存储的策略为 `"unsafe"`。
> 
> 



正是这条记录，使工具执行中途的崩溃能够恢复。只有恢复流程才会单独进入 `execute` 阶段。如果后续进程发现任务处于这个阶段，工具就可能已经运行；存储的 `replay` 决定是再次执行，还是写入被中断的错误结果。见 `src/harness/tool.ts`。1\.1 节（原书第10页）中的 `deploy` 正是这种情况。

### commit 9–11：先输出，再写入结果



工具输出作为进度commit，默认至少间隔 100 ms。commit 9 将 `pi.live.tools[0].output` 设为 `"1\n"`；commit 10 追加 `"2\n3\n"`。观察者看到输出逐渐增长；**若发生崩溃，只会丢失自上次成功的进度commit以来的输出。**这个间隔没有固定的时间上限。`execute()` 返回时，commit 11 追加 `pi.tool-result` 条目 13，内容为 `"1\n2\n3\n"`，并使任务 12 进入终态，结果为 `{status: "completed", result: {entryId: 13}}`。

> commit 9–17 承载工具输出、结果、第二次生成和答案。琥珀色箭头表示仅涉及任务的commit：预留，以及提示词未发生变化时移到 `request` 阶段的操作。

### commit 12–17：第二次生成与答案



任务 12 已进入终态，因此任务 9 的等待结束。commit 12 在 `tools` 阶段预留它。工具执行期间发送的排队写入和引导消息，会在这一阶段被放入对话。见收件箱（原书第84页）。然后，它交接这次运行：commit 13 创建生成任务 14，将 `pi.live.run.taskId` 移到 14，清除工具执行轮，并以 `completed` 状态结束任务 9，其结果为 `result: {entryId: 11}`。见 `src/harness/generation.ts`（`finishToolRound`）。



生成任务 14 重复第一次生成的各个阶段，只有一点不同。它的 `prepare` 阶段发现提示词与工具没有变化，因此不追加 `pi.system` 条目，commit 15 只将任务移到 `request` 阶段。系统条目是按位置记录的增量，只有发生变化时才会发送。见系统提示词（原书第115页）。commit 16 在 `pi.live` 中标记本次尝试，模型随后以停止原因 `stop` 作答。



commit 17 一次完成所有收尾工作。它将答案追加为 `pi.assistant` 条目 15，并把commit请求 8 结算为 `done`，设置 `answer: 15`。它使任务 14 进入终态，删除 `pi.live.run` 和 `pi.live.generation`，让对话再次空闲，并将第二个响应的词元数计入 `pi.usage`。Submissions 组件在commit发布时看到已结算的记录，随后兑现宿主的 `wait()`。
