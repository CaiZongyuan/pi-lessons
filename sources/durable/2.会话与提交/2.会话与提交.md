# 2\.会话与提交

# 记录与 ID

---

五种记录类型和一个编号空间，容纳了 Session 存储的一切；记录之间有两种看起来相似、含义却不同的关联。



**打开一个 Pi Durable 数据库，你只会发现五类记录，它们都从同一个计数器获取编号。**掌握这五种结构，以及一个对话指向另一个对话的两种方式，就能读懂任何存储转储。

## 四张表与文档



**Session 存储四类表记录，外加文档：“表包括 conversations、entries、tasks 和 submissions。”**见 `spec §4`。文档是应用的 JSON 状态，也有一条小型的自身记录。见文档（原书第53页）。每条记录都是一个普通 JSON 对象，在 `src/types.ts` 中声明为 TypeScript 类型。下图展示了全部五种记录，以及每个字段的用途。



![image\.png](图片和附件/image%203.png)

> 五种记录类型共享一个 ID 空间，它们的引用是带类型的 ID。字段名来自 `src/types.ts`；卡片标题中的数字是深入介绍各类型的章节号。
> 
> 



记录的变化方式有所不同：

- 对话和条目在创建它们的提交之后就不再变化。见不变量 5，以及不变量（原书第16页）

- 任务和提交请求是整条替换的。每次变化都在同一个 ID 下写入一条完整的新记录。见 `src/types.ts`（`TaskRecord`）

- 文档记录描述一个文档从创建到退役的全过程。其内容另行存储，形式为完整副本和 Chord 操作。见基值与增量（原书第56页）



- **ConversationRecord**：只有 `id`，以及可选的 `parent` 和 `owner`。对话的模型、设置和应用状态不在这条记录中。它们位于 `pi.agent` 等文档中。见内置文档（原书第60页）。

- **EntryRecord**：一个不可变的对话记录事件。它分别为模型（`model`）、应用（`data`）以及上下文控制（`head`、`edits`）设置独立字段。见条目（原书第37页）。

- **TaskRecord**：包含身份（`kind`、`version`、`input`）、所有权（`owner`、`background`）、持久化中止标记，以及一个状态联合类型。见作为状态机的任务（原书第63页）。

- **SubmissionRecord**：由 `type`（`input` 或 `write`）与 `status` 构成的联合类型。输入会经过 `queued`、`placed`、`done` 和 `unanswered` 状态。写入没有 `placed` 状态，只有输入才有 `answer`。见提交请求（原书第84页）。

- **DocumentRecord**：包含 `kind`、可选的文档族 `key`、`scope`，以及对话文档所用的 `history` 和 `fork` 策略。`createdAt` 和 `retiredAt` 是由存储盖章的提交序号。

## ID 是带类型标签的普通数字



每个记录 ID 都是一个普通的 JavaScript 数字。TypeScript 添加了一个称为品牌（brand）的标签，让你无法把 `EntryId` 传给要求 `TaskId` 的地方。品牌只存在于编译期：



**ID、Seq 与根对话** · `src/types.ts`

```TypeScript
export type ConversationId = Id<"conversation">;
export type EntryId = Id<"entry">;
export type TaskId<Result = unknown> = Id<"task", Result>;
export type SubmissionId = Id<"submission">;
export type DocumentId = Id<"document">;

/** 分配给一次原子存储提交的严格递增序号；允许存在间隙。 */
export type Seq = number & { readonly [seqBrand]: "sequence" };

/** 根对话始终使用这个保留 ID。 */
export const ROOT_CONVERSATION_ID = 1 as ConversationId;
```

> 此处省略了泛型 `Id` 类型和两个品牌符号的声明。`TaskId` 还携带其任务的结果类型，因此 `waitForTask()` 能返回带类型的结果。
> 
> 



“ID 和序号在内存、JSON、JSONL 和 SQLite 中始终都是普通数字。”见 `spec §2`。软件包没有导出给数字添加品牌的辅助函数。代码从 JSON、URL 或 UI 消息接收 ID 时，请自行使用 `as EntryId` 进行类型断言，并在该处检查它。

## 所有记录共用一个计数器



**对话、条目、任务、提交请求和文档，都从 Session 范围内的同一个计数器 ****`Storage.mintId()`**** 获取 ID。**见 `src/types.ts`。因此，**无论类型如何，任何两条记录都不会拥有相同编号。**SQLite 捕获运行直观展示了这一点：各类型按照提交需要它们的顺序交错出现。



![image\.png](图片和附件/image%202.png)

> **除根对话外，每条记录都从同一个计数器取得 ID；**提交则另行编号。ID 1 保留给根对话，因此提交 1 只分配五个文档 ID，即 2–6。每条线将一组 ID 连接到分配它们的提交；17 次提交中有十次没有分配任何 ID。虚线单元格是 `durable_metadata` 中的 `next_id` 和 `next_seq`。ID 和类型来自 `research/capture/sqlite-rows.txt` 的 `record_ids`，提交来自 `research/capture/sqlite-commits.txt`。
> 
> 



一个计数器带来三个事实：

- **ID 在不同对话之间为条目排序**：“条目 ID 在 Session 内全局有效且有序。”见 `spec §2.1`。分叉上限和上下文范围都通过条目 ID 比较来确定，即使条目属于不同对话也一样。见分叉（原书第43页）。

- **根对话 ID 是保留的，不是分配出来的**：`ROOT_CONVERSATION_ID` 为 1，`MemoryStorage` 从 2 开始分配。见 `src/storage/memory.ts`。因此，普通 Session 创建的第一个对话得到的是 ID 2（`run 00`）。Harness 通过 `root()` 按需创建对话 1。

- **回滚的提交也会消耗已分配的 ID**：ID 分配发生在回调内部，早于该批写入到达存储。创建记录的事务方法是异步的，“因为远程存储可能以持久化方式分配全局唯一的数字 ID”。见 `spec §3.3`。在捕获的失败运行中，三次回滚提交领取了 ID 3、4 和 5，下一个成功提交的条目则是 6。见 `research/capture/extra-p23/commit-failures.txt`。保证仅限于：ID“在已提交的写入之后绝不复用”（不变量 5）。



`Seq` 是第二个计数器。它为提交编号，而不是为记录编号：存储会为每个已提交批次分配一个序号，且“在提交之间严格递增；允许存在间隙”。见 `spec §2`。两个计数器推进的速度不同。在捕获中，17 次提交分配了 14 个 ID（2–15）；其中十次提交根本没有分配 ID，只改变了任务状态或 `pi.live`。你会在文档的 `createdAt` 和 `retiredAt`、每次提交发布，以及每条已存储条目上遇到 `Seq`。在条目上，它让文档能够按该条目时刻的状态读取。见可回溯历史（原书第56页）。

## 两种关联：parent 与 owner



`ConversationRecord` 有两种形状相同的可选关联。两者都指向一个对话，但含义不同。“对话的历史父子关系与任务所有权彼此分离。”见 `spec §2`：

|**项目**|**PARENT**|**OWNER**|
|---|---|---|
|结构|`{ conversationId, at: EntryId }`|`{ conversationId, taskId: TaskId }`|
|设置来源|在条目 `at` 处分叉|使用 `{ kind: "task", taskId }` 所有权创建|
|控制内容|继承的条目与历史文档|归因、子树中止、空闲遍历|
|调用者提供|父对话与条目|只提供任务 ID；Session 推导出对话|
|任务结束之后|—|仍保留在记录中|

> 依据 `spec §2` 和 `src/types.ts` 中的字段注释。
> 
> 



**`owner`**** 关联“不是访问控制能力”。**见 `spec §2`；它记录谁创建了这个对话。**创建时始终要声明所有权，要么是 ****`{ kind: "ownerless" }`****，要么是 ****`{ kind: "task", taskId }`****，Session 会自行填入任务所属的对话。分叉可以同时带有这两种关联：它从一个对话继承历史，同时归另一个对话中的某个任务所有。**



记录还有三种使用相同 ID 的关联。任务的 `owner` 是一个 `TaskId`，由此构成任务树。见所有权与结构化并发（原书第76页）。条目的 `byTaskId` 指出通过提交追加它的任务。提交请求的 `entry` 和 `answer` 分别指出它放入的用户条目，以及回答它的助手条目。捕获中的提交请求 8 最终变为 `{ status: "done", entry: 7, answer: 15 }`。见 `research/capture/sqlite-rows.txt`。



> **这对你意味着什么：**
> 
> - ID 在所有记录类型之间唯一，但数字本身不能说明记录属于哪种类型。将类型与 ID 一起保留，让品牌类型帮助发现混用
> 
> - 预期会有间隙。失败的提交会消耗它已分配的 ID，这是正常现象
> 
> - 用 `parent` 回答“这段历史来自哪里”，用 `owner` 回答“哪个任务创建了它”
> 
> 

# 提交与变更串行队列

---

> 每次写入都经过一个串行化回调；其中的所有写入要么一起存储，要么全部不存储。在存储确认成功之前，观察者看不到任何变化。
> 
> 

**Session 的每个变更都经过 ****`commit()`****。提交是一次原子保存：其中所有内容要么一起存储，要么全都不存储。提交在称为变更串行队列的队列中逐个运行。**本节介绍你能在提交内部做什么，以及程序的其他部分何时能够看到变化。

## 唯一的写入方式



**`session.commit(change, context)`**** 是唯一的写入路径。你的回调收到一个事务 ****`tx`****。回调返回时，它所写的一切会作为一个批次存储；若回调抛出异常，则全部丢弃。**见 `ex 00`。“**一次 Session 提交在所有记录与文档写入之间具有原子性。**”见不变量 1，`spec §1`。**`Conversation.commit()`**** 将它绑定到一个对话；任务的 ****`runtime.commit()`**** 还会在所追加的每个条目上标记该任务的 ID。**



**一次读取、追加条目、编辑文档并创建任务的提交** · `docs/spec.md §4`

```TypeScript
await session.commit(async tx => {
    const conversation = await tx.conversation(conversationId); // 表读取
    const live = await tx.doc(LiveDoc, conversationId);

    await tx.appendEntry(conversationId, message); // 第一次表写入
    delete live.generation; // 文档变更仍然有效
    await tx.createTask(Follow, {}, {
        ownership: { kind: "conversation" }, conversationId,
    }); // 继续进行表写入没有问题
}, context);
```

> 读取排在最前面，因为它必须如此；首次写入之后，文档草稿仍然可用。
> 
> 

## 变更串行队列



**变更串行队列一次运行一个提交。一个提交从回调开始的那一刻起就占据队列，直到存储已经保存该批写入且观察者已被通知**：“覆盖回调执行、准备、存储结算、已提交基线采纳以及发布入队”。见 `spec §4`。在此期间，其他提交都不会开始。下图展示一次提交如何经过这些阶段。

### 步骤 1–5：你的回调内部



如果 Session 正在关闭或已经中毒，`commit()` 会立即拒绝。否则，回调会拿到一个全新的事务并开始运行；其操作分为三组，见下表。



**需要牢记的规则是先读后写。“第一次表写入之后的任何表读取都会抛出 ****`ReadAfterWrite`****。”**见 `spec §4`。错误消息可能是 `Tx.conversation() cannot read tables after the first table write`。表读取直接访问存储，而存储尚未看到当前事务的写入，因此写后读可能与这些写入相矛盾。你永远不需要这样读：创建方法会返回自己创建的记录。



|**分组**|**操作**|**规则**|
|---|---|---|
|表读取|`conversation`、`entry`、`task`、`scanConversations`、`scanEntries`、`latestHeadMarker`、`scanTasks`、`submissionByRequest`|只能在第一次表写入之前进行|
|表写入|`createConversation`、`forkConversation`、`appendEntry`、`createTask`、`createSubmission`、`settleSubmission`、`placeSubmission`|返回创建的记录或 ID|
|文档|`doc`（获取或创建）、`retireDoc`|表写入前后都可使用|

> 接口来自 `src/types.ts` 中的 `Tx`；规则来自 `spec §4`。
> 
> 



![image\.png](图片和附件/image.png)

> 从接纳开始直到发布入队，始终持有队列；回调在之后运行。水蓝色条表示被持有的队列。依据 `src/session/session.ts` 和 `src/session/transaction.ts` 绘制。
> 
> 



文档的工作方式不同。`tx.doc()` 返回一个草稿，即可像普通对象一样编辑的可变副本，并且能看到你自己的修改。你赋入的值“按值复制，且必须是严格 JSON”；`undefined` 或 `Date` 会让提交在存储任何内容之前失败。见 `spec §1`（不变量 6）；`test/session-documents.test.ts`。回调结束时，每个草稿都会被撤销。保留到回调之后的草稿，在下一次使用时会抛出异常；迟到的 `tx` 方法调用则会以 `Transaction has settled` 拒绝。

### 步骤 5 与 6 之间：检查批次



回调返回后，Session 将其工作汇成一个批次并进行检查。首先会捕获忘记 `await` 的情况：如果仍有待完成的 `tx` 调用，提交就会失败，错误为 `Session commit callback settled before its pending Tx operations`。随后，草稿转化为最终值，批次接受验证，例如检查每个所有者任务是否存在且仍处于活动状态。这里的任何失败都会回滚整个提交。见提交失败时会怎样（原书第33页）。没有写入的批次永远不会到达存储：既不存储，也不发布。

### 步骤 6–8：先存储，再通知其他各方



`Storage.commit(writes)` 以原子方式保存该批写入，并返回其 `Seq`。提交一旦开始，取消你的 `context` 就不再能停止它：“调用者取消不会中断存储结算，也不会撤销提交。”见 `spec §4`。存储成功之后，Session 换入新的文档值，并构造一个发布对象 `{ seq, changes }`。仍在队列上时，它把该对象交给每个 `subscribeCommits()` 监听者。下面是模型请求调用工具的那一轮中的一次发布：



**提交观察者看到的提交 seq 6** · `research/capture/sqlite-commits.txt`

```Plain Text
commit seq=6
    entry 11 kind=pi.assistant byTask=9
    task 9 pi.generation status=waiting phase=tools on=[12] policy=allSettled
    task 12 pi.tool status=pending phase=call
    document pi.live (2) 2 op(s)
    document pi.usage (4) 1 op(s)
```

> 每行对应一项变更，由捕获脚本概括。助手条目、父任务的等待、新工具任务以及两个文档变更，要么一起变得可见，要么全部不可见。
> 
> 



提交观察者在队列上运行，“仅用于捕获不可变状态”（不变量 7）。它们“不得抛出异常、阻塞或调用 Session API”。见 `spec §4`。你的观察订阅回调和文档状态回调稍后会在队列之外运行，见 Chord 与文档状态（原书第125页），因此缓慢的屏幕永远不会阻碍下一次提交。

## 绝不要在提交内部等待副作用



“外部模型、进程、工具、网络和人工副作用都在其外部运行。”见 `spec §4`。违反这条规则会付出双重代价：

- **队列停滞**：当回调等待网络调用时，其他所有提交都会排在后面等待，包括工具进度、其他对话和调度器的提交。

- **记录失真**：如果进程在副作用发生之后、批次存储之前终止，副作用已经发生，却没有任何记录。如果回调在副作用之后抛出异常，批次会回滚，而副作用仍然没有记录。



修正方式是先提交意图，再在任何提交之外执行副作用，然后提交结果：这就是副作用三明治（原书第70页）。所有内置工具任务和生成任务都按这种方式工作。



> **发后即忘**
> 
> 在回调内部启动后放任继续运行的工作，仍然可能修改尚未结束的事务；事务一旦结算，这些工作就会失败。规范明确不支持这种做法。见 `spec §12`。等待每个 `tx` 调用，并且只在 `commit()` 兑现之后才启动后台工作。
> 
> 



> **这对你意味着什么：**
> 
> - 先完成所有表读取，再进行写入。文档可以在任意时刻读取和修改
> 
> - 等待每个 `tx` 调用，保持回调简短，并且不包含 I/O
> 
> - 草稿中只能放 JSON，绝不要在回调结束后保留草稿
> 
> - 在观察订阅中响应变化，不要在提交观察者中响应
> 
> 

### 细节



即便只有一条队列，读取仍然成本低廉。对于已缓存其已提交值的文档，读取不必排队。见 `src/session/session.ts`（`snapshot`）。存储只在 `Storage.commit()` 结算之前借用批次，并且“每次存储读取都返回一个独立的 JSON 值”。见 `spec §4`。因此，你持有的任何对象都不会与已存储状态共享引用。批次检查会验证分叉来源、所有者和任务替换，退役在本次提交中结束的任务所拥有的文档，最后运行每个文档的 `checkpointWhen` 谓词，决定写入完整副本还是增量。见基值与增量（原书第56页）；`src/session/transaction.ts`。



> 来源：`spec §1`（不变量 1、4、6、7）、§2\.2、§3\.3、§4、§12；`src/session/session.ts`（`commit`、发布、`snapshot`）；`src/session/transaction.ts`（Tx 操作、结算、批次组装、采纳）；`src/errors.ts`（`ReadAfterWrite`）；`src/types.ts`（`Tx`、`StorageWrite`、`CommitPublication`、`Storage.commit`）；`ex 00`；`research/capture/sqlite-commits.txt`；`research/capture/extra-p23/commit-failures.txt`

# 提交失败时会怎样

---

> 失败发生的位置决定其结果：在存储之前，是普通回滚；在存储内部，则要么是保证无写入的拒绝，要么是致命的不确定性。
> 
> 

**大多数失败的提交都无害：没有存储任何内容，你可以继续工作。但有一种失败并非如此。如果存储失败时有可能已经保存了该批写入，Session 就会停止接收工作，直到你关闭它并重新打开存储。**本节介绍如何区分这些情况，以及分别应当如何处理。

## 三种结果



提交可能在五个位置失败，而每种失败最终都会落入三种结果之一：回滚、被存储拒绝或中毒。不变量 8 明确了这一区分：“不确定的存储失败会使已打开的 Session 发生致命故障。它不会发布任何内容，且必须重新打开。准备和检查点失败发生在存储接纳之前，会正常回滚。”见 `spec §1`。



![image\.png](图片和附件/image%201.png)

> Storage 接纳之前的失败会回滚；Storage 结果不确定，或 Storage 已提交之后的采纳失败，都会使 Session 中毒。底部一行说明了各情况下接下来该做什么。分支依据 `src/session/session.ts` 和 `src/session/transaction.ts`。
> 
> 



捕获的失败运行在一个普通 Session 上展示了每种结果；其底层是 `MemoryStorage`，可以人为使其下一次提交失败：

```Bash
$ node --conditions=source --experimental-strip-types test/capture-p23-context.ts
read after write -> ReadAfterWrite: Tx.conversation() cannot read tables after the first table write
callback throws -> Error: validation failed
empty commit -> ok "nothing written"
storage rejects -> StorageRejected: rejected before any durable effect
next commit -> ok {"kind":"app.note","data":"after rejection","id":6,"conversationId":2}
uncertain storage failure -> Error: disk vanished
next commit -> Error: Session is poisoned by a failed commit after storage admission;
reopen it (cause: Error: disk vanished)
snapshot -> Error: Session is poisoned by a failed commit after storage admission; ...

```

## 存储之前：普通回滚



五个失败位置中有三个发生在存储之前：回调本身、settle（仍有待完成的 `tx` 调用）和 prepare（批次检查）。其中任何一步失败，都会丢弃所有变更，并重新抛出原始错误。见 `src/session/transaction.ts`。这包括你自己抛出的异常、`ReadAfterWrite`、草稿中的非 JSON 值，以及指向不存在的对话或任务的引用（`Conversation N does not exist`）。



回滚是完整的。没有任何内容被存储，也没有任何内容被发布，每个文档都保留原先的值。有一个测试让修改了两个文档的提交失败；之后读取两个文档，结果都与之前相同，而下一次提交正常工作。见 `test/session-documents.test.ts`。唯一留下的痕迹是 ID 序列中的间隙。见记录与 ID（原书第25页）。



在任务内部，回滚的提交通常会结束该任务。如果阶段处理函数让错误向外传播，任务就以 `faulted` 结束。见阶段、步骤与进度（原书第67页）。在一个捕获场景中，某个任务试图在结束自身的同一次提交中创建归自己所有的工作；批次检查以 `Task owner 12 is completing` 拒绝它，随后任务以 `faulted` 结束，该提交没有存储任何内容。见 `research/capture/NOTES.md`（笔记 6）。

## 存储内部：拒绝或不确定



批次一旦交给 `Storage.commit()`，Session 就不能再作任何假设。存储契约定义了唯一安全的例外：“StorageRejected 表示一个批次在产生任何持久化效果之前就已被拒绝，保证没有提交。Session 会正常回滚这样的批次；Storage 接纳之后的未知失败仍然是致命的，因为其提交状态不确定。”见 `spec §10`。后端只在能够证明失败没有产生任何效果时才使用它。例如，SQLite 会将失败的分叉复制报告为 `Document copy N was rejected`。见 `src/storage/sqlite/storage.ts`。



任何其他存储错误都会使 Session 中毒：它把自身标记为不可用。存储刚刚成功之后，Session 在换入新值时发生失败，也会导致同样的结果，因为这时存储已经持有一次提交，而内存尚未反映它。见 `src/session/session.ts`。



中毒的 Session 会拒绝一切依赖其状态的操作。之后的每次提交、`snapshot()`、`state`、`watch` 和队列读取，都会抛出 `Session is poisoned by a failed commit after storage admission; reopen it`，并将原始错误作为 `cause`。见 `src/session/session.ts`。失败批次中的任何内容都不会发布，因此没有观察者会看到一个可能并不存在的值。见 `test/session-documents.test.ts`。



Session 不会重试，因为两种猜测都不安全。如果批次已经提交，内存就落后于存储；如果没有提交，在内存中应用它就会发布一个并不存在的变更。只有存储知道事实，而新的 Session 会准确读取它实际保存的内容。“不要捕获错误后继续使用它。”见 `spec §12`。JSONL 存储在一次不确定的追加之后，也会使自身中毒。见 JSONL（原书第148页）。



|**错误**|**抛出时机**|**此后 Session 的状态**|
|---|---|---|
|`ReadAfterWrite`|表写入之后进行表读取|可用|
|`...settled before its pending Tx operations`|回调过早返回|可用|
|`Transaction has settled`|结算之后使用 Tx 或草稿|可用|
|`StorageRejected`|存储中，在任何持久化效果之前|可用|
|其他任何存储错误|存储中，结果未知|中毒|
|采纳错误|存储已经提交之后|中毒|
|`Session is closed`|`close()` 开始后的任何调用|关闭中|

> 消息来自 `src/errors.ts`、`src/session/session.ts` 和 `src/session/transaction.ts`。第三个导出的错误类 `ConversationBusy` 是一种接纳结果，不是提交失败。见提交请求（原书第84页）。

## 先关闭，再重新打开



恢复从 `close()` 开始；即便 Session 已中毒，它也能工作。它按固定顺序运行。见 `spec §2.2`：

1. **封闭接纳**：立即关闭接纳入口。新的提交和读取以 `Session is closed` 拒绝；Harness 还会拒绝新的对话操作和提交请求操作

2. **通知**：同步运行 `subscribeClose()` 监听者。Harness 在这里停止观察订阅，并向任务调用发出信号；每个文档状态和观察订阅都保留最后一个值

3. **等待汇合**：Harness 等待任务、工具和钩子调用返回，“包括忽略自身信号的代码”。见调度器（原书第73页）

4. **结算**：封闭接纳之前已获接纳的提交，会在队列上完成。随后队列清除监听者和缓存，并关闭存储



“关闭不会写入任何任务结果。”见 `spec §2.2`。运行中的任务在存储中仍保持 `running`，与进程终止完全一样。`close()` 兑现之后，“新的 Harness 可以打开同一个 Storage”。



重新打开，就是对同一个存储执行普通的 `Harness.open()`。它只会发现已经提交的内容，并将遗留下来的 `running` 任务改回 `pending`。见调度器（原书第73页）。请获取新句柄；旧句柄已经失效。如果某个任务在意图提交后被重新打开，它可能已经执行过副作用；这正是副作用三明治（原书第70页）处理的情形。



> **如果进程终止**
> 
> 在 `Storage.commit()` 内部发生崩溃，就是一种不确定情形，只不过已经没有进程可以被标记为中毒。SQLite 将每次提交存储在一个 SQL 事务中；JSONL 则只在其侧文件写好之后才发布提交标记。无论哪种方式，重新打开时，该批写入要么完整存在，要么完全不存在。见 SQLite（原书第144页）、JSONL（原书第148页）。
> 
> 



> **这对你意味着什么**
> 
> - 除非 Session 已经中毒，否则应将抛出异常的提交视为“什么也没发生”
> 
> - 绝不要捕获中毒错误后继续工作。关闭 Harness，然后重新打开存储
> 
> - 如果你编写存储后端，只有在能够证明没有存储任何内容时，才抛出 `StorageRejected`
