# 9\.存储与环境

# 存储契约

---

> 存储以全有或全无的方式保存每次提交，并响应查找和分页扫描；其他所有规则都由 Session 负责。
> 
> 

**Session 提交的所有内容最终都会进入存储：SQLite 文件、文本文件目录或内存。提交是一次原子保存：其中的全部内容一起存入，或者全部不存。存储必须为每次提交保持这种性质，并响应精确查找和分页扫描。**这几乎就是 Pi Durable 对存储的全部要求。读完本节，你就能说明存储承诺什么、哪些规则实际归 Session 负责，以及提交失败时该怎么做。

## 小接口，职责窄



任何实现 src/types\.ts 中 Storage 接口的对象都可以成为后端。**包内提供三种：SqliteStorage、JsonlStorage 和 MemoryStorage**（SQLite，原书第144页；JSONL，原书第148页；内存，原书第152页）。你选定一种，交给 Harness。此后只有 Session 会调用它，所有写入都通过提交进行（提交与变更串行队列，原书第29页）。



这种分工是有意设计的。Session 检查语义：记录是否合法、引用、祖先关系以及任务状态转换。存储只检查它能独立检查的内容：批次是否原子、ID 是否唯一、不可变记录是否仍然不可变，以及返回的是否是副本，见 src/types\.ts。存储从不接触文档定义；它原样存储文档编辑，只在响应读取时重放这些编辑。Session 已经让提交一次一个地运行，因此后端不需要自己的锁，见 spec §10。

## 唯一的写入操作：commit



commit\(writes, context\) 原子地存储一批写入，并返回其 Seq，即本次提交的序列号。序列号“严格递增，但可以有间隔”；commit\(\) 一旦完成，之后的每次读取都能看到这批数据，见 spec §10。存储会把序列号标记在它保留的内容上。正因如此，之后才能按某个给定条目写入时的状态读取文档（基值、增量与迁移，原书第56页）。



|**写入类型**|**携带内容**|**存储保留的内容**|
|---|---|---|
|conversation|value: ConversationRecord|一条新的不可变记录|
|entry|value: EntryRecord|一条新的不可变记录及其提交序列号|
|task|value: TaskRecord|完整记录，替换前一条记录|
|submission|value: SubmissionRecord|完整记录，替换前一条记录|
|document\.create|record, content（一个基值）|一个新实例世代，标记 createdAt|
|document\.copy|record, source: \{ id, at \}|一个从来源的已提交值开始的新实例世代|
|document\.change|id, content（基值或增量）|另一个修订版|
|document\.retire|id|该实例世代，标记 retiredAt|

> 来源：src/types\.ts 中的 StorageWrite 联合类型。基值是文档的完整值；增量是在上一修订版之上应用的一批 Chord 操作。
> 
> 

## 提交失败时



只有一种失败是安全的。StorageRejected“表示批次在产生任何持久化效果之前就被拒绝，并保证没有提交”。Session 会回滚并继续运行。commit\(\) 抛出的其他任何错误都会使 Session 中毒：它再也无法知道这批数据是否已经存入，因此拒绝后续提交，见 spec §10。中毒对宿主意味着什么，见“提交失败时”（原书第33页）。

## 读取：按键查找与分页扫描



按键查找返回一条记录，或 undefined。扫描返回一页 \{ items, next? \}；把 next 传回去即可取得下一页。游标是不透明的：只能把它传回同一个存储的同一种扫描，见 spec §10。Harness 每页读取256项，它的每次读取背后都有索引支持，见 spec §10。



|**方法**|**返回内容**|**说明**|
|---|---|---|
|conversation\(id\)|record|精确 ID|
|entry\(id\)|\{ entry, commitSeq \}|任意条目|
|entry\(conversationId, id\)|\{ entry, commitSeq \}|仅当该对话可以看到此条目时返回|
|findLatestHeadMarker\(conversationId, at?\)|entry|at 时刻或之前最新的头指针标记|
|task\(id\), submission\(id\)|record|最新的完整记录|
|submissionByRequest\(conversationId, requestId\)|record|宿主去重（提交请求，原书第84页）|
|findDocument\(address, at\)|DocumentRecord|某个地址上存活的是哪个实例世代|
|document\(id, at\)|StoredProcedure〔原文如此，疑为提取错误，返回类型名待核〕|值及其版本，已重放增量|
|scanConversations\(query\)|page|按所有者筛选；ID 升序|
|scanEntries\(query\)|page|一个 ID 范围，最新的在前，遍历分叉祖先|
|scanTasks\(query\)|page|按 conversation、kind、status、中止标记、background 筛选|
|scanSubmissions\(query\)|page|按 conversation、status 筛选；ID 升序|
|scanDocuments\(query\)|page|一个作用域，可选 kind；ID 升序|
|close\(\)|\-|释放资源；后续每次调用都会失败|

> 每个方法还都接受最后一个参数 context。来源：src/types\.ts 和 spec §10。
> 
> 



document\(id, at\) 是唯一会做计算的读取。它找到该时点或之前最新的基值，依次应用之后的增量，再返回值。在 "current" 时点，已退役的实例世代返回 undefined。请求一个不保留历史的文档的旧时点会失败，而不会猜测（定义文档，原书第50页）。



**这对你意味着什么：**

- 你很少需要直接调用存储。选择一个后端，打开它，再传给 Harness。

- 除 StorageRejected 外，任何提交错误都会使 Session 中毒。关闭它并重新打开存储；重新打开后的状态才是事实。

- 在编写后端吗？请通过一致性测试套件（9\.4节，原书第152页）。

## 后端作者需要了解的细节



所有记录共享 mintId\(\) 提供的同一个 ID 空间；ID 1 是根对话。对于每个文档实例世代，一个批次至多包含一次创建或变更，以及可选的一次退役；版本变化必须使用基值，见 spec §10。commit\(\) 落定后，不得保留参数中的任何内容，并且要返回与内部数据脱离的值，见 spec §4。

# SQLite

---

> 一个 SQL 事务对应一次提交；每条记录都以完整 JSON 保存，旁边只有查询所需的少量列。
> 
> 

SQLite 把整个 Session 保存在一个文件中。对于必须经受重启而保留的内容，它就是应选的后端。读完本节，你就能打开数据库、用普通 SQLite 客户端找到任意记录、预测崩溃或断电的代价，并在 Node 之外运行同一个后端。

## 打开文件



来自 @earendil\-works/pi\-durable/storage/sqlite/node 的 openNodeSqliteStorage\(path, options\) 会创建父目录，并使用 Node 内置的 node:sqlite 打开文件。它启用预写日志（journal\_mode = WAL，synchronous = NORMAL），并应用所有待执行的模式迁移，见 src/storage/sqlite/node\.ts。

|**选项**|**默认值**|**效果**|
|---|---|---|
|walAutoCheckpointPages|1,000|WAL 自动检查点阈值，以页为单位；0 表示禁用|
|busyTimeoutMs|5,000|等待另一个连接所持锁的时长（SQLite 自身默认值为0）|

> 来源：NodeSqliteStorageOptions，src/storage/sqlite/node\.ts。
> 
> 



这些设置决定哪些内容能在故障后保留。“WAL 模式配合 synchronous = NORMAL：提交可以经受进程崩溃；最新的提交可能因断电或宿主机故障而丢失”，见 README §Storage。一个 SQL 事务对应一次提交，因此进程在提交中途终止，只会留下完整提交或完全不留下，见 spec §11\.2。close\(\) 会把预写日志合并回文件。关闭之后，捕获中只剩一个 session\.sqlite，没有 WAL 文件，见 research/capture/extra\-p9/sqlite\-revisions\.txt。

## 九张表



每张记录表都有相同的形态：少量用于查询过滤的列，以及一个以 JSON 保存完整记录的 record 列。读取只选择 record 并解析它。其他列都是在同一条语句中从记录复制写入的，因此 JSON 始终是真实依据。

tasks 表及其索引，来源：research/capture/sqlite\-schema\.sql：

```SQL
CREATE TABLE tasks (
    id INTEGER PRIMARY KEY,
    conversation_id INTEGER NOT NULL,
    kind TEXT NOT NULL,
    status TEXT NOT NULL CHECK (status IN ('pending', 'running', 'waiting', 'completing', 'terminal')),
    abort_requested INTEGER NOT NULL CHECK (abort_requested IN (0, 1)),
    background INTEGER NOT NULL CHECK (background IN (0, 1)),
    record TEXT NOT NULL CHECK (json_valid(record))
) STRICT;

CREATE INDEX tasks_by_status ON tasks (status, id);
CREATE INDEX tasks_by_conversation ON tasks (conversation_id, id);
```



这里省略了另外三个分别针对 kind、abort\_requested 和 background 的索引。每个索引都以 id 结尾，因此扫描按 ID 顺序分页。



对话和条目从不改变，因此只使用普通插入，对同一 ID 的第二次写入会失败。任务和提交请求则原地替换：“存活任务的状态转换会替换一行。终态任务作为小型记录保留”，见 spec §11\.2。运行期间的捕获显示，生成任务9正在等待工具任务12，而后者正在运行。运行结束后，两行都变为 terminal，并且只保留一个结果，见 research/capture/sqlite\-rows\-midrun\.txt、sqlite\-rows\.txt。

## 手工读取文件



被索引的字符串以 JSON 编码形式保存：任务的 kind 列读出来是 `"\"pi.generation\""`。这能让特殊 Unicode 字符在不同 SQLite 绑定之间保持无损，见 src/storage/sqlite/storage\.ts。



durable\_metadata\.next\_id 的类型是 TEXT（"16"），因为 node:sqlite 会拒绝超出 JavaScript 安全范围的整数。



record\_ids 为每个已提交 ID 保存一行，连同其记录类型。正是它让 ID 空间保持全局统一。

## 一次提交，一个事务



SqliteStorage\.commit\(\) 先在内存中检查文档命令，再执行一个 SQL 事务：读取下一个序列号，检查每个新 ID 和文档命令，写入各行，并推进计数器。如果任何一步抛出异常，事务就会回滚，也不会消耗序列号，见 src/storage/sqlite/storage\.ts。



mintId\(\) 是一个内存计数器，不是写入操作。后来失败的事务所分配的 ID，可能在重新打开后再次分配。这是安全的：只有已提交写入中的 ID 才必须永不复用（不变量5，原书第16页）。

## 文档修订版



文档内容保存在 document\_revisions 中，每个文档在每次改变它的提交中各占一行。一行要么是保存完整值的基值，要么是保存 Chord 操作的增量。读取文档时，SQLite 找到该时点或之前最新的基值，然后应用它之后的增量；这一切在同一个事务中完成，因此并发提交无法替换基值，见 src/storage/sqlite/storage\.ts。



![image\.png](图片和附件/image%207.png)

> 可回溯文档保留每个修订版；仅保留当前状态的文档在提交基值时丢弃旧行。图中的行和读取来自 research/capture/extra\-p9/sqlite\-revisions\.txt：两个应用文档在相同的提交中发生变化，seq 为2–7。
> 
> 



是否保留历史取决于文档。可回溯文档保留每一行，因此 document\(2, 4\) 可以从 seq 2 的基值和两个增量重建 seq 4 时的值。其他所有文档都仅保留当前状态：新基值提交时，同一个事务会删除它的旧行。这就是一次轮次运行结束后，每个内置文档都只剩一行基值的原因，见 research/capture/sqlite\-rows\.txt。每次这样的读取都是索引查找；捕获中的查询计划没有显示任何全表扫描，见 research/capture/extra\-p9/sqlite\-revisions\.txt。

## Node 之外



SQLite 核心不需要任何 Node API。来自 @earendil\-works/pi\-durable/storage/sqlite 的 SqliteStorage\.open\(db\) 接受任何实现 SqliteDatabase 的对象。只要有人编写一个小型适配器，同一个后端就能在那里运行，“例如 Bun 或 Cloudflare Durable Objects”，见 README §Storage。



适配器实现的门面接口，来源：src/storage/sqlite/database\.ts：

```TypeScript
export interface SqliteExecutor {
    exec(sql: string): Promise<void>;
    run(sql: string, ...params: SqliteValue[]): Promise<void>;
    get<T extends object>(sql: string, ...params: SqliteValue[]): Promise<T | undefined>;
    all<T extends object>(sql: string, ...params: SqliteValue[]): Promise<T[]>;
}

export interface SqliteDatabase extends SqliteExecutor {
    transaction<T>(callback: (transaction: SqliteExecutor) => Promise<T>): Promise<T>;
    close(): Promise<void>;
}
```

文档注释和 SqliteValue 类型（null、number、bigint、string 或 bytes）已省略。



适配器的规则很少，但很严格。在事务内部，只能使用回调收到的句柄；回调落定后，该句柄就失效。其他工作会一直等到事务完成，因此在回调内部直接调用数据库本身，调用永远不会落定。如果回调拒绝，就回滚并以同一个错误拒绝。如果回滚也失败，则要以另一个错误拒绝，例如 AggregateError，“以免调用方误把回调错误当作已保证回滚”，见 src/storage/sqlite/database\.ts。



模式变更是带版本的迁移，在文件打开时于一个事务中应用。目前只有一个版本，即版本1。较新包写入的文件会被拒绝（“Durable SQLite schema version 2 is newer than supported version 1”）；迁移失败会回滚，数据保持完整，见 src/storage/sqlite/migrations\.ts；test/sqlite\-migrations\.test\.ts。



“同一时间，一个存储只由一个进程拥有；不存在跨进程锁”，见 README §Storage。每个 SqliteStorage 都从自己的计数器分配 ID，因此访问同一个文件的两个进程可能分配出同一个 ID。第二次提交随后会失败并使那个 Session 中毒，或者悄无声息地替换另一个进程的任务或提交请求。保证只有一个所有者运行，是宿主的职责（限制与非目标，原书第168页）。



**这对你意味着什么：**

- 任何长期存在的内容都使用 SQLite。进程崩溃不会丢失已提交内容；断电可能丢失最新的提交。

- 调试时，用任意 SQLite 客户端打开文件，读取 record 列。

- 在其他运行时上，编写一个 SqliteDatabase 适配器，并针对它运行一致性测试套件。



> 来源：spec §4、§11\.2；README §Storage；src/storage/sqlite/\{storage,node,database,migrations\}\.ts；test/sqlite\-storage\.test\.ts；test/sqlite\-facade\.test\.ts；test/sqlite\-migrations\.test\.ts；research/capture/sqlite\-schema\.sql、sqlite\-rows\.txt、sqlite\-rows\-midrun\.txt；research/capture/extra\-p9/sqlite\-revisions\.txt。
> 
> 

# JSONL

---

> 先写旁文件记录，再在 main\.jsonl 中写一个标记：提交恰好在其标记存在时成立。
> 
> 

JSONL 存储是一个纯文本文件目录，可以直接用 cat 阅读。它适合开发和调试，此时看清每条记录比速度更重要。读完本节，你就能阅读这些文件、说明崩溃可能丢失什么，并决定是否启用 fsync。

## 目录



来自 /storage/jsonl/node 的 openNodeJsonlStorage\(directory, context, options\) 会打开或创建目录。在其他运行时上，来自 /storage/jsonl 的 JsonlStorage\.open\(directory, fs, context, options\) 通过任意 FileSystem 完成同样的工作（执行环境，原书第155页）。每一行都是一个 JSON 对象，位于三类文件中的一种，见 spec §11\.3：



main\.jsonl——每次提交一行标记。它只会增长。



`doc-<id>.jsonl`——一个文档的内容：它的基值和增量。



`task-<id>.jsonl`——一个存活任务的历次记录。任务完成后会删除这个文件。



文档文件和任务文件是旁文件（sidecar）：它们保存体积较大且不断变化的数据。标记会完整携带较小的记录，例如条目和任务的最终记录。对于其余内容，标记携带一个指针：文件名，加上一个从0开始为本次提交的旁文件行编号的 ordinal，见 src/storage/jsonl/storage\.ts。

## 发布



每次提交都遵循同样的三个步骤，见 spec §11\.3：

1. 把本次提交的记录追加到每个受影响的旁文件。

2. 向 main\.jsonl 追加一个完整标记，列出这些记录。

3. 只有这时，才让读取能够看到本次提交。

    

![image\.png](图片和附件/image%209.png)

> 旁文件记录先落定，标记使它们成为一次提交，回收则只在发布后运行。图中是为仅保留当前状态的文档写入新基值的一次提交，文件操作顺序由 test/jsonl\-storage\.test\.ts 断言；步骤2、5和7只在 fsync: true 时发生。
> 
> 



未通过验证的批次不会接触任何文件。一旦开始写入，任何追加或刷盘失败都会使后端中毒：直到重新打开之前，每次调用都会以 JsonlStoragePoisonedError 拒绝，Session 也会中毒（2\.3节，原书第33页）。



fsync 选项决定故障后保留什么，默认值为 false。没有它，JSONL 能经受进程崩溃，却不能保证经受断电、内核或磁盘故障。设置 fsync: true 后，每个旁文件都会先刷入磁盘，然后才写入其标记。最新的提交在断电时仍可能消失，“但保留下来的标记不应先于它的旁文件数据落盘”，见 spec §11\.3。

|**提交**|**fsync: false**|**fsync: true**|
|---|---|---|
|两个新文档|append ×2，append main|append ×2，flush ×2，append main|
|任务完成|append main，remove sidecar|append main，flush main，remove sidecar|

> 每次提交的文件操作，来源：test/jsonl\-storage\.test\.ts。
> 
> 

## 恢复



打开目录就是执行一遍恢复，规则很简短，见 spec §11\.3；src/storage/jsonl/storage\.ts：

- 残缺行——如果文件不是以换行符结尾，就把它截断到最后一个换行符。

- 未确认记录——旁文件中的一行只有被某个标记指明时才算数。末尾未确认的行会被截去。

- 损坏——已确认的行如果缺失、乱序，或位于未确认行之后，打开操作就会以 JsonlCorruptionError 失败（除非后来出现的基值已使它不再必要）。没有任何机制会修复它，见 spec §13。

- 残留内容——删除因回收中断而残留的文件，并完成所有尚未执行的回收。



![image\.png](图片和附件/image%203.png)

> 打开 JSONL 目录时，会截去残缺的标记，以及每条没有标记确认的旁文件记录。来源：research/capture/extra\-p9/jsonl\-crash\.txt。
> 
> 



在捕获中，提交4本来要把计数器设为2，并将一个任务移入 effect 阶段。它的旁文件行已写入，但标记是残缺的。重新打开时，这三行都被截去：计数器读作 \{"n":1\}，任务在 intent 阶段处于 running 状态，而下一次提交再次获得 seq 4，见 research/capture/extra\-p9/jsonl\-crash\.txt。提交4从未发生，因此重新打开的 Harness 会再次运行 intent 阶段（5\.3节，原书第70页）。

## 回收



回收会删除因较新的基值、退役或任务完成而不再必要的旁文件行，而且只会在相应提交之后进行，见 spec §11\.3。可回溯文档绝不回收。如果回收失败，提交仍然保持已发布状态，下一次打开会完成这项工作，见 src/storage/jsonl/storage\.ts。



**这对你意味着什么**

- 进程崩溃绝不会留下半次提交。提交恰好在其标记行完整时存在。

- 如果文件必须在断电后仍保持一致状态，请启用 fsync: true。大型存储的打开速度会较慢，请做好准备（9\.4节，原书第152页）。

# 内存、一致性与可移植性

---

> MemoryStorage 定义每个后端应具备的语义，共享的测试套件负责检查；只要适配器能运行，存储核心就能运行。
> 
> 

三种后端可以互换，是因为它们遵循同一个参考实现，并接受同一套测试。读完本节，你就能根据实测成本选择后端，用共享套件测试自己的后端，并让存储在 Node 之外的运行时上运行。

## MemoryStorage 是参考实现



内存存储定义了其他后端必须做到什么。它会复制自己保留的每条记录，也会复制自己返回的每条记录：“这是有意模拟 SQLite 编码／解码和 JSONL 序列化自然形成的所有权边界”，见 spec §11\.1。因此，调用方修改读取到的记录，无法改变存储中的内容，无论后端在内存还是磁盘上。内存存储也严格按持久化后端的方式保留或丢弃文档历史。测试若读取仅保留当前状态的文档的旧时点，在内存后端上也会像在 SQLite 上一样失败。



内存存储不持久化任何内容。将它用于测试、示例和短生命周期的会话。test/examples 中的大多数示例都基于它运行；恢复和重启示例（示例13、23、24、31）使用 SQLite，示例17使用 JSONL。JSONL 内部也使用内存存储来响应每次读取，见 src/storage/jsonl/storage\.ts。

## 一致性测试套件



自定义后端需要通过内置后端也必须通过的同一套测试，以此证明自身符合要求。该套件从 @earendil\-works/pi\-durable/testing 导出，能在任何兼容 Vitest 或 Jest 的测试运行器下运行：



运行存储测试套件，来源：README §Storage：

```TypeScript
    }
});
```

> 每个测试用例恰好调用一次 use，并传入一个全新、空白的存储。
> 
> 



该套件有23个用例，覆盖 ID 空间、原子批次和与内部数据脱离的值、条目与分叉、对话和任务扫描、提交请求、文档历史与地址，以及无损字符串键，见 src/testing/storage\-conformance\.ts。包内会运行它五次：分别针对内存、SQLite 和 JSONL，以及每次提交后都关闭再重新打开的 SQLite 和 JSONL。套件固定的是语义，不是实现机制。崩溃恢复、刷盘顺序和查询计划按后端分别测试；自定义后端也需要自行测试这些内容。

## 实测成本



包内提供一个基准测试，在三个后端上执行相同的读写：npm run bench:storage。其数据集包含1,000个条目、300个任务和300个文档。下图展示了在 Apple M3 Max、Node 24\.13\.0 上某次运行结果中的三行。



![image\.png](图片和附件/image%201.png)

> JSONL 的读取与内存一样快，因为它本来就是从内存读取；代价体现在每次提交和打开时。均值来自 research/capture/extra\-p9/bench\-storage\.txt（Apple M3 Max，macOS 26\.2，Node 24\.13\.0，2026\-10\-05）。提交和重新打开两行各有20个样本，误差幅度为 ±8–66%。每个面板使用独立刻度。

# 执行环境

---

> 工具只能通过宿主为每次使用构建的 ExecutionEnv 接触文件和进程，因此对话在哪里运行，由宿主决定，而不是由工具决定。
> 
> 

你的智能体工具会读取文件和运行命令。执行环境决定在哪里做这些事：你自己的磁盘、每个用户独立的沙盒目录，或远程容器。工具从不直接接触机器；它们通过 ExecutionEnv 操作，宿主在每次需要时构建这个环境。读完本节，你就能为每段对话提供独立沙盒，为远程宿主实现这个接口，并了解内置工具的要求。

## 每次使用时构建



宿主提供一个函数 HarnessOptions\.env。只要工作需要环境，Harness 就会调用它；调用绝不发生在 Session 的变更串行队列上，而且它可以是异步的，见 src/harness/types\.ts。它接收 conversationId、对话的工作目录 cwd（如果在 pi\.agent 文档中设置了该值，见“每段对话的智能体”，原书第106页），以及用于读取已提交文档的 read。



![image\.png](图片和附件/image%208.png)

> 工具、提示词区段和任务阶段只能通过宿主在每次使用时根据已提交状态构建的环境访问文件和进程。调用方来自 README §Environment 和 src/harness/\{tool,generation,scheduler\}\.ts；目标接口来自 src/harness/types\.ts。
> 
> 



三类工作会请求环境。工具调用通过 api\.env 收到它（定义工具，原书第112页）。系统提示词区段通过 input\.env 收到它（系统提示词，原书第115页）。任意任务阶段都可以通过 runtime\.env\(\) 请求环境。允许返回 undefined：此时内置工具会以错误结果失败，错误为“No execution environment is configured”。env 抛出的异常也会变成工具调用的错误结果，见 README §Environment；src/tools/env\.ts。



由于环境按每次使用构建，崩溃后重跑的工具调用会得到一个全新环境，“使用对话当前的 cwd，它可能与第一次尝试时不同”，见 spec §12。只根据已提交状态来构建它；示例29就是这样为每段对话提供独立沙盒的：

```TypeScript
const harness = await Harness.open(
    new MemoryStorage(),
    {
        models,
        registry,
        // 只读取已提交内容；没有沙盒的对话不会获得环境，
        // 因此它的工具会以明确的错误失败。
        env: async ({ conversationId, read }, envContext) => {
            const sandbox = await read.snapshot(Sandbox, conversationId, envContext);
            return sandbox?.path === undefined
                ? undefined
                : new NodeExecutionEnv({ cwd: sandbox.path });
        },
    },
    context,
);
```

```PowerShell
bob's sandbox: from bob
```



Sandbox 是创建每段对话时设置的应用文档。两段对话都运行了同一个 write 工具，每份便笺都落在自己的目录中（运行29）。三元表达式为了适应页面宽度重新换行。

## 接口



ExecutionEnv 由 FileSystem 加 Shell 组成，来自 @earendil\-works/pi\-durable/env。每个操作都返回结果，而不抛异常：\{ ok: true, value \} 或 \{ ok: false, error \}，其中 error 携带诸如 not found 或 timeout 这样的代码，见 src/env/index\.ts。



|**分组**|**FileSystem 成员**|
|---|---|
|标识|id, cwd|
|路径|absolutePath, joinPath, canonicalPath, exists|
|读取|readTextFile, readTextLines, openTextLineReader, readBinaryFile, openBinaryReader|
|写入|writeFile, appendFile, truncateFile, flushFile, renameFile|
|目录|Alternatives〔原文此处混入该词，疑为提取错误，含义待核〕；fileInfo, listDir, openDirReader, createDir, remove|
|临时内容|createTempDir, createTempFile, cleanup|
|变更|watch|

> 来源：src/env/index\.ts。truncateFile 和 flushFile 是为 JSONL 存储提供的。
> 
> 



id 为文件命名空间命名：“相同的 id 会在相同的路径看到相同的文件，无论 cwd 是什么”，见 src/env/index\.ts。每个本地 NodeExecutionEnv 都使用 "node:local"；每个容器或远程宿主都需要自己的 id。有了 id，宿主就能为每次调用构建一个新的环境对象。内置 edit 和 write 工具仍会轮流操作同一文件，因为它们按 id 加路径排队。这个队列属于单个进程，“不是针对 bash 或其他进程的锁”，见 src/tools/file\-mutation\-queue\.ts。

## 运行命令



exec\(command, options, context\) 接受字符串或数组。字符串通过 shell 运行；NodeExecutionEnv 使用 bash，无法使用时回退到 sh \-c。数组形式会直接运行 command\[0\]，其余元素作为参数，因此参数会完全按给定形式到达程序，见 src/env/index\.ts；src/env/node\.ts。当参数来自模型或用户时，优先使用数组形式。



在 NodeExecutionEnv 中，timeout 的单位是秒；非零退出码仍是一个成功结果，并带有对应的 exitCode。onOutput 接收每个输出块，并标记它来自 stdout 还是 stderr。中止 context 会终止该命令；关闭时，cleanup\(\) 会终止所有剩余命令。

## 输出窗口



如果工具只保留命令输出的尾部，可以明确声明这一点；远程环境于是可以不发送其他内容。调用方传入一个 window（包含 maxBytes、maxLines 和节奏限制）。环境可以丢弃该尾部窗口之外的输出，并在下一个输出块中通过 info\.skipped 报告丢弃了什么，见 src/env/index\.ts；CHANGELOG 1\.0\.3。



![image\.png](图片和附件/image%204.png)

> 带窗口的 exec 可以丢弃调用方本来也会丢弃的输出，并精确统计丢弃量。图中展示 info\.skipped 的规则（src/env/index\.ts），以及一个通过200字节、5行窗口打印2,000行的一致性测试用例。
> 
> 



跳过输出之所以安全，是因为一条规则：跳过之后的那个输出块始终大于窗口，因此被丢弃的文本不可能属于要保留的尾部。内置 bash 工具使用窗口，见 src/harness/tool\.ts；src/tools/bash\.ts。NodeExecutionEnv 忽略 window，并交付全部内容；当输出需要跨网络传输时，窗口才有收益。会转换输出的工具包装器必须关闭窗口，否则被跳过的文本会绕过它的转换（定义工具，原书第112页）。



**这对你意味着什么：**

- 要隔离对话，就从 HarnessOptions\.env 为每段对话返回不同的环境。返回 undefined 可以关闭文件工具和 shell 工具。

- 只根据已提交状态构建环境：崩溃后重跑时，会重新构建它。



对于自定义环境，实现 FileSystem 和 Shell，把失败作为结果返回，为每个文件命名空间提供自己的 id，并运行 /testing 中有21个用例的 registerEnvConformance。

## 细节：1\.0\.3 新增的能力



1\.0\.3 版本将四项能力设为必需，因此自定义环境必须补上它们，见 CHANGELOG 1\.0\.3。



openBinaryReader\(path, \{ noFollow? \}\) 按位置读取一个已打开的文件，其 scanLines\(\) 通过一次扫描找到一段行范围；read 工具同时使用这两项能力。openDirReader\(path\) 分页遍历目录。watch\(targets, onChange\) 报告变化的路径、溢出（重新扫描全部内容）或错误。此外，exec 接受数组形式。
