# 7\.实验性功能与运维

# 实验性技术栈

---

1\.0\.4 版中的六个软件包勾勒出这样一种 Pi：能够在崩溃后继续工作、在其他机器上运行工具，并通过一个套接字服务多个客户端。稳定版 `pi` 命令没有使用其中任何一个软件包，npm 用户也无法访问将它们连接起来的代码。



这些软件包分别是 `pi-durable`、`pi-env`、`chord`、`pi-protocol`、`pi-server` 和 `pi-client`。它们合计有 32,038 行非空源代码，超过编码智能体自身代码规模的三分之一，见 `research/out/stats.txt` 的“软件包行数”一节。本节先展示这些部分如何组成一个进程拓扑，再逐一介绍各软件包：它们存储什么、通过线路传输什么，以及施加哪些限制。“一页看懂 monorepo”（原书第11页）介绍了构建过程如何将这些代码排除在 npm 软件包之外；本节从那里接着讲起，也就是在源代码检出目录中设置 `PI_EXPERIMENTAL=1`。

## 如何使用



实验性入口点位于 `CA/src/experimental/cli.ts`。它调用 `runExperimentalCommand(args)`，如果返回 `false`，就继续执行常规的 `main()`，见 `CA/src/experimental/cli.ts:8`。除非 `PI_EXPERIMENTAL` 恰好为 `"1"`，且第一个参数是 `server` 或 `client`，否则该函数会返回 `false`，见 `CA/src/experimental/commands.ts:86`。其文档注释明确了边界：“仅供开发使用的命令分派。已发布的入口点不得导入此模块。”



三个事实使这些代码无法进入普通安装。`tsconfig.build.json` 将 `src/client`、`src/experimental` 和 `src/cli/experimental` 排除在编译之外，见 `CA/tsconfig.build.json:19`。`pi-client`、`pi-protocol` 和 `pi-server` 只是编码智能体的 `devDependencies`，见 `CA/package.json:78`。而且，如果发布的软件包中包含 `dist/experimental`，或者上述三个软件包中的任何一个能够被解析到，消费者冒烟测试就会判定该版本发布失败，见 `scripts/coding-agent-consumer.mjs:82`。在源代码检出目录中，`./pi-test.sh` 会通过 TypeScript 解析器运行源代码入口点，见 `pi-test.sh`：



**从源码启动服务器并连接客户端** · 来源：`CA/src/experimental/services/README.md`

```Bash
PI_EXPERIMENTAL=1 ./pi-test.sh server
PI_EXPERIMENTAL=1 ./pi-test.sh client
```



上述命令复制自服务 README。`pi server` 接受 `--server-id`、`--session-dir`、`--provider`、`--model`、可重复使用的 `-e`，以及 `--auth-token` 或 `--auth-token-file`；`pi client` 还增加了 `--connect`、`--session-id`、`-c/--continue` 和 `-r/--resume`，见 `CA/src/cli/experimental/commands/server.ts`、`CA/src/cli/experimental/commands/client.ts`。



`CA/src/experimental/` 下另有两个较小的程序，不借助服务器就能使用 `pi-durable`。`durable/main.ts` 是带有自身 TUI 的单进程持久化编码智能体；`vacation/main.ts` 使用同一套运行框架，只是用度假规划提示替换了编码工具，见 `CA/src/experimental/durable/README.md`、`CA/src/experimental/vacation/README.md`。两者都不检查 `PI_EXPERIMENTAL`。

## pi\-durable：先提交，再展示



README 开篇就给出了约定：“对话、模型轮次、工具调用以及你自己的状态，都会在任何内容展示之前提交到存储。如果进程在轮次中途终止，重新打开存储就能从停止之处继续工作”，见 `durable/README.md`。规范性文档是 `durable/docs/spec.md`，共 4,692 行，标题为“Pico5 规范”。它列出了八条必须满足的不变量；前三条是：“一次 Session 提交对所有记录和文档写入具有原子性”“文档更新只会在存储提交成功之后发布”，以及“所有可见进展都是持久化的，不存在易失性发布路径”，见 `durable/docs/spec.md` 第1节。



一个 `Session` 拥有一条变更序列。`Storage.commit(writes, context)` 原子性地持久化一批写入，并返回解析为 `Seq` 的结果，见 `durable/src/types.ts:997`。这条序列包含五种记录：对话、不可变条目、任务、提交项和文档。内置条目类型是 `pi.user`、`pi.assistant`、`pi.tool-result`、`pi.system`、`pi.reset` 和 `pi.compaction`，见 `durable/src/entries.ts`。内置文档是 `pi.agent`、`pi.provider`、`pi.live`、`pi.inbox` 和 `pi.usage`。



恢复并不是重放事件日志；“Session 内核语义事件日志”被明确列为非目标，见 `durable/docs/spec.md` 第13节。每个任务从其最后一次已提交的检查点恢复：



**任务的五种持久化状态** · 来源：`durable/src/types.ts`

```TypeScript
export type TaskState<S, R> =
    | {
        /** 可以被调度。 */
        readonly status: "pending";
        /** 执行恢复时所依据的完整持久化状态。 */
        readonly checkpoint: S;
        readonly outcome?: never;
    }
    | {
        /** 由一次内存中的任务调用预留。 */
        readonly status: "running";
        ...
    }
    | {
        /** 暂停且不保留调用，直到 'on' 中每个任务都进入终态；随后从 'checkpoint' 恢复。 */
        readonly status: "waiting";
        readonly checkpoint: S;
        readonly on: readonly TaskId[];
        readonly policy: JoinPolicy;
        readonly outcome?: never;
    }
    | {
        /** 结果已确定；下属普通归属工作全部不再活动后进入终态。不再运行代码。 */
        readonly status: "completing";
        ...
    }
    | {
        /** 永久确定的持久化结果回执。 */
        readonly status: "terminal";
        ...
    };
```

> 以上摘自第486行。`running` 的主体重复了 `pending` 的字段；`completing` 和 `terminal` 携带 `outcome: TaskOutcome<R>`，不带 `checkpoint`。省略处以 `…` 标记。`JoinPolicy` 是 `"failFast" | "allSettled"`，见 `durable/src/types.ts:267`。
> 
> 



`TaskOutcome` 可以是 `completed`、`failed`、`aborted`、`orphaned` 或 `faulted`，见 `durable/src/types.ts:449`。每个阶段处理器“必须通过 `runtime.commit()` 提交变更后的检查点或终态结果；若返回时没有产生持久化进展，就会使任务进入故障状态”，见 `durable/src/types.ts:148`。中止从下往上执行：“只有当一个任务所拥有的普通工作不再活动时，才会开始该任务的中止调用”，见 `durable/docs/spec.md` 第5节。



|**任务**|**阶段**|**提交内容**|
|---|---|---|
|`pi.generation`，`durable/src/harness/generation.ts:115`|`prepare → request → retry · poll · tools`，另加 `abort`|只有当计划使用的提示或工具不同于对话记录重放出的内容时，才提交 `pi.system` 条目，见 `durable/src/harness/prompt.ts:66`；部分输出；`pi.assistant` 条目|
|`pi.tool`，`durable/src/harness/tool.ts:50`|`call`、`execute`（仅用于恢复），另加 `abort`|运行前提交意图 `{ phase: "execute", arguments, replay }`，然后提交 `pi.tool-result`|
|`pi.compaction`，`durable/src/harness/compaction.ts:103`|`select → summarize → retry`，另加 `abort`|带有摘要的 `pi.compaction` 条目|



三个内置任务驱动一个轮次。默认值为：压缩的 `reserveTokens` 为 16,384，`keepRecentTokens` 为 20,000，`backgroundTokens` 为 32,768；重试 3 次，基础延迟为 2,000 ms；部分文本和工具输出最多每 100 ms 提交一次，见 `durable/src/harness/agent.ts:19`。



工具任务是持久性与副作用交汇的地方。`call` 在一个处理器中完成以下步骤：解析工具、验证、运行 `beforeTool`、提交意图、执行、运行 `afterTool`，并追加结果。只有恢复过程会进入 `execute`：



![image\.png](图片和附件/image%204.png)

> 只有两份记录都认定重复执行安全时，工具才会运行两次。崩溃前存储的意图和崩溃后注册的工具都必须声明 `replay: "safe"`；`replay` 默认为 `"unsafe"`，见 `durable/src/harness/types.ts:215`。第4行记录的是失败结果，因此该调用拥有的对话会被中止。来源：`ToolTask.execute`，`durable/src/harness/tool.ts:94`。
> 
> 



内置 `CodingTools`（`read`、`write`、`edit`、`bash` 以及 `durable/src/tools/` 下的其他工具）没有设置 `replay`，因此调用中途发生崩溃时，它们一律会被中断。钩子也按相同方式处理：它们“脱离变更序列，按扩展顺序运行；如果在使用其结果的提交完成之前发生崩溃，钩子可能会重新运行”，见 `durable/docs/spec.md` 第7\.2节。必须只作出一次决定的钩子，可以通过 `memo(name, candidate)` 记录决定；它“是一次受控提交”，见 `durable/docs/spec.md` 第5节。钩子和发起询问的任务共享同一组备忘记录，见 `durable/src/harness/types.ts:604`。生成任务的钩子包括 `beforeRequest`、`afterResponse`、`onYield` 和 `afterTools`；工具任务的钩子包括 `beforeTool` 和 `afterTool`；压缩任务的钩子是 `beforeCompact`。



提交项通过请求 id 实现幂等：使用相同 `requestId` 再次调用 `submit()` 时，会返回已有提交项，见 `durable/src/harness/submissions.ts:155`。



|**后端**|**打开方式**|**持久性**|
|---|---|---|
|内存|`new MemoryStorage()`|不持久化任何内容|
|SQLite|`openNodeSqliteStorage(file)`|`PRAGMA journal_mode = WAL`、`synchronous = NORMAL`，见 `durable/src/storage/sqlite/node.ts:190`：“提交可以经受进程崩溃；断电或宿主机故障时，最新的提交可能丢失”|
|JSONL|`openNodeJsonlStorage(directory, context)`|仅追加文件；`{ fsync: true }` 会在每个提交标记之前刷盘，默认关闭，见 `durable/src/storage/jsonl/storage.ts:256`|



三种后端，每个都只有一个所有者。“同一时刻只有一个进程拥有一份存储；不存在跨进程锁”，见 `durable/README.md` 的“存储”一节。实验性服务器在每个会话工作进程中使用 `proper-lockfile` 提供这把锁。



工具通过 `ExecutionEnv` 访问机器，它由 `FileSystem` 加 `Shell` 组成，见 `durable/src/env/index.ts:324`。其操作返回 `Result<T, E>`，即 `{ ok: true, value } | { ok: false, error }`，而不是抛出异常，见 `durable/src/env/index.ts:4`。本地实现是 `NodeExecutionEnv`，其 id 为 `"node:local"`，见 `durable/src/env/node.ts:605`。

## pi\-env：在另一台机器上运行工具



**`pi-env`**** 是第二种 ****`ExecutionEnv`****：“智能体的工具在另一台机器上运行，通常通过 SSH 连接，而 Durable 工作进程、存储和凭据留在本地”**，见 `env/README.md`。除它自己的测试外，仓库内没有任何地方导入它。远程部分是 `env/daemon/` 中的 Rust 守护进程，13 个 `.rs` 文件共 4,027 行。README 说，该软件包在 `bin/` 中附带了适用于 x86\-64 和 arm64 的 Linux、macOS、Android（Termux）及 Windows 预构建版本；`bin/` 是构建产物，不包含在源代码检出目录中。



客户端使用 `serve --token <hex>` 启动守护进程，见 `env/src/connection.ts:268`，并丢弃 stdout 中 `PI-ENV <token>` 这一行之前的所有内容，从而避免 shell 启动时的杂音破坏数据流，见 `env/src/connection.ts:329`。此后，stdout 只承载帧：

> JSON 说明要做什么；原始字节承载文件内容和输出。如果帧短于 9 字节或长于 16 MiB，连接会以“Corrupt frame from pi\-env”（来自 pi\-env 的损坏帧）错误结束，见 `env/src/connection.ts:345`。布局来自 `env/docs/protocol.md` 的“帧”一节；此图为示意图，不按比例绘制。

双方每 5 s 发送一次 `ping`。“如果 30 秒内没有收到任何字节，或 stdin 结束，守护进程就会终止它启动的每个进程组并退出”，见 `env/docs/protocol.md` 的“存活性”一节。客户端在同样的 30 s 静默后放弃连接，见 `env/src/connection.ts:15`。



`sshArguments()` 构建 ssh 命令行，见 `env/src/ssh.ts:77`。它传入 `-T -a -x`，并设置 `BatchMode=yes`、`ClearAllForwardings=yes`、`ForwardAgent=no`、`ForwardX11=no`、`ControlMaster=no`、`ControlPath=none`、`RemoteCommand=none`、`PermitLocalCommand=no`、`SendEnv=-*`、`StrictHostKeyChecking=yes`、调用方提供的 `UserKnownHostsFile`、`GlobalKnownHostsFile=none`，以及固定的 `HostKeyAlias`。主机密钥通过 `scanHostKey()` 和 `acceptHostKey()` 在带外接受一次。



远程守护进程文件的名称为 `pi-env-<first 32 hex digits of its SHA-256>`，即以其 SHA\-256 的前 32 个十六进制数字作为后缀，见 `env/src/ssh.ts:371`。`deployDaemon()` 在每次启动前计算远程文件的哈希，只有文件缺失或不同时才上传；如果上传文件的哈希不匹配，会删除该文件并报出“pi\-env upload is corrupt”（pi\-env 上传内容已损坏），见 `env/src/ssh.ts:396`。

## chord：组合运行时



尽管名为 chord，它与组合键并无关系。“Chord 是面向由插件／扩展组装而成的系统的应用组合运行时”，并且“它不是 Pi 软件包：它不依赖其他任何 Pi 工作区软件包”，见 `chord/README.md`。其组成部分包括：

- Facet：同步设置单元。一个 facet 会调用 `env.use()`、`env.observe()`、`env.provide()` 和 `env.provideMany()`，见 `chord/src/types.ts:281`；宿主根据这些调用构建依赖图，先激活提供方再激活使用方，并按相反顺序释放它们。

- 服务：模式为 `"singleton"` 或 `"keyed"` 的带类型令牌，见 `chord/src/types.ts:123`；可以仅供进程本地使用，也可以发布给远程使用方。参数、结果、快照和更新都必须是严格 JSON。

- 复制状态：`change(context, draft => …)` 发布一个修订版本，见 `chord/src/services/state.ts:202`。副本接收增量操作。

- 控制服务：`$chord.service`，成员包括 `catalogue`、`subscribe` 和 `unsubscribe`，见 `chord/src/services/wire.ts:40`。订阅方最多缓存 100 次更新；第101次更新会用一个重置快照替换缓冲区，见 `chord/src/services/provider.ts:453`。

- 上下文：“类似 Go 的上下文系统，用于取消和调用作用域内的应用值”，见 `chord/README.md`；包括 `BACKGROUND_CONTEXT`、`TODO_CONTEXT`、`withAbortSignal`、`withCancel` 和 `withContextValue`，见 `chord/src/context/index.ts:55`。

    

**七种增量操作** · 来源：`chord/src/delta/index.ts`

```TypeScript
export type Op =
    | readonly ["r", JsonValue]
    | readonly ["s", NonEmptyPath, JsonValue]
    | readonly ["d", NonEmptyPath]
    | readonly ["a", NonEmptyPath, string]
    | readonly ["t", NonEmptyPath, number]
    | readonly ["p", Path, number, number, JsonValue[]]

```

> 以上是第32行起的完整内容。依次表示：替换根、设置、删除、追加字符串、截去字符串前端、数组 splice、置换。字符串追加使流式回答能够以很低的成本复制。
> 
> 



Node 打包器使用 esbuild 将每个 facet 入口构建为一个名为 `facet-<12 hex>-[hash].cjs` 的 CommonJS 文件，并记录一个 `sha256-…` 完整性值，见 `chord/src/node/bundle.ts:88`。加载器使用 `node:vm` 编译源码前会重新计算哈希；如果不匹配，就以“Facet bundle integrity check failed”（Facet 包完整性检查失败）报错，见 `chord/src/node/bundle-loader.ts:231`。`FacetHost.reload()` 在运行时替换 facet，见 `chord/src/facets/host.ts:423`；服务器的 `/reload` 就使用它。

## pi\-protocol、pi\-server、pi\-client



`PROTOCOL_VERSION` 为 `8`，见 `protocol/src/protocol.ts:5`；README 说得很直接：“该协议是实验性的，不保证兼容性”，见 `protocol/README.md:41`。一帧包含一个 4 字节无符号大端长度，以及一个由该软件包自身编解码器处理的确定长度 CBOR 项。默认限制为：每帧 16 MiB，见 `protocol/src/framing.ts:6`；数组元素或映射条目 1,000,000 个；嵌套层级 64 层，见 `protocol/README.md:41`、`protocol/src/cbor/options.ts:8`。

封装消息是设置了 `additionalProperties: false` 的 TypeBox 对象，因此额外字段会导致验证失败；采集记录显示，带有一个额外键的 `hello` 会触发“Invalid client protocol message”（无效的客户端协议消息），见 `research/out/experimental-stack-frames.txt`。

|---|---|---|
|客户端 → 服务器|`hello`|`version`；必须是第一帧|

|服务器 → 客户端|`response`|`id, ok: true, result?` 或 `ok: false, error`|
|服务器 → 客户端|`service_update`|`subscriptionId`、`update`|
|服务器 → 客户端|`attachment`|一个会话目标，或 `null`|

> 共有八种封装消息类型，其载荷是不透明的。`target` 是 `{serverId}` 或 `{serverId, sessionId, attachmentId}`，且 `serverId` 必须是小写 UUIDv4。`call` 和 `result` 是 Chord 值，`pi-protocol` 只检查它们是否为严格 JSON。来源：`protocol/src/protocol.ts`。
> 
> 



`pi-server` 只监听 Unix 域套接字；该软件包没有 HTTP 或 WebSocket 监听器。套接字路径为 `<dir>/<serverId>.sock`，见 `server/src/transports/unix/address.ts:8`，权限模式为 `0600`，见 `server/src/transports/unix/listener.ts:11`。如果客户端未能在 5 s 内完成握手，连接就会以“Handshake timeout”（握手超时）断开，见 `server/src/server.ts:42`。错误码包括 `wrong_server`、`session_not_found`、`session_ambiguous`、`session_not_attached` 和 `server_draining`，见 `server/src/errors.ts:5`。服务器并未包装 `AgentSession`：会话工作进程从 `pi-durable` 导入 `Harness`，并打开 `openNodeSqliteStorage`，见 `CA/src/experimental/session-worker.ts:15`。



`pi-client` 导出 `Client`、`createClientServiceTransport`（Chord 适配器）和三个错误类，见 `client/src/index.ts`；`discoverUnixServers()` 扫描服务器目录，见 `client/src/unix.ts:37`。它“从不自动重连或重放请求”；应用需要调用 `reconnect()`、重新连接会话，并且只重复自己确定安全的操作，见 `client/README.md:34`。



> 这对你意味着什么：
> 
> - 不要围绕 `pi server` 规划集成：npm 和二进制发行版都不包含它，协议 8 也不承诺兼容性。
> 
> - 如果现在就需要能够经受崩溃的轮次，可以直接嵌入 `pi-durable`；只有能安全运行两次的工具，才应声明 `replay: "safe"`。
> 
> - 每份持久化存储必须恰好由一个进程拥有；这个软件包不会阻止第二个进程访问它。
> 
> - 对 `pi-env`，先在带外接受一次主机密钥，之后让采用内容寻址的守护进程自行重新部署。
>

# 安全模型

---

Pi 使用你的账户权限运行每一次工具调用，不会请求批准。项目信任决定一个文件夹中的哪些文件可以配置 Pi；它并不决定 Pi 启动后模型可以做什么。



你今天早上克隆的一个仓库里包含 `.pi/extensions/`、一个 `AGENTS.md` 和一个测试脚本。在其中启动 Pi，可能运行三种代码：扩展、模型读取 `AGENTS.md` 后决定运行的内容，以及模型调用的脚本。本节展示 Pi 会对这三者中的哪些设置关卡，以及具体如何实施。它引用 Pi 自己的安全立场，沿着代码追踪项目信任的决策过程，比较文档提供的隔离方案，并列出各个组件内部的控制措施。

## 安全立场



随软件提供的指南开篇就确立了一条规则：“应将模型生成的命令和代码视为不可信。Pi 可以使用启动它的账户权限读取、修改和执行文件，而且不会在每次工具调用之前请求批准”，见 `CA/docs/security.md`。扩展、软件包安装器、语言服务器及其他子进程“以相同的权限运行，除非操作系统或虚拟化边界限制了它们”。指南也点明哪些东西不构成边界：“查看对话记录、使用项目信任以及审查变更，都不会形成安全边界。”



仓库的 `SECURITY.md` 在同一处划定了漏洞报告范围：“Pi 将本地用户账户及该账户可写的文件，视为与 Pi 进程本身处于同一信任边界之内”，见 `SECURITY.md`。用指南的话说，提示注入、没有内置沙箱，以及用户安装的扩展的行为，“通常不属于安全边界内的问题，除非报告证明存在权限边界绕过，或取得了本地用户原本不具备的访问权限”，见 `CA/docs/security.md` 的“报告安全问题”一节。报告应发送至 `security@earendil.com`，或通过私密 GitHub 安全公告提交，见 `SECURITY.md`。



工作文件夹也不限制访问范围：它“控制资源发现和工具的默认位置，但不会阻止命令访问 Pi 进程能够访问的其他路径”，见 `CA/docs/security.md`。

## 项目信任



项目信任是启动时针对配置设置的关卡。如果一个文件夹的 `.pi/` 下包含八项内容中的任意一项，就需要作出信任决定：`settings.json`、`mcp.json`、`extensions`、`skills`、`prompts`、`themes`、`SYSTEM.md`、`APPEND_SYSTEM.md`，见 `CA/src/core/trust-manager.ts:30`；该文件夹或任一祖先目录中存在 `.agents/skills` 目录时也一样。`~/.agents/skills` 本身属于用户资源，不会触发这个决定，见 `CA/src/core/trust-manager.ts:186`。仅有 `.pi` 目录本身不需要作出决定。



![image\.png](图片和附件/image%203.png)

> 第一个给出答复的行决定结果；所有未得到答复的路径最终都被视为不可信。顺序来自 `resolveProjectTrusted()`，见 `CA/src/core/project-trust.ts:46`。命令行覆盖项在资源扫描之前检查，因此即使文件夹中没有需要保护的内容，`--no-approve` 也会生效。只有存在受保护资源时，才会执行第3至6行。
>

第3行在加载任何项目代码之前执行。`loadProjectTrustExtensions()` 强制将项目视为不可信，并加载用户、全局和命令行扩展以及 SDK 工厂，因此项目本地扩展无法对自身是否可信投票，见 `CA/src/core/resource-loader.ts:501`。内置扩展要等到最后一轮才加载，因为“项目设置可能禁用它们，而已加载的扩展无法卸载”，见 `CA/src/core/resource-loader.ts:683`。处理器循环返回第一个 `"yes"` 或 `"no"`；抛出异常的处理器会被报告并跳过，见 `CA/src/core/extensions/runner.ts:295`。



信任存储是智能体目录中的 `trust.json`，见 `CA/src/core/trust-manager.ts:214`，它是一个把规范化目录路径映射为 `true` 或 `false` 的 JSON 对象。查找从当前文件夹向上遍历到根目录，并采用遇到的第一个显式值，见 `CA/src/core/trust-manager.ts:45`。读取和写入都会持有 `trust.json.lock` 上的 `proper-lockfile` 锁。交互式提示显示“Trust project folder?”（是否信任项目文件夹？），并提供五个选项：



|**选项**|**决定**|**写入 ****`trust.json`**** 的内容**|
|---|---|---|
|信任（Trust）|可信|此文件夹 → `true`|
|信任父文件夹（Trust parent folder \(\.\.\.\)）|可信|父文件夹 → `true`；删除此文件夹自身的条目|
|信任，仅本次会话（Trust \(this session only\)）|可信|无|
|不信任（Do not trust）|不可信|此文件夹 → `false`|
|不信任，仅本次会话（Do not trust \(this session only\)）|不可信|无|



五个选项中有两个不会留下记录。来源：`getProjectTrustOptions()`，`CA/src/core/trust-manager.ts:67`。也可以稍后在会话中通过 `/trust` 保存决定，见 `CA/src/core/slash-commands.ts:36`。



Print、JSON 和 RPC 模式没有信任提示。如果没有覆盖项、扩展答复或已保存的决定，它们只会在 `defaultProjectTrust: "always"` 下加载受保护资源，见 `CA/src/core/project-trust.ts:86`。自动化中应使用 `--approve` 或 `--no-approve`。



授予信任会加载项目设置、项目 MCP 服务器、`.pi` 下的扩展、技能、提示模板、主题和系统提示文件，以及项目软件包。拒绝信任还会禁止软件包管理器访问项目软件包存储：“Project is not trusted; refusing to access project package storage”（项目不可信；拒绝访问项目软件包存储），见 `CA/src/core/package-manager.ts:1777`。`.pi` 下的 `npm` 和 `git` 目录也在该检查范围内，但仅仅存在这些目录不会触发信任决定。



有两类内容绕过了这道关卡。上下文文件，包括 `AGENTS.override.md`、`AGENTS.md`、`CLAUDE.md` 及其大写变体，无须信任检查就会加载；只有 `--no-context-files` 能阻止它们，见 `CA/src/core/resource-loader.ts:642`。此外，会话目录在信任决定完成之前就会选定，优先级依次为 `--session-dir`、`PI_CODING_AGENT_SESSION_DIR`，以及启动设置管理器读取的 `sessionDir` 设置，见 `CA/src/main.ts:688`。因此，即使项目被拒绝信任，它的 `.pi/settings.json` 仍然可以改变会话文件的写入位置；`CA/docs/security.md` 记录了这一缺口。



拒绝信任并不会阻止一个文件夹引导模型。`AGENTS.md` 和 `CLAUDE.md` 仍然会进入系统提示，模型也仍然使用你的权限运行工具。应将不可信仓库中的指令视为输入；如果尚未读过这些指令，就使用 `-nc` 启动 Pi；如果必须在那里运行模型，就隔离整个进程。



示例扩展 `CA/examples/extensions/project-trust.ts` 写道：“可以在包含 `.pi`、`AGENTS.md/CLAUDE.md` 或 `.agents/skills` 的项目中试用。”仅有 `.pi`、`AGENTS.md` 或 `CLAUDE.md` 并不会触发 `project_trust`：只有存在上述八项 `.pi` 内容之一，或项目中的 `.agents/skills` 时，该事件才会运行，见 `CA/src/core/trust-manager.ts:186`。

## 组件内部的控制措施



下面各组件都实施了一条范围较窄的规则。它们都不能把 Pi 变成沙箱，但各自堵住了一个具体缺口：

- **凭据：**`auth.json` 以 `0600` 模式写入，其目录以 `0700` 模式创建；“该模式只在创建时应用，因此管理员管理的权限模式和 ACL 会保持不变”，见 `CA/src/core/auth-storage.ts:24`。每次读取—修改—写入都会持有 `proper-lockfile` 锁。`mcp-auth.json` 使用相同后端，见 `CA/src/extensions/mcp/oauth.ts:144`。已经开始的 OAuth 刷新会忽略取消：“提供商可能已经轮换了刷新令牌，因此刷新及其持久化会忽略 `signal`，只受超时限制”，见 `ai/src/auth/resolve.ts:105`。

- **MCP 配置：** 项目的 `.pi/mcp.json` 只在项目信任时加载，而且不能设置 `auth`：“`auth` 只允许出现在全局 `mcp.json` 中”，因此“仓库不能决定凭据的去向”，见 `CA/src/extensions/mcp/config.ts:133`。设置了 `auth.provider` 的服务器必须使用 `https`，或在 `localhost`、`127.0.0.1`、`[::1]` 上使用 `http`，见 `CA/src/core/mcp-servers.ts:285`。`oauth.callbackUrl` 必须是 `http` 回环 URI，见 `CA/src/core/mcp-servers.ts:178`；`oauth.authServerMetadataUrl` 必须使用 `https` 或回环 `http`，见 `CA/src/core/mcp-servers.ts:201`。

- **MCP OAuth：** 对于不是 `https` 的非回环端点，该流程会抛出 `OAuthInsecureEndpointError`，见 `mcp/src/oauth/flow.ts:121`；当返回的 `iss` 与元数据中的颁发者不同时，会抛出 `OAuthIssuerMismatchError`，见 `mcp/src/oauth/flow.ts:373`。

- **MCP 进程：** stdio 服务器通过 `cross-spawn` 启动，不经过 shell；除 Windows 外，在所有平台上都会分离到各自独立的进程组中，因此关闭时会终止整个进程组，见 `mcp/src/transports/stdio.ts:101`。`env` 和 `headers` 中的值会经过 `resolveConfigValue`，其中开头的 `!` 会让余下内容作为 shell 命令运行，见 `CA/src/core/resolve-config-value.ts:140`。因此，受信任的配置可以在服务器连接时执行代码。

- **Codemode：** 脚本在编译为 WebAssembly 的 QuickJS 中运行，“唯一的能力是调用注入的工具”，见 `codemode/README.md`。前置代码会先冻结内置对象，见 `codemode/src/runtime/prelude-source.ts:28`；编码智能体将 VM 内存上限设为 256 MiB，见 `CA/src/extensions/codemode/execute.ts:55`；工作进程设置 QuickJS 的最大栈大小，见 `codemode/src/runtime/worker.ts:59`；宿主在 `terminate()` 之前设置中断标志，见 `codemode/src/runtime/host.ts:323`。嵌套调用是通过 `ctx.executeTool` 发出的真实调用，所以会应用 `tool_call` 钩子和权限检查，见 `CA/src/extensions/codemode/tool.ts:7`；而且“故障发生前已经执行的调用不会被撤销”，见 `CA/docs/codemode.md`。

- **实验性技术栈：** 没有声明 `replay: "safe"` 的持久化工具，崩溃后绝不会重新运行。`pi-env` 使用固定别名锁定主机密钥，关闭所有转发，每次启动前重新验证守护进程的 SHA\-256，并在静默 30 s 后终止远程进程组。`pi server` 在自己拥有的 `0700` 目录中绑定一个 `0600` 套接字，而且只有持有凭据时才会连接 Radius 中继，见“实验性技术栈”（原书第166页）。

## 供应链



仓库的 `AGENTS.md` 为贡献者和智能体设定了规则：“将 npm 依赖和锁文件的变更作为代码审查。直接外部依赖保持锁定到精确版本。”安装时使用 `--ignore-scripts`，而且“带有生命周期脚本的新依赖必须经过审查，并在 `scripts/generate-coding-agent-install-lock.mjs` 中添加明确的允许列表条目”，见 `AGENTS.md` 的“依赖与安装安全”一节。在 `28dcce2` 版本中，该允许列表有三个条目：`@google/genai@2.21.0`、`esbuild@0.28.2` 和 `protobufjs@7.6.6`，每个都附有一行理由，见 `scripts/generate-coding-agent-install-lock.mjs:17`。`scripts/check-pinned-deps.mjs` 强制要求精确版本；除非设置了 `PI_ALLOW_LOCKFILE_CHANGE`，否则提交前检查会阻止锁文件提交，见 `scripts/check-lockfile-commit.mjs:5`。上面的 Docker 配方在安装 Pi 时也使用 `--ignore-scripts`。



> **这对你意味着什么：**
> 
> - 对每个仓库分别决定是否信任，并记住，被拒绝信任的项目仍然会提供 `AGENTS.md`。
> 
> - 在 CI 中传入 `--approve` 或 `--no-approve`；非交互模式永远不会弹出询问。
> 
> - 当仓库或任务不属于你时，在容器或虚拟机中运行 Pi；工具级隔离会把扩展留在宿主机上。
> 
> - 不要将提供商凭据放入任何被隔离程序的环境中；也可以改用 Docker Sandboxes 代理。
> 
> - 加载扩展之前先审查它：它会在 Pi 进程中，以你的权限运行。

# 遥测与评测

---

Pi 提供了一套 span 约定，但仓库中没有任何代码向其发出 span；它还提供了默认开启的安装 ping。其评测衡量的是另一件事：自身文档在多大程度上帮助模型完成任务。



这里的遥测指三种不同的事，很容易混淆。`pi-telemetry` 是用于追踪的接口库。产品遥测是编码智能体发送给 `pi.dev` 和提供商的少量数据。评测是一个私有软件包，针对模型运行真实的智能体会话，并为结果评分。本节按这个顺序介绍，准确说明哪些信息会在什么时候离开机器，最后讲述评测运行如何被隔离，以及如何报告结果。

## pi\-telemetry：没有生产方的约定



该软件包自称提供“供应商中立的遥测约定和带类型的 schema 实用工具”，且“不包含导出器、全局当前 span 状态，也不依赖遥测后端”，见 `telemetry/README.md:11`。包括一致性测试套件在内，它共有 935 行，而且不读取任何环境变量：在 `telemetry/src` 中 grep `process.env` 没有任何结果。



**完整的运行时约定** · 来源：`telemetry/src/index.ts`

```TypeScript
export interface TelemetryContext {
    startSpan<T>(options: SpanOptions, callback: (span: TelemetrySpan) => T | Promise<T>): Promise<T>;
}
export interface TelemetrySpan extends TelemetryContext {
    addEvent(name: string, attributes?: SpanAttributes): void;
    setAttributes(attributes: SpanAttributes): void;
    focal Status(status: SpanStatus): void;
}
```

> 译注：已修复可明确判断的 `start Span`、`add Event` 以及 `set Attributes.attributes:` 的空格或标点损坏。所提供文本中的 `focal Status` 无法唯一还原，因此原样保留；这一行不是合法的 TypeScript，不能把本代码块视为可直接编译的源码。
> 
> 



以上完整对应第14至22行。`SpanStatus` 为 `{ status: "ok" }` 或 `{ status: "error"; error?: { name, message } }`；属性值是标量或由同一种标量类型组成的数组，见 `telemetry/src/index.ts:1`。



Span 的作用域由回调限定：一个 span 只存在于 `startSpan` 回调内部，而 span 本身也是子 span 的上下文。围绕这一约定，该软件包导出了 `NOOP_TELEMETRY_CONTEXT`，见 `telemetry/src/noop.ts:20`；参考实现 `InMemoryTelemetryContext`，见 `telemetry/src/memory.ts:192`；schema 辅助函数 `defineTelemetrySchema` 和 `createTypedSpanStarter`，见 `telemetry/src/index.ts:72`；以及位于 `@earendil-works/pi-telemetry/testing` 的适配器一致性测试套件，见 `telemetry/src/testing/index.ts:1`。



`pi-ai` 在每个提供商请求上通过 `telemetryContext` 接受上下文，即“该逻辑请求生成遥测时所使用的显式父上下文”，见 `ai/src/types.ts:136`，并将它复制到 simple\-stream 选项中，见 `ai/src/api/simple-options.ts:48`。这就是全部集成内容。在 `telemetry/` 之外的全部十四个软件包中 grep `startSpan`，找不到任何调用，因此传给 `pi-ai` 的上下文不会收到 span。

## 编码智能体发送什么



产品遥测位于编码智能体中，而不在 `pi-telemetry` 中。一个开关控制它：



**安装遥测开关** · 来源：`CA/src/core/telemetry.ts`

```TypeScript
function isTruthyEnvFlag(value: string | undefined): boolean {
    if (!value) return false;
    return value === "1" || value.toLowerCase() === "true" || value.toLowerCase() === "yes";
}

export function isInstallTelemetryEnabled(
    settingsManager: SettingsManager,
    telemetryEnv: string | undefined = process.env.PI_TELEMETRY,
): boolean {
    return telemetryEnv !== undefined ? isTruthyEnvFlag(telemetryEnv) :
    settingsManager.getEnableInstallTelemetry();
}
```



以上是该文件除导入语句外的全部内容。只要设置了 `PI_TELEMETRY`，它就具有优先权：`1`、`true` 或 `yes` 开启遥测，其他任何值，包括空字符串，都会关闭遥测。若未设置，则由 `enableInstallTelemetry` 设置决定；其默认值为 `true`，见 `CA/src/core/settings-manager.ts:1142`。

|**发送内容**|**发送时机**|**控制条件**|
|---|---|---|
|GET https://pi\.dev/api/report\-install?version=\<v\> with User\-Agent: pi/\<v\> \(\<platform\>;\<runtime\>; \<arch\>\), 5 s 超时，忽略响应。|交互模式中的新会话；没有记录变更日志版本时（全新安装），或变更日志包含比已记录版本更新的条目时，见 `CA/src/modes/interactive/interactive-mode.ts:1324`|先检查是否设置了任意值的 `PI_OFFLINE`，再检查 `isInstallTelemetryEnabled`，见 `CA/src/modes/interactive/interactive-mode.ts:1351`|

`PI_OFFLINE` 有两种检查方式。`main()` 将 `1`、`true`、`yes` 或 `--offline` 视为离线，然后设置 `PI_OFFLINE=1`，见 `CA/src/main.ts:576`。安装 ping 和版本检查只判断变量是否为非空，因此 `PI_OFFLINE=0` 也会抑制它们。



`enableAnalytics` 默认为 `false`，见 `CA/src/core/settings-manager.ts:1152`。只有首次设置界面会写入它，见 `CA/src/cli/startup-ui.ts:193`；而该界面只在以下条件同时成立时运行：`PI_EXPERIMENTAL=1`、使用官方发行版、采用默认智能体目录，并且尚无 `settings.json`，见 `CA/src/cli/startup-ui.ts:131`。选择加入时还会保存一个随机 `trackingId`，见 `CA/src/core/settings-manager.ts:1160`。在 `28dcce2` 中，没有任何代码读取这两个值：`getEnableAnalytics()` 和 `getTrackingId()` 没有调用方，而错误报告包会从所附设置中删除 `trackingId` 和 `deviceId`，见 `CA/src/core/bug-report.ts:62`。





> **经验法则：**对于不允许向外回传自身信息的机器，应设置 `PI_OFFLINE=1` 和 `PI_TELEMETRY=0`。前者会停止 ping、版本检查、目录刷新和软件包自动安装；后者会移除归属标识请求头。两者都不会移除 OpenCode 会话请求头，该头部只会发送给 OpenCode。

## 评测



`packages/evals` 对应 `@earendil-works/pi-evals`，标记为 `private`，从未发布，见 `evals/package.json`。它基于 `vitest-evals 0.15.0` 构建，运行真实的进程内 `AgentSession`。运行框架先将 `HOME`、`USERPROFILE` 和 `PI_CODING_AGENT_DIR` 指向一个全新的临时目录，见 `evals/src/harness.ts:82`，再使用 `createAgentSessionServices` 创建服务，并使用 `createAgentSessionFromServices` 创建会话，见 `evals/src/harness.ts:337`。每次运行都会在一个 `mkdtemp("pi-eval-")` 根目录下，获得独立的主目录、智能体目录、工作区和会话目录，见 `evals/src/harness.ts:283`。提供商凭据从宿主机的 `auth.json` 复制到内存存储中；如果加载了自身内联扩展之外的任何扩展，运行就会失败并报出“Isolated eval loaded unexpected extensions”（隔离评测加载了意外扩展），见 `evals/src/harness.ts:362`。



|**类型**|**文件**|**运行方式**|**衡量内容**|
|---|---|---|---|
|宿主机评测|`evals/*.eval.ts`：`smoke`、`documentation-audit`|`npm run eval:host`，在本机运行 Vitest|普通的通过或失败；`smoke` 在不提供工具的情况下询问法国首都，并期望回答 Paris，见 `evals/evals/smoke.eval.ts`|
|文档提升效果评测|`evals/*.docs.eval.ts`：`custom-provider`、`extensions`、`models`、`openai-provider`、`tui`|`npm run eval:docs`，每个实验组使用一个 Docker 容器|`without_docs` 和 `with_docs` 之间的通过率差异|



两个套件：一个检查智能体是否正常工作，另一个检查文档是否有帮助。两者都需要 `PI_PROVIDER` 和 `PI_MODEL`，它们必须同时设置或同时不设置，见 `evals/src/cli.ts:76`。`PI_EVAL_RUNS_PER_VARIANT` 或 `--runs-per-variant` 设置重复次数；默认是一次，见 `evals/src/cli.ts:79`。



`without_docs` 镜像不包含编码智能体的 `README.md`、`CHANGELOG.md`、`docs/` 和 `examples/`，运行框架还会从默认系统提示中删去“Pi documentation”（Pi 文档）一节；如果提示中没有这一节，就会抛出异常，见 `evals/src/harness.ts:498`。`with_docs` 则保留文档和提示中的这一节。文档评测只允许使用 `read`、`write`、`edit`、`grep`、`find` 和 `ls`，见 `evals/src/harness.ts:485`，因此模型没有 shell。容器内的运行框架会降权到一个非特权 UID，此后评测定义和评分器就不可读取，见 `evals/README.md` 的“文档变体”一节。

> 
> - 使用真实模型测试自己的扩展时，可以借鉴评测运行框架的模式：每次运行使用全新的主目录、智能体目录和工作区，并确保没有意外扩展。
