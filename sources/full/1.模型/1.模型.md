# Pi 的用途

---

Pi 是一个小巧的核心，将提示变成模型调用、工具执行和 JSONL 中的各行。产品通常会在此基础上内置的其他功能，例如子智能体、规划模式和权限弹窗，都被有意留给扩展实现。



Pi 是一个终端编码智能体。作者将其描述为“一个极简、可扩展的智能体运行框架，你可以将它打造成自己的工具”（`CA/README.md`）。这句话是一项设计约束，而非口号：核心决定提示如何送达模型、工具如何运行，以及对话如何存储；几乎所有其他决策，都交由你加载的代码处理。本节列出提交 `28dcce2` 中随包提供的内容，从源代码统计各个功能面的规模，并说明核心有意不提供哪些功能。

## 这些数量如何统计



上表中的每个数字都来自检出版本，并且都依赖某项统计规则。规则改变，数字也会改变，因此这里明确列出规则：

- **传输 API：10 种。** 统计 `KnownApi` 联合类型中的成员（`ai/types.ts:17`），它们对应加载时注册到 `BUILTIN_APIS` 的十个条目（`ai/compat.ts:180`）。`KnownImageApi` 另加 `openrouter-images`，`KnownClassifierApi` 另加三种分类器 API（`ai/types.ts:31`）；两者都不是聊天 API。不能用 `ai/api/` 中的 40 个文件来计数：其中 15 个是 `.lazy.ts` 加载器，另一些是共享辅助模块（`research/out/stats.txt` 的 `§api-files`）。

- **提供商：42 个。** 统计 `KnownProvider` 联合类型中的成员（`ai/types.ts:39`）。其集合与 42 个 `ai/providers/*.models.ts` 目录文件完全一致（`research/out/stats.txt` 的 `§provider-files`）。仅用于测试的 `faux` 提供商不在这两者之中。

- **工具：4 \+ 4 个。** `DEFAULT_TOOL_NAMES` 为 `["read", "bash", "edit", "write"]`（`CA/src/core/settings-manager.ts:215`）。`ToolName` 联合类型再加上 `powershell`、`grep`、`find` 和 `ls`，共八个内置工具（`CA/src/core/tools/index.ts:95`）。内置扩展提供的 `tool_search` 工具注册时未激活，因此不计入。

- **扩展事件：41 个。** 统计 `ExtensionAPI` 的 `on()` 重载接受的不同事件名（`CA/src/core/extensions/types.ts:1558`）。`ExtensionEvent` 联合类型只有 32 个成员（`CA/src/core/extensions/types.ts:1366`），因为所有会话事件被合并到一个 `SessionEvent` 成员中。

- **扩展方法：31 个。** 统计 `ExtensionAPI` 除 `on` 之外的不同方法名，从 `registerTool` 到 `unregisterVirtualModel`（`CA/src/core/extensions/types.ts:1632`）。重载只算一次。`events` 属性是一个共享 `EventBus`，不是方法（`CA/src/core/extensions/types.ts:1878`）。

- **运行模式：4 种。** `resolveAppMode` 从四种应用模式中选择一种：`--mode` 指定的 `rpc` 和 `json`；使用 `-p`，或 stdin 或 stdout 不是终端时选用的 `print`；其他情况为 `interactive`（`CA/src/main.ts:112`）。因此，单独使用 `--mode text` 并不会选择 print：在终端中它仍会打开 TUI。Print 与 JSON 共用一个运行器 `runPrintMode`，其输出模式为 `"text" | "json"`（`CA/src/modes/print-mode.ts:20`）。SDK 是另一种入口：在自己的进程中调用 `createAgentSession()`（`CA/src/core/sdk.ts`）。因此，项目首页会写成“四种模式：交互式、print/JSON、RPC 和 SDK”。

## `PI_EXPERIMENTAL` 控制什么



一个函数掌握着开关：**实验性功能开关 · ****`CA/src/core/experimental.ts`**** · TypeScript**

```TypeScript
export function areExperimentalFeaturesEnabled(): boolean {
  return process.env.PI_EXPERIMENTAL === "1";
}
```



这就是整个文件，共三行。



值必须恰好为 `"1"`；`true` 或 `yes` 都不会开启它。有三处读取这个开关。除非开关开启，并且第一个参数是 `server` 或 `client`，否则 `runExperimentalCommand` 返回 `false`（`CA/src/experimental/commands.ts:86`）。交互式界面的页脚（`CA/src/modes/interactive/components/footer.ts:213`）和首次设置（`CA/src/cli/startup-ui.ts:141`）也会检查它。仅打开这个开关，并不能让 npm 安装版本访问实验性代码，因为包的 `files` 列表排除了 `!dist/client`、`!dist/experimental` 和 `!dist/cli/experimental`（`CA/package.json:31`）。services README 明确说明了这一意图：“server、client 和 experimental 包子路径不会包含在 npm 包和独立可执行程序中”（`CA/src/experimental/services/README.md`）。实验性入口点是 `CA/src/experimental/cli.ts`，`./pi-test.sh` 会从源码检出版本中运行它（`pi-test.sh`）；从该入口开始的路径是“实验性技术栈”（原书第 166 页）的主题。

# 一个提示的生命周期

---

回答一个需要读取一次文件的问题，会产生两次模型调用、29 个会话事件和 8 行 JSONL。提示先写入磁盘，再送达模型；运行到 `agent_settled` 才结束，而不是到 `agent_end` 就结束。



你输入“What does hello\.txt say?”（`hello.txt` 写了什么？），然后按 Enter。在回答出现之前，Pi 已经运行了扩展钩子、写入会话文件、调用模型两次、读取文件，并又追加了三行。本节通过与源代码核对的 22 个步骤，追踪这一输入在稳定版 CLI 中的全过程。随后展示采集工具包针对同一交互记录下来的真实事件流和会话文件。每一步都指出详细解释该步骤的章节；请先读本节，将它作为地图。

## 样本



采集工具包使用 `pi-ai` 的 `faux` 提供商驱动真实的 `AgentSession`，因此不涉及网络或 API 密钥（`research/capture/one-turn.mjs`）。`faux` 模型按脚本给出两次回复。第一次是文本“Reading it\.”，加上针对 `hello.txt` 的 `read` 调用，停止原因为 `toolUse`。第二次是“It says: Hello from the capture kit\.”。脚本订阅会话，调用 `session.prompt()`，将每个事件及会话文件的每一行转储到 `research/out/one-turn.txt`。它在 Node 26\.10\.0 下运行，使用从 `28dcce2` 构建的 `pi-coding-agent` 1\.0\.4。在交互式 CLI 中，同一个 `session.prompt()` 调用来自编辑器；下面的步骤就从这里开始。

## 进入循环：步骤 1–12



模型看到提示之前，提示已经写入磁盘。这是稳定版 CLI 处理一个提示的步骤 1–12。实线箭头表示调用，虚线箭头表示提供商流，点线箭头表示递交给 `AgentSession` 的智能体事件。依据提交 `28dcce2` 的 `CA/src/core/agent-session.ts`、`agent/agent-loop.ts` 和 `CA/src/core/model-runtime.ts` 核验。示意图。

### **1 · 提交**



编辑器的 `onSubmit` 自行处理内置斜杠命令和以 `!` 开头的 bash 行。其他内容进入 `InteractiveMode` 的主循环，它会等待 `session.prompt(userInput)`（`CA/src/modes/interactive/interactive-mode.ts:1247`）。Print、JSON 和 RPC 模式调用同一个方法，见运行模式（原书第 127 页）。

### **2 · 提示处理流水线**



`AgentSession.prompt()` 按固定顺序执行（`CA/src/core/agent-session.ts:1954`）。若输入是 `/foo` 这样的扩展命令，执行后直接返回。然后输入处理器可以改写或消费文本。接着展开技能命令和提示模板。如果已有运行正在流式输出，文本会作为引导消息或后续消息入队，`prompt()` 随即返回。否则，会检查模型及其身份验证，检查上一个回答是否需要压缩，再运行 `before_agent_start` 处理器；这些处理器可以添加消息或替换系统提示（`CA/src/core/agent-session.ts:2048`）。各阶段见“从 `prompt()` 到 `agent_settled`”（原书第 67 页），各钩子见“扩展事件与上下文”（原书第 120 页）。

### **3 · 交接**



**`prompt()`**** 构建用户消息；**若系统提示的分节与对话记录中的不同，则在前面插入一条系统消息（`CA/src/core/agent-session.ts:2091`）。它在 `_runAgentPrompt` 内调用 `agent.prompt(messages)`（`CA/src/core/agent-session.ts:1818`）。系统提示是对话记录中的一条消息，而非请求字段，见系统提示词构建（原书第 75 页）。

### **4 · 循环开始**



**`runAgentLoop`**** 将该系统消息上的工具变化声明为 ****`toolsAdded`****，随后发出 ****`agent_start`****、****`turn_start`****，以及每条新消息各自的一对 ****`message_start`**** / ****`message_end`**（`agent/agent-loop.ts:117`）。循环本身见智能体循环（原书第 49 页），事件见智能体事件与 `Agent` 类（原书第 57 页）。

### **5 · 第一次写入**



**`AgentSession`**** 接收每个智能体事件，先传给扩展，再传给订阅者；遇到 ****`message_end`**** 时将消息追加到会话**（`CA/src/core/agent-session.ts:1127`）。**只有出现用户或助手消息后，会话文件才会存在**（`CA/src/core/session-manager.ts:1166`）。**在用户消息的 ****`message_end`**** 时，****`SessionManager`**** 创建文件，将此前保留在内存中的五个条目一次写入**，见会话：JSONL 树（原书第 86 页）。

### **6 · 请求投影**



**每次调用模型之前，循环都会调用 ****`prepareRequest`**（`agent/agent-loop.ts:219`）。**`AgentSession`**** 安装的实现会用会话树的一份投影替换上下文**（`CA/src/core/agent-session.ts:781`）。**压缩摘要和上下文编辑就在这个投影中生效**，见压缩与分支摘要（原书第 92 页）。

### **7 · 上下文钩子**



`streamAssistantResponse` 先将消息交给 `transformContext`，再交给 `convertToLlm`（`agent/agent-loop.ts:390`）。在 CLI 中，`transformContext` 发出 `context` 扩展事件（`CA/src/core/sdk.ts:418`）。

### **8–9 · 模型调用**



**循环调用流式函数**（`agent/agent-loop.ts:403`）；**SDK 将该函数连接到 ****`modelRuntime.streamSimple`**（`CA/src/core/sdk.ts:412`）。**`ModelRuntime`**** 解析提供商及其凭据，再将请求交给提供商的 ****`streamSimple`**（`CA/src/core/model-runtime.ts:739`）。提供商通过 HTTP 使用十种传输 API 之一进行通信，见提供商与模型（原书第 24 页）、传输 API 与跨提供商交接（原书第 36 页），以及身份验证、费用、重试与模型目录（原书第 41 页）。

### **10–11 · 流式输出**



**提供商返回 ****`AssistantMessageEvent`****：先是 ****`start`****，然后是 ****`text_*`****、****`thinking_*`**** 和 ****`toolcall_*`**** 增量，最后是 ****`done`**** 或 ****`error`**，见流式事件协议（原书第 30 页）。**循环将 ****`start`**** 转为 ****`message_start`****，将每个增量转为 ****`message_update`****，将 ****`done`**** 转为 ****`message_end`**（`agent/agent-loop.ts:414`）。

### **12 · 第二次写入**



在助手消息的 `message_end` 时，`AgentSession` 将它作为第 6 行追加（`CA/src/core/agent-session.ts:1149`）。

## 经过工具并退出：步骤 13–22



**一次运行在 ****`agent_settled`**** 时结束，而不是 ****`agent_end`****。步骤 13–22。****`tool_call`**** 和 ****`tool_result`**** 通过 ****`AgentSession`**** 安装到智能体上的 ****`beforeToolCall`**** 和 ****`afterToolCall`**** 钩子到达扩展**（`CA/src/core/agent-session.ts:640`）；图中从调用这些钩子的循环画出箭头。依据提交 `28dcce2` 的 `agent/agent-loop.ts` 与 `CA/src/core/agent-session.ts` 核验。示意图。

### **13–17 · 一批工具调用**



**循环收集回答中的 ****`toolCall`**** 块。除非智能体被设置为顺序执行，或者某个被调用工具声明 ****`executionMode: "sequential"`****，否则它们并行运行（****`agent/agent-loop.ts:519`****）；默认值是 ****`"parallel"`****（****`agent/agent.ts:253`****）。**对每个调用，循环发出 `tool_execution_start`，验证参数，再运行 `beforeToolCall`，由它触发 `tool_call` 扩展事件；若返回 `{ block: true }`，就直接生成错误结果，不执行工具（`agent/agent-loop.ts:727`）。`execute()` 之后，`afterToolCall` 触发 `tool_result`；其处理器可替换 `content`、`details` 或 `isError`（`agent/agent-loop.ts:864`）。随后是 `tool_execution_end`，以及结果消息的 `message_start` / `message_end`。`read` 工具与其他七个工具见内置工具（原书第 81 页）。

### **18 · 第三次写入**



工具结果是第 7 行。

### **19 · 下一轮次**



**`turn_end`**** 结束当前轮次**（`agent/agent-loop.ts:287`）。因为回答包含工具调用，内层循环再次运行。步骤 6–12 重复之前，`prepareNextTurn` 给 `AgentSession` 一个压缩和刷新系统提示的机会（`CA/src/core/agent-session.ts:892`）。第二次回答没有工具调用，因此是最后一次回答；它成为第 8 行。

### **20 · 循环结束**



当不再有工具调用、引导消息或后续消息时，循环发出 `agent_end`（`agent/agent-loop.ts:320`）。`AgentSession` 为订阅者在该事件上附加 `willRetry`（`CA/src/core/agent-session.ts:1128`）。

### **21 · 循环之后**



此时 `_runAgentPrompt` 还不会返回。它先检查最后一次回答是否存在可重试错误，然后检查压缩，再检查队列中的消息；只要其中任何一项需要再次运行，就调用 `agent.continue()`（`CA/src/core/agent-session.ts:1839`）。最后，`agent_before_settle` 处理器可以请求继续（`CA/src/core/agent-session.ts:1879`）。这些分支见 `AgentSession`：组装运行时（原书第 61 页）和压缩与分支摘要（原书第 92 页）。

### **22 · 收束**



在 `finally` 块内，`_emitAgentSettled` 先向扩展、再向订阅者发出 `agent_settled`（`CA/src/core/agent-session.ts:1066`），随后 `session.prompt()` 完成。

两个轮次，29 个事件，四次写入。“毫秒”是自订阅开始经过的时间。整个运行只耗时 5 毫秒，因为 `faux` 模型按脚本作答；换成真实提供商，事件 7–14 和 21–26 需要等待网络。“步骤”指向图 1\.4（原书第 16 页）与图 1\.5（原书第 18 页）。数据来自 `research/out/one-turn.txt`（`§events`）。每次运行的 `text_delta` 事件数量会变化；事件顺序不会变化。



轮次是循环的基本单位：每个轮次包含一次模型响应，以及该响应所调用的工具。轮次 1 覆盖事件 2–19，轮次 2 覆盖事件 20–27。29 个事件中有十个是 `message_update`，TUI 根据这串增量流重绘。步骤 2、7、14、16 和 21 中的钩子都不会出现在这份列表里。`input`、`before_agent_start`、`context`、`tool_call`、`tool_result` 和 `agent_before_settle` 只分发给 `ExtensionRunner`，并且其中几个在没有注册处理器时会跳过（`CA/src/core/agent-session.ts:651`）。`session.subscribe()` 监听器永远看不到它们，见扩展事件与上下文（原书第 120 页）。

## 磁盘上的八行



会话文件有八行，每行一个 JSON 对象（`research/out/one-turn.txt` 的 `§session-jsonl`）。前三行描述会话，后五行是对话。

|**行**|**类型**|**ID ← 父条目**|**写入时机**|
|---|---|---|---|
|1|`session`，版本 3|`01a10e5a-...`（会话 ID）|事件 6|
|2|`model_change`，`faux/faux-1`|`2cd13c47 ← null`|事件 6|
|3|`thinking_level_change`，`off`|`f99fc4be ← 2cd13c47`|事件 6|
|4|`message`，`system`：5 个分节，4 个 `toolsAdded`|`ff9b46f6 ← f99fc4be`|事件 6|
|5|`message`，`user`|`dd741bf1 ← ff9b46f6`|事件 6|
|**6**|**`message`****，****`assistant`****，****`stopReason: "toolUse"`**|**`0f939fd7 ← dd741bf1`**|**事件 14**|
|7|`message`，`toolResult`，`toolCallId: "call_1"`|`81cb0f01 ← 0f939fd7`|事件 18|
|8|`message`，`assistant`，`stopReason: "stop"`|`01f5647e ← 81cb0f01`|事件 26|



每个条目都指明父条目，所以这八行构成一棵树的一条分支。新建会话时，第 2、3 行由 `createAgentSession` 追加到内存中（`CA/src/core/sdk.ts:436`）；它们和第 5 行一起写入文件。`version` 来自 `CURRENT_SESSION_VERSION`（`CA/src/core/session-manager.ts:41`）。数据来自 `research/out/one-turn.txt`（`§session-jsonl`）。



第 6 行包含完整的第一次回答：文本、工具调用、生成它的模型、用量，以及停止原因。



**第 6 行：第一次回答及其工具调用 · ****`research/out/one-turn.txt`**** · JSONL**

```JSON
{
  "type": "message",
  "id": "0f939fd7",
  "parentId": "dd741bf1",
  "timestamp": "2026-10-05T23:16:41.752Z",
  "message": {
    "role": "assistant",
    "content": [
      { "type": "text", "text": "Reading it." },
      { "type": "toolCall", "id": "call_1", "name": "read", "arguments": { "path": "hello.txt" } }
    ],
    "api": "faux",
    "provider": "faux",
    "model": "faux-1",
    "usage": { ... },
    "stopReason": "toolUse",
    "timestamp": 1791242201744,
    "thinkingLevel": "off"
```

节选自 `§session-jsonl` 的第 6 行。省略了 `usage` 对象（token 数量，以及 `faux` 提供商的零费用），并将两个内容块各排成一行；键保留存储时的顺序。



条目中有两个时间戳。外层的 `timestamp` 是 `SessionManager` 追加条目时写入的 ISO 字符串。内层的 `message.timestamp` 是自纪元起的毫秒数，由消息的创建者设置，此处即 `faux` 提供商。会话：JSONL 树（原书第 86 页）会逐字段解释每种条目类型。



> **易踩的坑**
> 
> `agent_end` 不是一次运行的终点。在它之后，`AgentSession` 还可能重试失败响应、压缩后继续，或为排队消息启动新一轮运行；这一切仍然发生在同一次 `prompt()` 调用内。等待空闲状态的代码必须等待 `agent_settled`，或等待 `session.prompt()` 完成。把 `agent_end` 视作最终结束前，要先检查它的 `willRetry`。
>
