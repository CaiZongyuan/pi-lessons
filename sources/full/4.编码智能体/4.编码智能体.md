# 4\.编码智能体

# 系统提示词构建

---

Pi 的提示词是一个由具名分节组成的有序映射，而不是一个字符串。因此，会话进行中的变化可以作为一个小补丁追加到对话记录中，之前的每条消息则逐字节保持发送时的原样。



**Pi 发送的每个请求都以系统提示词开头，而编码智能体的提示词会在会话期间发生变化：安装了技能、关闭了工具，或者扩展添加了指令。本节介绍九类分节及其顺序，以及各项输入的读取来源。**随后会展示变化如何在对话记录中成为 `SystemMessage` 补丁，而不是重写提示词。Pi 自身的默认提示词很短：一句开场说明、工具列表、少量规则，以及指向其文档的路径。见 `CA/src/core/system-prompt.ts:128`。

## 分节及其顺序



`buildSystemPromptSections()` 返回一个 `Record<string, string>`，其键的顺序就是提示词的顺序。见 `CA/src/core/system-prompt.ts:128`。`preamble` 是不带标签的文本。其余每节都包裹为 `<name>\n…\n</name>`，见 `CA/src/core/system-prompt.ts:190`，这样后续更新便能按名称指定要替换的分节。



![image\.png](图片和附件/image%209.png)

> **自定义提示词替换的是四节，而不是一节。**当 `SYSTEM.md` 或 `--system-prompt` 提供 `preamble` 时，根本不会构建 `tools`、`rules` 和 `docs`，见 `CA/src/core/system-prompt.ts:152`。带斜线底纹的框表示自定义提示词会移除的分节；空分节会被省略。本图为示意图，依据 `buildSystemPromptSections()` 绘制。
> 
> 



- `preamble`：**默认文本是一句说明：“你是一名专业编码助手，运行在编码智能体运行框架 pi 中。你通过读取文件、执行命令、编辑代码和编写新文件来帮助用户。”**见 `CA/src/core/system-prompt.ts:156`。**自定义提示词会原样替换它。**

- **`tools`****：对于每个声明了且具有 ****`promptSnippet`**** 的工具，生成一行 ****`- ${name}: ${snippet}`****，然后加上“除上述工具外，根据项目情况，你可能还可以使用其他自定义工具。”没有片段的工具不会列入；如果一个也没有，列表显示 ****`(none)`**。见 `CA/src/core/system-prompt.ts:157`。被 `prepareLoadout` 钩子隐藏的工具会被排除，因为请求没有声明这些工具，见 `CA/src/core/system-prompt.ts:150`。

- **`rules`****：来自 ****`buildRules()`**** 的去重项目列表**，见 `CA/src/core/system-prompt.ts:88`。**先是“使用 bash 进行 ls、rg、find 等文件操作”，再是额外的 ****`promptGuidelines`****，最后始终附上“回答要简洁”和“处理文件时清楚地显示文件路径”。**

- **`docs`****：指向 Pi 的 ****`README`****、****`docs/`**** 和 ****`examples/`**** 的绝对路径，并指示仅“在用户询问 pi 本身时”阅读这些文档**，见 `CA/src/core/system-prompt.ts:162`。

- **`addendum`****：追加提示词文本；有多个时用空行连接**，见 `CA/src/core/agent-session.ts:1697`。

- **`project_context`****：“项目特定的指令和准则：”，后面为每个上下文文件附上一个 ****`<project_instructions path="…">…</project_instructions>`**** 块**，见 `CA/src/core/system-prompt.ts:79`。加载哪些文件，详见“上下文文件、技能、模板、主题与包”（原书第106页）。

- `skills`：`<available_skills>` 索引；每个允许模型调用的技能都有一个 `<skill>`，包含 `name`、`description` 和 `location`，见 `CA/src/core/skills.ts:358`。只有选用了 `read` 或 `bash` 时才会添加；如果两者都隐藏，提示便不会指定任何工具，见 `CA/src/core/system-prompt.ts:175`。

- `cwd`：工作目录，其中反斜杠会转为 `/`，见 `CA/src/core/system-prompt.ts:183`。

- **自定义分节：来自 ****`systemPromptOptions.sections`**** 的扩展分节。**名称必须匹配 `^[a-z][a-z0-9_-]*$`，且不能是 `preamble`，否则构建会抛出 `Invalid system prompt section name`（系统提示词分节名称无效），见 `CA/src/core/system-prompt.ts:58`。



![image\.png](图片和附件/image%206.png)



**工作目录是提示词中唯一的环境信息。****`system-prompt.ts`**** 中没有任何地方会注入日期、时间、操作系统或 shell。需要这些信息的扩展可以在 ****`before_agent_start`**** 中添加一个分节**，详见“扩展事件与上下文”（原书第120页）。

## 来自采集工具包的已存储提示词



**提示词并不是以纯文本保存的。它存储为一条系统消息的分节，位于单轮会话文件的第四行**，详见“一个提示的生命周期”（原书第15页）。**此次采集使用了四个默认工具，没有上下文文件、技能或追加提示词**，所以包含**五节**：

    "role": "system",

删节说明：省去了十条规则中的四条、`docs` 的正文，以及四个 `toolsAdded` 声明中的三个（`bash`、`edit`、`write`）。`content` 为空，因为提示词由结构化分节承载，见 `CA/src/core/system-prompt.ts:199`。路径已由采集脚本脱敏。

## 提示词变化是对话记录补丁



`_preparePromptAndToolLoadout()` 会在每次 `prompt()` 开始时，以及之后每个轮次之前，通过 `prepareNextTurnWithContext` 运行，见 `CA/src/core/agent-session.ts:1724`、`CA/src/core/agent-session.ts:892`。**它从不重新发送整个提示词，而是重放对话记录中的系统消息，得到模型当前持有的分节，再将它们与新构建的分节比较，并追加差异。**



![image\.png](图片和附件/image%201.png)

> **之前的消息绝不会被重写。发生变化的分节作为文本发送，被移除的分节作为 ****`null`**** 发送；工具变化放在同一条系统消息中。只有模型接受对话中途的系统消息时，提供商才会在原位置发送后续系统消息，并以 ****`Updated system prompt section "name"`****（已更新系统提示词分节“name”）标示。**依据 `agent-session.ts`（`_preparePromptAndToolLoadout`）、`system-prompt.ts:217`、`agent-loop.ts:333`、`ai/utils/transcript.ts:115`。
> 
> 



补丁：变化的分节为文本，移除的分节为 `null`。来源：`CA/src/core/system-prompt.ts`。

```TypeScript
export function diffSystemPromptSections(
    previous: Record<string, string | null>,
    current: SystemPromptSections,
): Record<string, string | null> | undefined {
    const patch: Record<string, string | null> = {};
    for (const [name, text] of Object.entries(current)) {
    if (previous[name] !== text) patch[name] = text;
    }
    for (const name of Object.keys(previous)) {
    if (current[name] === undefined) patch[name] = null;
    }
    return Object.keys(patch).length > 0 ? patch : undefined;
}
```

> 完整函数，第217–229行。
> 
> 



重放逻辑只在 `getCurrentSystemMessage()` 中定义一次：依次遍历每条系统消息，拼接非空的 `content`，按名称设置或删除分节，并对每条消息先应用 `toolsRemoved`、再应用 `toolsAdded`，从而解析工具。见 `ai/utils/transcript.ts:73`。提供商接收打过补丁的对话记录。`renderSystemMessageUpdate()` 将每个补丁分节标示为 `Updated system prompt section "name":`（已更新系统提示词分节“name”：）或 `Removed system prompt section "name"`（已移除系统提示词分节“name”）。见 `ai/utils/text.ts:28`。当模型的兼容性标志 `supportsMidConvoSystemMessages` 为 `false`（默认值）时，`collapseSystemMessages()` 会改为把所有系统消息合并成一条置于开头的消息，见 `ai/utils/transcript.ts:108`。



![image\.png](图片和附件/image%2010.png)



最后这种情况决定了这项设计能带来什么收益。对于接受对话中途系统消息的模型，安装技能或连接 MCP 服务器会追加一个补丁，提供商已缓存的前缀仍然有效。对于不接受的模型，合并后的头部会改变，从该次请求开始就会丢失缓存前缀。哪些模型带有这个标志，详见“传输 API 与跨提供商交接”（原书第36页）。



> **易踩的坑**
> 
> 返回 `systemPrompt`（或设置 `forceSystemPrompt`）的 `before_agent_start` 处理器不会改变对话记录。结构化分节仍然会进行差异比较并存储；强制文本只投影到请求中，成为一条携带当前工具的头部消息，见 `CA/src/core/agent-session.ts:1773`。这种投影只持续本次运行。之后的运行以及任何读取会话文件的程序，看到的都是结构化提示词。最好修改 `systemPromptOptions` 中的分节、工具或准则，`docs/extensions.md` 也给出了同样的建议。
> 
> 



> 这对你意味着什么
> 
> - 通过重放会话的系统消息来读取提示词，而不是只读第一条。
> 
> - 让扩展以具名分节的形式添加指令；重命名会表现为一次移除加一次新增。
> 
> - 将日期或环境信息放在独立分节中；默认提示词只包含 `cwd`。
> 
> - 在期望提示词变化后仍能命中缓存之前，先检查 `supportsMidConvoSystemMessages`。
> 
>

# 内置工具

---

**Pi 自带八个工具，默认启用四个。它们都遵循同一个输出约定：2,000 行或 50 KB，因此单个工具结果绝不会填满上下文窗口；****`edit`**** 工具则会拒绝任何无法唯一定位的修改。**



**内置工具是默认智能体接触机器的唯一途径。**本节列出这八个工具及其选择方式，然后说明它们共同遵循的截断约定，以及各工具的参数和行为。接着结合采集工具包中的真实错误消息，讲解 `edit` 算法。最后介绍包裹每次调用的钩子流水线，其中也包括一个工具代表另一个工具发起的调用。

## 八个工具，默认启用四个



`ToolName` 为 `"read" | "bash" | "powershell" | "edit" | "write" | "grep" | "find" | "ls"`，见 `CA/src/core/tools/index.ts:95`。`DEFAULT_TOOL_NAMES` 为 `["read", "bash", "edit", "write"]`，见 `CA/src/core/settings-manager.ts:215`。`createReadOnlyTools()` 返回 `read`、`grep`、`find` 和 `ls`，见 `CA/src/core/tools/index.ts:204`。



工具选择分三层进行。`defaultTools` 设置可以用普通名称替换默认列表，也可以按列表顺序应用 `+name` 和 `-name` 修饰符来修改它，见 `CA/src/core/settings-manager.ts:236`。在命令行中，`--tools` 是允许列表，`--exclude-tools` 是拒绝列表；两者都接受 `*` 模式，`--no-tools` 和 `--no-builtin-tools` 则会关闭整组工具，见 `CA/src/cli/args.ts:151`。完整标志列表详见“CLI 参考”（原书第191页）。



每个工具都是一个 `ToolDefinition`，由 `wrapToolDefinition()` 转成 `AgentTool`；该函数复制名称、模式、`prepareArguments` 和 `constrainedSampling`，并向 `execute` 传入每次调用专属的上下文，见 `CA/src/core/tools/tool-definition-wrapper.ts:8`。路径相对于会话的 `cwd` 解析，展开 `~` 并移除开头的 `@`，见 `CA/src/core/tools/path-utils.ts:48`。

## 截断约定



每个返回文件或进程输出的工具，都会将输出交给 `truncate.ts` 处理。存在两个限制，先触及哪个就按哪个截断：



所有内置工具共用的三个限制。来源：`CA/src/core/tools/truncate.ts`。

```TypeScript
export const DEFAULT_MAX_LINES = 2000;
export const DEFAULT_MAX_BYTES = 50 * 1024; // 50KB
export const GREP_MAX_LINE_LENGTH = 500; // Max chars per grep match line
```

> 第11–13行，原样引用。
> 
> 



|**函数**|**保留内容**|**使用方**|
|---|---|---|
|`truncateHead`|开头；绝不拆分一行；如果仅第1行就超过字节限制，不返回任何内容，并设置 `firstLineExceedsLimit`|`read`、`grep`、`find`、`ls`|
|`truncateTail`|末尾；如果仅最后一行就超过字节限制，保留其末尾，并设置 `lastLinePartial`|`bash`、`powershell`（通过 `OutputAccumulator`）、用户的 `!` 命令|
|`truncateLine(line, 500)`|前500个字符，然后附上 `... [truncated]`|`grep` 的匹配行|
|`truncateMiddle(text, maxBytes)`|两端各占一半预算，中间放置 `...N chars truncated...`|MCP 工具结果，限制为 20 KiB，见 `CA/src/extensions/mcp/tools.ts:51`|



文件保留头部，进程保留尾部。读取文件从顶部开始；失败命令最后才输出错误。依据 `truncate.ts` 及 `CA/src` 中各函数的调用位置。



截断从来不会悄无声息。每个工具都会追加一条提示，告诉模型如何获取剩余内容。采集工具包用真实的 `read` 工具读取了一个2,500行的文件：

```Plain Text
read long.txt (2,500 lines) → ...line 1999\nline 2000\n\n[Showing lines 1-2000 of 2500. Use offset=2001 to continue.]
read offset=10 limit=3 → line 10\nline 11\nline 12\n\n[2488 more lines in file. Use offset=13 to continue.]
read offset=9999 × Offset 9999 is beyond end of file (2500 lines total)
```

## 工具参考



|**工具**|**参数**|**行为**|
|---|---|---|
|`read`|`path`、`offset?`（从1开始）、`limit?`|先应用 `limit`，再应用 `truncateHead`。第一行超过 50 KB 时，不返回文本，而是给出 `sed -n '...p' ... | head -c 51200` 提示。图片（jpg、png、gif、webp、bmp，根据文件内容检测）以图片块返回，并根据模型的输入限制缩放；如果模型不接受图片输入，则添加说明。会尝试 macOS 文件名变体：AM/PM 之前的窄不换行空格、NFD、弯撇号。见 `CA/src/core/tools/path-utils.ts:86`。|
|`bash`|`command`、`timeout?`（秒；无默认值；最多2,147,483\.647）|启动配置的 shell，分离到独立进程组，并合并 stdout 和 stderr。中止或超时会终止进程树。保留输出末尾；完整输出写入提示中指定的临时文件 `pi-bash-*.log`。更新节流为每100 ms最多一次。非零退出会返回 `isError`，并附上 `Command exited with code N`（命令以代码 N 退出）。|
|`powershell`|与 `bash` 相同|使用相同定义，但采用 PowerShell 配置、UTF\-8 控制台前缀和临时文件前缀 `pi-powershell`，见 `CA/src/core/tools/powershell.ts:16`。|
|`edit`|`path`、`edits: [{oldText,newText}]`|一次调用中执行多处互不重叠的替换（算法见下文）。`prepareArguments` 也接受 JSON 字符串或单个对象形式的 `edits`，以及旧式顶层 `oldText`/`newText`，见 `CA/src/core/tools/edit.ts:103`。|
|`write`|`path`、`content`|在按文件划分的修改队列内创建父目录，以 UTF\-8 写入。返回 `Successfully wrote to path`（已成功写入 path）。|
|`grep`|`pattern`、`path?`、`glob?`、`ignoreCase?`、`literal?`、`context?`、`limit? = 100`|运行 `rg --json --line-number --color=never --hidden`；如果缺少 ripgrep，会进行下载。遵循 `.gitignore`。每行截断至500个字符；输出上限为 50 KB。|
|`find`|`pattern`（glob）、`path?`、`limit? = 1000`|运行 `fd --glob --color=never --hidden --max-results N`；返回相对于搜索目录的路径，以 `/` 作为分隔符。|
|`ls`|`path?`、`limit? = 500`|读取目录，按不区分大小写的顺序排序，为目录追加 `/`，包括点文件。|



只有四种工具请求严格的模式解码。`read`、`bash`（因而也包括 `powershell`）、`edit` 和 `write` 设置 `constrainedSampling: {type: "json_schema", strict: "prefer"}`；`grep`、`find` 和 `ls` 不设置。依据 `CA/src/core/tools/*.ts`。



`bash` 有两种输出。模型看到的是经过截断的尾部。以程序方式调用它的调用方，例如 codemode 脚本（“codemode”，原书第151页），得到的是 `structuredContent`，即 `{output, truncated, full_output_path?, exit_code, wall_time_seconds}`，其中 `output` 的上限改为 1 MiB，见 `CA/src/core/tools/bash.ts:24`。除非 `exposeSessionEnvironment` 为 `false`，否则子进程的环境会包含 `PI_SESSION_ID`、`PI_SESSION_FILE`、`PI_PROVIDER`、`PI_MODEL` 和 `PI_REASONING_LEVEL`，而这五个变量继承而来的值会先被移除，见 `CA/src/core/tools/bash.ts:186`。

# 会话：JSONL 树

---

**会话文件是仅追加的，每个条目都指明其父节点，因此一个文件就能容纳整棵对话树。当前位于哪个分支只保存在内存中，重启后会选择最后写入的那一行。**



**智能体在会话中做过的一切，都可以从一个 JSONL 文件中恢复**：它收到的提示词、模型的每次响应、每个工具结果，以及用户尝试过的每条分支。本节介绍文件的存放位置与命名方式，随后介绍文件头和十一种条目类型。接着沿着 `parentId` 构建的树，以及在树上移动的叶指针展开说明。最后讨论加载与迁移，以及一条路径上的条目如何变成发送给模型的消息。相关代码是 `SessionManager`，共2,013行，位于单个文件中，见 `CA/src/core/session-manager.ts:987`。

## 位置、命名与标识



目录：`~/.pi/agent/sessions/--<cwd>--/`。`cwd` 会移除开头的 `/` 或 `\`，并将每个 `/`、`\` 和 `:` 替换为 `-`，见 `CA/src/core/session-manager.ts:592`。`/Users/me/proj` 会变为 `--Users-me-proj--`。



目录优先顺序：`--session-dir`，然后是 `$PI_CODING_AGENT_SESSION_DIR`，再是 `sessionDir` 设置，最后是按 `cwd` 划分的默认目录，见 `CA/src/main.ts:688`。



文件名：`<将 : 和 . 替换为 - 的 ISO 时间戳>_<session id>.jsonl`，见 `CA/src/core/session-manager.ts:1079`。采集工具包中的文件为 `2026-10-05T23-16-41-747Z_01a10e5a-ea92-7225-8c3a-c148ed81dc38.jsonl`。



会话 ID：UUIDv7，见 `CA/src/core/session-manager.ts:264`，所以 ID 按创建时间排序。通过 `--session-id` 或 SDK 提供的自定义 ID 必须匹配 `^[A-Za-z0-9](?:[A-Za-z0-9._-]*[A-Za-z0-9])?$`，见 `CA/src/core/session-manager.ts:268`。



条目 ID：`randomUUID()` 的前8个十六进制字符，最多与现有 ID 检查100次，之后改用完整 UUID，见 `CA/src/core/session-manager.ts:277`。



**文件采用延迟创建。在会话包含用户或助手消息之前，条目都留在内存中；只打开再关闭 Pi、不输入内容，不会留下文件**，见 `CA/src/core/session-manager.ts:1166`。第一次刷新以 `"wx"` 标志打开文件（文件已存在就会失败），并写入所有缓冲的条目。之后，每个条目都通过一次 `appendFileSync` 追加一行，见 `CA/src/core/session-manager.ts:1172`。`sessions-tree` 采集展示了这个转变：在 `model_change` 之后，磁盘上的文件有0行；在第一条用户消息之后，有3行。

## 加载与迁移



`loadEntriesFromFile()` 以 1 MiB 为单位读取，按 `\n` 拆分，并跳过空行和格式错误的行，不发出警告，见 `CA/src/core/session-manager.ts:627`。如果第一个解析出的条目不是带有字符串 `id` 的文件头，就返回 `[]`。最后一行即使没有末尾换行符也会保留，并向文件追加换行符。



空文件会用一个新文件头初始化。非空文件如果无法得到任何条目，则抛出 `Session file is not a valid pi session: path`（会话文件不是有效的 pi 会话：path），且不会被修改，见 `CA/src/core/session-manager.ts:1039`。



文件头版本低于3时会运行迁移（缺失时按1处理），之后重写整个文件，见 `CA/src/core/session-manager.ts:337`：

- v1 → v2：为每个条目分配 ID，按文件顺序线性连接 `parentId`，并将压缩条目的 `firstKeptEntryIndex` 转换为 `firstKeptEntryId`，见 `CA/src/core/session-manager.ts:287`。

- v2 → v3：消息角色 `hookMessage` 改为 `custom`，见 `CA/src/core/session-manager.ts:316`。

模型从不会看到文件本身。它看到的是文件中某条路径的投影，由 `buildSessionProjection()` 重建，见 `CA/src/core/session-manager.ts:543`。

> 只有路径上最新的一次压缩会提供摘要。保留范围内更早的压缩在投影中不产生任何内容；切分点之前的原始系统消息会被丢弃，因为压缩本身携带自己的快照。依据 `session-manager.ts`（`buildSessionPath`、`getSessionContextSettings`、`buildContextEntries`、`buildSessionProjection`、`sessionEntryToContextMessages`）。

- 路径：从叶节点回溯到根节点，再反转，见 `CA/src/core/session-manager.ts:390`。其他分支上的兄弟节点不在这条路径上。

- 设置：`thinkingLevel` 是路径上最后一个 `thinking_level_change` 的值，默认为 `"off"`。`model` 来自最后一个 `model_change` 或助手消息，以较晚者为准，见 `CA/src/core/session-manager.ts:418`。

- 压缩：当路径上存在压缩条目 `C` 时，条目顺序为 `C`，然后是从 `C.firstKeptEntryId` 到 `C` 之间去掉原始系统消息后的条目，最后是 `C` 之后的所有内容，见 `CA/src/core/session-manager.ts:476`。“压缩与分支摘要”（原书第92页）介绍了 `C` 的生成方式。

- 上下文编辑：每个目标以最新的 `context_edit` 为准；`null` 会省略目标，有值时只替换其 `content`，见 `CA/src/core/session-manager.ts:519`。只考虑当前路径上的编辑，因此编辑仅在所在分支内生效。

- 消息：`message` 产生其 `message`；`custom_message` 产生自定义消息；`branch_summary` 产生 `branchSummary` 消息；`compaction` 先产生其 `systemMessage` 快照，再产生一条 `compactionSummary` 消息；其他类型都不产生内容，见 `CA/src/core/session-manager.ts:439`。



应用于分支采集时，重新打开的会话路径为 `mc → u1 → a1 → u2 → a2 → bs`，上下文包含五条消息：`user`、`assistant`、`user`、`assistant`、`branchSummary`。`model_change` 设置状态，不产生消息；分支 B 及其标签不在路径上。



易踩的坑：移动叶指针不会被保存。不带摘要或标签的 `/tree` 导航、SDK 中的 `branch()`，以及重新定位叶指针的扩展，在下一次追加之前都不会改变文件，见 `CA/src/core/agent-session.ts:4113`。如果 Pi 在那之前退出，会话重新打开时会定位到文件最后一行，而那一行可能属于用户刚刚离开的分支。向目标追加标签是固定位置成本最低的方式。



这对你意味着什么：

- 通过构建 `parentId` 索引解析会话，而不是按行顺序读取。

- 只有文件处于静止状态时，才将最后一行视为叶节点；运行中的 Pi 可以把叶指针放在别处。

- 用 `custom` 条目保存扩展状态，用 `custom_message` 保存模型应当看到的文本。

- 用 `context_edit` 隐藏或重写更早的消息；原始行仍留在文件中。

# 压缩与分支摘要

---

**当上下文窗口填满时，Pi 会让模型为旧消息编写结构化检查点，并将它作为一个条目追加。文件保留每一行原始内容；只有模型看到的投影会变短。**



**长时间的编码会话终究会超出任何上下文窗口。Pi 的办法是压缩：总结当前路径中最旧的部分，逐字保留最新部分，并将结果记录为会话树中的 ****`compaction`**** 条目**，详见“会话：JSONL 树”（原书第86页）。本节介绍压缩何时触发、如何从溢出中恢复、切分点如何选取，以及摘要如何生成、使用什么提示词。最后介绍模型之后看到的内容，以及用户离开分支时 `/tree` 写入的分支摘要。

## 何时触发



默认值和阈值检查。来源：`CA/src/core/compaction/compaction.ts`。

```TypeScript
export const DEFAULT_COMPACTION_SETTINGS: CompactionSettings = {
    enabled: true,
    reserveTokens: 16384,
    keepRecentTokens: 20000,
};
...
export function shouldCompact(contextTokens: number, contextWindow: number, settings: CompactionSettings):
boolean {
    if (!settings.enabled) return false;
    return contextTokens > contextWindow - settings.reserveTokens;
}
```

采用默认值时，200,000 token 的窗口会在超过183,616 token 时压缩。`reserveTokens` 和 `keepRecentTokens` 可以在 `compaction.modelOverrides["provider/modelId"]` 下按模型覆盖，键必须精确匹配且区分大小写；`enabled` 仍然是全局设置，见 `CA/src/core/settings-manager.ts:940`。这三个键都列在“设置参考”（原书第202页）中。



上下文大小先测量，再估算。基础值取最后一条有效助手消息的 `usage.totalTokens`，或者其各部分之和；中止、出错以及用量全为零的响应不计入，见 `CA/src/core/compaction/compaction.ts:148`。之后的消息按字符数 ÷ 4 估算，每张图片按4,800个字符计，见 `CA/src/core/compaction/compaction.ts:276`。如果用量是在分支上最新的 `context_edit` 或压缩之前采集的，则不予采信，改为估算整个投影，见 `CA/src/core/compaction/compaction.ts:227`。

|---|---|---|
|每个后续轮次之前<br>|`prepareNextTurnWithContext → _compactBeforeNextAssistantResponse`，见 `CA/src/core/agent-session.ts:764`|阈值|

五个入口，一个生成器。手动和自动压缩最终都会进入 `_runDefaultCompaction()` 及 `compaction/` 中的 `compact()` 函数，除非 `session_before_compact` 处理器取消操作或提供了结果。依据 `agent-session.ts`。



溢出在一次运行之后处理，见 `CA/src/core/agent-session.ts:2933`。上下文溢出错误，或者在未达到模型自身输出限制时发生的 `length` 停止，都会启动恢复。Pi 通过 `replacement` 为 `null` 的 `context_edit` 条目隐藏失败的响应及其工具结果，见 `CA/src/core/agent-session.ts:1224`，然后压缩，并重试该轮次一次。第二次失败会以如下消息结束：`Context overflow recovery failed after one compact-and-retry attempt. Try reducing context or switching to a larger-context model.`（经过一次压缩并重试后，上下文溢出恢复失败。请尝试减少上下文，或切换到上下文窗口更大的模型。）如果是 `length` 停止，则消息为 `Truncated response recovery failed after one compact-and-retry attempt.`（经过一次压缩并重试后，截断响应恢复失败。）由不同于当前模型的模型报告的溢出会被忽略，早于最新压缩的任何助手消息也会被忽略。如果响应以 `stop` 完成，但仍然超过窗口，Pi 会执行压缩而不重试。

## 选择切分点



**`prepareCompaction()`**** 处理的是投影路径，而不是原始行**，见 `CA/src/core/compaction/compaction.ts:872`。**它从最新一次提供摘要的压缩之后开始，因此该次压缩所保留的条目，会与它的摘要一起再次被总结。随后，****`findProjectedCutPoint()`**** 从最新条目开始向后遍历，累加估算 token，直到总量达到 ****`keepRecentTokens`****，然后对齐到该条目或其后最近的有效切分点**，见 `CA/src/core/compaction/compaction.ts:802`。



![image\.png](图片和附件/image.png)

> 切分点绝不会落在工具结果上。**有效切分点是会产生 ****`user`****、****`assistant`****、****`bashExecution`****、****`custom`****、****`branchSummary`**** 或 ****`compactionSummary`**** 消息的条目**，因此调用及其结果会留在同一侧。此处切分点落在轮次中途的一条助手消息上，所以该轮次的开头会单独总结。本图为示意图，依据 `compaction.ts`（`isCutPointMessage`、`isTurnStartMessage`、`findProjectedCutPoint`、`prepareCompaction`）绘制。
> 
> 



对齐后，切分点会继续向前回退，越过相邻且不产生消息的条目，例如 `model_change`，让它们留在保留部分。如果切分条目不是轮次的起点，这次切分就是拆分轮次：**从轮次起点到切分点之前的消息会成为 ****`turnPrefixMessages`**，见 `CA/src/core/compaction/compaction.ts:903`。**轮次从 ****`user`****、****`bashExecution`****、****`custom`****、****`branchSummary`**** 或 ****`compactionSummary`**** 消息开始。**



![image\.png](图片和附件/image%202.png)



如果路径本来就以压缩条目结束，或者没有任何内容需要总结，`prepareCompaction()` 返回 `undefined`；手动压缩会分别报告 `Already compacted`（已压缩）和 `Nothing to compact (session too small)`（没有可压缩的内容，会话太小），见 `CA/src/core/agent-session.ts:2771`。否则，它返回一个 `CompactionPreparation`，供 `session_before_compact` 处理器接收：

- `firstKeptEntryId`：第一条逐字保留的条目的 ID。

- `messagesToSummarize`：从前一次边界到切分点的消息；若为拆分轮次，则到轮次起点为止；系统消息已移除。

- `turnPrefixMessages`：被拆分轮次中切分点之前的消息；其他情况下为空。

- `previousSummary`：即将被替换的压缩摘要，用于选择更新提示词。

- `fileOps`：读取、写入和编辑过的文件，取自 `read`、`write`、`edit` 工具调用、工具结果中记录的嵌套调用，以及前一次压缩的 `details`（如果该压缩由 Pi 生成），见 `CA/src/core/compaction/compaction.ts:60`。

- `tokensBefore`：压缩前对投影上下文的估算值。

## 生成摘要



![image\.png](图片和附件/image%207.png)

> **最多调用模型两次，每次都是单次请求。默认预留16,384 token 时，历史摘要最多可使用13,107个输出 token，轮次前缀摘要最多可使用8,192个输出 token，并且两者各自都受模型的 ****`maxTokens`**** 上限约束。**依据 `compaction.ts`（`compact`、`generateSummaryWithUsage`、`generateTurnPrefixSummary`）和 `agentsession.ts`（`compact`、`_runAutoCompaction`）。

**摘要请求有自己的系统提示词 ****`SUMMARIZATION_SYSTEM_PROMPT`****：“你是一个上下文总结助手。……不要继续对话。不要回答对话中的任何问题。只输出结构化摘要。**”见 `CA/src/core/compaction/utils.ts:161`。对话会被序列化为文本，因此模型是在阅读它，而不是继续它，见 `CA/src/core/compaction/utils.ts:114`：



摘要请求中的用户消息。来源：`CA/src/core/compaction/compaction.ts`（`generateSummaryWithUsage`、`SUMMARIZATION_PROMPT`）。

<conversation>

[Assistant thinking]: ...
[Assistant]: ...

[Tool result]: ...first 2,000 characters...

[... N more characters truncated]
</conversation>

...
</previous-summary>

The messages above are a conversation to summarize. Create a structured context checkpoint summary that another LLM will use to continue the work.

Use this EXACT format:
## Goal

### Blocked
## Key Decisions
## Next Steps

**根据代码组装；工具调用参数为示例，各标题下方括号内的提示已省略。仅在存在先前摘要时才出现 ****`<previous-summary>`****，此时 ****`UPDATE_SUMMARIZATION_PROMPT`**** 会将指令替换为保留条目、添加条目，以及将条目从 ****`In Progress`****（进行中）移到 ****`Done`****（已完成）的规则。只有 ****`/compact`**** 附带指令时才会出现 ****`Additional focus:`****（额外关注点：）。**



对于拆分轮次，会在 `Original Request`（原始请求）、`Progress So Far`（目前进展）和 `Context Needed to Continue`（继续工作所需的上下文）这几个标题下，单独总结轮次前缀。两段文本按 `history\n\n---\n\n**Turn Context (split turn):**\n\nprefix` 拼接；如果没有更早的历史，第一部分为 `No prior history.`（没有先前历史），见 `CA/src/core/compaction/compaction.ts:1032`。然后以 `<read-files>` 和 `<modified-files>` 块的形式追加排序后的文件列表；一个文件若既被读取又被修改，则只列为已修改，见 `CA/src/core/compaction/utils.ts:67`。



每个摘要请求都采用 `cacheRetention: "none"` 和新生成的 UUIDv7 `sessionId`，并经过会话的重试策略，见 `CA/src/core/compaction/compaction.ts:619`。只有模型支持推理，且为该请求解析出的思考级别不是 `off` 时，才会请求推理，见 `CA/src/core/compaction/compaction.ts:606`。响应如果以 `error` 或 `length` 停止，或包含工具调用，都会使压缩失败：`length` 停止意味着摘要不完整，绝不会存储，见 `CA/src/core/compaction/compaction.ts:585`。

## 之后模型会看到什么



`appendCompaction()` 存储 `summary`、`firstKeptEntryId`、`tokensBefore`、`details` 和 `usage`，以及 `systemMessage`：该时刻完整重放后的提示词和工具集，见 `CA/src/core/session-manager.ts:1261`。路径的下一次投影为：



```Plain Text
[ compaction.systemMessage ] ← 一条系统消息：所有分节、所有工具
[ user: "The conversation history before this point was compacted into the following summary:
<summary>
...
</summary>" ]
[ 从 firstKeptEntryId 到压缩条目之前的条目，移除原始系统消息 ]
[ 压缩之后追加的条目 ]
```



摘要以用户消息的形式送达提供商，由 `convertToLlm()` 根据 `COMPACTION_SUMMARY_PREFIX` 和 `COMPACTION_SUMMARY_SUFFIX` 构建，见 `CA/src/core/messages.ts:11`。原始条目仍留在 JSONL 文件中；压缩只改变 `buildSessionProjection()` 的返回内容。将叶指针移到不包含这次压缩的分支，就能恢复完整历史。



快照替换此前所有系统消息，因此摘要跟在一个完整的提示词之后，而不是一串补丁之后。这既重置了提示词历史，也重置了对话。也就是说，压缩后的第一次请求具有新的前缀，提供商缓存会从头开始。

## 分支摘要



当用户通过 `/tree` 跳转到另一个节点时（“斜杠命令与快捷键”，原书第197页），Pi 可以总结正在离开的分支。`navigateTree()` 分五步完成此事，见 `CA/src/core/agent-session.ts:3949`：

1. `collectEntriesForBranchSummary(oldLeaf, target)` 收集从旧叶节点回溯至它与目标最深共同祖先的条目，见 `CA/src/core/compaction/branch-summarization.ts:108`。

2. `session_before_tree` 处理器可以取消操作、提供摘要、替换或扩展指令，或者设置标签。

3. `generateBranchSummary()` 在 `contextWindow − branchSummary.reserveTokens` 的预算内，按从新到旧的顺序保留条目（默认预留16,384；窗口为0时按128,000计），跳过工具结果，并在预算使用量低于90%时尽量放入更早的一次压缩或分支摘要，见 `CA/src/core/compaction/branch-summarization.ts:195`。提示词采用压缩摘要的标题，但去掉 `Critical Context`（关键上下文）；`maxTokens` 为 `min(4096, model.maxTokens)`。

4. 结果前面加上 `The user explored a different conversation branch before returning here.\nSummary of that exploration:\n\n`（用户在回到这里之前探索了另一条对话分支。以下为该次探索的摘要：），后面加上文件列表，见 `CA/src/core/compaction/branch-summarization.ts:253`。

5. 如果目标是用户消息或自定义消息，新叶节点就是目标的父节点，目标文本会放回编辑器。否则，叶节点就是目标。随后 `branchWithSummary()` 将摘要追加为新叶节点的子节点，而不是旧分支的子节点。

    

在上下文中，该条目会变成一条用户消息，外面包裹 `The following is a summary of a branch that this conversation came back from:`（以下是本次对话返回前所在分支的摘要：）和 `<summary>` 标签，见 `CA/src/core/messages.ts:19`。设置 `branchSummary.skipPrompt` 会跳过交互提问，并默认不生成摘要。



> **经验法则**
> 
> 如果只是想让摘要聚焦某件事，向 `/compact` 传入指令即可。如果需要完全不同的摘要，就通过 `session_before_compact` 返回一个；它会以 `fromHook: true` 存储，其 `details` 不会作为文件列表读回。如果某个模型的窗口远大于其他模型，请为它设置一条 `modelOverrides`，而不是修改全局 `reserveTokens`。
