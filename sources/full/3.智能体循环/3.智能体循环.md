# 3\.智能体循环

# 智能体循环

---

**`pi-agent-core`**** 中的循环是一个自身不保存状态的函数：它以流式方式获取响应，运行工具调用，只要工具结果或排队消息仍有内容需要发送，就再次循环。它没有轮次上限。**



**Pi 在对话期间发出的每一次模型调用，都经过同一个函数：agent/agent\-loop\.ts 中的 ****`runLoop`****。**本节先介绍用于配置循环的类型，再逐个状态走读循环，区分向它提供消息的两个队列，最后跟踪一批工具调用的准备、执行和结果排序过程。“智能体事件与 Agent 类”（原书第57页）列出了它发出的事件；“AgentSession：组装运行时”（原书第61页）展示了编码智能体如何填充它的钩子。

## 包及其类型



@earendil\-works/pi\-agent\-core 1\.0\.4 由六个文件组成，共 2,513 行，其中非空行 2,281 行（research/out/stats\.txt）。它分为两层：无状态循环接收上下文和配置并发出事件；有状态的 Agent 类持有对话记录和两个队列。

|**文件**|**行数**|**内容**|
|---|---|---|
|agent/types\.ts|529|StreamFn、AgentLoopConfig、AgentMessage、AgentTool、AgentEvent、钩子类型|
|agent/agent\-loop\.ts|940|agentLoop、agentLoopContinue、runLoop、工具执行、runToolCall|
|agent/agent\.ts|613|Agent：状态归约器、Steering与follow\-up队列、运行生命周期|

整个运行时集中在三个文件中。行数由 28dcce2 版本上的 `wc -l` 得出。



循环从不直接调用提供商。它调用 `StreamFn`（agent/types\.ts:33），其形式与 pi\-ai 中的 `streamSimple` 相同（“流式事件协议”，原书第30页）。类型上写明了契约：流函数“不得因请求、模型或运行时故障而抛出异常或返回被拒绝的 Promise”；故障以最终消息的形式到达，其 stopReason 为 "error" 或 "aborted"。循环传入的是规范化后的对话记录，其中“系统提示词和工具声明由对话记录中的系统消息承载，绝不由 context\.systemPrompt 或 context\.tools 承载”（agent/types\.ts:23）。



消息是一个开放联合类型。`AgentMessage` 为 `Message | CustomAgentMessages[keyof CustomAgentMessages]`，而 `CustomAgentMessages` 是一个空接口，应用通过声明合并来扩展它（agent/types\.ts:365）。编码智能体以这种方式添加了四种角色（“AgentSession：组装运行时”，原书第61页）。



工具由 pi\-ai 的 Tool 加上运行时执行它所需的信息构成（agent/types\.ts:464）：

- `label`：供 UI 使用的人类可读名称

- `prepareArguments?(args)`：在模式校验之前，应用于原始参数的兼容性适配层

- `outputSchema?`：成功结果中 structuredContent 的 JSON Schema

- `execute(toolCallId, params, signal?, onUpdate?)`：返回 `AgentToolResult`，包含供模型使用的 content、供日志和 UI 使用的 details、可选的 structuredContent（不发送给模型）、usage、isError 和 terminate。Promise 结束后的 onUpdate 调用会被忽略（agent/types\.ts:458）

- `replay?`："never" 或 "safe"，用于结果未知的副作用的恢复策略

- `executionMode?`："sequential" 或 "parallel"，按工具覆盖整批执行模式

    

`AgentLoopConfig` 继承 `SimpleStreamOptions`，并承载所有钩子（agent/types\.ts:193）。思考级别通过继承来的 reasoning 字段传递，其中 "off" 存储为 undefined。

|**字段**|**调用时机**|**契约**|
|---|---|---|
|`model`|—|下一次请求使用的模型|
|`convertToLlm(messages)`|每次请求之前|`AgentMessage[] → Message[]`；丢弃仅供 UI 使用的消息；不得抛出异常|
|`transformContext?(messages, signal)`|convertToLlm 之前|在 AgentMessage 层级裁剪或注入消息；不得抛出异常|
|`getApiKey?(provider)`|每次请求之前|解析会过期的令牌；不得抛出异常|
|`prepareRequest?`|每次请求之前，包括第一次|可以替换本次及后续请求的上下文、模型和思考级别|
|`prepareNextTurn?`|turn\_end 之后、下一个 turn\_start 之前|返回 \{context?, messages?, model?, thinkingLevel?\}|
|`finishTurn?`|工具结果之后、turn\_end 之前|返回 \{action: "continue"\}、\{action: "end"\} 或不返回任何内容|
|`getSteeringMessages?`|循环开始时、每个轮次之后、prepareNextTurn 之后|取出并清除Steering队列中的待处理消息|
|`getFollowUpMessages?`|内层循环即将退出时|取出并清除follow\-up队列中的待处理消息|
|`toolExecution?`|—|"parallel"（默认）或 "sequential"|
|`beforeToolCall? / afterToolCall?`|每次工具调用|阻止调用；覆盖结果中的字段|



除 convertToLlm 外，每个钩子都是可选的。依据 agent/types\.ts:193–342 中的 AgentLoopConfig。

## 逐个状态走读循环



有两个入口：

- `agentLoop(prompts, context, config, signal, streamFn)`（agent/agent\-loop\.ts:38）从新的提示消息开始，返回 `EventStream<AgentEvent, AgentMessage[]>`。

- `agentLoopContinue(...)`（agent/agent\-loop\.ts:71）从现有上下文恢复；上下文为空时，它抛出 `Cannot continue: no messages in context`；最后一条消息是助手回复时，它抛出 `Cannot continue from message role: assistant`。

两者都有 run… 变体，这些变体接收事件接收器，而不是返回流，Agent 使用的就是这些变体。



**`runAgentLoop`****（agent/agent\-loop\.ts:102）在提示消息之前声明所有工具变更，发出 ****`agent_start`**** 和 ****`turn_start`****，再为每条提示消息发出 ****`message_start`**** 和 ****`message_end`****，然后将控制权交给 runLoop**（原文此处的源码引用截断为 `agent/agent-`）。

按从上到下的顺序阅读图3\.1（原书第51页），即可跟踪一个轮次。第一次经过时跳过 `prepareNextTurn`，因为 `runAgentLoop` 已经发出了 `turn_start`。此后每次经过都会运行它，再发出自己的 `turn_start`。待处理消息通过 `declareToolChanges`（agent/agent\-loop\.ts:333）注入；该函数比较运行时能够执行的工具（context\.tools）与对话记录中已声明的工具。差异会转化为系统消息上的 `toolsAdded` 或 `toolsRemoved`：若已有待处理的系统消息，就合并进去；否则，在第一条非系统消息之前插入一条内容为空的新系统消息。没有差异，就没有消息。



模型边界是 `streamAssistantResponse`（agent/agent\-loop\.ts:381），它足够简短，可以直接引用：

```JavaScript
// Apply context transform if configured (AgentMessage[] → AgentMessage[])
let messages = context.messages;
if (config.transformContext) {
    messages = await config.transformContext(messages, signal);
}

// Convert to LLM-compatible messages (AgentMessage[] → Message[])
const llmMessages = await config.convertToLlm(messages);

const llmContext = normalizeContext({ messages: llmMessages});

// Resolve API key (important for expiring tokens)
const resolvedApiKey =
(config.getApiKey ? await config.getApiKey(config.model.provider) : undefined) ||
config.apiKey;

const response = await streamFunction(config.model, llmContext, {
    ...config,
    apiKey: resolvedApiKey,
    signal,
});
```



提供商的 start 事件将部分消息推入上下文，并发出 `message_start`。九种块事件（text\_\*、thinking\_\*、toolcall\_\*）中的每一种都会替换最后一条消息，并随原始 `assistantMessageEvent` 发出 `message_update`。done 和 error 会等待 `response.result()`，在最终消息上写入 `thinkingLevel`，并发出 `message_end`（agent/agent\-loop\.ts:409）。



这些结果值得集中说明一次：

- 一个轮次是一次助手响应，加上它的工具调用及结果。AgentEvent 类型的注释明确这样说明（agent/types\.ts:518）

- 工具结果通过推入 `currentContext.messages` 反馈回来（agent/agent\-loop\.ts:274）。下一次经过循环时，会把它们放在上下文中，以流式方式获取新的响应

- 没有轮次上限。`runLoop` 中没有任何轮次计数逻辑

- 循环恰好在三个位置停止：响应的 `stopReason` 为 "error" 或 "aborted"（agent/agent\-loop\.ts:245）；finishTurn 返回 \{action: "end"\}（agent/agent\-loop\.ts:289）；以及某次经过时，没有未终止的工具结果、没有Steering、没有follow\-up，也没有显式继续的要求（agent/agent\-loop\.ts:317）

- 在错误出口，finishTurn 仍会运行，但其决定会被忽略；紧接着就会发出 turn\_end 和 agent\_end（agent/agent\-loop\.ts:252）



> **易踩的坑**
> 
> 被输出上限截断的响应，可能包含参数能够解析并通过校验、但实际并不完整的工具调用。当 stopReason 为 "length" 时，循环不会运行其中任何调用。每个调用都会得到错误结果：`Tool call "<name>" was not executed: the response hit the output token limit, so its arguments may be truncated. Re-issue the tool call with complete arguments.`（agent/agent\-loop\.ts:493）。模型看到的是错误，而非执行结果，循环会再次运行。
> 
> 

## Steering与follow\-up



两个队列从运行之外向循环提供消息。它们都存放 `AgentMessage`，由 `getSteeringMessages` 和 `getFollowUpMessages` 钩子取出待处理消息；Agent 将这两个钩子连接到 `PendingMessageQueue` 实例（agent/agent\.ts:496）。它们唯一的区别，是循环轮询它们的位置。

|**项目**|**Steering**|**follow\-up**|
|---|---|---|
|API|agent\.steer\(msg\)|agent\.followUp\(msg\)|
|用途|“在当前助手轮次结束后注入”（agent/agent\.ts:298）|“仅在智能体原本即将停止后运行”（agent/agent\.ts:303）|
|轮询位置|循环开始时 :176；每个 turn\_end 之后 :295；若上次轮询为空，则在 prepareNextTurn 之后 :204|内层循环退出时 :302|
|是否打断当前工具调用|否；“不会跳过当前助手消息中的工具调用”（agent/types\.ts:287）|否|
|交互快捷键|流式输出时按 Enter|Alt\+Enter（Windows 上为 Ctrl\+Q）|
|取出模式|steeringMode："one\-at\-a\-time"（默认）或 "all"|followUpMode：相同|



**Steering等待当前轮次的工具完成；follow\-up等待整个运行\(run\)结束。**轮询位置来自 agent/agent\-loop\.ts；快捷键来自 CA/src/core/keybindings\.ts:134 中的 `app.message.followUp`，以及 CA/src/modes/interactive/interactive\-mode\.ts:3358 中的提交处理器。



`one-at-a-time` 表示每个取出点只取出一条消息（agent/agent\.ts:159，TS）。

```TypeScript
peek(): AgentMessage[] {
    if (this.mode === "all") return this.messages.slice();
    const first = this.messages[0];
    return first ? [first] : [];
}

drain(): AgentMessage[] {
    const drained = this.peek();
    this.messages = this.messages.slice(drained.length);
    return drained;
}
```



`PendingMessageQueue.peek` 和 drain，第159–169行，内容未改动。



`prepareNextTurn` 之后再次轮询，是因为这个钩子可能运行数秒：编码智能体在那里进行压缩（“压缩与分支摘要”，原书第92页）。源码解释了这项保护：“只有前一次轮询没有返回任何内容时才再次轮询；否则，one\-at\-a\-time 模式会在此轮次交付两条消息”（agent/agent\-loop\.ts:202）。



采集工具在一个正在运行的工具内部，将一条Steering和一条follow\-up放入队列，随后让循环完成（research/out/agent\-loop\-queues\.txt）。Steering作为第2轮的用户消息进入，紧跟在工具结果之后；follow\-up则等到第2轮产生普通回答后，才开启第3轮。一次 agent\.prompt\(\) 产生了三个轮次，以及一个携带 8 条新消息的 agent\_end。

## 工具执行



`executeToolCalls`（agent/agent\-loop\.ts:508）为每一批调用选择执行模式。当 `config.toolExecution === "sequential"`，或任一被调用工具声明了 executionMode: "sequential" 时，按顺序执行；否则采用默认的并行执行。



每次调用首先由 `prepareToolCall`（agent/agent\-loop\.ts:707）依次完成准备：

1. 按名称查找工具。未知工具 → 错误结果 `Tool <name> not found`

2. 应用 prepareArguments，再运行 validateToolArguments。抛出的错误会成为错误文本

3. 调用 beforeToolCall。如果此时信号已中止 → `Operation aborted`。\{block: true\} → 带有 reason 的错误结果，默认文本为 `Tool execution was blocked`



上述任一结果都会立即返回：调用根本不会执行。否则，execute 会运行，抛出的错误会变成 isError: true 的结果（agent/agent\-loop\.ts:841）。随后，afterToolCall 逐字段覆盖结果：content、details、usage、terminate、structuredContent 和 isError（agent/agent\-loop\.ts:877）。若替换 content 却没有返回 structuredContent，则会丢弃 structuredContent，“因为它可能不再与内容匹配”（agent/types\.ts:85）。



![image\.png](图片和附件/image%202.png)

> 预检按顺序进行，执行并发进行，结果按原始顺序返回。research/out/agent\-loop\-queues\.txt 的事件7–15：faux 模型先请求 slow（id A），再请求 fast（id B）。tool\_execution\_end 遵循完成顺序（B 在 A 之前）；toolResult 消息遵循助手消息中调用的顺序（A 在 B 之前）。立即产生的结果会在预检期间发出其 tool\_execution\_end。
> 
> 



在顺序模式下，每次调用都会完成 `start → prepare → execute → finalize → tool_execution_end → toolResult 消息`，下一次调用才开始；若信号中止，整批调用会提前停止（agent/agent\-loop\.ts:575）。



只有当“一批调用中每个已最终确定的工具结果”都设置了 terminate: true 时，这一批调用才会提前结束运行（agent/agent\-loop\.ts:689）。只要有一个结果没有设置它，循环就会继续。



`runToolCall(toolCall, options)`（agent/agent\-loop\.ts:810）运行相同的 prepare → execute → finalize 流程，但“不发出事件，也不添加消息”。编码智能体将它用于工具通过 ctx\.executeTool\(\) 发起的调用（“扩展、加载与 API”，原书第113页）；codemode 正是通过这种方式，使用相同的权限钩子来运行嵌套调用（“codemode”，原书第151页）。



> 这对你意味着什么：
> 
> - 绝不要在 StreamFn、convertToLlm、transformContext 或队列钩子中抛出异常；应返回失败消息或安全的回退结果
> 
> - 要预期多个 `tool_execution_end` 事件可能按任意顺序到达；通过 toolCallId 匹配它们，并从 toolResult 消息中按原始顺序读取结果
> 
> - 使用Steering，在当前工具完成后改变方向；使用follow\-up，将工作排队到智能体原本即将停止时执行
> 
> - 在 finishTurn 中或通过中止来自行限制长时间运行：循环没有轮次上限
> 
>

# 智能体事件与 Agent 类

---

十种事件类型描述每一次运行，按运行、轮次和消息嵌套。Agent 类会在任何监听器看到事件之前，根据该事件更新自身状态；直到最后一个 agent\_end 监听器返回之前，它都保持忙碌。



所有观察 Pi 工作的组件，包括终端 UI、JSON 和 RPC 输出、扩展、会话文件，都由同一条事件流驱动。本节列出十种 AgentEvent 类型及其载荷，并通过一次真实运行展示它们的到达顺序。随后介绍发出这些事件的 Agent 类：它的默认值、prompt 和 continue 规则、状态归约器，以及它如何收尾一次抛出异常的运行。

## 十种事件



**AgentEvent 是包含十个成员的可辨识联合类型**（agent/types\.ts:514）。它们分布于三个嵌套生命周期和一个工具生命周期中。

|**事件**|**载荷**|**发出时机**|
|---|---|---|
|`agent_start`|—|一次；运行的第一个事件|
|`agent_end`|messages: AgentMessage\[\]|一次；运行的最后一个事件；messages 为本次运行的新消息|
|`turn_start`|—|每次助手响应之前|
|`turn_end`|message: AgentMessage, toolResults: ToolResultMessage\[\]|响应及其所有工具结果之后|
|`message_start`|message: AgentMessage|用于 system、user、assistant、toolResult 和自定义消息|
|`message_update`|message, assistantMessageEvent: AssistantMessageEvent|仅用于助手消息；每个流式块事件对应一次|
|`message_end`|message: AgentMessage|消息最终确定时|
|`tool_execution_start`|toolCallId, toolName, args|调用准备之前|
|`tool_execution_update`|toolCallId, toolName, args, partialResult|正在运行的工具每次调用 onUpdate 时|
|`tool_execution_end`|toolCallId, toolName, result, isError|afterToolCall 之后，按完成顺序|



只有助手消息以流式方式传递；其他消息都以 start/end 对的形式到达。依据 agent/types\.ts:514–529 中的 AgentEvent；发出位置位于 agent/agent\-loop\.ts。



`message_update` 携带触发它的 pi\-ai 事件（text\_delta、toolcall\_end 等，见“流式事件协议”，原书第30页），以及部分消息的浅拷贝。agent\_end 是运行的最后一个事件，但该类型自己的注释提醒说：被等待的“该事件监听器仍属于运行收尾的一部分。只有这些监听器结束后，智能体才会变为空闲”（agent/types\.ts:510）。

## Agent 类

# 从 prompt\(\) 到 agent\_settled

```TypeScript
    if (this._agentRunAbortRequested) break;
    await this.agent.continue();
    }
} finally {
    if (this._agentRunAbortRequested) this._finishCancelledRetry();
    this._failedResponse = undefined;
    this._runSystemPromptOptions = undefined;
    this._flushPendingBashMessages();
    this._flushPendingCustomMessages();
    await this._emitAgentSettled();
}
```

`_handlePostAgentRun`（CA/src/core/agent\-session\.ts:1839）在以下三种情况下返回 true，表示再次运行，并按此顺序检查：

1. 最后一条助手消息是可重试错误，且 `_prepareRetry` 已安排重试

2. `_checkCompaction` 在溢出或可恢复的 length 停止之后执行了压缩，并要求继续被打断的轮次（“压缩与分支摘要”，原书第92页）

3. 队列中仍有消息，例如循环取完两个队列后，agent\_end 处理器又加入的消息



当它返回 false 时，`_runBeforeSettleBoundary` 通过 `agent_before_settle` 事件，让扩展作出最后决定（CA/src/core/agent\-session\.ts:1879）。处理器可以追加条目并要求继续；只有当投影后的上下文能够继续时，驱动器才会继续，否则会报告 `agent_before_settle requested continuation without runnable model context`。如果没有处理器，则只有存在排队消息时才会继续。

## 自动重试



当 pi\-ai 的 `isRetryableAssistantError` 判定失败响应可重试，且它不是由压缩机制处理的上下文溢出时，该响应才可重试（CA/src/core/agent\-session\.ts:1694）。isRetryableAssistantError 要求 stopReason 为 "error"，且 errorMessage 匹配可重试提供商模式，同时不匹配不可重试限制模式（ai/utils/retry\.ts:250；“身份验证、费用、重试与模型目录”，原书第41页）。



|**设置**|**默认值**|**作用**|
|---|---|---|
|retry\.enabled|true|开启或关闭智能体级重试|
|retry\.maxRetries|3|首次失败后的尝试次数|
|retry\.baseDelayMs|2000|第1次重试之前的延迟|
|retry\.maxAgentDelayMs|60000|任意单次延迟的上限|



三次重试分别等待 2 s、4 s 和 8 s。getRetrySettings 位于 CA/src/core/settings\-manager\.ts:1000；延迟为 baseDelayMs × 2^\(attempt − 1\)，上限为 maxAgentDelayMs（ai/utils/retry\.ts:126）。随软件提供的 CA/docs/settings\.md 设置表与此一致。



`_prepareRetry`（CA/src/core/agent\-session\.ts:3747）递增尝试计数器，并发出 auto\_retry\_start \{attempt, maxAttempts, delayMs, errorMessage\}。随后，它通过 replacement 为 null 的 context\_edit 条目（\_omitRecoveryAttempt），向模型隐藏失败消息：这次尝试仍保留在原始 JSONL 中，但从投影中消失（“会话：JSONL 树”，原书第86页）。经过可中止的等待后，驱动器调用 agent\.continue\(\)。如果所选模型为虚拟模型，该请求会以 reason "retry" 路由，并将失败消息作为 failed 传入（CA/src/core/agent\-session\.ts:810）。



尝试以三种方式之一结束。后续响应若不是错误，会发出 `auto_retry_end {success: true}`。尝试次数耗尽时，发出 `auto_retry_end {success: false, finalError}`（CA/src/core/agent\-session\.ts:1860）。若在等待期间中止，则发出 `finalError: "Retry cancelled"` 的 auto\_retry\_end（CA/src/core/agent\-session\.ts:3739）。



如果客户端需要知道“模型已完成回答”，应等待 agent\_settled。如果需要知道“本次尝试失败”，则读取 agent\_end 上的 willRetry：true 表示后面还有一次运行。

## 模型与思考控制



`setModel(model, {persist})`（CA/src/core/agent\-session\.ts:2463）在没有身份验证信息时抛出 `No API key for <provider>/<id>`。随后，它设置 agent\.state\.model，追加 model\_change 条目，可选择保存默认模型，应用思考级别，并在模型发生变化时发出扩展事件 model\_select。级别按以下顺序选择：显式级别（仅限限定范围内的模型）、按模型设置、默认级别设置、当前级别，最后为 "medium"（CA/src/core/agent\-session\.ts:2655）。



`setThinkingLevel(level, {persist})`（CA/src/core/agent\-session\.ts:2598）将级别限制在模型支持的范围内。只有限制后的级别不同于当前级别时，才会追加 thinking\_level\_change、发出 thinking\_level\_changed，并触发扩展事件 thinking\_level\_select。设置 persist 时，它保存的是请求的级别，而非限制后的级别。



`cycleModel(direction)`（CA/src/core/agent\-session\.ts:2505）在限定范围内（\-\-models 或 enabledModels）当前可用的模型中循环切换；如果没有限定范围，则在所有可用模型中切换。候选模型至多一个时，它返回 undefined。



运行期间所作的更改，在下一轮生效，而不是影响当前请求。prepareNextTurn 会向循环返回当前的 agent\.state\.model 和 thinkingLevel（“AgentSession：组装运行时”，原书第61页）。

## 用户 bash：\!cmd 和 \!\!cmd



在编辑器中，`!cmd` 运行 shell 命令，而 `!!cmd` 运行命令时会设置 `excludeFromContext`（CA/src/modes/interactive/interactive\-mode\.ts:3327）。首先发出扩展事件 user\_bash 的是模式，而不是会话（CA/src/modes/interactive/interactive\-mode\.ts:6956）。处理器可以返回完整结果，由 recordBashResult 记录，而不实际运行任何内容；也可以返回替代本地执行的操作，例如通过 SSH 或在 VM 中运行。RPC 模式对其 bash 命令采用相同方式（CA/src/modes/rpc/rpc\-mode\.ts:562）。



`executeBash(command, onChunk?, {excludeFromContext, id, operations})`（CA/src/core/agent\-session\.ts:3826）会在单独的一行中前置 shellCommandPrefix 设置，在会话的工作目录中运行命令，并为每个输出块发出 bash\_execution\_update \{id, delta\}。随后，recordBashResult 存储一条 BashExecutionMessage。如果智能体正在流式输出，则先保留该记录，在运行收尾时或下一次提示之前追加，因此它绝不会落在工具调用和其结果之间（CA/src/core/agent\-session\.ts:3877）。



**`!!cmd`**** 的输出会显示并保存，但绝不会发送给模型**：convertToLlm 会丢弃设置了 excludeFromContext 的 bashExecution 消息（“AgentSession：组装运行时”，原书第61页）。

## AgentSessionEvent



**`AgentSessionEvent`**（CA/src/core/agent\-session\.ts:191）**在 AgentEvent 事件流的基础上作了两项修改，并增加了十二种自身事件。通过 ****`ctx.executeTool()`**** 发起的调用，其工具执行事件携带 ****`parentToolCallId`****；agent\_end 则增加 willRetry。**

|**事件**|**载荷**|**含义**|
|---|---|---|
|`agent_end`|messages, willRetry|一次底层运行结束；若后续有自动重试，则 willRetry 为真|
|`agent_settled`|—|prompt\(\) 已没有剩余自动工作|
|`queue_update`|steering: string\[\], followUp: string\[\]|两个队列当前的完整文本|
|`compaction_start`|reason: "manual" \| "threshold" \| "overflow"|压缩开始|
|`compaction_end`|reason, result, aborted, willRetry, errorMessage?|压缩完成、失败或被中止|
|`entry_appended`|entry|追加了非消息条目（见“AgentSession：组装运行时”，原书第61页）|
|`session_info_changed`|name|显示名称已设置或清除|
|`thinking_level_changed`|level|实际生效的思考级别已改变|
|`auto_retry_start`|attempt, maxAttempts, delayMs, errorMessage|已安排重试|
|`auto_retry_end`|success, attempt, finalized?|重试序列结束|
|summarization\_retry\_sched/\_attempt\_start/\_finished|尝试数据；source 为 "compaction" 或 "branchSummary"|压缩请求或分支摘要请求的重试|
|`bash_execution_update`|id?, delta|一块用户 bash 输出|



十种智能体事件之上，还有十二种会话事件。依据 CA/src/core/agent\-session\.ts:191–232 的 AgentSessionEvent 联合类型；三种 summarization\_retry\_\* 类型共用一行。“RPC 模式与 SDK”（原书第133页）展示了它们在线路上传输时的形式。



> 这对你意味着什么：
> 
> - 对每一个可能在运行中途到达的 prompt\(\)，都传入 streamingBehavior；没有它，调用会抛出异常
> 
> - 将 agent\_settled 视为空闲，将 agent\_end 视为一次尝试结束
> 
> - 在设置中调整 retry\.\*，而不是由客户端重试；Pi 已经会向模型隐藏失败尝试
> 
> - 拦截 user\_bash，可将 \! 命令转移到另一台机器；executeBash 自身不会发出该事件
