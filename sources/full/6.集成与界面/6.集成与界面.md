# 6\.集成与界面

# MCP：从 mcp\.json 到工具调用

---

**Pi 1\.0 自带 MCP 客户端，并将每个服务器工具注册到常规工具流水线中。默认情况下，这些工具不会以声明的形式呈现给模型；模型通过 codemode 脚本访问它们。**



Model Context Protocol（模型上下文协议）服务器是提供工具和资源的进程或 URL。Pi 不借助官方 SDK 便可连接服务器，将每个工具命名为 `mcp__<server>__<tool>`，并让每次调用走与 `read` 或 `bash` 相同的流水线，因此 `tool_call` 钩子和权限关卡照常生效。本节介绍实现这一机制的两层结构，以及客户端的连接和超时规则，随后说明配置文件及其信任规则、决定模型如何访问工具的四种暴露方式，以及服务器故障时哪些操作会重试。

## 两层结构



第一层是 `@earendil-works/pi-mcp` 1\.0\.4：“一个小型、独立的 Model Context Protocol 客户端，不依赖官方 MCP SDK 或其他 pi 包”（`mcp/README.md`）。它唯一的运行时依赖是 `cross-spawn` 7\.0\.6（`mcp/package.json`）。OAuth 代码“改编自采用 MIT 许可证的 Model Context Protocol TypeScript SDK v1\.29\.0”，其许可证随包附在 `LICENSES/` 下（`mcp/README.md` 的“OAuth”节）。



第二层是 `CA/src/extensions/mcp/` 中内置的 `mcp` 扩展。它注册为可替换的内置扩展：如果某个扩展注册了 `/mcp`，就会接替它，而不是与它并行运行（`CA/src/extensions/index.ts:9`）。与服务器通信的部分采用延迟加载，因此“未配置服务器的会话永远不必承担这部分开销”（`CA/src/extensions/mcp/index.ts:1021`）。

## 客户端



`McpClient` 使用协议版本 `2025-11-25`，也接受协商为 `2025-06-18`、`2025-03-26` 或 `2024-11-05` 的服务器（`mcp/src/protocol/types.ts:4`）。它有 `idle`、`connecting`、`connected` 和 `closed` 四种状态（`mcp/src/client.ts:41`）；除 `idle` 外，`connect()` 拒绝在任何其他状态下运行（`mcp/src/client.ts:202`）。



![image\.png](图片和附件/image%204.png)

> 服务器只有通过版本检查并完成 `notifications/initialized` 后才可用。如果服务器选择了未列出的版本，就会报错“MCP 服务器选择了不受支持的协议版本……”并关闭客户端。步骤 1–3 为 `connect()`，步骤 4 为 `listAll`，步骤 5 为带进度通知的 `requestInternal`。来源：`mcp/src/client.ts`。
> 
> 



**超时。** 库中的请求会在 30 s 后超时（`mcp/src/client.ts:38`），而 Pi 中为 60 s；Pi 的每服务器配置项 `timeout` 以秒为单位（`CA/src/extensions/mcp/runtime.ts:48`）。请求的每条进度通知都会重新启动计时器（`mcp/src/client.ts:531`）。计时器到期或调用方的 signal 中止时，客户端会拒绝该请求并发送 `notifications/cancelled`；它绝不会取消 `initialize`，因为规范禁止这样做（`mcp/src/client.ts:556`）。



支持的功能包括：`ping`、分页的 `tools/list`、带结构化内容的 `tools/call`、资源和模板、服务器发起的 `ping` 和 `roots/list` 请求、日志和列表变更通知、进度、取消以及 OAuth。“批量 JSON\-RPC 消息、旧式 HTTP\+SSE、服务器、采样和任务不在初始核心范围内”（`mcp/README.md` 的“支持的协议范围”节）。



|**传输方式**|**行为**|
|---|---|
|stdio，`transports/stdio.ts`|使用 `cross-spawn`，不经过 shell；除 Windows 外，在所有平台上都分离到自身的进程组中（`mcp/src/transports/stdio.ts:101`）。关闭时先结束 stdin，500 ms 后向进程组发送 `SIGTERM`，再过 2 s 发送 `SIGKILL`。Windows 上使用 `taskkill /T /F`。退出钩子在 Pi 退出时向仍存活的进程组发送 `SIGTERM`。保留 stderr 的最后 64 KiB|
|Streamable HTTP，`transports/streamable-http.ts`|发送带有 `accept: application/json, text/event-stream` 的 POST。捕获 `Mcp-Session-Id` 并在后续请求中带回；关闭时发送 DELETE。初始化后打开 GET SSE 流（405 表示不提供该流），对断开的流进行 5 次重连，退避从 1 s 增长至 30 s，并通过 `Last-Event-ID` 恢复。401，或质询信息为 `insufficient_scope` 的 403，会交给认证提供商处理|
|SSE（旧式）|校验时拒绝：“不支持旧式 SSE 传输；请使用 streamable HTTP URL”（`CA/src/core/mcp-servers.ts:270`）|



两种传输方式，共用同一个消息大小上限。两者都会拒绝超过 16 MiB 的单条消息（`mcp/src/transports/transport.ts:3`）。来源：`mcp/src/transports/`。

## 配置



Pi 先读取智能体目录中的 `mcp.json`，即 `~/.pi/agent/mcp.json`，再读取项目中的 `.pi/mcp.json`；只有项目受信任时才会读取项目文件（`CA/src/extensions/mcp/config.ts:145`）。两者都使用其他 MCP 客户端采用的 `mcpServers` 结构：



一个 stdio 服务器和一个 HTTP 服务器。来源：`CA/docs/mcp.md`。

```JSON
{
  "mcpServers": {
    "filesystem": {
      "command": "npx",
      "args": ["-y", "@modelcontextprotocol/server-filesystem", "."]
    },
    "docs": {
      "url": "https://example.com/mcp",
      "headers": { "Authorization": "Bearer ${DOCS_TOKEN}" },
      "description": "Search and read the product documentation"
    }
  }
}
```

> 完整示例，出自“配置服务器”节。`command` 选择 stdio，`url` 选择 streamable HTTP；`type` 可省略。
> 
> 



这些条目的类型定义位于 core 而非扩展中，因为扩展也能通过 `pi.registerMcpServer()` 注册服务器（`CA/src/core/mcp-servers.ts:1`）：

- **所有服务器：** `exposure?`（默认 `"codemode"`）、`description?`、`toolExposure?: Record<string, McpExposure>`、`enabled?`（默认 `true`）、以秒为单位的 `timeout?`（默认 60）（`CA/src/core/mcp-servers.ts:59`）

- **Stdio：** `type?: "stdio"`、`command`、`args?`、`env?`、`cwd?`。`env` 的值可以是 `${NAME}` 或 `!command`；相对的 `cwd` 会以会话目录为基准解析（`CA/src/core/mcp-servers.ts:80`）

- **HTTP：** `type?: "http"`（也接受 `"streamable-http"`）、`url`、`headers?`、`oauth?: McpOAuthConfig` 以及 `auth?: { provider }`。`auth` 会发送 `/login` 提供商的令牌，除回环主机外都要求使用 https（`CA/src/core/mcp-servers.ts:137`）

- **服务器名称：** 必须匹配 `^[A-Za-z0-9_-]+$`（`CA/src/core/mcp-servers.ts:152`）。仅在 `-` 和 `_` 上不同的两个名称共享同一命名空间，因此第二个会因冲突而被拒绝（`CA/src/extensions/mcp/config.ts:128`）

- **工具名称：** 采用 `mcp__<server>__<tool>`，其中不属于 `[A-Za-z0-9_]` 的字符都替换为 `_`。若名称超过 64 个字符，或已被其他 MCP 工具占用，则会截短，并追加 `_` 和服务器与工具的 SHA\-256 的 8 个十六进制字符（`CA/src/extensions/mcp/tools.ts:84`）



采集工具集对该构建运行了 `createMcpToolName`。`dev-radius / list.items` 变为 `mcp__dev_radius__list_items`；`github` 上一个 60 字符的工具名变为以 `_5204ba68` 结尾的 64 字符名称；如果某台服务器上的 `mcp__srv__a_b` 已被占用，则 `a-b` 会变为 `mcp__srv__a_b_5c15ffbd`（`research/out/mcp-naming.txt`）。



**合并规则。** 同名项目条目会替换用户条目。但不含 `command`、`url` 或 `type` 的项目条目属于覆盖项，只能设置用户条目的 `enabled`、`exposure` 和 `toolExposure`；其他内容都会报错（`CA/src/extensions/mcp/config.ts:108`）。项目文件不能设置 `auth`：“项目文件不能使用它，这样仓库就无法决定凭据发往何处”（`CA/src/extensions/mcp/config.ts:25`）。顶层的 `autoEnableCodemode`（默认 `true`）可以出现在任一文件中，项目值优先（`CA/src/extensions/mcp/config.ts:28`）。

## 模型如何访问 MCP 工具



每个工具都有四种暴露方式之一：优先使用其 `toolExposure` 条目，其次使用服务器的 `exposure`，最后默认为 `codemode`。精确工具名优先于模式匹配；多个模式中，对象中最先匹配的那个生效（`CA/src/core/mcp-servers.ts:234`）。`codemode-deferred` 可作为 `codemode` 的旧别名（`CA/src/core/mcp-servers.ts:57`）。

|**暴露方式**|**是否向模型声明**|**能否从 codemode 调用**|**Pi 激活的工具**|
|---|---|---|---|
|`codemode`（默认）|否|是|`codemode`，除非 `autoEnableCodemode` 为 `false`|
|`deferred`|由 `tool_search` 加载后声明|是|`tool_search`|
|`direct`|是|是|—|
|`hidden`|否|否|—|



四种暴露方式中，有三种不会将工具加入请求。来源：`McpExposure` 的文档注释（`CA/src/core/mcp-servers.ts:43`）和 `ensureDiscoveryActive`（`CA/src/extensions/mcp/index.ts:466`）。在 Pi 内部，`codemode` 和 `deferred` 都映射为工具暴露方式 `deferred`；两者仅在所激活的辅助工具上不同（`CA/src/extensions/mcp/tools.ts:44`）。

> 每条路径最终都进入同一流水线并使用同一连接。不同的仅是第一跳：脚本调用、已加载的声明或已声明的工具。示意图来源：`CA/src/extensions/mcp/index.ts`（模块注释、`ensureDiscoveryActive`、`tool_call` 处理器）和 `tools.ts`（`createMcpToolDefinition`）。
> 
> 



**`mcp_servers`**** 章节。** 模型通过系统提示词中的一个章节得知 `codemode` 或 `deferred` 服务器的存在，因为 `codemode` 和 `tool_search` 都不会列出这类服务器（`CA/src/extensions/mcp/index.ts:186`）。每台已启用的服务器占一行，包含其命名空间、访问路径，以及描述的第一行；连接后则使用服务器指令的第一行。每台服务器最多 250 个字符，整个章节最多 4,096 个字符（`CA/src/extensions/mcp/index.ts:154`）。对上面的 `docs` 服务器加上随附文档中的 GitHub 示例，该构建生成如下内容：



```Plain Text
工具尚未向你声明的 MCP 服务器。请通过 codemode 脚本调用 `codemode` 服务器的工具。
- mcp_docs (codemode): 搜索和阅读产品文档
- mcp_github (codemode)
```



还传入了第三台只有 `direct` 工具的服务器；它按设计被排除在外（`research/out/mcp-naming.txt`）。该章节在 `before_agent_start` 中设置（`CA/src/extensions/mcp/index.ts:1062`）。当它与对话记录中已有的内容不同时，会话会追加一条仅包含已变化章节的系统消息，而不会改写之前的消息（`CA/src/core/agent-session.ts:1714`）；“从 `prompt()` 到 `agent_settled`”（原书第67页）介绍了这项差异。



**谁等待谁。** 服务器在后台连接。第一个提示词最多等待 10 s，而且只等待包含 `direct` 工具的服务器，因为必须在请求中声明这些工具（`CA/src/extensions/mcp/index.ts:93`）。只有在 `scriptNeedsServer` 判定需要时，codemode 脚本才等待尚未连接完成的服务器：代码中包含服务器的命名空间，或包含 `searchTools`、`describeNamespace`、`describeTool`、`ALL_TOOLS` 中任意一项（`CA/src/extensions/mcp/index.ts:223`）。`tool_search` 和资源工具会等待所有服务器（`CA/src/extensions/mcp/index.ts:1073`）。



**结果。** 面向模型的文本超过 20 KiB 时，会保留开头和结尾，中间插入 `…N chars truncated…` 标记；完整文本写入结果中指定的临时文件（`CA/src/extensions/mcp/tools.ts:51`）。脚本接收移除 `_meta` 后的完整 `CallToolResult`，绝不截断；带有 `isError` 的结果在脚本中正常 resolve，但对直接调用而言属于错误结果。



资源通过 `list_mcp_resources`、`list_mcp_resource_templates` 和 `read_mcp_resource` 呈现给模型，这些是“Codex 和 opencode 使用的工具”（`CA/src/extensions/mcp/resources.ts:2`）。MCP App 资源，即 `ui://` URI 或 `profile=mcpapp` HTML，会被排除（`CA/src/extensions/mcp/resources.ts:47`）。

## 故障、重试与登录



|**失败情况**|**Pi 的处理**|**位置**|
|---|---|---|
|连接 HTTP 服务器，发生暂时性错误|250 ms 后重试，然后 1,000 ms 后再次重试|`CA/src/extensions/mcp/runtime.ts:362`|
|连接 stdio 服务器|不重试|同上|
|`tools/call`，任何 HTTP 错误|不重试：“它们可能已经运行过”|`CA/src/extensions/mcp/runtime.ts:297`|
|任何请求，会话过期（404）|在新会话中重试一次|同上|
|列出或读取资源，发生暂时性错误|250 ms 后重试一次|同上|
|连接断开|状态设为 `disconnected`；下次调用时重新连接|`CA/src/extensions/mcp/runtime.ts:53`|



只会重试不可能已经执行过的请求。“暂时性”错误指 HTTP 408、429，以及除 501 外的 500 及以上状态码，再加上 `fetch` 抛出的 `TypeError`（`CA/src/extensions/mcp/runtime.ts:70`）。



**OAuth。** 未设置 `auth` 且没有 `Authorization` 标头的 HTTP 服务器通过 OAuth 登录（`CA/src/extensions/mcp/runtime.ts:83`）。流程使用 PKCE 和回环回调。Pi 通过动态客户端注册，以 `client_name` 为 `pi`（或 `oauth.clientName`）标识自身，也可以通过 https://pi\.dev/oauth 上的 Client ID Metadata Document 标识自身；如果 403 要求更大的权限范围，则会再次登录以提升授权（`mcp/README.md` 的“支持的协议范围”节；`CA/src/extensions/mcp/oauth.ts:272`）。授权服务器发送 RFC 9207 的 `iss` 参数时，CIMD 客户端 ID 为 https://pi\.dev/oauth/client\.json；未发送时则为 `https://pi.dev/oauth/<id>/client.json`，并使用匹配的回调路径（`CA/src/extensions/mcp/oauth.ts:253`）。凭据保存在智能体目录的 `mcp-auth.json` 中（`CA/src/extensions/mcp/oauth.ts:144`），文件以 `0600` 模式创建（`CA/src/core/auth-storage.ts:25`）。



**命令。** `pi mcp add | remove | list | login | logout` 无需会话即可运行；`add` 和 `remove` 接受 `-l/--local` 来操作项目文件，`list` 接受 `--json`（`CA/src/extensions/mcp/cli.ts:33`）。在会话中，`/mcp` 打开管理器（`CA/src/extensions/mcp/index.ts:1141`）。`--no-mcp` 在本次运行中禁用内置支持（`CA/src/cli/args.ts:185`）。



> **文档 ≠ 代码**
> 
> `CA/docs/mcp.md` 写道：“HTTP 网络错误和暂时性状态码（408、429 和 5xx）会重试两次。”但 `isTransientError` 排除了 501（`CA/src/extensions/mcp/runtime.ts:72`）。同一页面及 `config.ts` 中的注释还说，Pi 会“在采用 codemode 暴露方式的服务器连接后”激活 codemode。实际上，`ensureDiscoveryActive` 会在会话开始时依据配置激活它，此时还没有任何服务器连接，因此即使某台服务器永远连不上，也仍会启用 codemode（`CA/src/extensions/mcp/index.ts:466`）。
> 
> 



> **对你的意义：**
> 
> - 默认情况下，MCP 工具不会出现在请求中；请在 `mcp_servers` 章节和 codemode 脚本中寻找它们
> 
> - 为每台服务器写一句话的描述；这是模型在连接前唯一会读到的内容
> 
> - 对少数常用工具使用 `direct`，并接受第一个提示词最多等待其服务器 10 s
> 
> - 将凭据和 `auth` 放在用户级 `mcp.json` 中；项目文件只能切换启用状态和调整暴露方式
> 
> - 将失败的工具调用视为可能已经执行过；Pi 不会重试，你也不应重试
> 
>

# Codemode：调用工具的脚本

---

**Codemode 在全新的 QuickJS VM 中运行模型编写的 JavaScript；这个 VM 唯一的能力就是调用工具。每个嵌套调用都会经过完整的工具流水线，但只有脚本输出进入上下文。**



**如果模型需要从五十个 issue 中筛出三个，可以发起五十次工具调用，也可以编写一个脚本。Codemode 就是第二种选择。**模型发送 JavaScript；Pi 在 WebAssembly 沙箱中运行它，`tools.<name>(args)` 是沙箱唯一的出口；嵌套调用的结果会留在脚本中，除非脚本将其打印出来。本节介绍沙箱，以及为什么它由一个 worker、一个 wasm 实例和一个共享标志构成，随后介绍 codemode 工具：它的 schema 和语法、模型读取的描述、嵌套调用如何执行，以及最终返回的内容。

## 两个包



`@earendil-works/pi-codemode` 1\.0\.4“在 QuickJS VM（编译为 WebAssembly）中运行模型编写的 JavaScript，其唯一能力是调用注入的工具。嵌套工具调用永远不会进入 LLM 上下文；只有脚本的输出和返回值会进入”（`codemode/README.md`）。它不依赖 Pi，唯一的运行时依赖是 `quickjs-wasi` 3\.6\.2（`codemode/package.json`）。

## 沙箱



**每次 ****`execute()`**** 都创建一个新的 ****`worker_threads`**** Worker，而 worker 从编译好的 wasm 模块实例化一个新的 QuickJS VM。**“每次运行使用一个全新 worker，可以让终止操作保持简单：失控的脚本，包括只会让微任务队列空转的脚本，都会被 `terminate()` 杀死，无法污染后续运行”（`codemode/src/runtime/host.ts:120`）。



![image\.png](图片和附件/image%201.png)

> VM 只能通过一个桥接函数访问主机，而主机有两种方式可以停止 VM。消息以 JSON 字符串形式传递；worker 自身从不构建结构化值。示意图来源：`codemode/src/runtime/protocol.ts`（`WorkerData`、`WorkerToHostMessage`、`HostToWorkerMessage`）、`worker.ts` 和 `host.ts`。
> 
> 



**隔离。** VM 是独立的 wasm 实例，拥有自己的线性内存。它唯一的导入是一个 WASI 适配层和一个主机调用入口；worker 会丢弃该适配层写入 stdout 和 stderr 的内容（`codemode/src/runtime/worker.ts:32`）。其中没有计时器、`fetch`、`process`、`require`、模块或 `WebAssembly`；“`eval` 和 `Function` 可以工作，但只能在同一个 VM 内生成更多代码”（`codemode/README.md`）。脚本运行前，前置代码会冻结内置对象，因此即使脚本修改 `Array.prototype.toJSON`，也无法破坏前置代码向主机报告的内容（`codemode/src/runtime/prelude-source.ts:28`）。



**为什么使用 worker。** QuickJS 同步运行；若脚本在主机线程上空转，就会阻塞 Pi 的事件循环。**为什么使用标志。** 在 Bun 上，`terminate()`“无法停止一个正在 wasm 内空转的线程”（`codemode/src/runtime/protocol.ts:21`），所以主机先设置共享的 `Int32`，VM 的 `interruptHandler` 再轮询它（`codemode/src/runtime/worker.ts:60`）。**为什么设置 ****`maxStackSize`****。** 没有它，“深度递归会使 wasm 栈溢出并触发陷阱，而不是抛出可捕获的 `RangeError`”（`codemode/src/runtime/worker.ts:57`）。



采集工具集对固定版本的构建运行了五个脚本，执行期限为一秒：

**嵌套调用。** 脚本可以调用已激活的 `direct` 工具，以及所有 `codemode` 或 `deferred` 工具，但不能调用 codemode 本身，因为它的暴露方式是 `model-only`（`CA/src/extensions/codemode/tool.ts:392`）。每次调用都通过 `ctx.executeTool(name, args, { signal })`，因此校验、`tool_call` 和 `tool_result` 钩子，以及权限关卡，都与直接调用一样生效（`CA/src/extensions/codemode/execute.ts:405`）。嵌套调用的 ID 为 `<codemode call id>/<n>`，其中 `n` 从 1 开始计数；其执行事件携带 `parentToolCallId`（`CA/src/core/nested-tool-calls.ts:188`）。



调用会 resolve 为什么（`CA/src/extensions/codemode/execute.ts:347`）：

- 声明了 `outputSchema` 的工具会 resolve 为其 `structuredContent`；即使是错误结果，只要带有结构化内容，也同样如此。每个 MCP 工具都声明了该 schema。因此 MCP 调用会 resolve 为完整的 `CallToolResult`，包括 `isError`（“MCP”，原书第144页）

- 其他工具会 resolve 为其文本内容组成的一个字符串

- 失败、被阻止或无效的调用会以包含工具错误文本的 `Error` reject

    

**存储。** `store(key, value)` 和 `load(key)` 在不同调用之间保留 JSON 值。成功的脚本只要写入过任何内容，就会追加一个 `codemode-store` 自定义条目 `{ set, delete }`（`CA/src/extensions/codemode/execute.ts:451`）。`load()` 从根节点开始，沿当前分支重放这些条目（`CA/src/extensions/codemode/execute.ts:217`），因此存储会跟随 `/tree`、恢复和分叉操作（“会话：JSONL 树”，原书第86页）。失败的脚本不会报告任何写入。它的嵌套调用已经执行，而且不会有任何操作撤销它们。



**结果。** 内容首先是 `Script completed` 或 `Script failed`，然后是 `Wall time N seconds`，再接着是 `Output:`（`CA/src/extensions/codemode/execute.ts:470`）。返回值会像 `text()` 一样追加到输出中；失败时，会在部分输出后追加 `Script error:` 和错误信息。文本超过 `max_output_tokens` 时（默认 10,000；`CA/src/extensions/codemode/execute.ts:231`），会保留头尾，中间插入 `…N tokens truncated…` 标记，完整文本则写入临时文件。图像会保存为临时文件，结果中列出每个路径。

# pi\-tui：终端 UI 框架

---

每个组件将给定宽度转换为一组行，渲染器在一个同步输出块中只写出发生变化的行。Pi 默认使用备用屏幕渲染器，它从不会因行过宽而报错；保留终端回滚历史的渲染器则会。



人们在交互式 Pi 中看到的一切，包括编辑器、流式对话记录、工具输出、`/mcp` 和每个扩展对话框，都由 `@earendil-works/pi-tui` 绘制。其 README 称它是“一个采用差分渲染与同步输出的极简终端 UI 框架，用于构建无闪烁的交互式 CLI 应用”（`tui/README.md`）。本节介绍组件契约、两种渲染器及其写出的字节、键盘输入如何协商和路由、浮层、终端能力与原生附加模块，以及内置组件。该包有两个运行时依赖：`get-east-asian-width` 1\.6\.0 和 `marked` 18\.0\.11；测试使用 `node:test` 运行，其中多项针对 `@xterm/headless` 5\.5\.0（`tui/package.json`）。

## 组件是宽度的函数



完整的组件契约。来源：`tui/tui.ts`。

```TypeScript

  /**
   * 按给定视口宽度将组件渲染为多行
   * @param width - 当前视口宽度
   * @returns 字符串数组，每个字符串表示一行
   */
  render(width: number): string[];
  /** 组件获得焦点时可选的键盘输入处理器。 */
  handleInput?(data: string): void;

  /** 可选的标准化鼠标处理器。 */
  handleMouse?(event: TuiMouseEvent): TuiMouseEventResult | undefined;

  /**
   * 若为 true，组件会接收按键释放事件（Kitty 协议）。
   * 默认为 false，即过滤掉释放事件。
   */
  wantsKeyRelease?: boolean;

  /**
   * 使所有缓存的渲染状态失效。
   * 在主题变化或组件需要从头重新渲染时调用。
   */
  invalidate(): void;
}
```

> 完整内容，第 117–142 行。
> 
> 



组件返回带有 ANSI 样式的行；当组件获得焦点时，`handleInput` 接收原始字节，包括转义序列。`Focusable` 组件多一个字段 `focused`；当该值为 `true` 时，它会在光标应在的位置输出 `CURSOR_MARKER`，即 `"\x1b_pi:c\x07"`，这是一个零宽 APC 序列。渲染器找到该标记，将其移除，并把硬件光标移到相应位置；输入法就在这里绘制候选窗口（`tui/tui.ts:180`；`tui/tui.ts:196`）。`Container` 将子组件纵向堆叠，并根据鼠标事件的 `y`，将事件路由给其所在行对应的子组件（`tui/tui.ts:347`）。



合成后，渲染器在每个非图像行末尾追加 `SEGMENT_RESET`，即 `"\x1b[0m\x1b]8;;\x07"`（SGR 重置加上 OSC 8 关闭），以免样式或超链接泄漏到下一行（`tui/tui.ts:412`；`tui/tui.ts:1413`）。



**宽度规则。** README 的要求很严格：“每行都不能超过 width，否则 TUI 会报错”（`tui/README.md`）。代码中，一个渲染器执行得更严格，另一个则更宽松，详见下方“文档 ≠ 代码”提示。

- `TuiAltScreen` · 模式 `"fullscreen"`：备用屏幕 · 按行比较差异 · 鼠标、选择、搜索、滚动条 · 过宽行被裁切 · Pi 的默认选择

    

除非 `tuiMode` 为 `"regular"`，否则 Pi 选择备用屏幕渲染器。两者共享 `TuiBase`；只有 `doRender()` 不同。示意结构来源：`tui/tui.ts`（`Component`、`Container`、`TUI`、`TuiBase`）、`tui-main-screen.ts`、`tui-alt-screen.ts`，以及 `CA/src/modes/interactive/tui-renderer.ts`（`createInteractiveTui`）。



编码智能体的 `tuiMode` 设置默认为 `"fullscreen"`（`CA/src/core/settings-manager.ts:184`），`createInteractiveTui` 会为其构建 `TuiAltScreen`，只有设置为 `"regular"` 才构建 `TuiMainScreen`（`CA/src/modes/interactive/tui-renderer.ts:22`）。



**调度。** `MIN_RENDER_INTERVAL_MS` 为 16，约每秒 60 帧（`tui/tui.ts:507`）。`requestRender()` 设置标志并延后到 `process.nextTick`；后者安排一个 `setTimeout`，等待这 16 ms 中剩余的时间；期间的后续请求会合并到这一帧中（`tui/tui.ts:990`）。键盘输入跳过节流，因为“即使是 `setTimeout(0)`，在 Windows 上也可能花费完整的一个 16 ms 时钟周期”（`tui/tui.ts:1117`）。



**主屏幕帧。** `TuiMainScreen.doRender()` 渲染组件树、合成浮层、提取光标标记、应用逐行重置，然后决定采用全量写入还是差分写入（`tui/tui-main-screen.ts:247`）。



![image\.png](图片和附件/image%202.png)

> 首个匹配项生效；每个玫瑰色行都会清除回滚历史。每次写入都包裹在同步输出序列（`CSI ? 2026 h/l`）内，因此终端显示的是完整帧。写入经过 `BoundedTerminalWriter`，它以 1 MiB 块流式输出，因此全量渲染也不会构造出超过 V8 限制的字符串。来源：`tui/tui-main-screen.ts:247–567`。
>

采集工具集使用一个 20 × 10 的桩终端和三行 `Text` 驱动 `TuiMainScreen`，然后修改中间那一行。转义字节表示为 `\u001b`：

```Plain Text
<# frame 1: first render
"\u001b[?2026halpha               \u001b[0m\u001b]8<;\u0007\r\nbeta
\u001b[0m\u001b]8<;\u0007\r\ngamma               \u001b[0m\u001b]8<;\u0007\u001b[?2026l"
<# frame 2: line 1 changed
"\u001b[?2026h\u001b[1A\r\u001b[2KBETA                \u001b[0m\u001b]8<;\u0007\u001b[?2026l"
<# frame 3: nothing changed
fullRedraws: 1
```

> 第 2 帧正是这种设计的意义所在：一次光标上移、一次清行、20 列内容以及一次重置；单词变更只需 55 字节。第 3 帧不写入任何内容。`Text` 会把每行填充到给定宽度，因此重置落在第 20 列之后（`research/out/tui-frames.txt`）。
> 
> 



**备用屏幕帧。** `TuiAltScreen` 以 `\x1b[?1049h` 进入备用屏幕，关闭自动换行；启用鼠标时，还会开启模式 1000、1002、1004（焦点报告）和 1006（SGR 鼠标）（`tui/tui-alt-screen.ts:63`）。它与前一屏逐行比较差异，并用绝对位置 `CSI <row>;1H` 加上 `CSI 2K` 重写发生变化的行（`tui/tui-alt-screen.ts:1745`），同样包裹在 `CSI ? 2026 h/l` 内。在此之上，它还增加了 `VStack`、`HStack` 和 `ScrollView` 布局、跟随末尾的对话记录、OSC 133 提示符跳转、滚动条、支持 OSC 52 复制的拖动选择、可点击的 OSC 8 链接，以及对话记录搜索（`tui/tui-alt-screen.ts:202`）。退出时，Pi 恢复主屏幕并打印对话记录；如果 `fullscreenExitOutput` 为 `"resume-hint"`，则只打印恢复提示（`CA/src/core/settings-manager.ts:185`）。



三个环境变量有助于调试：`PI_TUI_DEBUG_REDRAW=1` 将主屏幕每次全量重绘的原因记录到 `pi-tui-debug.log`（`tui/tui-main-screen.ts:321`）；`PI_TUI_DEBUG=1` 在 `/tmp/tui` 下为每个差分帧写一个日志文件（`tui/tui-main-screen.ts:569`）；`PI_TUI_WRITE_LOG=<file>` 捕获原始输出流（`tui/terminal.ts:152`）。



> **文档 ≠ 代码**
> 
> README 说，过宽的行会导致“TUI……报错”。在 `TuiMainScreen` 中，检查只位于差分路径上：某行比终端更宽时，会写入 `pi-tui-crash.log`、停止 TUI，并抛出“渲染行 N 超过终端宽度”（`tui/tui-main-screen.ts:517`）；首次帧或全量重绘则不检查，直接写出。Pi 默认的 `TuiAltScreen` 从不抛出这一异常，而是通过 `sliceByColumn` 将行裁切至给定宽度（`tui/tui-alt-screen.ts:1692`）。采集工具集确认了该异常：一个原始组件在 20 列终端中返回 25 列内容，导致第 5 帧停止，并报错“渲染行 3 超过终端宽度（25 \> 20）。”（`research/out/tui-frames.txt`）
>

## 输入与键盘协议



`ProcessTerminal.start` 将 stdin 设为原始模式，并通过 `\x1b[?2004h` 启用括号粘贴（`tui/terminal.ts:174`）。随后，它在一次写入中协商 Kitty 键盘协议：



请求标志 7，查询标志，并发送 DA1 作为哨兵。来源：`tui/terminal.ts`。

```JavaScript
const DESIRED_KITTY_KEYBOARD_PROTOCOL_FLAGS = 7;
const KEYBOARD_PROTOCOL_RESPONSE_FRAGMENT_TIMEOUT_MS = 150;
const KITTY_KEYBOARD_PROTOCOL_QUERY = `\x1b[>${DESIRED_KITTY_KEYBOARD_PROTOCOL_FLAGS}u\x1b[?u\x1b[c`;
```

> 第 12–14 行。标志 7 = 1（消除转义码歧义）\+ 2（报告按下、重复和释放）\+ 4（报告替代按键）。
> 
> 



若回复为 `CSI ? <flags> u` 且标志非零，则开启 Kitty 模式。若标志为零，或先收到 DA1 回复而之前没有 Kitty 回复，则改用 `\x1b[>4;2m` 开启 xterm `modifyOtherKeys`（`tui/terminal.ts:267`）。每个终端都会回复 DA1，所以这一回退机制不需要启动超时。



`StdinBuffer` 会重新拼接被拆分到多次读取中的转义序列。单独的 ESC 会在 10 ms 后被视为 Escape 键；如果设置了 `SSH_CONNECTION` 或 `SSH_TTY`，则等待 100 ms，因为旧式 Alt\+按键以 ESC 加一个字节的方式到达。`PI_TUI_ESC_TIMEOUT` 可以覆盖这两个值（`tui/terminal.ts:115`）。



**路由。** `TuiBase.handleTerminalInput` 让每条输入经过一个固定的处理阶梯；最先消费它的步骤会结束后续处理（`tui/tui.ts:1044`）：

1. 终端颜色回复（OSC 10、11、4）和配色方案报告

2. 按顺序执行输入监听器；每个监听器都能消费或改写输入

3. 终端的单元格大小回复

4. 如果设置了调试处理器，则处理调试快捷键 Shift\+Ctrl\+D

5. 修复浮层焦点：已聚焦但不再可见的浮层，将焦点交给最顶层的可见浮层

6. Kitty 按键释放事件；除非获得焦点的组件设置了 `wantsKeyRelease`，否则丢弃

7. 获得焦点的组件的 `handleInput`，随后立即渲染

    

**键绑定。** `interface Keybindings` 是一个注册表，其他包通过声明合并来扩展它；pi\-tui 声明 `tui.*` 操作（`tui/keybindings.ts:3`）。编码智能体合并其 `app.*` 操作（`CA/src/core/keybindings.ts:69`），并从智能体目录中的 `keybindings.json` 读取覆盖项（`CA/src/core/keybindings.ts:380`）；“斜杠命令与键绑定”（原书第197页）列出了这些操作。

## 浮层



`showOverlay(component, options)` 将组件压入浮层栈，并返回一个句柄。浮层在差分比较之前合成进底层行，使用可识别 ANSI 的列切片（`compositeTuiLine`），因此浮层的开销只涉及其覆盖的那些行（`tui/tui.ts:415`）。

|**`OverlayOptions`**** 字段**|**含义**|
|---|---|
|`width`、`maxHeight`|列数或行数，或百分比字符串，例如 `"50%"`|
|`minWidth`|最小列数|
|`anchor`|`center`（默认）、`top-left`、`top-right`、`bottom-left`、`bottom-right`、`top-center`、`bottom-center`、`left-center`、`right-center`|
|`offsetX`、`offsetY`|相对锚点的偏移|
|`row`、`col`|用绝对位置或百分比位置代替锚点|
|`margin`|到终端边缘的距离，可用一个数值或分别指定各边|
|`visible(termWidth, termHeight)`|仅在其返回 `true` 时渲染|
|`nonCapturing`|显示但不获取键盘焦点|



九个锚点，每种尺寸都可使用百分比。来源：`OverlayOptions`，`tui/tui.ts:243`。返回的 `OverlayHandle` 包含 `hide`、`setHidden`、`isHidden`、`focus`、`unfocus`、`isFocused` 和 `getBounds`（`tui/tui.ts:298`）。



扩展通过 `ctx.ui.custom(factory, { overlay: true, overlayOptions, onHandle })` 使用浮层；它会 resolve 为组件传给 `done` 的值（`CA/src/core/extensions/types.ts:214`）。“扩展：加载与 API”（原书第113页）介绍了 UI 上下文。

## 图像、颜色与原生附加模块



pi\-tui 使用 Kitty 图形协议（`a=T,f=100,q=2`、以 4,096 字符块传送的 base64、范围为 `1–0xffff` 的随机图像 ID）或 iTerm2 的 OSC 1337 绘制图像（`tui/terminal-image.ts:217`；`tui/terminal-image.ts:230`）。是否使用，以及使用哪一种，由环境决定：



![image\.png](图片和附件/image%206.png)

> 首个匹配项生效，未知终端不会获得图像或超链接支持。`PI_IMAGE_PROTOCOL`（`kitty` 或 `iterm2`）、`PI_TRUE_COLOR` 和 `PI_HYPERLINKS`（`1` 或 `0`）会覆盖检测结果。来源：`tui/terminal-image.ts`（`detectCapabilitiesFromEnvironment`、`detectCapabilities`）。
> 
> 



颜色可以是索引色、sRGB、OKLCH 或 OKHSL 值；`parseColor` 读取 `oklch(…)` 和 `okhsl(…)` 字符串，`mixColors` 默认在 OKLCH 中混色（`tui/colors.ts:121`；`tui/colors.ts:241`）。通过查询 OSC 10、OSC 11 和 16 个调色板条目，并以 DA1 请求收尾，可以读取终端自身的颜色，用于 system 主题（`tui/tui.ts:168`）。



原生附加模块是提交在 `tui/native/<platform>/prebuilds/` 下的预构建 N\-API 二进制文件，因此安装 Pi 时绝不会运行 `node-gyp`：

|**平台**|**二进制文件**|**提供的能力**|
|---|---|---|
|darwin arm64、x64|`darwin-platform.node`（AppKit）|剪贴板文本、图像和文件路径；修饰键状态，将 Apple Terminal 中的 Shift\+Enter 转换为 `\x1b[13;2u`|
|linux x64、arm64|`linux-platform-x11.node`（libxcb）|读取 X11 剪贴板；仅在设置了 `DISPLAY` 时加载；Wayland 回退为 `wl-paste`|
|win32 x64、arm64|`win32-platform.node`|控制台输入设置、修饰键状态、剪贴板|



六个预构建二进制文件，每个平台与架构组合各一个。缺失或失败的附加模块会降级为 `undefined`，调用方随后执行回退（`tui/native-platform.ts:28`）。使用 `npm run build:native:<platform>` 重新构建（`tui/package.json`）。来源：`tui/native/*/README.md` 和 `tui/terminal.ts:11`。

对你的意义：

- 用 `visibleWidth()` 测量返回的每一行，并用 `truncateToWidth()` 裁切；Pi 的全屏模式会掩盖这个错误，而 regular 模式会因此崩溃

- 在每一行重新应用样式；渲染器在每行末尾重置 SGR 和 OSC 8

- 按宽度缓存渲染行，并在 `invalidate()` 中清除缓存；`render()` 每帧都会运行

- 对 `tuiMode` 的两种值都进行测试；如果 regular 模式持续全量重绘，设置 `PI_TUI_DEBUG_REDRAW=1`
