# 5 配置与扩展

# 配置、模型与身份验证

---

Pi 从两个目录读取配置，一个属于用户，一个属于项目。项目目录只有在该文件夹受信任后才会生效，而且有四项设置绝不会从项目目录读取。



在发送第一个请求之前，Pi 必须确定四件事：文件放在哪里、哪些设置生效、调用哪个模型，以及发送哪个凭据。每个问题的答案都按固定顺序来自磁盘上的文件。本节说明智能体目录的布局，展示用户设置与项目设置如何合并，逐字段解读 `models.json` 模式，并给出 API 密钥与初始模型的解析顺序。

## 两个目录



智能体目录是 Pi 为每位用户存储所有内容的根目录。如果设置了 `$PI_CODING_AGENT_DIR`，`getAgentDir()` 就返回它，否则返回 `~/.pi/agent`，见 `CA/src/config.ts:605`。这两个名称都不是硬编码的。`CONFIG_DIR_NAME` 来自 `package.json` 中的 `piConfig.configDir`，默认值为 `.pi`；`APP_NAME` 来自 `piConfig.name`，默认值为 `pi`，见 `CA/src/config.ts:579`。环境变量名称由应用名称构造，因此名为 `tau` 的改名分支读取的是 `TAU_CODING_AGENT_DIR`，见 `CA/src/config.ts:585`。

`auth.json` 创建时的权限为 `0600`，其所在目录创建时的权限为 `0700`。这些权限只在创建时设置，因此管理员之后设置的权限不会被更改，见 `CA/src/core/auth-storage.ts:24`。每次读写 `auth.json`、`settings.json` 和 `trust.json` 都会获取 `proper-lockfile` 锁，最多重试 10 次，间隔 20 ms，见 `CA/src/core/auth-storage.ts:69`。

## models\.json



`~/.pi/agent/models.json` 用于添加提供商和模型，或者修补内置提供商和模型。与 `settings.json` 不同，它可以包含注释：`ModelConfig.load()` 在 `JSON.parse` 之前运行 `stripJsonComments`，然后根据 TypeBox 模式验证结果，见 `CA/src/core/model-config.ts:310`。解析错误或模式错误不会让 Pi 停止运行。配置会以空内容加载，同时显示错误，例如在 TUI 中显示 `models.json error: …`。每次刷新目录都会重新读取该文件，见 `CA/src/core/model-runtime.ts:840`；打开 `/model` 选择器时也会在后台启动一次刷新。



```TypeScript
const ProviderConfigSchema = Type.Object({
    name: Type.Optional(Type.String({ minLength: 1 })),
    baseUrl: Type.Optional(Type.String({ minLength: 1 })),
    apiKey: Type.Optional(Type.String({ minLength: 1 })),
    api: Type.Optional(Type.String({ minLength: 1 })),
    oauth: Type.Optional(Type.Literal("radius")),
    headers: Type.Optional(Type.Record(Type.String(), Type.String())),
    compat: Type.Optional(ProviderCompatSchema),
    authHeader: Type.Optional(Type.Boolean()),
    models: Type.Optional(Type.Array(ModelDefinitionSchema)),
    modelOverrides: Type.Optional(Type.Record(Type.String(), ModelOverrideSchema)),
});

const ModelsConfigSchema = Type.Object({
    providers: Type.Record(Type.String(), ProviderConfigSchema),
});
```

> 第 242–257 行，未删节。`ProviderCompatSchema` 是 OpenAI Completions、OpenAI Responses 和 Anthropic Messages 兼容性对象的联合类型。
> 
> 



- `baseUrl`、`api`：端点与传输 API。自定义模型必须同时具备这两项，可在模型层或提供商层指定，也可从同一提供商的内置模型继承。否则加载会失败，并报出 `no "api" specified` 或 `"baseUrl" is required when defining custom models`，见 `CA/src/core/provider-composer.ts:216`。

- `apiKey`、`headers`：使用下文介绍的值语法。

- `authHeader`：为 `true` 时，使用解析出的密钥添加 `Authorization: Bearer <key>`。如果没有密钥，会报错 `authHeader requires a resolved API key`，见 `CA/src/core/provider-composer.ts:382`。

- `oauth: "radius"`：模式接受的唯一 OAuth 值。它要求设置 `baseUrl`，见 `CA/src/core/provider-composer.ts:306`。

- `models`：完整定义。如果某个定义的 `id` 与该提供商的内置聊天模型相同，就在原位置替换它；否则追加到列表中，见 `CA/src/core/provider-composer.ts:331`。

- `modelOverrides`：以模型 `id` 为键的局部补丁。除 `id`、`api` 和 `baseUrl` 外，它们接受定义中的所有字段。



如果某个提供商条目没有设置 `baseUrl`、`headers`、`compat`、`modelOverrides`、`models`、`apiKey`、`oauth` 和 `authHeader` 中的任何一项，就会被拒绝，见 `CA/src/core/provider-composer.ts:310`。新模型省略字段时采用以下默认值，见 `CA/src/core/provider-composer.ts:236`：



|**字段**|**默认值**|
|---|---|
|`name`|`id` 的值|
|`reasoning`|`false`|
|`input`|`["text"]`|
|`cost`|`{ input: 0, output: 0, cacheRead: 0, cacheWrite: 0 }`|
|`contextWindow`|`128000`|
|`maxTokens`|`16384`|



在 Pi 的记账中，没有标价的本地模型不产生费用。来源：`modelFromJson()`。如果设置了 `contextWindow` 和 `maxTokens`，它们必须为正数。

### 值语法



`apiKey` 和每个请求头的值都经过同一个解析器，见 `CA/src/core/resolve-config-value.ts:145`。以 `!` 开头的值是 shell 命令；去除首尾空白后的标准输出就是最终值，该命令有 10 秒超时限制，见 `CA/src/core/resolve-config-value.ts:189`。其他值都是模板：`$NAME` 和 `${NAME}` 插入环境变量，`$$` 表示字面量 `$`，`$!` 表示字面量 `!`。只要引用的任意变量未设置，整个值就无法解析；解析密钥时会报错 `Failed to resolve API key for provider "<id>" from environment variable: NAME`，见 `CA/src/core/resolve-config-value.ts:243`。



`resolveConfigValue()` 的注释说，命令输出会在进程的整个生命周期内缓存。但密钥和请求头的处理路径并不使用它：`composeApiKeyAuth()` 调用 `resolveConfigValueOrThrow()`，后者运行的是不带缓存的变体，见 `CA/src/core/provider-composer.ts:467`。`models.json` 中的 `!` 命令会在每次解析凭据时运行，因此要让它尽快完成。`CA/docs/models.md` 对这种不缓存的行为描述正确。

## 选择模型



模型引用的格式为 `provider/id` 或单独的 `id`，可以带可选的 `:level` 思考级别后缀。`parseModelPattern()` 首先尝试将整个字符串作为模型解析。只有失败后，它才会在最后一个 `:` 处分割，并在后缀对应某个思考级别时将其视为思考级别，见 `CA/src/core/model-resolver.ts:204`。因此，诸如 `…:exacto` 的 OpenRouter ID 会按 ID 解析。精确匹配不区分大小写。部分匹配优先选择别名，即没有 `-YYYYMMDD` 后缀或以 `-latest` 结尾的 ID，而不是带日期的 ID，见 `CA/src/core/model-resolver.ts:74`。`--models` 和 `enabledModels` 中的 glob 模式匹配也不区分大小写，见 `CA/src/core/model-resolver.ts:318`。

### 虚拟模型



虚拟模型是一个目录条目，它会为每个请求选择一个实际模型。扩展通过 `pi.registerVirtualModel({ provider, id, name, route })` 注册虚拟模型，见 `CA/src/core/extensions/types.ts:1872`。每次请求之前，Pi 都会调用 `route(request, ctx)`，将 `request.reason` 设置为 `user`、`continuation`、`retry` 或 `direct`；路由器返回实际模型、思考级别以及可选状态，见 `CA/src/core/virtual-models.ts:50`。模型选择、`ctx.model` 和 `model_change` 条目使用虚拟模型的名称；助手消息记录的是实际模型。路由器状态以自定义条目的形式保存在会话分支上，其 `customType: "pi.virtual-model-state"`，见 `CA/src/core/virtual-models.ts:8`。`CA/docs/virtual-models.md` 记录了完整约定。



> **这对你意味着什么：**
> 
> - 使用 `/login` 将凭据放入 `auth.json`，或者在 `models.json` 中使用 `$VAR` 引用；绝不要把明文密钥提交到项目中。
> 
> - 不要在 `settings.json` 中写注释。只有 `models.json` 会移除注释。
> 
> - 在全局文件中设置 `defaultProjectTrust`、`cacheWarming` 和 `httpProxy`；项目文件无法更改它们。
> 
> - 为脚本使用 `--model provider/id:level` 固定模型；否则，恢复的会话会保留上次使用的模型。
>

# 上下文文件、技能、模板、主题与包

---

Pi 加载的每一种资源都经过同一个函数：`DefaultResourceLoader.reload()`。它确定信任状态，从五类来源收集路径，并让同名资源的第一个副本胜出，因此收集顺序决定了一切。



项目可以提供自己的技能、提示词模板、主题和扩展，用户、包和命令行也一样。如果两个资源使用相同的名称，其中一个就会被静默丢弃。本节沿着 `reload()`，从信任决定一直讲到最后一个主题，给出解决冲突的优先级排名，并用一次采集实验将同名技能放到七个位置进行验证。随后介绍每类资源，以及分发这些资源的包管理器。

## 上下文文件



上下文文件是指 `AGENTS.md` 和 `CLAUDE.md`，其中的文本作为项目上下文进入系统提示词，见“系统提示词的构建”（原书第75页）。在每个目录中，Pi 从 `AGENTS.override.md`、`AGENTS.md`、`AGENTS.MD`、`CLAUDE.md` 和 `CLAUDE.MD` 中选取第一个存在的文件，见 `CA/src/core/resource-loader.ts:185`。每个目录只读取一个文件。



`loadProjectContextFiles()` 首先读取智能体目录，然后从工作目录向上遍历到文件系统根目录，并按根目录优先的顺序输出祖先目录，跳过已见过的路径，见 `CA/src/core/resource-loader.ts:232`。如果 git 链接工作树嵌套在主仓库内部，就会跳过主仓库中同一文件的副本，因为两者覆盖的是同一个逻辑仓库，见 `CA/src/core/resource-loader.ts:214`。`--no-context-files`（`-nc`）会关闭加载。



> **易踩的坑**
> 
> 上下文文件不要求信任。`loadProjectContextFiles()` 的遍历过程没有信任检查，因此刚克隆、不受信任的仓库及其每一级上层目录中的 `AGENTS.md` 都会传递给模型。信任控制的是 `.pi/` 和 `.agents/skills`，不是上下文文件。如果不希望检出目录中的文本传递给模型，请使用 `-nc`。
> 
> 

## 加载流水线



`reload()` 会在启动时以及执行 `/reload` 时运行，见 `CA/src/core/resource-loader.ts:509`。首先确定信任状态，因为它决定配置中的项目部分是否存在。

### 冲突：优先级排名



`packageManager.resolve()` 将资源收集到每类资源各自的映射中，然后按 `resourcePrecedenceRank()` 排序，见 `CA/src/core/package-manager.ts:192`。排名数字越小越靠前，同名资源的第一个副本胜出。



|**排名**|**来源**|**示例**|
|---|---|---|
|0|项目设置条目|`.pi/settings.json` 中的 `skills: ["/tools/skills"]`|
|1|项目中自动发现的资源|`.pi/skills/`，然后是从 cwd 向上直到 git 根目录的 `.agents/skills/`|
|2|用户设置条目|`~/.pi/agent/settings.json` 中的 `skills`|
|3|用户范围内自动发现的资源|`~/.pi/agent/skills/`，然后是 `~/.agents/skills/`|
|4|包资源|包提供的任何资源，项目包先于用户包|
|5|内置资源|`builtin:mcp`、`builtin:codemode`、……（仅扩展）|



设置条目的优先级高于同一作用域中的约定目录。来源：`resourcePrecedenceRank()` 以及 `addAutoDiscoveredResources()` 的插入顺序，见 `CA/src/core/package-manager.ts:2413`。JavaScript 的排序是稳定排序，因此排名相同时保留插入顺序。



排名并不是完整的顺序。`reload()` 会将命令行路径放在排序列表的前面或后面，而且不同种类资源的位置不同，见 `CA/src/core/resource-loader.ts:573`。通过 `-e` 指定的扩展最先加载。通过 `-e` 指定的包所包含的技能、提示词和主题也最先加载，但单独指定的 `--skill`、`--prompt-template` 和 `--theme` 路径会追加到最后。采集工具包在每个作用域中都放置了一个名为 `dup` 的技能、一个 `/dup` 模板和一个 `dup_tool` 工具，再询问加载器哪个胜出：

## 技能



技能是一个包含 Agent Skills 格式 `SKILL.md` 的目录，或一个带有 frontmatter 的独立 Markdown 文件。“系统提示词的构建”（原书第75页）展示了技能在提示词中的位置。加载器读取三个 frontmatter 字段，见 `CA/src/core/skills.ts:67`：

- `name`：可选；默认为父目录名称。按规范进行检查：最多 64 个字符，符合 `^[a-z0-9-]+$`，不能以连字符开头或结尾，也不能出现连续两个连字符，见 `CA/src/core/skills.ts:92`。违反规则只会产生警告，技能仍会加载。

- `description`：必需。缺少此字段的 `SKILL.md` 会被报告并跳过；缺少此字段的独立 `.md` 文件会被静默跳过，见 `CA/src/core/skills.ts:304`。超过 1,024 个字符会产生警告。

- `disable-model-invocation: true`：在系统提示词中隐藏该技能；只能通过 `/skill:name` 访问它。



规范中的其他字段，如 `license`、`compatibility` 和 `allowed-tools`，会被解析，但随后被忽略。发现过程将包含 `SKILL.md` 的目录视为技能根目录，不会继续向下遍历。其他位置则会递归遍历，跳过点开头的条目和 `node_modules`，并遵守 `.gitignore`、`.ignore` 和 `.fdignore`，见 `CA/src/core/package-manager.ts:371`。对于独立的 `.md` 文件，在 `~/.pi/agent/skills` 和 `.pi/skills` 中只认可顶层文件，而在 `.agents/skills` 目录中只认可顶层以下的文件，见 `CA/src/core/package-manager.ts:428`。



系统提示词只列出每个技能的名称、描述和绝对路径，从不包含正文。模型在任务匹配时读取文件，因此添加一个技能只会在提示词中增加一个条目，而不是增加它的全部指令：

## 提示词模板



提示词模板是一个 Markdown 文件，通过 `/name args` 展开到提示词中。名称就是去掉 `.md` 后的文件名。描述使用 frontmatter 中的 `description`；如果没有，则使用第一个非空行，截取到 60 个字符，超出时追加 `...`；`argument-hint` 为可选字段，见 `CA/src/core/prompt-templates.ts:129`。



对约定目录 `~/.pi/agent/prompts/` 和 `.pi/prompts/`（受信任时）的扫描不递归，传给 `--prompt-template` 的目录也一样，见 `CA/src/core/prompt-templates.ts:159`。在 `prompts` 设置或包中指定的目录则与其他资源目录一样，会递归收集，见 `CA/src/core/package-manager.ts:651`。



参数按空白分割，可以用 `'` 和 `"` 分组，不支持转义字符，见 `CA/src/core/prompt-templates.ts:25`。替换只对模板执行一遍；如果参数值本身包含 `$1`，不会再次展开，见 `CA/src/core/prompt-templates.ts:71`。



|**语法**|**值**|
|---|---|
|`$1`、`$2`、……|位置参数；缺失时 → `""`|
|`$@`、`$ARGUMENTS`|所有参数以空格连接|
|`${N:-default}`|第 N 个参数；缺失或为空时使用默认值|
|`${@:-default}`、`${ARGUMENTS:-default}`|所有参数；没有参数时使用默认值|
|`${@:N}`|从第 N 个开始的所有参数|
|`${@:N:L}`|从第 N 个开始的 L 个参数|



Bash 风格，只执行一遍。来源：`substituteArgs()`。



`AgentSession.prompt()` 对以 `/` 开头的文本应用四个阶段：先运行已注册的扩展命令并消耗该输入；否则，输入处理器会看到原始文本；接着展开 `/skill:`；最后展开模板，见 `CA/src/core/agent-session.ts:1963`。“从 `prompt()` 到 `agent_settled`”（原书第67页）继续追踪之后的文本流向。

# 扩展：加载与 API

完整的扩展示例，`CA/docs/extensions.md`（TypeScript）



```TypeScript

export default function (pi: ExtensionAPI) {
    pi.registerCommand("hello", {
    description: "Show a greeting",
    handler: async (name, ctx) => {
    ctx.ui.notify(`Hello, ${name || "world"}!`, "info");
    },
    });
}
```



扩展就是一个函数，它接收含有 32 个方法和一个事件总线的 `ExtensionAPI`。在这次调用期间注册的内容会一直暂存，直到调用返回，因此抛出异常的工厂函数不会留下任何内容。



扩展是 Pi 添加功能的主要方式。内置 MCP 客户端、codemode 和工具搜索本身就是扩展。本节展示 Pi 如何查找并导入扩展文件、采用什么顺序、两个扩展声明同一名称时会发生什么，以及 `/reload` 如何替换它们。随后列出每个 `ExtensionAPI` 方法，以及扩展传给 `registerTool()` 的 `ToolDefinition`。扩展可以订阅的事件见“扩展事件与上下文”（原书第120页）。

## 查找与导入



扩展路径来自“上下文文件、技能、模板、主题与包”（原书第106页）介绍的资源流水线。在这条流水线中，扩展有自己的顺序：首先是命令行 `-e` 路径，然后是按优先级排序的列表，最后是内联工厂函数，见 `CA/src/core/resource-loader.ts:573`。

流程：

1. `-e <source>`：CLI，临时作用域，也支持 `builtin:`

2. 项目设置：`.pi/settings.json` 中的 `extensions` 条目，排名 0

3. `.pi/extensions/`：仅限受信任项目

4. 用户设置：`~/.pi/agent/settings.json` 中的 `extensions` 条目，排名 2

5. `~/.pi/agent/extensions/`：始终加载，排名 3

6. 包：先项目包，后用户包，排名 4

7. 内置扩展：`builtin:lama.cpp`、`codemode`、`tool-search`、`mcp`，排名 5

### 事务式注册



扩展收到的 API 对象有三个状态：`loading`、`active` 和 `failed`，见 `CA/src/core/extensions/loader.ts:253`。会改变共享运行时状态的注册操作，即 `registerProvider`、`unregisterProvider`、`registerMcpServer`、`unregisterMcpServer`、`registerVirtualModel`、`unregisterVirtualModel` 以及标志默认值，在工厂函数运行时会进入队列。只有工厂函数返回后，`commit()` 才会应用它们。如果工厂函数抛出异常，`discard()` 会丢弃队列、取消加载期间添加的事件总线监听器，并把 API 标记为失败，此后调用将抛出 `Extension "<path>" failed to load and its API is no longer active.`，见 `CA/src/core/extensions/loader.ts:532`。加载完成后，同样的调用会立即生效，因此命令处理器可以直接注册提供商，无须 `/reload`。



工具、命令、快捷键、标志、渲染器和处理器会直接写入扩展对象。只有扩展进入已加载列表后，它们才会变得可见；抛出异常的工厂函数不会进入该列表。

### 两个扩展，同一个名称



资源加载器不会拒绝重复项。如果两个扩展注册了相同的工具或标志，两者都会保持加载状态，加载器会把 `Tool "x" conflicts with <path>` 加入扩展错误列表，见 `CA/src/core/resource-loader.ts:1246`；工具查找会采用加载顺序中的第一个注册项，见 `CA/src/core/extensions/runner.ts:631`。CLI 会将该列表的每个条目转换为错误诊断，见 `CA/src/main.ts:800`，而错误诊断会终止启动：



```Shell
$ pi -ne -e <tmp>/a.js -e <tmp>/b.js -p hi
Error: Failed to load extension "<tmp>/b.js": Tool "dup_tool" conflicts with <tmp>/a.js
Hint: Start without extensions using "pi -ne".
exit code: 1
```



这是 `research/out/extensions-conflict.txt` 的内容，来自两个各自只有一行、都注册 `dup_tool` 的扩展，针对固定构建离线运行。自行构建 `DefaultResourceLoader` 的 SDK 调用方会在 `getExtensions().errors` 中收到相同条目，并自行决定如何处理。



内置扩展是例外。如果可替换的内置扩展与其他任意扩展共享工具、命令或标志名称，它会在冲突检查之前被移除，见 `CA/src/core/resource-loader.ts:120`。因此，注册 `/mcp` 的第三方扩展会替换内置 MCP 客户端，并产生一条同时列出二者名称的警告。



易踩的坑：两个已安装扩展如果注册同名工具，会阻止 `pi` 命令启动，而 `CA/docs/extensions.md` 完全没有提到这一点。建议使用的 `pi -ne` 在任一扩展来自 `-e` 时都无济于事，因为即使指定 `--no-extensions`，`-e` 路径仍会加载。移除或禁用这两个扩展中的一个；注册通用名称之前，先用 `pi.getAllTools()` 检查名称。

有些行为无法从签名看出：

- `sendUserMessage`：始终触发一个轮次。只有设置 `expandPromptTemplates: true` 时才展开提示词模板和技能命令；默认值为 `false`，见 `CA/src/core/agent-session.ts:2376`。

- `registerProvider(name, config)`：带有 `models` 时，替换该提供商的所有模型；只有 `baseUrl` 时，重定向现有模型。`unregisterProvider` 会恢复它覆盖的内置模型。`config.apiKey` 的优先级高于 `models.json`，见“配置、模型与身份验证”（原书第99页）。

- `registerMcpServer`：不会持久化；每次加载都要重新注册。`mcp.json` 中的同名服务器优先；如果名称已由另一个扩展注册，则抛出异常，见“MCP”（原书第144页）。

- `getFlag`：如果某个标志不是调用此方法的扩展自己注册的，就返回 `undefined`。

- 在工厂函数中注册；在 `session_start` 中启动进程和定时器。

- 使用 `-e ./ext.ts` 测试扩展；它会先于所有已安装扩展加载。

# 扩展事件与上下文

---

扩展通过 41 个事件了解 Pi，其中大约一半允许它改变接下来发生的事情。处理器若抛出异常，系统会报告错误并跳过它；但 `tool_call` 和 `user_bash` 是例外，在这两个事件中抛出异常会阻止操作。



Pi 提供的并非单一拦截点。它为一次运行的每个步骤都提供了带类型的事件：启动、会话变更、输入、系统提示词、消息列表、提供商请求、每条消息和每次工具调用，以及轮次之间的边界。本节介绍所有事件共用的分发规则，并给出完整的事件表，列明各处理器可以返回的内容；还会从头到尾展示一次被阻止的调用，列出处理器接收的上下文对象，并梳理 `CA/examples/extensions/` 中的 80 个条目。

## 分发规则



所有分发都经过 `ExtensionRunner`，见 `CA/src/core/extensions/runner.ts`。每个事件都遵循四条规则：



顺序：处理器先按扩展加载顺序执行，再按同一扩展内部的注册顺序执行（“扩展、加载与 API”，原书第113页，给出了加载顺序）。`pi.on()` 返回一个函数，用于移除这一次注册；已经开始的分发仍保留其快照。



等待：必须等待每个处理器完成，才会运行下一个处理器。缓慢的 `provider_stream_event` 处理器会延迟流的消费。



错误：抛出的异常通过错误监听器以 `{ extensionPath, event, error, stack }` 的形式报告，随后继续分发给下一个处理器，见 `CA/src/core/extensions/runner.ts:1104`。



错误规则的例外：在 `tool_call` 中，运行器没有 `try`，因此抛出的异常会传出运行器并阻止调用，见 `CA/src/core/extensions/runner.ts:1242`。在 `user_bash` 中，异常会先被报告，然后再次抛出，见 `CA/src/core/extensions/runner.ts:1285`。两者都采取出错即拒绝的方式。



多个处理器的结果如何合并，取决于事件。`input` 串联转换，并在遇到第一个 `handled` 时停止，见 `CA/src/core/extensions/runner.ts:1519`。`tool_call` 在遇到第一个 `block: true` 时停止。`session_before_*` 事件在遇到第一个 `cancel: true` 时停止；否则，采用最后一个非空结果，见 `CA/src/core/extensions/runner.ts:1098`。`message_end` 串联替换；如果替换改变了角色，就拒绝它，并报告 `message_end handlers must return a message with the same role`（`message_end` 处理器必须返回角色相同的消息）。`cache_warming_decision` 采用最后返回的 `action`。`project_trust` 采用第一个 `yes` 或 `no`。

# 运行模式：交互式、print 与 JSON

---

无论以哪种方式启动 Pi，都会运行同一个 `main()`，并构建同一个 `AgentSessionRuntime`；模式选择发生在较晚阶段，由两个标志和两次 TTY 检查决定，而且它只决定由谁读取事件。



在终端中运行 `pi` 会打开全屏编辑器。`pi -p "…"` 打印一个答案后退出。`pi --mode json` 将每个事件以一行 JSON 的形式流式输出，而 `pi --mode rpc` 则在 stdin 和 stdout 上保持一个开放的 JSONL 对话。本节跟随 `main()`，从 argv 一直追踪到它将运行时交给某个模式的那一刻，随后介绍人或 shell 脚本可以直接驱动的三种模式：交互、print 和 JSON。RPC 与进程内 SDK 见“RPC 模式与 SDK”（原书第133页）。这里提到的每个标志都列在“CLI 参考”（原书第191页）中。

### 判定阶梯



完整的模式判定逻辑。来源：`CA/src/main.ts:112`。

```TypeScript
function resolveAppMode(parsed: Args, stdinIsTTY: boolean, stdoutIsTTY: boolean): AppMode {
    if (parsed.mode === "rpc") {
        return "rpc";
    }
    if (parsed.mode === "json") {
        return "json";
    }
    if (parsed.print || !stdinIsTTY || !stdoutIsTTY) {
        return "print";
    }
    return "interactive";
}
```

> 这是完整函数，复制自固定提交版本的检出代码。
> 
> 



这个判定阶梯有一个出人意料的结果：`--mode text` 不会选中任何模式。`parseArgs` 接受它，见 `CA/src/cli/args.ts:103`，但 `resolveAppMode` 从不检查它，所以在终端中运行 `pi --mode text` 仍会打开 TUI。一次性文本输出应使用 `-p`。只要重定向 stdout 或 stdin 中的任意一个，就足以进入 print 模式；即便两次检查均通过，之后读到管道 stdin 仍会强制采用 print，见 `CA/src/main.ts:895`。



|**调用**|**模式**|**原因**|
|---|---|---|
|`pi`|`interactive`|两个流都是 TTY|
|`pi --mode text`|`interactive`|没有检查 `text`|
|`pi -p "..."`|`print`|`--print`|
|`pi "..." > out.txt`|`print`|stdout 不是 TTY|
|`echo "..." | pi`|`print`|stdin 不是 TTY|
|`pi --mode json "..."`|`json`|在 `--print` 之前检查|
|`pi --mode rpc`|`rpc`|最先检查|



`--mode` 的优先级高于 `--print`；在两者都未指定时，重定向会决定模式。来源：`CA/src/main.ts:112` 中的 `resolveAppMode`，以及 `CA/src/main.ts:895` 中根据 stdin 进行的降级。

## 交互模式



`InteractiveMode` 有 7,072 行，位于 `CA/src/modes/interactive/interactive-mode.ts`，通过 `pi-tui` 绘制所有内容，见“pi\-tui”（原书第158页）。它有两种布局，由 `tuiMode` 设置或 `--tui-mode` 选择：默认的 `fullscreen`，见 `CA/src/core/settings-manager.ts:1349`，会固定编辑器和状态区域，让对话记录在窗口内部滚动；`regular` 则写入终端自身的回滚缓冲区，见 `CA/docs/usage.md`。



编辑器的提交处理器按以下顺序判断一行输入的含义，见 `CA/src/modes/interactive/interactive-mode.ts:3179`：

|**输入**|**效果**|
|---|---|
|内置 `/command`|由模式自身处理；24 个命令列在“斜杠命令与快捷键”（原书第197页）中|
|`! cmd`|用 bash 运行 `cmd`，并将输出加入上下文|
|`!! cmd`|运行 `cmd`，但不将其加入上下文|
|压缩期间输入的任何文本|排队，直到压缩结束；扩展命令仍会立即运行|
|流式输出期间输入的任何文本|`session.prompt(text, { streamingBehavior: "steer" })`|
|空闲时输入的任何文本|一个新提示词|



Enter 会向正在运行的智能体发送引导消息，而不会等待。Alt\+Enter 则将后续消息排入队列，Alt\+Up 会将排队文本取回编辑器。提交处理器见 `CA/src/modes/interactive/interactive-mode.ts:3179`；按键定义来自 `CA/src/core/keybindings.ts:135`。



Escape 具有多种用途，采用第一个匹配的状态，见 `CA/src/modes/interactive/interactive-mode.ts:3050`。智能体进行流式输出时，Escape 会中止运行，并将所有排队的引导消息和后续消息移回编辑器，用空行连接，见 `CA/src/modes/interactive/interactive-mode.ts:4702`。`!` 命令运行期间，它会中止该命令。在 bash 模式中，它会清空当前行。编辑器为空时，在 500 ms 内按两次 Escape，会根据 `doubleEscapeAction` 打开 `/tree`、`/fork` 或不执行任何操作，见 `CA/src/modes/interactive/interactive-mode.ts:3064`。Ctrl\+C 会清空编辑器，500 ms 内再次按下则退出，见 `CA/src/modes/interactive/interactive-mode.ts:4231`。

## print 模式



print 模式按顺序发送提示词，然后退出。第一个提示词由三部分组装而成：管道 stdin、`@file` 文本，以及第一个位置参数消息；其余消息随后作为独立提示词发送，见 `CA/src/cli/initial-message.ts:20`、`CA/src/modes/print-mode.ts:131`。



print 模式写出的文本。来源：`CA/src/modes/print-mode.ts:139`。



```TypeScript
if (mode === "text") {
    const state = session.state;
    const lastMessage = state.messages[state.messages.length - 1];

    if (lastMessage?.role === "assistant") {
        const assistantMsg = lastMessage as AssistantMessage;
        if (assistantMsg.stopReason === "error" || assistantMsg.stopReason === "aborted") {
            console.error(assistantMsg.errorMessage || `Request ${assistantMsg.stopReason}`);
            exitCode = 1;
        } else {
            for (const content of assistantMsg.content) {
                if (content.type === "text") {
                    writeRawStdout(`${content.text}\n`);
                }
            }
        }
    }
}
```

> 这是完整代码块。最后一条消息中的思考块和工具调用块不会打印；更早的消息则完全不会打印。
> 
> 



只有最后一条助手消息会进入 stdout。如果运行以错误或中止结束，错误会写入 stderr，退出码为 1。抛出的异常也会导致以退出码 1 退出，见 `CA/src/modes/print-mode.ts:159`。



管道 stdin 与提示词之间没有分隔符。`readPipedStdin` 会去掉输入首尾的空白，见 `CA/src/main.ts:93`，而 `buildInitialMessage` 用 `""` 连接 stdin、文件文本和第一条消息，见 `CA/src/cli/initial-message.ts:40`。因此，`cat notes.txt | pi -p "Summarise this"` 会把文件的最后一行与“Summarise this”粘在一起发送。单元测试传入的 stdin 带有末尾换行符，而 CLI 永远不会传入这样的内容，见 `CA/test/initial-message.test.ts`。可以在提示词开头添加换行符或空格，也可以把指令放进管道传入的文本中。

## JSON 模式



JSON 模式就是换了订阅者的 print 模式。第 1 行是会话头，在绑定扩展之前写入，见 `CA/src/modes/print-mode.ts:122`。之后每个 `AgentSessionEvent` 都经过 `toJsonEvent`，各占一行 JSON，见 `CA/src/modes/print-mode.ts:110`。stdout 不会写入其他内容，退出码遵循与文本模式相同的规则。

# RPC 模式与 SDK

---

RPC 模式就是在 SDK 的 `AgentSession` 两端接上 JSONL：输入 33 种命令，输出事件与响应。它真正新增的只有一个小型协议，让扩展能够向客户端提问。



想使用 Pi 的 IDE、Python 服务或 Web 后端有两个入口。它可以启动 `pi --mode rpc`，通过管道用 JSONL 通信；也可以导入 `@earendil-works/pi-coding-agent`，在自己的进程中持有一个 `AgentSession`。本节记录一次真实的 RPC 对话，列出每个命令及其响应数据，介绍扩展 UI 子协议和 TypeScript `RpcClient`，然后展示 CLI 本身赖以构建的 SDK 调用。CLI 如何执行到 `runRpcMode`，见“运行模式”（原书第127页）；事件本身见“智能体事件与 Agent 类”（原书第57页）。

## 分帧：严格的 JSONL



每条记录都是一个 JSON 对象，后面跟一个 LF。`serializeJsonLine` 就是 `JSON.stringify(value) + "\n"`，见 `CA/src/modes/rpc/jsonl.ts:10`。读取器仅按 `\n` 分割，并去掉末尾的一个 `\r`，因此也支持 CRLF 输入，见 `CA/src/modes/rpc/jsonl.ts:26`。



Pi 为什么不使用 readline。来源：`CA/src/modes/rpc/jsonL.ts:14`。

> 在前两条语句之后截断；余下代码会缓冲数据块，并发出每个以 LF 结尾的行。
> 
> 



这里所说的分隔符是 U\+2028 和 U\+2029。两者都可以合法地出现在 JSON 字符串中，模型也可能生成其中任意一个。使用 Node readline 读取的客户端会把这样的记录拆成两段，且两段都无法解析，见 `CA/docs/rpc.md` 的 §Framing。`runRpcMode` 在做任何其他事情之前先调用 `takeOverStdout()`，见 `CA/src/modes/rpc/rpc-mode.ts:55`，因此扩展调用 `console.log` 时会写入 stderr，不会破坏事件流。

## 响应与错误



每个命令至多生成一条响应记录。事件不携带命令 ID，只有一个例外：`bash_execution_update` 会重复带上启动它的 `bash` 命令的 ID，见 `CA/src/core/agent-session.ts:3847`。



成功：`{ id?, type: "response", command, success: true, data? }`。命令不返回内容时，会省略 `data`，见 `CA/src/modes/rpc/rpc-mode.ts:64`。



失败：`{ id?, type: "response", command, success: false, error }`，见 `CA/src/modes/rpc/rpc-types.ts:245`。处理器抛出的错误会变成一个失败响应，使用该命令自己的 ID 和类型，见 `CA/src/modes/rpc/rpc-mode.ts:790`。



解析错误：不是 JSON 的行会得到 `command: "parse"`，且没有 ID，见 `CA/src/modes/rpc/rpc-mode.ts:755`。



未知命令：`command` 是那个未知的类型，`error` 是 `Unknown command: <type>`（未知命令：`<type>`），见 `CA/src/modes/rpc/rpc-mode.ts:715`。



`prompt`：在预检接受提示词时，通过 `preflightResult` 回调作答，而非等到运行结束，见 `CA/src/modes/rpc/rpc-mode.ts:403`。`disposition` 为 `started`、`queued` 或 `handled`，见 `CA/src/core/agent-session.ts:301`。`handled` 表示某个扩展已消费输入，不会开始运行，因此后面也不会出现 `agent_settled`。预检之前就被拒绝的提示词会改为收到失败响应。



`agent_end` 并不代表结束。重试、溢出恢复、压缩和排队的后续消息，都可能在它之后启动另一次底层运行。应等待 `agent_settled`，见 `CA/docs/rpc.md` 的 §Run lifecycle。

## 扩展 UI 子协议



RPC 模式使用真正的 `uiContext` 绑定扩展，见 `CA/src/modes/rpc/rpc-mode.ts:320`，因此 `ctx.hasUI` 为 `true`，`ctx.mode` 为 `"rpc"`。每个受支持的调用都会变成一个 `extension_ui_request`，带有通过 `crypto.randomUUID()` 新生成的 ID，见 `CA/src/modes/rpc/rpc-mode.ts:99`。对话框会等待带有该 ID 的 `extension_ui_response`；其他方法不需要回复。



|**方法**|**请求字段**|**客户端回复**|**超时或中止时的默认值**|
|---|---|---|---|
|`select`|`title, options[], timeout?`|`{ value }` 或 `{ cancelled: true }`|`undefined`|
|`confirm`|`title, message, timeout?`|`{ confirmed }` 或 `{ cancelled: true }`|`false`|
|`input`|`title, placeholder?, timeout?`|`{ value }` 或 `{ cancelled: true }`|`undefined`|
|`editor`|`title, prefill?`|`{ value }` 或 `{ cancelled: true }`|无：等待客户端|
|`notify`|`message, notifyType?`|无需回复|—|
|`setState`|`statusKey, statusText`|无需回复|—|
|`setWidget`|`widgetKey, widgetLines, widgetPlacement?`|无需回复|—|
|`setTitle`|`title`|无需回复|—|
|`set_editor_text`|`text`|无需回复|—|



对话框超时由 Pi 执行，而不是由客户端执行。超时触发或扩展的信号中止时，`createDialogPromise` 会解析为默认值，见 `CA/src/modes/rpc/rpc-mode.ts:91`。只有字符串数组形式的 `setWidget` 会被发送；组件工厂会被丢弃，见 `CA/src/modes/rpc/rpc-mode.ts:197`。`pasteToEditor` 会变成 `set_editor_text`。



`ExtensionUIContext` 的其余功能会直接降级，不发送消息。`custom()` 返回 `undefined`，`getEditorText()` 返回 `""`，`setTheme()` 返回 `{ success: false, … }`，而页脚、页眉、工作指示器和编辑器组件的设置方法不执行任何操作，见 `CA/src/modes/rpc/rpc-mode.ts:179`。如果响应的 ID 与任何待处理请求都不匹配，就会被静默丢弃，见 `CA/src/modes/rpc/rpc-mode.ts:774`。



> **易踩的坑**
> 
> `editor` 是唯一不经过 `createDialogPromise` 的对话框。它不接受超时，并且忽略中止信号，见 `CA/src/modes/rpc/rpc-mode.ts:254`。客户端如果一直不回答 `editor` 请求，就会让扩展在进程剩余的整个生命周期中一直等待。`CA/docs/rpc-extension-ui.md` 说智能体端会在超时时自动结束对话框，但这只对另外三种对话框成立。始终回答 `editor`，哪怕只回复 `{ cancelled: true }`。
> 
> 

## 关闭与 RpcClient



关闭 stdin 是有序的关闭方式：Pi 会释放运行时，由此发出 `session_shutdown`，然后以退出码 0 退出，见 `CA/src/modes/rpc/rpc-mode.ts:802`。扩展调用 `ctx.shutdown()` 会设置一个标志；Pi 会在当前命令之后，或在下一个 `agent_settled` 之后退出，见 `CA/src/modes/rpc/rpc-mode.ts:745`。信号处理见“运行模式”（原书第127页）。



对于仍希望使用子进程的 TypeScript 调用方，该包导出了 `RpcClient`，见 `CA/src/modes/rpc/rpc-client.ts`。每个命令都有一个带类型的方法（`prompt`、`getState`、`fork`、`getCommands` 等），此外还有三个基于 `agent_settled` 的辅助方法：



|**成员**|**作用**|
|---|---|
|`new RpcClient({ cliPath?, cwd?, env?, provider?, model?, args? })`|仅设置选项；不会运行任何内容|
|`start()`|启动 `node --mode rpc ...`，`cliPath` 默认为 `dist/cli.js`；等待 100 ms，如果子进程已经退出则抛出异常|
|`stop()`|发送 `SIGTERM`，然后在 1,000 ms 后发送 `SIGKILL`|
|`onEvent(listener)`|接收所有不是待处理请求之响应的记录|
|`waitForIdle(timeout = 60000)`|在下一个 `agent_settled` 时解析|
|`collectEvents(timeout = 60000)`|收集到下一个 `agent_settled` 为止的每个事件|
|`promptAndWait(message, images?, timeout = 60000)`|先订阅，再发送提示词，然后收集|



每个辅助方法默认都在 60 秒后超时。长时间运行需要显式指定超时。来源：`CA/src/modes/rpc/rpc-client.ts`（`RpcClientOptions`、`start`、`stop`、`onEvent`、`waitForIdle`、`collectEvents`、`promptAndWait`）。

## RpcClient 无法回答对话框



`RpcClient` 将 `extension_ui_request` 记录当作事件交给 `onEvent` 监听器，见 `CA/src/modes/rpc/rpc-client.ts:523`。它没有可以写入 `extension_ui_response` 的公开方法；`send` 是私有方法，见 `CA/src/modes/rpc/rpc-client.ts:556`。扩展如果调用 `ctx.ui.editor()`，或调用不带超时的 `confirm`，就会阻塞运行，直到客户端被停止。使用 `RpcClient` 时，只加载为对话框设置了超时的扩展，或者改用 SDK。此外，`cliPath` 相对于子进程的 `cwd` 解析，并由 `node` 启动，因此默认值只有在已经构建好的该包检出目录内才有效。

## SDK



SDK 是 CLI 的基础。不带参数调用 `createAgentSession()`，会从工作目录和 `~/.pi/agent` 发现资源，选择设置中的默认模型或第一个可用模型，并将会话存储到 JSONL 文件中，见 `CA/src/core/sdk.ts:181`。



最小 SDK 程序。来源：`CA/examples/sdk/01-minimal.ts`。

```TypeScript
import { createAgentSession } from "@earendil-works/pi-coding-agent";

const { session } = await createAgentSession();

try {
    session.subscribe((event) => {
        if (event.type === "message_update" && event.assistantMessageEvent.type === "text_delta") {
            process.stdout.write(event.assistantMessageEvent.delta);
        }
    });

    await session.prompt("What files are in the current directory?");
    session.state.messages.forEach((msg) => {
        console.log(msg);
    });
    console.log();
} finally {
    session.dispose();
}
```

> 这是去掉头部注释后的完整文件。进程内事件是完整的 `AgentSessionEvent`：`message_update` 仍携带累积的 `message`，而 JSON 和 RPC 模式会将它移除。
> 
> 



`session.prompt()` 在已接受的运行完成后解析，其中包括重试，见 `CA/docs/sdk.md` 的 §Prompting。`CreateAgentSessionOptions` 有 14 个字段，全部可选，见 `CA/src/core/sdk.ts:42`：



|**选项**|**省略时的默认值**|
|---|---|
|`cwd`|会话管理器的 `cwd`，否则为 `process.cwd()`|
|`agentDir`|`getAgentDir()`：`~/.pi/agent` 或 `PI_CODING_AGENT_DIR`|
|`modelRuntime`|基于 `auth.json` 和 `models.json` 的 `ModelRuntime.create()`|
|`model`|从会话恢复；否则采用设置中的默认值；再否则采用第一个可用模型|
|`thinkingLevel`|从会话恢复；否则采用模型专属设置；再否则采用设置中的默认值；最后为 `"medium"`|
|`scopedModels`|无；即 Ctrl\+P 循环切换的列表|
|`noTools`|未设置；可为 `"all"` 或 `"builtin"`|
|`tools`|`defaultTools` 设置，否则为 `read`、`bash`、`edit`、`write`|
|`excludeTools`|无；在 `tools` 之后应用，包含 MCP 工具|
|`customTools`|无|
|`resourceLoader`|一个新的 `DefaultResourceLoader`，并执行重新加载|
|`sessionManager`|`SessionManager.create(cwd, ...)`：持久化文件|
|`settingsManager`|`SettingsManager.create(cwd, agentDir)`|
|`sessionStartEvent`|启动时的 `session_start` 载荷|



> **文档 ≠ 代码**
> 
> 如果没有传入 `sessionManager`，SDK 就会写入会话文件；要避免写入，传入 `SessionManager.inMemory()`。结果为 `{ session, extensionsResult, modelFallbackMessage? }`，见 `CA/src/core/sdk.ts:99`。默认值来自 `CA/src/core/sdk.ts:181` 和 `CA/src/core/defaults.ts`。
> 
> 



CLI 不直接调用 `createAgentSession`。它使用三个更底层的调用，这三个调用都已导出：



`createAgentSessionServices(opts)`：构建绑定到 cwd 的服务 `{ cwd, agentDir, modelRuntime, settingsManager, resourceLoader, diagnostics }`，重新加载资源加载器，并注册扩展先前排入队列的提供商，见 `CA/src/core/agent-session-services.ts:135`。



`createAgentSessionFromServices({ services, sessionManager, … })`：使用这些服务调用 `createAgentSession`，见 `CA/src/core/agent-session-services.ts:214`。



`createAgentSessionRuntime(factory, { cwd, agentDir, sessionManager })`：运行一次工厂函数并保留它。返回的 `AgentSessionRuntime` 提供 `newSession`、`switchSession`、`fork`、`importFromJsonl`、`setRebindSession` 和 `dispose`；每次替换都会通过 `session_shutdown` 拆除旧会话，再通过同一工厂函数构建新会话，见 `CA/src/core/agent-session-runtime.ts:420`。



有两个步骤很容易遗漏。第一，`createAgentSession` 从不发出 `session_start`；宿主必须调用 `session.bindExtensions({ … })`，正如每种模式所做的那样，见 `CA/src/core/agent-session.ts:3244`。MCP 扩展会在该处理器中连接其服务器，见“MCP”（原书第144页）。第二，内置的 `codemode`、`tool-search`、`mcp` 和 `lama.cpp` 扩展来自 CLI 的 `main()`，见 `CA/src/main.ts:575`，而不是来自 SDK。SDK 宿主通过 `DefaultResourceLoader` 的 `extensionFactories` 中的 `createCodemodeExtension()`、`createToolSearchExtension()` 和 `createMcpExtension()` 添加它们，见 `CA/examples/sdk/14-codemode-mcp.ts`。`CA/examples/sdk/` 中有十四个示例，从 `01-minimal.ts` 到 `14-codemodemcp.ts`，每个分别介绍一个功能。



`createAgentSession` 的 JSDoc 展示了 `createAgentSession({ continueSession: true })`，见 `CA/src/core/sdk.ts:163`。`CreateAgentSessionOptions` 没有 `continueSession` 字段，因此 TypeScript 会拒绝它。要继续最近的会话，应传入 `sessionManager: SessionManager.continueRecent(cwd)`；这正是 `pi -c` 的做法，见 `CA/src/main.ts:433`。

## 选择集成方式



|**选择**|**适用场景**|**需要放弃的能力**|
|---|---|---|
|SDK|同一进程中的 Node 或 Bun TypeScript|进程隔离|
|RPC|其他语言、IDE、沙箱化子进程|直接访问对象；24 个内置命令|
|`RpcClient`|希望将 Pi 作为子进程运行的 TypeScript|回答扩展对话框|
|JSON 模式|一次脚本化运行，并保留完整事件日志|启动之后的任何输入|
|print 模式|一次脚本化运行，只需要最终文本|事件、工具输出|



每一行运行的都是同一个 `AgentSession`。区别只有传输方式和 UI 上下文。来源：`CA/docs/rpc.md`（接口表）以及上文各节。



> **对你的启示：**
> 
> - 以字节方式读取 RPC stdout，仅按 LF 分割；绝不要使用 readline。
> 
> - 将 `prompt` 响应视为“已接受”，并等待 `agent_settled`，除非 `disposition` 为 `handled`。
> 
> - 按 ID 关联响应；命令处理是异步的。
> 
> - 回答每个 `editor` 请求；扩展会打开对话框时，避免使用 `RpcClient`。
> 
> - 在 SDK 中，一次性会话应传入 `SessionManager.inMemory()`，并在第一个提示词之前调用 `bindExtensions`。
> 
>
