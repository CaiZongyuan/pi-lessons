# 2\.提供商层

# 提供商与模型

---

提供商负责一家厂商的模型、身份验证和传输格式；Models 集合只负责路由。pi\-ai 之上的所有部分都与这个集合交互，永远不必知道究竟是 42 个提供商中的哪一个作出了响应。



无论背后是哪家厂商，@earendil\-works/pi\-ai 都会把“一个模型加一段对话”转换成一条事件流。本节介绍它的两个层次、软件包入口，以及后面各部分都会复用的核心类型：消息、内容块、工具、模型和思考级别。最后介绍一个影响 Pi 其余部分的设计选择：系统提示词和工具列表位于对话记录之内，而不是与它并列存放。

## 两个层次：Provider 与 Models



这个软件包有 151 个源文件、23,581 行非空代码，不包括生成的目录包装器中的 420 行（research/out/stats\.txt §package\-lines）。它的运行时模型有两个层次，都在同一个文件 ai/models\.ts 中声明。

**Provider 是一个运行时单元**（ai/models\.ts:149）。**它包含 id、name、可选的 baseUrl 和 headers、必需的 auth: ProviderAuth、同步的 getModels\(\)，以及两个聊天操作 stream 和 streamSimple。**可选成员包括 getAllModels、refreshModels、filterModels、filterAllModels、fetchDeferred、cancelDeferred、generateImages 和 classify。getModels\(\)“不得抛出异常”；集合会把抛出异常的提供商视为没有模型的提供商（ai/models\.ts:429）。



**Models 集合由 ****`createModels({ credentials?, modelsStore?, authContext? })`**** 构建**（ai/models\.ts:990）。不传参数时，它使用内存凭据存储、内存模型存储和默认身份验证上下文（ai/models\.ts:398）。集合在以 id 为键的映射中保存提供商，解析身份验证，规范化上下文，并把每个请求委派给该模型所属的提供商。它的方法分为五类（ai/models\.ts:249）：



|**类别**|**方法**|**说明**|
|---|---|---|
|提供商<br>|getProviders、provider<br>|MutableModels 增加 setProvider（按 id 插入或更新）、deleteProvider、clearProviders|
|目录读取|Models、getModel、modelsOfType、modelOfType、getAllModels、refresh|同步读取最后已知的列表；refresh 更新动态提供商<br>|
|可用性与身份验证|checkAuth、getAvailable、getAvailableOfType、getAllAvailable、getAuth、login、logout|参见“身份验证、费用、重试与模型目录”（原书第41页）|
|聊天|stream、complete、streamSimple、completeSimple、streamDeferred、fetchDeferred、cancelDeferred|complete\* 会等待 stream\*\(\)\.result\(\)|
|一次性操作|generateImages、classify|永不拒绝 Promise；失败时返回错误结果|



24 个方法，只有一条路由规则：模型的 provider 字段决定使用哪个提供商。依据 ai/models\.ts:249–365（Models、MutableModels 接口）。



每种 API 的实现都位于 `ai/api/<api-id>.ts`，并导出 stream 和 streamSimple（ai/types\.ts:288）。同目录中的 `<api-id>.lazy.ts` 用 `lazyApi(() => import(...))` 包装它，所以厂商 SDK 只会在首次发出请求时加载（ai/api/lazy\.ts）。Bedrock 更进一步，通过变量形式的模块说明符导入，防止打包器沿依赖追踪到仅限 Node 的 AWS SDK（ai/api/bedrock\-converse\-stream\.lazy\.ts）。



提供商工厂很薄。下面是一份完整示例：



完整的提供商工厂 · `packages/ai/src/providers/groq.ts`

```TypeScript
export function groqProvider(): Provider<"openai-completions"> {
    return createProvider({
        id: "groq",
        name: "Groq",
        baseUrl: "https://api.groq.com/openai/v1",
        auth: { apiKey: envApiKeyAuth("Groq API key", ["GROQ_API_KEY"]) },
        models: Object.values(GROQ_MODELS),
        api: openAICompletionsApi(),
    });
}
```



函数上方的四行 import 已省略。



createProvider 既接受供所有聊天模型共用的单个 api，也接受按 model\.api 为键的映射，供混合型提供商使用（ai/models\.ts:1024）。GitHub Copilot、OpenCode 和 OpenRouter 使用映射形式：它们的目录混合了 Anthropic、OpenAI Completions 和 OpenAI Responses 模型（ai/providers/github\-copilot\.ts）。如果某个模型的 api 没有对应条目，不会抛出异常；它的流会以 `Provider <id> has no API implementation for "<api>"` 结束（ai/models\.ts:1077）。如果一个提供商既没有 api，也没有 images 或 classifiers，则会在构建时被拒绝（ai/models\.ts:1051）。

## 消息与内容块



四种内容块类型和四种消息角色承载所有对话（ai/types\.ts:397）。

|**内容块**|**字段**|**说明**|
|---|---|---|
|TextContent|type: "text"、text、textSignature?|签名保存提供商消息元数据，例如 OpenAI Responses 的消息 id|
|ThinkingContent<br>|type: "thinking"、thinking、thinkingSignature?、redacted?|签名是不透明的重放数据；当 redacted 为真时，加密载荷位于签名中|
|ImageContent|type: "image"、data（base64）、mimeType|仅用于用户消息和工具结果的内容|
|ToolCall|type: "toolCall"、id、name、arguments: JsonObject、thoughtSignature?、namespace?|thoughtSignature 属于 Google；namespace 属于 OpenAI Responses|



助手内容由文本、思考和工具调用构成；用户内容由文本和图像构成。依据 ai/types\.ts:397–427：

- **SystemMessage**（ai/types\.ts:524）：role: "system"、content: string \\\| TextContent\[\]、sections?: `Record<string, string | null>`、toolsAdded?: Tool\[\]、toolsRemoved?: ToolReference\[\]、timestamp。开头的一条是系统提示词；后续的系统消息会修改它。

- **UserMessage **（ai/types\.ts:542） // role: "user"，content: string \| \(TextContent \| ImageContent\)\[\]，timestamp。

- **AssistantMessage**（ai/types\.ts:548）：content，生成这条消息的 api、provider 和 model，usage、stopReason、timestamp；可选字段为 responseModel（当厂商实际使用了不同模型时）、responseId、providerThinkingLevel、thinkingLevel、diagnostics、deferred、errorMessage、rawStopReason 和 endTurn。

- **ToolResultMessage**（ai/types\.ts:596）：role: "toolResult"、toolCallId、toolName、content: \(TextContent \\\| ImageContent\)\[\]、isError、timestamp；可选字段为 details、usage 和 nestedCalls。nestedCalls 会保留在会话记录中，且“不会发送给模型”。

- **Usage**（ai/types\.ts:429）：input、output、cacheRead、cacheWrite、可选的 cacheWrite1h（仅 Anthropic）和 reasoning（output 的子集）、totalTokens，以及包含相同四个部分外加 total 的 cost，单位为美元。

- **StopReason**（ai/types\.ts:452）："pending" \\\| "stop" \\\| "length" \\\| "toolUse" \\\| "error" \\\| "aborted" \\\| "deferred"。pending 只在流尚未关闭时存在。

- **Message **是上述四种角色的联合类型（ai/types\.ts:612）。单轮采集记录第 6 行中的真实助手消息包含全部必需字段，以及一个可选字段 thinkingLevel（research/out/one\-turn\.txt §session\-jsonl）。

## 工具、模型与思考级别



Tool 包含 name、description、一个 TypeBox parameters 模式，以及可选的 constrainedSampling 设置（ai/types\.ts:717）。该设置可以是 false、\{ type: "json\_schema", strict: "prefer" \\\| "require" \}，或带有 openai\_lark 和 openai\_regex 编码的 \{ type: "grammar", variants \}。单轮采集中的所有内置工具都声明为 json\_schema，且 strict: "prefer"（research/out/one\-turn\.txt §session\-jsonl，第4行）。



validateToolArguments\(tool, toolCall\) 会在调用执行前对其进行检查（ai/utils/validation\.ts:317）。它复制参数，规范化可选的 null 值，运行 TypeBox Value\.Convert 进行强制转换；当模式不是 TypeBox 对象时，应用 JSON\-schema 强制转换，然后验证。失败时会抛出 `Validation failed for tool "<name>":`，后面为每个错误附上一行 \- path: message，并以缩进 JSON 形式列出接收到的参数。



每个目录条目都共享 BaseModel：id、name、api、provider、baseUrl、input（"text"、"image"）、可选的 inputLimits、cost 和可选的 headers（ai/types\.ts:1099）。聊天 Model 增加下列字段（ai/types\.ts:1113）。ImageModel（type: "image"、output）和 ClassifierModel（type: "classifier"、contextWindow）也扩展同一个基类。



|**字段**|**类型**|**含义**|
|---|---|---|
|type|"chat"，可选|缺省表示聊天|
|reasoning|boolean|是否适用思考级别|
|thinkingLevelMap|`Partial<Record<level, string | null>>`|每个 Pi 级别对应的提供商值；null = 不支持|
|promptCache|\{ short?, long? \}，单位为秒|缓存存续时间未知时不设置|
|contextWindow、maxTokens|number|输入窗口与输出上限|
|cost|\{ input, output, cacheRead, cacheWrite, tiers? \}|每百万 token 的美元价格；参见“身份验证、费用、重试与模型目录”（原书第41页）|
|samplingParams、samplingParamsByThinkingLevel|记录类型|合并到 OpenAI 兼容请求体中|
|compat|五种 compat 接口之一，由 api 决定|按模型覆盖自动检测结果|



限制、价格和特殊行为都随模型一起传递。适配器从传入的记录读取窗口、上限、成本和 compat 标志。依据 ai/types\.ts:1098–1172。



**Pi 有七个思考级别**：先是 off，然后是 ThinkingLevel = minimal、low、medium、high、xhigh、max（ai/types\.ts:85）。对于 reasoning: false 的模型，getSupportedThinkingLevels\(model\) 返回 \["off"\]（ai/models\.ts:1222）。否则，它返回从 off 到 high 中所有未被映射为 null 的级别；只有映射中明确列出时，才额外返回 xhigh 和 max。clampThinkingLevel 会保留受支持的级别，否则向上查找下一个受支持的级别，再不行则向下查找（ai/models\.ts:1233）。如果请求的 xhigh 不受模型支持，而映射中列出了 max，则变成 max；否则变成 high。



使用 token 预算的提供商通过 DEFAULT\_THINKING\_BUDGETS 转换级别：minimal 为 1,024、low 为 2,048、medium 为 8,192、high 为 16,384 token（ai/api/simple\-options\.ts:70）。xhigh 和 max 使用 high 的预算（ai/api/simple\-options\.ts:77）。当思考预算与回答共用输出上限时，至少为回答预留 MIN\_ANSWER\_TOKENS = 1,024 token（ai/api/simple\-options\.ts:68）。

## 系统提示词位于对话记录中



调用方传入 Context：systemPrompt?、messages、tools?（ai/types\.ts:734）。提供商永远看不到它们。提供商接收的是带品牌标记的 TranscriptContext，只有 normalizeContext\(\) 能生成它（ai/types\.ts:748）。normalizeContext 把提示词和工具折叠到开头的一条 SystemMessage 中，其字段为 content: systemPrompt ?? ""、toolsAdded: tools 和 timestamp: 0（ai/utils/transcript\.ts:30）。提示词和工具列表都为空时，它不添加任何内容，因此空的对话记录仍然为空（ai/utils/transcript\.ts:10）。



后续系统消息以三种方式修改提示词。content 追加指令。sections 替换具名分节，而 null 删除某个分节。toolsAdded 和 toolsRemoved 修改工具集。getCurrentSystemMessage 和 getCurrentTools 逐条重放系统消息，得到当前状态（ai/utils/transcript\.ts:58）。



![image\.png](图片和附件/image%206.png)

> **追加会保留缓存前缀；折叠则会重写它。**只有模型的 compat 声明接受对话中途的系统消息时，resolveTranscript 才会把后续系统消息保留在原处；否则，重放得到的状态会放到最前面，并删除后续所有系统消息。示意图，依据 ai/utils/transcript\.ts:108–120 和 ai/utils/text\.ts（renderSystemMessageUpdate）。
> 
> 



**对于接受对话中途系统消息的模型，后续系统消息会在其原有位置发送。分节变更会表示为 ****`Updated system prompt section "<name>":`****，后接该值，或者 ****`Removed system prompt section "<name>"`**（ai/utils/text\.ts:28）。对于其他所有模型，collapseSystemMessages 会把重放状态折叠成开头的一条消息（ai/utils/transcript\.ts:108）。Google 适配器始终执行折叠（ai/api/google\-shared\.ts:193）。compat 标志 supportsMidConvoSystemMessages 默认为 false，生成的目录只对“已验证模型”启用它（ai/types\.ts:847）。



**这个设计的原因是提示词缓存。修改工具或提示词分节时，会追加一条消息，而不是重写请求的开头，因此采用前缀缓存的提供商可以保留缓存。**编码智能体也因此使用具名分节构建提示词；参见“系统提示词构建”（原书第75页）。



> **这对你意味着什么：**
> 
> - 从 @earendil\-works/pi\-ai 导入类型和 createModels；在意打包体积时，从 `./providers/<id>` 导入单个工厂。
> 
> - 把 AssistantMessage\.provider、api 和 model 视为记录的一部分：“传输 API 与跨提供商交接”（原书第36页）中的重放规则依赖这三个字段。
> 
> - 通过追加系统消息修改提示词和工具，不要编辑第一条消息。
> 
> - 向用户显示思考级别前，先使用 clampThinkingLevel；模型支持的级别可能少于七个。
>

# 流式事件协议

---

无论使用哪家厂商，Pi 中每个请求都返回相同的流，包含十二种事件类型。失败不会抛出异常，而是作为最后一个事件到达；甚至在身份验证尚未解析时，流就已经返回了。



智能体循环、TUI、RPC 客户端和扩展读取的都是同一套协议：AssistantMessageEvent。本节列出其中的事件，陈述并图示其顺序约定，并展示从 faux 提供商采集的一条真实事件流。随后追踪一次 models\.stream\(\) 调用如何从调用方抵达适配器：惰性初始化、身份验证、请求头合并，以及 streamSimple 添加的选项。

## 十二种事件



每次聊天调用都返回一个 `AssistantMessageEventStream`（ai/utils/event\-stream\.ts）。它是一个事件异步可迭代对象，还提供 `result(): Promise<AssistantMessage>`，最终解析为终止事件 done 或 error 携带的消息。在终止事件之后推入的事件都会被丢弃。



|**事件**|**partial 之外的载荷**|**含义**|
|---|---|---|
|start|—|厂商已接受请求；partial 是空消息，stopReason: "pending"|
|text\_start|contentIndex|在该索引处追加了一个空文本块|
|text\_delta|contentIndex、delta|向内容块追加文本|
|text\_end|contentIndex、content|该内容块的最终文本|
|thinking\_start · \_delta · \_end|与文本相同|思考块也采用相同的三个步骤|
|toolcall\_start|contentIndex|追加了一个工具调用块|
|toolcall\_delta|contentIndex、delta|参数 JSON 的原始片段|
|toolcall\_end|contentIndex、toolCall|已解析的最终 ToolCall|
|done|reason、message（无 partial）|reason 为 stop、length、toolUse 或 deferred|
|error|reason、error（无 partial）|reason 为 aborted 或 error；error 是最终消息|



三种内容块 × start、delta、end，再加上一个起始事件和两个结束事件。依据 ai/types\.ts:769–785。

## 核心规则



“成功的流在任何局部更新之前发出 start，并以 done 终止。如果在开始生成之前，请求初始化就失败，流可以直接以 error 终止；在 start 之后，失败也会以［原文缺失事件名］终止。当请求缺少身份验证时，直接调用会同步抛出异常。更新和［原文缺失事件名］绝不能出现在 start 之前。”（ai/types\.ts:753）



![image\.png](图片和附件/image%203.png)

> **一个起始事件、任意数量的内容块、恰好一个终止事件。**第二行是“核心规则”允许的路径：没有 start，直接发出 error。示意图，依据 ai/types\.ts:753–785；每一种转换都在 research/out/streaming\-protocol\-events\.txt 中观察到。
> 
> 



这一语法附带四条规则（ai/types\.ts:762）：

- **partial 是实时对象，不是快照。**它是“共享的、表示迄今响应内容的实时辅助对象，而不是事件发生时的快照”。Anthropic 适配器会在每个事件中推入同一个 output 对象（ai/api/anthropic\-messages\.ts:658）。如果需要保存某个事件发生时的状态，请复制它。

- **文本和思考只能通过增量增长。**它们的内容块“在发出 `*_start` 事件时为空，之后仅通过对应的 `*_delta` 事件增长，直到作为权威结果的 `*_end`”。被隐藏的思考是例外：它“可能在 start 时已经完整，且不发出任何 delta”。

- **工具调用参数始终是对象。**toolcall\_delta\.delta 是原始 JSON 片段。适配器保存拼接后的字符串，并在每个 delta 到来时用 parseStreamingJson 重新解析：它先尝试带修复的 JSON\.parse，再尝试 partial\-json，然后对修复后的字符串使用 partial\-json，失败时返回 \{\} 而不是抛出异常（ai/utils/json\-parse\.ts:104）。

- **返回之后的错误是事件，而不是异常。**“错误终止必须生成一条带有 stopReason ‘error’ 或 ‘aborted’ 以及 errorMessage 的 AssistantMessage，并通过流协议发出”（ai/types\.ts:371）。

## 一条真实的流



采集工具为 faux 提供商（参见“身份验证、费用、重试与模型目录”，原书第41页）编排了一个思考块、一个文本块和一个工具调用，并打印通过 models\.stream\(\) 收到的每个事件。token 大小固定为 4 token，因此每个 delta 携带 16 个字符，运行结果是确定的（research/capture/streaming\-protocol\-events\.mjs）。



```Plain Text
# $success（thinking + text + toolCall → done）
    1 start    · stopReason=pending
    2 thinking_start [0] · stopReason=pending
    3 thinking_delta [0] delta="The user wants t" · stopReason=pending
    4 thinking_delta [0] delta="he file." · stopReason=pending
    5 thinking_end [0] content="The user wants the file." · stopReason=pending
    6 text_start [1] · stopReason=pending
    7 text_delta [1] delta="Reading hello.tx" · stopReason=pending
    8 text_delta [1] delta="t." · stopReason=pending
    9 text_end [1] content="Reading hello.txt." · stopReason=pending
    10 toolcall_start [2] · stopReason=pending
    11 toolcall_delta [2] delta="{{\"path\":\"hello.t" · stopReason=pending
    12 toolcall_delta [2] delta="xt\"}" · stopReason=pending
    13 toolcall_end [2] toolCall={"id":"call_1","name":"read","arguments":{"path":"hello.txt"}} · stopReason=pending
    14 done    reason=toolUse · stopReason=toolUse
    result(): stopReason=toolUse blocks=["thinking","text","toolCall"]

# $no-response（faux 队列为空 → error，没有 start）
    1 error    reason=error · stopReason=error errorMessage="No more faux responses queued"
# $unconfigured（Provider 未配置 → error，没有 start）
    1 error    reason=error · stopReason=error errorMessage="Provider is not configured: nokey"
# $abort（在第一个 text_delta 之后中止 signal）
    1 start    · stopReason=pending
    2 text_start [0] · stopReason=pending
    3 text_delta [0] delta="This answer is l" · stopReason=pending
    4 text_delta [0] delta="ong enough to be" · stopReason=pending
    5 text_delta [0] delta=" cut off in the " · stopReason=pending
    6 text_delta [0] delta="middle of stream" · stopReason=pending
    7 error    reason=aborted · stopReason=aborted errorMessage="Request was aborted"
    result(): stopReason=aborted text="This answer is long enough to be cut off in the middle of stream"
```



可以把成功的那次运行理解为沿图 2\.3（原书第31页）的语法走了一遍：一个 start，索引分别为 0、1、2 的三个内容块，一个 done。工具调用的 20 字符参数分两段到达，只有 toolcall\_end 携带解析后的对象。同样的结构会包装在 message\_update 事件中送达智能体循环；单轮采集从智能体一侧展示了这一过程（research/out/one\-turn\.txt §events）。



接下来的两次运行都在 start 之前结束。空响应队列和未配置的提供商都只产生一个 error。中止运行说明了两件事。signal 触发时已经排队的 delta 仍会送达：消费方在事件 3，也就是第一个 delta 时执行中止，之后又收到三个 delta。最终消息保留了迄今流式传输的文本，stopReason 为 aborted，而不是 error。



> **易踩的坑**
> 
> “核心规则”中的同步抛出只适用于直接调用适配器的 streamSimple\(\) 时；Anthropic 适配器在创建流之前调用 assertRequestAuth（ai/api/anthropic\-messages\.ts:933）。通过 Models 调用时，同样的缺失密钥会成为 error 事件，正如未配置提供商的那次运行所示，因为 Models 先构建流，再在后台解析身份验证。需要处理这两种路径的代码，既要在调用外围加 try，也要在循环中设置 error 分支。
> 
> 

## 适配器如何构建消息



适配器遵循同一个六步模式，Anthropic 适配器完整展示了这一过程（ai/api/anthropic\-messages\.ts:571）：

1. 创建 output，content 为空、usage 为零、stopReason: "pending"（ai/api/anthropic\-messages\.ts:582）。

2. 通过 retryProviderRequest 发送请求，以状态和响应头调用 onResponse，然后推入 start（ai/api/anthropic\-messages\.ts:649）。

3. 对于每个厂商内容块，推入一个带有临时字段（index、partialJson）的块，并发出 `*_start`。修改它，再发出 `*_delta`。在厂商的块停止事件到达时，删除临时字段，并发出 `*_end`。

4. 每当厂商报告 usage 时更新它，并在每次更新之后调用 calculateCost（ai/api/anthropic\-messages\.ts:688）。

5. 结束时，如果 signal 已中止、stopReason 仍为 pending（“Anthropic stream ended without a stop reason”），或者厂商将停止映射为 error 或 aborted，则抛出异常。否则推入 done（ai/api/anthropic\-messages\.ts:861）。

6. 在 catch 中剥离临时字段；signal 已触发时将 stopReason 设为 aborted，否则设为 error；设置 errorMessage，并推入 error（ai/api/anthropic\-messages\.ts:887）。

    

由于第 6 步发生在任何局部输出之后，出错或中止的消息会保留其已有内容和 usage。“传输 API 与跨提供商交接”（原书第36页）会说明为什么这样的消息永远不会再次送入模型。



为了支持存储和重放，assistant\-message\-frame\.ts 定义了 AssistantMessageFrame：它沿用相同的事件，但没有 partial，start 携带克隆后的消息，并额外提供一个帧 toolcall\_checkpoint \{ json \}。有些适配器会把初始参数放在 toolcall\_start 中，随后又从空字符串开始流式传输 JSON；编码器会暂缓发送这些 delta，等它们赶上快照时，再发出一个 checkpoint（ai/utils/assistant\-message\-frame\.ts:236）。



AssistantMessageFrameEncoder 会拒绝顺序错误的输入，例如“Assistant message done event appears before start”（ai/utils/assistant\-message\-frame\.ts:153）。reduceAssistantMessageFrames 会重建消息（ai/utils/assistant\-message\-frame\.ts:372）。终止状态的结算“被有意排除在外，必须单独持久化”。

- applyAuth 构建提供商请求（ai/models\.ts:842）。它使用请求的 apiKey、env 和 signal 调用 getAuth\(model\)；如果没有解析到任何凭据，就抛出 `ModelsError("auth", "Provider is not configured: <id>")`；随后组装四项内容。

- apiKey：options\.apiKey ?? auth\.apiKey。每次请求显式提供的密钥优先。

- headers：按固定顺序进行不区分大小写的合并，后面的来源覆盖前面的来源：提供商身份验证请求头 → model\.headers（在 getAuth 内）→ options\.headers → options\.transformHeaders\(\)。最后一项是只有 Models 接受的钩子，会在分派之前移除（ai/models\.ts:751、ai/models\.ts:866）。

- env：已解析凭据中的提供商专属值，再叠加 options\.env。

- baseUrl：若设置了 auth\.baseUrl，它会在本次请求中替换 model\.baseUrl。GitHub Copilot 的 OAuth toAuth 从 Copilot 令牌的 proxy\-ep 字段推导出该值（ai/auth/oauth/github\-copilot\.ts:65）。



采集工具通过一个侦察提供商发送请求，以观察合并过程（research/capture/streaming\-protocol\-events\.mjs）：



```JavaScript
auth.headers {"X-Auth":"auth","X-Model":"auth","X-Req":"auth","X-Drop":"auth"}
model.headers {"x-model":"model","X-Req":"model"}
options.headers {"x-req":"request","x-drop":null}
transformHeaders 收到 {"X-Auth":"auth","x-model":"model","x-req":"request","x-drop":null}
provider.stream headers={"X-Auth":"auth","x-model":"model","x-req":"request","x-drop":null,"X-Last":"transform"} apiKey="k-auth"
```



可以看到三个细节。后面的来源会替换前面的请求头，无论大小写如何，而且保留后者的拼写：X\-Model 最终以 x\-model 到达。null 值会在合并中保留下来；真正丢弃它的是适配器，因为“null 值会抑制提供商/API 中同名的默认请求头”（ai/types\.ts:166）。Provider\.headers 不参与此过程：Models 从不读取它（ai/models\.ts:842）。



streamSimple 又增加了一层。适配器通过 buildBaseOptions，把不依赖提供商的选项转换成自身的选项（ai/api/simple\-options\.ts:36）。它将 maxTokens 限制在 contextWindow − 估计的上下文 token 数 − 4,096 以内，但永远不会低于 1（ai/api/simple\-options\.ts:18）。它按以下顺序合并采样参数：model\.samplingParams，然后是经过限制的级别对应的 samplingParamsByThinkingLevel\[level\]，最后是请求自身的参数，每个键都覆盖前一个来源中的同名键（ai/api/simple\-options\.ts:24）。只有 OpenAI 兼容适配器会发送这些参数（ai/types\.ts:202）。这里使用的估算方法见“身份验证、费用、重试与模型目录”（原书第41页）。

# 传输 API 与跨提供商交接

---

十个适配器文件将同一份对话记录翻译成十种厂商协议。在其中任何一个发送一个字节之前，一个共享函数会先重写历史，使始于一个模型的对话能够在另一个模型上继续。



一个会话可以从 Claude 开始，中途切换到 GPT，最后在 Gemini 上结束。只有每个适配器都能接受其他适配器写出的历史记录，这才可能实现。本节列出十种聊天传输 API 及其各自独有的行为、每种 API 在签名中保留的重放数据，以及 Anthropic 的 OAuth 模式。最后介绍让切换变得安全的函数 transformMessages，并在一段真实历史记录上运行它。

## Anthropic OAuth 模式



Claude Pro 或 Max 登录会存储一个 OAuth 令牌，适配器通过子串 sk\-ant\-oat 识别它（ai/api/anthropic\-messages\.ts:978）。使用这种密钥时，适配器会改变五件事。



它将令牌作为 Bearer authToken 发送，同时设置 user\-agent: claude\-cli/2\.1\.280 和 x\-app: cli（ai/api/anthropic\-messages\.ts:1014）。



它添加 beta 标志 claude\-code\-20250219 和 oauth\-2025\-04\-20，除非调用方显式设置了 anthropic\-beta（ai/api/anthropic\-messages\.ts:1106）。



它将 You are Claude Code, Anthropic's official CLI for Claude\. 作为第一个系统内容块发送，放在 Pi 自己的提示词之前（ai/api/anthropic\-messages\.ts:1167）。



发送时，它把工具名改成 Claude Code 的大小写形式：Read、Write、Edit、Bash、Grep、Glob，以及另外十一个名字（ai/api/anthropic\-messages\.ts:101）。



接收时，它通过与当前工具列表进行不区分大小写的匹配，把名称映射回来（ai/api/anthropic\-messages\.ts:127）。



源码把这一块标为“隐身模式：完全模仿 Claude Code 的工具命名”（ai/api/anthropic\-messages\.ts:95）。

# 身份验证、费用、重试与模型目录

---

每个请求都需要凭据、价格表和失败处理策略。pi\-ai 让已存储的凭据主导其提供商的身份验证，根据一个含 1,620 个模型的生成目录为 token 定价，并且只重试分类器判定为暂时性的问题。



前三节追踪的是成功的请求。本节介绍围绕请求发生的事情：usage 内容块如何换算成美元、凭据来自哪里以及何时刷新、哪些失败会被重试。最后介绍模型目录的来源，以及让这一切能够离线运行的 faux 提供商。

## 成本



calculateCost\(model, usage\) 把 token 计数转换成美元，写入 usage\.cost，并返回该对象（ai/models\.ts:1198）。适配器在每次 usage 更新后调用它，因此流中的 partial 带有持续累计的成本。



token 换算为美元 · packages/ai/src/models\.ts

```TypeScript
export function calculateCost(model: AnyModel, usage: Usage): Usage["cost"] {
    const inputTokens = usage.input + usage.cacheRead + usage.cacheWrite;
    let rates: ModelCostRates = model.cost;
    let matchedThreshold = -1;
    for (const tier of model.cost.tiers ?? []) {
        if (inputTokens > tier.inputTokensAbove && tier.inputTokensAbove > matchedThreshold) {
            rates = tier;
            matchedThreshold = tier.inputTokensAbove;
        }
    }

    // Anthropic 对 1 小时缓存写入收取基础输入价格的 2 倍。
    const longWrite = usage.cacheWrite1h ?? 0;
    const shortWrite = usage.cacheWrite - longWrite;
    usage.cost.input = (rates.input / 1000000) * usage.input;
    usage.cost.output = (rates.output / 1000000) * usage.output;
    usage.cost.cacheRead = (rates.cacheRead / 1000000) * usage.cacheRead;
    usage.cost.cacheWrite = (rates.cacheWrite * shortWrite + rates.input * 2 * longWrite) / 1000000;
    usage.cost.total = usage.cost.input + usage.cost.output + usage.cost.cacheRead + usage.cost.cacheWrite;
    return usage.cost;
}
```

> 完整函数，第1198–1218行。
> 
> 



费率以每百万 token 的美元金额表示（ai/types\.ts:1058）。当请求的全部输入，也就是新输入、缓存读取和缓存写入 token 的总和，超过某个阈值时，就适用相应阶梯；随后，这个阶梯会为请求中的每个部分定价，包括输出（ai/types\.ts:1071）。采集工具使用固定版本目录，为四个 usage 内容块计算了价格（research/capture/auth\-cost\-retries\-cost\.mjs）：

## 凭据及其解析



身份验证分成两半：存储什么，以及每个提供商知道如何解析什么（ai/auth/types\.ts）：

- Credential：“每个提供商有一个带类型标签的凭据，即当前 auth\.json 的结构”（ai/auth/types\.ts:36）。它可以是 ApiKeyCredential \{ type: "api\_key", key?, env? \}，也可以是 OAuthCredential \{ type: "oauth", refresh, access, expires, … \}。

- CredentialStore：由应用拥有、以提供商 id 为键的存储，提供 read、list、modify 和 delete（ai/auth/types\.ts:65）。modify\(providerId, fn\)“是唯一写入路径”，按提供商串行执行；当底层存储支持锁时，也在进程之间串行执行。编码智能体的 auth\.json 就是其中一种实现；参见“配置、模型与身份验证”（原书第99页）。

- ProviderAuth：\{ apiKey?: ApiKeyAuth, oauth?: OAuthAuth \}，至少存在一项（ai/auth/types\.ts:247）。ApiKeyAuth\.resolve\(\) 将已存储的密钥与环境来源合并；如果提供商未配置，则返回 undefined。OAuthAuth 将 refresh（一次网络调用）与 toAuth（根据有效凭据纯粹推导请求身份验证）分离。

- ModelAuth：解析的结果，包含 apiKey?、headers?、baseUrl?（ai/auth/types\.ts:7）。“如果一个值无法表示为 apiKey、headers 或 baseUrl，那么它属于提供商配置，而不是身份验证。”

- resolveProviderAuth 决定哪个来源优先（ai/auth/resolve\.ts:33）。它的文件头注释陈述了这一策略：“已存储的凭据主导该提供商：只有在未存储任何凭据时才查询环境来源或环境变量。刷新失败，或凭据类型没有匹配处理程序时，不会悄悄回退到环境变量。”

## 重试、错误、溢出与中止



失败分两层处理，pi\-ai 提供这两层机制。



提供商级重试由 retryProviderRequest 实现（ai/utils/provider\-retry\.ts:105）。它复现了 OpenAI 和 Anthropic SDK 的重试策略，但其休眠可被中止信号打断；SDK 自身的计时器会忽略中止信号，因此适配器以 maxRetries: 0 调用 SDK，再包装请求（ai/api/anthropic\-messages\.ts:647）。当响应头 x\-shouldretry 为 true、没有状态码，或者状态码为 408、409、429、任何 500 及以上值时，它会重试。延迟先取自 retryafter\-ms，再取自 retry\-after（秒数或日期），否则采用 min\(0\.5 × 2^i, 8\) 秒，再减去最多 25% 的随机抖动。服务器要求的延迟如果超过 maxRetryDelayMs（默认 60,000），会立即失败并显示 `Server requested <n>s retry delay (max: <m>s).`，以便外层展示它。尝试次数默认为 options\.maxRetries ?? 0（ai/utils/provider\-retry\.ts:109）。八个适配器文件使用它；Bedrock、Codex、Mistral 和 pi\-messages 不使用。



智能体级重试会重新运行整个助手轮次。isRetryableAssistantError 只检查 stopReason: "error" 的消息，先排除不可重试的模式，再接受可重试的模式（ai/utils/retry\.ts:250）。不可重试列表涉及配额和计费：insufficient\_quota、quota exceeded、billing、OpenCode 用量限制、ChatGPT 订阅限制（ai/utils/retry\.ts:7）。可重试列表涵盖过载、速率限制、5xx 状态码、网络和套接字错误、WebSocket 关闭、过早结束的流，例如“stream ended before message\_stop”，以及上述重试延迟消息（ai/utils/retry\.ts:30）。retryAssistantCall 等待 baseDelayMs × 2^\(attempt−1\)，默认上限为 60 秒，并且绝不重试中止操作（ai/utils/retry\.ts:126）。编码智能体在 AgentSession 中应用该分类器（CA/src/core/agent\-session\.ts:52），并在压缩中使用 retryAssistantCall（CA/src/core/compaction/compaction\.ts:638）；参见“AgentSession：组装运行时”（原书第61页）。



上下文溢出是第三种判定，在重试之前检查。isContextOverflow\(message, contextWindow?\) 在三种情况下返回 true（ai/utils/overflow\.ts:137）：

1. stopReason: "error"，且消息匹配 25 种厂商模式中的一种，例如 prompt is too long、exceeds the context window 或 maximum context length is \\d\+ tokens，除非它同时匹配节流或速率限制模式。Cerebras 没有响应体的 400/413 也计算在内。

2. 静默溢出：stopReason: "stop"，且 input \+ cacheRead 超过窗口，如 z\.ai 的行为。

3. 长度溢出：stopReason: "length"、输出为零，且 input \+ cacheRead 达到窗口的 99% 或更高，如 Xiaomi MiMo 的行为。



采集工具针对示例消息运行了这两个分类器，使用 200,000 token 的窗口：

```Plain Text

Bedrock 节流                    overflow=false retryable=false
原始 ThrottlingException        overflow=true  retryable=false
过载                            overflow=false retryable=true
配额                            overflow=false retryable=false

```



> **易踩的坑**
> 
> Bedrock 节流错误既不会被重试，也不会被视为溢出。适配器将其格式化为 Throttling error: Too many tokens, please wait…（ai/api/bedrock\-converse\-stream\.ts:375）。溢出检查排除了这一前缀，而可重试模式中没有任何一项匹配“throttling”，因此该轮次失败。如果排除检查碰到原始 SDK 文本 ThrottlingException: Too many tokens…，/too many tokens/i 就会匹配，随后这个轮次会被报告为上下文已满。上面两行都来自 research/out/auth\-cost\-retries\-cost\.txt。
> 
> 



从溢出中恢复需要 token 计数，而 pi\-ai 不用 tokenizer 就能作出估算（ai/utils/estimate\.ts）。它按每 token 4 个字符、每张图像 4,800 个字符计数。上下文估算值取自最后一条成功且时间晚于所有更早消息的助手消息的 usage，再加上其后消息的估算量（ai/utils/estimate\.ts:97）。“压缩与分支摘要”（原书第92页）为智能体消息保留了同一方法的一个独立副本（CA/src/core/compaction/compaction\.ts:196）；“流式事件协议”（原书第30页）展示了 buildBaseOptions 如何用它限制 maxTokens。



中止会把调用方的 signal 传给 SDK 或 fetch。已中止的消息会保留迄今流式传输的内容和 usage，正如“流式事件协议”（原书第30页）中的中止运行所示。上下文估算会跳过它，重放时 transformMessages 也会跳过它（“传输 API 与跨提供商交接”，原书第36页）。

## faux 提供商



fauxProvider\(options\) 是一个响应经过编排的真实提供商（ai/providers/faux\.ts:687）。本书中的每一次采集都使用它。它在 http://localhost:0 注册模型 faux\-1，价格为零，并使用始终能够解析成功的 API 密钥身份验证，因此不需要密钥（ai/providers/faux\.ts:24）。



响应：通过 setResponses 或 appendResponses 设置的队列。每一步可以是使用 fauxAssistantMessage、fauxText、fauxThinking 和 fauxToolCall 构建的 AssistantMessage，也可以是一个接收 context、options、调用状态和 model 的工厂。队列为空时，流以 No more faux responses queued 结束。



流式输出：每个内容块按 tokenSize token 拆成小块；默认每块 3–5 token，每个 token 按 4 个字符计算，并以真实 delta 事件发出（ai/providers/faux\.ts:270）。tokensPerSecond 控制发送节奏；未设置时，会以消费方读取的速度尽快发出。



提示词缓存：存在 sessionId，且 cacheRetention 不为 none 时，usage 将当前提示词与该会话前一次提示词的公共前缀计为 cacheRead，其余计为 cacheWrite（ai/providers/faux\.ts:230）。单轮采集展示了这一点：第一次调用写入 1,468 token，第二次读取这 1,468 token，并写入 24 token（research/out/one\-turn\.txt §session\-jsonl）。



延迟响应：选项中带有 deferred 时，流以 stopReason: "deferred" 和一个句柄结束；轮询 pendingFetches 次后，fetchDeferred 返回编排好的响应。它是唯一实现了 fetchDeferred 和 cancelDeferred 的内置提供商。



编码智能体的测试套件通过兼容辅助函数 registerFauxProvider 在它之上运行（CA/test/suite/harness\.ts:18），仓库规则也要求这样做：“对于 packages/coding\-agent/test/suite/，请使用 test/suite/harness\.ts 加 faux 提供商。不得使用真实提供商 API、密钥或付费 token”（AGENTS\.md）。



> **这对你意味着什么：**
> 
> - 想让环境变量中的密钥生效，先移除已存储的凭据。
> 
> - 如果希望在编码智能体之外启用提供商级重试，请显式设置 maxRetries；pi\-ai 默认不重试。
> 
> - 先检查 isContextOverflow，再检查 isRetryableAssistantError：溢出需要压缩，而不是重试。
> 
> - 将 usage\.cost 视为基于目录价格的估算值；它只针对阶梯价格、一小时缓存写入和 OpenAI 服务层级作了调整。
> 
> - 使用 fauxProvider 进行测试；它执行的事件协议与厂商完全相同。
